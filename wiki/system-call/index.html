System Call

6 min · AA

1. 개요#

시스템 콜은 유저 프로그램이 커널에 일을 요청하는 정해진 입구다. 프로그램은 요청 번호와 인자를 레지스터에 담고 CPU 명령 하나(x86-64 의 syscall)로 커널 모드에 들어간다. 커널은 번호로 처리할 커널 함수를 골라 실행하고, 결과를 레지스터에 담아 돌려준다.

유저 프로그램은 하드웨어와 다른 프로세스의 메모리를 직접 다룰 수 없다. 파일을 열고, 네트워크로 보내고, 새 프로그램을 실행하는 일은 모두 시스템 콜로 커널에 맡긴다. echo hello 하나에도 시스템 콜이 백 번 넘게 일어난다(Cilium & eBPF.01 3.1).

  • 요청과 처리 — 시스템 콜은 “무엇을 해 달라"는 약속, 곧 번호와 인자의 형식이다. 그 일을 하는 코드는 커널 함수다. execve 는 시스템 콜 이름이고, x86-64 에서 그 요청을 받는 함수는 __x64_sys_execve 다.
  • 안정성 — 번호와 인자의 뜻은 한 번 정하면 바꾸지 않는다. 오래된 바이너리가 새 커널에서도 도는 이유다. 커널 내부 함수에는 이런 약속이 없다.

2. 번호와 인자#

시스템 콜은 이름이 아니라 번호로 고른다. 인자는 최대 6개이고, 정해진 레지스터에 순서대로 담는다.

2.1. 번호표#

번호는 아키텍처마다 따로 매긴다. 같은 execve 도 x86-64 에서는 59, arm64 에서는 221, 32비트 x86 에서는 11 이다. eBPF 프로그램이 번호로 시스템 콜을 가를 때 아키텍처를 정해 두어야 하는 이유다.

이름x86-64arm64
read063
write164
openat25756
execve59221
exit_group23194

x86-64 에는 400개가 넘는 번호가 있다. 더 쓰지 않는 번호는 비워 둘 뿐 다른 시스템 콜에 다시 주지 않는다.

2.2. 반환값과 errno#

커널은 결과를 반환값 레지스터 하나로 돌려주고, 성공과 실패는 값의 범위로 나뉜다.

strace 에 보이는 = -1 ENOENT (No such file or directory) 가 C 라이브러리가 바꾼 뒤의 모습이다.

3. 호출 흐름#

셸이 ls 를 실행하는 execve 한 번을 기준으로 정리한다.

3.1. 유저 공간#

프로그램은 보통 syscall 명령을 직접 쓰지 않고, C 라이브러리(glibc, musl)의 같은 이름 함수를 부른다. 이 래퍼 함수가 번호와 인자를 레지스터에 담고 syscall 을 실행한다. execl, execvp 처럼 이름이 다른 함수도 안에서는 모두 execve 시스템 콜 하나를 부른다.

일부 시스템 콜은 커널에 들어가지 않고 끝난다. clock_gettime, gettimeofday 는 커널이 프로세스마다 붙여 주는 작은 코드 영역(vDSO)에서 유저 모드 그대로 실행된다. 그래서 strace 에도 sys_enter 에도 잡히지 않는다.

3.2. 커널 입구#

syscall 명령은 CPU 를 커널 모드로 바꾸고, 커널이 미리 등록해 둔 입구 코드 entry_SYSCALL_64 로 뛴다. 입구는 먼저 유저 레지스터를 커널 스택의 struct pt_regs 에 저장한다.

커널 4.17 부터 x86-64 의 입구 함수는 __x64_sys_execve(const struct pt_regs *regs) 처럼 이 묶음의 주소 하나만 받는다. 그래서 kprobe 로 이 함수의 인자를 읽으려면 레지스터가 아니라 묶음 안을 한 번 더 읽어야 한다.

3.3. 번호로 함수 고르기#

입구 다음의 do_syscall_64() 가 번호로 처리 함수를 고른다. 오랫동안 번호를 칸 번호로 쓰는 함수 포인터 표 sys_call_table 을 썼고, 6.9 부터 x86-64 는 같은 일을 switch 문(x64_sys_call())으로 한다. 표를 거치는 간접 호출을 노리는 CPU 취약점(BHI)을 피하기 위해서다.

고르기 직전에 raw_syscalls:sys_enter tracepoint 를 지나고, 처리 함수가 끝난 뒤에는 sys_exit 를 지난다. 모든 시스템 콜이 지나는 자리라서, eBPF 로 시스템 콜 전체를 볼 때 여기에 붙인다.

3.4. 복귀#

처리 함수의 반환값은 pt_regs 의 ax 칸에 쓰인다. 입구 코드가 저장해 둔 레지스터를 되돌린 뒤 유저 모드로 돌아가고, 프로그램은 syscall 다음 명령부터 이어서 rax 의 결과를 읽는다.

execve 만 예외다. 성공하면 프로세스의 메모리가 새 프로그램으로 바뀌어 돌아갈 원래 코드가 없다.

4. 커널 함수와의 관계#

커널 소스에서 시스템 콜은 매크로 SYSCALL_DEFINEn 으로 정의한다. n 은 인자 개수다.

// fs/exec.c
SYSCALL_DEFINE3(execve,
        const char __user *, filename,
        const char __user *const __user *, argv,
        const char __user *const __user *, envp)
{
    return do_execve(getname(filename), argv, envp);
}

이 정의 하나에서 아키텍처별 입구 함수가 만들어진다.

아키텍처입구 함수 이름
x86-64__x64_sys_execve
arm64__arm64_sys_execve
래퍼가 없는 아키텍처sys_execve

입구 함수는 인자를 꺼내 넘기는 얇은 껍데기이고, 실제 일은 그 아래 커널 함수들이 한다. 아래쪽 함수는 여러 시스템 콜이 함께 쓰기도 한다. 자세한 구조는 Kernel Function 에 정리한다. BCC 의 get_syscall_fnname("execve") 는 이 표에서 지금 머신의 이름을 찾아 준다.

5. 추적 지점#

시스템 콜 하나를 볼 수 있는 자리는 여럿이다. fentry 는 커널 5.5 부터 쓸 수 있다.

모든 시스템 콜을 번호로 나누려면 첫 줄, 하나를 인자 이름으로 보려면 둘째 줄을 쓴다. tracepoint 는 이름이 아키텍처와 무관해서 오래 쓰는 도구에 맞다.

6. 확인 명령#

strace -f -e trace=execve bash -c 'ls'     # execve 만 보기
strace -c ls                               # 시스템 콜별 횟수 요약
ausyscall --dump | head                    # 번호와 이름 대응 (audit 패키지)
grep -w __NR_execve /usr/include/x86_64-linux-gnu/asm/unistd_64.h
cat /proc/<pid>/syscall                    # 그 프로세스가 머물러 있는 시스템 콜 번호와 인자
