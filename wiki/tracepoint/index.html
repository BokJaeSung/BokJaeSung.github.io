tracepoint

7 min · AA

1. 개요#

tracepoint 는 커널 개발자가 소스 코드의 정해진 지점에 미리 넣어 둔 정적 갈고리다. 지점마다 이름과 넘겨줄 인자가 정해져 있고, 평소에는 아무 일도 하지 않다가 누군가 켜면 등록된 콜백을 그 인자로 부른다. 2008년(커널 2.6.28)에 들어왔다.

kprobe 와 하는 일은 같다. 커널이 그 지점을 지날 때 옆길로 빠져 등록된 코드를 먼저 실행하고 돌아온다. 다른 점은 자리를 누가 마련하느냐다. kprobe 는 아무 함수에나 실행 중에 자리를 만들고, tracepoint 는 개발자가 고른 지점에만 처음부터 자리가 있다.

  • 개수 — 보통 천 개 이상 있다. 대부분의 커널 함수에는 없다. 있는 곳은 1.1 에 정리한다.
  • 안정성 — 이름과 인자를 외부 도구가 쓰는 약속으로 여겨 함부로 바꾸지 않는다. 함수 이름이 버전마다 바뀌는 kprobe 보다 오래 쓰는 도구에 맞다.

1.1. 위치와 분류#

tracepoint 는 모두 커널 코드 안, 개발자가 넣어 둔 지점에만 있다. 시스템 콜 tracepoint 도 따로 있는 종류가 아니라 시스템 콜 공통 입구 함수 안에 넣어 둔 한 줄이다. 모든 시스템 콜이 그 함수를 지나서 하나로 전부를 볼 수 있을 뿐이다.

분야별로 묶여 있고, tracefs 의 events/ 아래 폴더 이름이 그 분류(하위 시스템)다. 이름은 분류:이름 으로 쓴다.

분류예보는 것
raw_syscalls, syscallssys_enter, sys_enter_execve시스템 콜 (5절)
schedsched_switch, sched_process_exec프로세스 전환·실행·종료
irqirq_handler_entry인터럽트
net, skb, tcpnet_dev_xmit, tcp_retransmit_skb패킷 송수신, 재전송
blockblock_rq_issue디스크 입출력
kmemkmalloc, mm_page_alloc메모리 할당
ext4 등ext4_sync_file_enter파일 시스템

붙일 수 없는 곳은 둘이다.

  • 개발자가 넣어 두지 않은 커널 지점 — kprobe 를 쓴다.
  • 유저 프로그램 안 — 같은 역할을 유저 공간에서는 USDT(프로그램이 미리 넣어 둔 지점)가, 아무 함수에나 거는 역할은 uprobe 가 한다.

2. 구성#

tracepoint 는 매크로 TRACE_EVENT() 한 번으로 정의한다. 정의 하나에서 호출 함수, 기록 형식, 출력 형식이 함께 만들어진다.

TRACE_EVENT(sched_switch,
    TP_PROTO(bool preempt, struct task_struct *prev, struct task_struct *next, …),  // 받는 인자
    TP_ARGS(preempt, prev, next, …),
    TP_STRUCT__entry(                                   // 링 버퍼에 남길 기록의 칸
        __array(char, prev_comm, TASK_COMM_LEN)
        __field(pid_t, prev_pid)
        …),
    TP_fast_assign(…),                                  // 인자 → 기록 칸 채우기
    TP_printk("prev_comm=%s prev_pid=%d …", …)          // trace_pipe 에 보일 글자
);
  • TP_PROTO — 소스에 넣는 호출 trace_sched_switch(preempt, prev, next, …) 의 인자다.
  • TP_STRUCT__entry · TP_fast_assign — ftrace 가 링 버퍼에 남길 기록의 모양과 채우는 법이다. 기록 형식은 tracefs 의 format 파일로 보인다.
  • TP_printk — 그 기록을 trace_pipe 로 읽을 때의 글자 형식이다.

커널 안에서는 지점마다 struct tracepoint 하나가 생긴다. 켜졌는지(key)와 부를 콜백 목록(funcs)을 가진다.

3. 켜고 끄는 방식#

호출 줄 trace_sched_switch(…) 는 컴파일되면 nop 하나가 된다. 꺼져 있으면 CPU 는 그 nop 을 지나 다음 명령으로 간다. 켜면 그 nop 을 콜백 호출 구간으로 가는 jmp 로 바꾼다.

  • static key — nop 과 jmp 를 실행 중에 바꿔 쓰는 커널 장치(jump label)다. 꺼져 있을 때는 조건 검사조차 하지 않아 비용이 거의 없다.
  • 콜백 목록 — 한 지점에 ftrace 기록기, perf, eBPF 프로그램이 함께 등록될 수 있고, 켜지면 차례로 불린다. 커널 5.10 부터는 콜백이 하나뿐이면 목록을 돌지 않고 그 콜백을 바로 부른다(static call).
  • kprobe 와의 차이 — kprobe 의 ftrace 기반 방식도 함수 입구 nop 을 바꿔 쓴다. 그 nop 은 컴파일러가 모든 함수 입구에 똑같이 넣은 것이고, tracepoint 의 nop 은 개발자가 고른 지점에 인자와 함께 넣은 것이다.

4. eBPF 에서 붙이는 방식#

같은 tracepoint 에 eBPF 프로그램을 붙이는 방식은 셋이다. 프로그램이 받는 ctx 의 모양이 다르다.

4.1. 일반 tracepoint#

BPF_PROG_TYPE_TRACEPOINT(커널 4.7). 커널이 TP_STRUCT__entry 대로 기록을 먼저 만들고, 그 기록을 ctx 로 넘긴다. 칸 이름으로 읽을 수 있어 쓰기 쉽지만, 기록을 만드는 비용이 든다.

TRACEPOINT_PROBE(sched, sched_switch) {           // BCC · 함수 정의와 연결을 한 번에
    bpf_trace_printk("%d -> %d", args->prev_pid, args->next_pid);
    return 0;
}

4.2. raw tracepoint#

BPF_PROG_TYPE_RAW_TRACEPOINT(커널 4.17). 기록을 만들지 않고 TP_PROTO 의 인자를 8바이트 칸 배열(u64 args[])에 그대로 담아 넘긴다. 일반 tracepoint 보다 빠르다. 인자가 포인터면 그 안의 값은 bpf_probe_read_kernel() 로 직접 읽어야 한다.

b.attach_raw_tracepoint(tp="sched_switch", fn_name="on_switch")   # BCC

int on_switch(struct bpf_raw_tracepoint_args *ctx) {
    struct task_struct *next = (struct task_struct *)ctx->args[2];   // TP_PROTO 세 번째 인자
    …
}

4.3. BTF tracepoint#

tp_btf(커널 5.5). raw tracepoint 와 같은 인자를 받되, 커널의 타입 정보(BTF)로 각 인자의 타입을 검증기가 안다. 그래서 next->pid 처럼 포인터를 바로 따라 읽을 수 있다. libbpf 에서 SEC("tp_btf/sched_switch") 로 쓴다.

5. 시스템 콜 tracepoint#

시스템 콜에는 tracepoint 가 두 갈래로 있다.

  • raw_syscalls:sys_enter · sys_exit — 모든 시스템 콜이 지나는 공통 입구·출구 코드(kernel/entry/common.c)에 하나씩 있다. 인자는 (struct pt_regs *regs, long id) 로, 시스템 콜을 부른 순간의 레지스터 묶음과 시스템 콜 번호다. raw tracepoint 로 붙이면 args[0] 이 레지스터 묶음 주소, args[1] 이 번호다.
  • syscalls:sys_enter_<이름> · sys_exit_<이름> — 시스템 콜마다 따로 있다. sys_enter_execve 는 filename, argv, envp 처럼 그 시스템 콜의 인자를 이름으로 준다. 커널 설정 CONFIG_FTRACE_SYSCALLS 가 켜져 있어야 생긴다.

모든 시스템 콜을 번호로 나눠 보려면 앞의 것을, 시스템 콜 하나의 인자를 자세히 보려면 뒤의 것을 쓴다. 시스템 콜 번호는 아키텍처마다 다르다(x86-64 에서 execve 는 59, ARM64 에서는 221).

6. kprobe 와의 비교#

tracepointkprobe
자리개발자가 고른 지점, 천 개 이상블랙리스트를 뺀 거의 모든 함수와 명령
함수 중간개발자가 넣은 곳이면 가능오프셋으로 가능
인자이름과 타입이 정해져 있음레지스터 묶음에서 직접 해석
커널 버전 사이거의 그대로함수 이름·인자·인라인 여부가 바뀔 수 있음
꺼져 있을 때 비용nop 하나없음 (걸 때 자리를 만듦)
인라인된 함수그 안에 tracepoint 가 있으면 그대로 동작걸 수 없음

원하는 지점에 tracepoint 가 있으면 tracepoint 를 쓰고, 없을 때 kprobe 로 내려간다.

7. 확인 명령#

sudo ls /sys/kernel/tracing/events/                         # 하위 시스템별 폴더
sudo cat /sys/kernel/tracing/available_events | wc -l       # tracepoint 개수
sudo cat /sys/kernel/tracing/events/sched/sched_switch/format   # 기록 칸 (4.1 ctx)
echo 1 | sudo tee /sys/kernel/tracing/events/sched/sched_switch/enable
sudo cat /sys/kernel/tracing/trace_pipe                     # 켠 tracepoint 의 기록
echo 0 | sudo tee /sys/kernel/tracing/events/sched/sched_switch/enable
sudo perf list tracepoint                                   # perf 로 보기

enable 에 1 을 쓰면 3절의 nop 이 jmp 로 바뀌고, ftrace 기록기가 콜백으로 등록된다.
