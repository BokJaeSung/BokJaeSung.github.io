1. Overview#

ArgoCD 는 굽지 않는다 — Git 에 적힌 상태를 클러스터에 맞추는 구간만 맡고, 그 뒤는 컨트롤러가 이어받는다

이전 편과 이번 편

  • 03편에서 ArgoCD 를 설치했다
  • 04편에서 앱 이미지가 ECR 까지 가는 길을 만들었다
  • 이번 편: 그 사이에 놓인 ArgoCD 가 실제로 무엇을 하는지

ArgoCD 가 하는 일

  • 이미지를 굽지 않는다
  • Git 에 적힌 쿠버네티스 YAML 을 읽어서 클러스터의 상태와 비교하고, 다르면 맞춘다 — 그게 전부다
  • ALB 를 만들거나 Secrets Manager 에서 값을 꺼내는 일은 다른 컨트롤러가 한다
    • ArgoCD 가 넣은 객체를 읽은 컨트롤러다

진행 상황(2026-10-15 기준)

  • 끝난 단계: 설치, 저장소 자격증명, 플랫폼 GitOps
  • 앱 저장소 연결: 코드만 병합된 채 저장소 등록을 기다린다(9장 그림)

4.1 Interval — 3분 주기의 확인#

감지 → 렌더링 → 비교 → 적용 — 다른 점은 마지막 화살표를 자동으로 긋느냐 뿐이다

확인 주기와 실제 반영 시간

  • 읽기 · 렌더링 · 비교 · 적용의 반복과 확인 주기(최대 3분)는 위키 1절과 9.1에 있다

  • 플랫폼 쪽 렌더링은 Helm 차트다
  • #40 을 병합하고 root Application 이 새 커밋을 읽기까지 실제로 약 1분 반이 걸렸다

GitOps 켜기: root Application 하나

  • 이 클러스터에서 “GitOps 를 켰다” 는 건 enable_gitops = true 로 root Application 하나를 만든 일이다
  • 켜진 시점을 알려 주는 기록(2026-10-15 14:59 KST)

앱 쪽 수동 동기화의 이유: 순서

  • member 이미지는 아직 ECR 에 없고, Secret 값도 비어 있다
  • 자동으로 두면 연결하는 순간 이미지 받기에 실패하는 Pod 가 생긴다
  • 수동이면 ArgoCD 가 kukie-manifest 를 읽고 렌더링까지는 한다
    • 저장소 연결과 YAML 이 맞는지를 배포 없이 먼저 볼 수 있다
  • kukie-manifest 는 비공개라 kukie-infra 의 CI 가 렌더링해 볼 수 없는 저장소이기도 하다
# argocd/dev/platform/templates/kukie-apps.yaml
spec:
  project: kukie-apps
  source:
    repoURL: https://github.com/durokukie/kukie-manifest.git
    targetRevision: main
    path: envs/dev
  syncPolicy:                       # automated 없음 — 읽고 비교만
    syncOptions: [RespectIgnoreDifferences=true]

병합 직후 상태: ComparisonError

  • 병합 직후 kukie-dev-apps 는 ComparisonError 였다
  • 원인: ArgoCD 에 kukie-manifest 저장소가 아직 등록되지 않아 authentication required 를 받았다
  • 등록하면 OutOfSync 로 바뀌고 만들 객체 목록이 보인다
  • 자동 동기화는 member digest, Secret 값, DB 허용이 끝난 뒤 별도 PR 로 켠다

5. Downstream Controllers — ArgoCD 이후의 컨트롤러#

ArgoCD 의 일은 쿠버네티스 객체까지 — ALB 와 Secret 은 그 객체를 읽은 컨트롤러가 만든다

객체를 넣은 뒤: 컨트롤러 셋

  • ArgoCD 는 객체를 넣는 데까지 한다
  • 실제 일은 그 객체를 읽는 컨트롤러가 한다(위키 8절)
  • 이 클러스터에서 그 일을 맡는 건 03편 3.3 에서 세운 컨트롤러 셋이다

Ingress 담당: LB Controller

  • 이 클러스터에서 Ingress(ingressClassName: alb)를 읽는 건 LB Controller 다
  • Ingress 의 기본 개념은 K8sPatterns.13 5.3 에 있다

ALB 의 자리와 수명

  • ALB 는 Pod 위에서 돌지 않는다
    • AWS 가 운영하는 장비가 private subnet 에 자리를 잡는다
    • target-type: ip 라서 노드를 거치지 않고 Pod IP 로 바로 요청을 보낸다
  • Pod 가 바뀌면 LB Controller 가 대상 목록을 고친다
  • ArgoCD 는 ALB 가 있는지도 모른다
  • 다만 ArgoCD 가 Ingress 를 지우면 LB Controller 가 ALB 를 지운다 → 결과적으로 ALB 의 수명은 Git 을 따라간다

Terraform 출력 자동 전달 없음

  • Terraform 출력을 manifest 로 자동으로 넘기는 장치는 없다
    • 보안 그룹 ID 는 다시 만들면 바뀐다
    • 값을 넘기려면 Terraform 쪽에 kukie-manifest 쓰기 권한이 생긴다
  • 이름과 태그가 약속 역할을 한다
  • 대신 이름을 바꾸면 세 곳을 같이 바꿔야 한다 — Terraform, manifest, admission policy

ingress_annotations 출력 정리

  • Terraform 의 ingress_annotations 출력은 원래 보안 그룹 ID 와 subnet ID 목록을 안내했다
    • Ingress 를 처음 쓰는 사람이 보라고 만든 메모였다
    • 실제 manifest 는 처음부터 이름과 자동 탐색을 썼다
  • 7장의 정책이 들어오면서 이 메모대로 쓴 Ingress 는 거부되게 됐다 → 출력을 이름과 자동 탐색으로 맞췄다

7. Admission Guard — 클러스터 입구의 검사#

ArgoCD 가 넣어도 API 서버가 거른다 — 앱 저장소가 바꿀 수 없는 namespace 와 클러스터 범위 객체에 규칙을 둔다

허용 목록의 빈칸: 종류만 본다

  • kukie-apps 의 허용 목록은 종류만 본다 — Deployment 는 허용, ClusterRole 은 금지
  • 허용된 Deployment 안에 무엇을 적었는지는 보지 않는다
  • #40 의 리뷰가 이 빈칸을 두 번 짚었다

검사 위치: API 서버 입구

  • ArgoCD 가 보낸 객체는 쿠버네티스 API 서버를 지나 저장된다 → 검사는 그 입구에 둔다
  • 규칙이 붙는 곳은 namespace 레이블과 클러스터 범위 객체다
    • kukie-apps 로는 건드릴 수 없다
    • 바꾸려면 kukie-infra 에 PR 을 내야 한다

7.1 Pod Security — 위험 설정과 baseline#

위험 설정: 격리에 낸 구멍

  • 컨테이너는 노드의 디스크, 네트워크, 다른 프로세스와 격리돼 있다
  • 위험 설정은 그 격리에 스스로 구멍을 내는 설정이다
  • 노드 하나를 뚫으면 그 노드의 모든 Pod 와 노드 IAM 권한까지 넘어간다

Pod Security Admission 켜기

  • 쿠버네티스에 들어 있는 검사다
  • namespace 레이블 한 줄로 켠다
# argocd/dev/platform/templates/namespace.yaml
metadata:
  name: kukie-dev
  labels:
    pod-security.kubernetes.io/enforce: baseline
    pod-security.kubernetes.io/enforce-version: latest
    pod-security.kubernetes.io/warn: restricted
    pod-security.kubernetes.io/audit: restricted

baseline 이 보지 않는 것

  • 이 값들을 적지 않으면 기본값이 안전한 쪽이라 그냥 통과한다
  • 이미지, 환경변수, 메모리 같은 설정은 보지 않는다
  • 지금 manifest 의 앱 넷은 이 항목을 하나도 쓰지 않는다

수준 결정: 실제 클러스터에 dry-run

  • 수준은 실제 클러스터에 물어보고 정했다
  • kubectl label --dry-run=server
    • 레이블을 바꾸지 않는다
    • 바꾸면 기존 Pod 중 무엇이 걸리는지만 돌려준다
  • 결과
    • baseline: 경고가 없었다
    • restricted: kukie-dev 의 Reloader 가 allowPrivilegeEscalation != false, unrestricted capabilities 로 걸렸다
  • 그래서 강제는 baseline, restricted 는 경고와 감사 기록만 남긴다

거부 시점: Pod 를 만드는 순간

  • 검사는 Pod 에 걸린다
  • Deployment 는 경고만 받고 들어간다
  • 그 Deployment 가 Pod 를 만들려는 순간 거부되어 FailedCreate 이벤트가 남는다
  • 노드 권한이 정말 필요한 도구(노드 지표 수집기 같은 것)는 kukie-dev 가 아니라 kukie-infra 가 관리하는 별도 namespace 에 둔다

7.2 Internal ALB — Ingress와 Service 제한#

두 번째 빈칸: 로드밸런서

  • kukie-apps 가 허용한 Ingress 와 Service 는 LB Controller 가 AWS 로드밸런서로 만든다
  • “CloudFront 만 들어오는 internal ALB” 라는 경계는 manifest 의 주석 한 줄이었다
  • 쓰기 권한이 새면 그 줄을 internet-facing 으로 바꿔 인터넷에 바로 열린 ALB 를 만들 수 있었다

차단 수단: ValidatingAdmissionPolicy

  • 쿠버네티스 1.30 부터 기본 기능이다
  • 웹훅 서버 없이 CEL 식으로 규칙을 적는다
  • Ingress 와 Service 는 필드가 달라 정책을 둘로 나눴다
    • 한 정책에 섞으면 서로 없는 필드를 참조한다는 타입 경고가 남는다
# argocd/dev/platform/templates/kukie-dev-admission.yaml (요약)
validations:   # kukie-dev-ingress-internal-alb
  - expression: "has(object.spec.ingressClassName) && object.spec.ingressClassName == 'alb'"
  - expression: "variables.annotations[?'alb.ingress.kubernetes.io/scheme'].orValue('') == 'internal'"
  - expression: "variables.annotations[?'alb.ingress.kubernetes.io/security-groups'].orValue('') == 'kukie-dev-internal-alb'"
  - expression: "!['alb.ingress.kubernetes.io/subnets', 'alb.ingress.kubernetes.io/customer-owned-ipv4-pool',
                   'kubernetes.io/ingress.class'].exists(key, key in variables.annotations)"
validations:   # kukie-dev-no-load-balancer-service
  - expression: "!has(object.spec.type) || object.spec.type != 'LoadBalancer'"

정책 연결과 CI 검사

  • 두 정책 모두 failurePolicy: Fail, 연결은 validationActions: [Deny] 다
  • kukie-dev namespace 에만 붙는다
  • 정책 두 개와 Deny 연결, namespace 레이블이 빠지면 kukie-infra 의 check-gitops.rb 가 PR 을 실패시킨다

7.3 Verification — kind 클러스터 검증#

지금 manifest 는 그대로 통과하고, 주석 한 줄로 바깥에 여는 시도는 모두 막힌다

kind 클러스터 시험: 아홉 가지 요청

  • 실제 클러스터에 넣기 전에 로컬 kind 클러스터(Kubernetes 1.36.1)에 같은 정책을 넣었다
  • server dry-run 으로 아홉 가지를 보냈다
    • 통과: 지금 manifest 의 Ingress, ClusterIP Service, 다른 namespace 의 internet-facing Ingress
    • 거부: internet-facing, 다른 보안 그룹, 다른 ingress class, 옛 kubernetes.io/ingress.class 주석, subnet 직접 지정, LoadBalancer Service
  • 처음 한 정책에 Ingress 와 Service 를 섞었을 때 남던 타입 경고는 둘로 나눈 뒤 사라졌다
  • 시험이 끝난 뒤 kind 클러스터는 지웠다

실제 클러스터 반영

  • #40 병합 뒤 실제 클러스터에도 레이블과 정책 두 개, 연결 두 개가 생겼다
  • kukie-dev 의 Reloader 는 그대로 Running 이었다

8. Operator View — 관리 화면 접속 경로#

건물 출입은 AWS 계정으로, 방 안 열쇠는 ArgoCD 계정으로 — 두 번의 확인

화면과 API 담당: argocd-server

  • ArgoCD Pod 넷의 역할은 위키 2절에 있다
  • 그중 화면과 API 를 내는 건 argocd-server 다

접속 방법: kubectl port-forward

  • argocd-server 는 ClusterIP 라 클러스터 밖에서 들어올 주소가 없다
  • 화면은 kubectl port-forward 로 본다
kubectl -n argocd port-forward svc/argocd-server 8080:443

port-forward 통로의 경로

  • 이 명령은 내 PC 의 8080 포트와 Pod 사이에 통로를 만든다
  • 통로는 이미 열려 있는 EKS API 연결 안을 지난다
  • 그래서 그 연결에 들어갈 수 있는 사람만 화면을 볼 수 있다
① 신원
어디서
AWS IAM
무엇을
kubectl 이 AWS 프로필로 받은 토큰 — "이 요청은 IAM 사용자 누구"
② 입장
어디서
EKS API 서버
무엇을
접속 IP 가 허용 목록에 있는지, 그 IAM 사용자가 access entry 관리자 명단에 있는지
③ 로그인
어디서
ArgoCD
무엇을
ArgoCD 자체 계정 admin

EKS 의 신원: AWS 신원 그대로

  • EKS 는 클러스터 계정을 따로 만들지 않고 AWS 신원을 쓴다
  • ①② 는 건물 출입증이고, ③ 은 그 건물 안 방 하나의 열쇠다
  • 관리자 명단과 IP 허용 목록은 02편 5장의 access entry 와 같은 것이다

Pod 쪽 포트가 8080 인 이유

  • 출력 Forwarding from 127.0.0.1:8080 -> 8080 에서 Pod 쪽은 443 이 아니라 8080 이다
  • 서비스의 443 이 Pod 의 8080 으로 이어진다
  • kubectl 은 서비스를 거치지 않고 Pod 포트에 바로 붙는다

9. Discussion#

플랫폼은 Git 이 바로 클러스터가 되고, 앱은 아직 읽기와 비교까지만

작업 대부분: ArgoCD 바깥의 일

  • ArgoCD 를 붙이는 일은 대부분 ArgoCD 바깥의 일이었다
    • 저장소를 읽을 자격증명(3장)
    • 무엇을 어느 울타리에 넣을지(2장)
    • 넣은 뒤 누가 이어받는지(5, 6장)
    • 넣기 전에 누가 거르는지(7장)
  • ArgoCD 자체의 설정은 Application 하나에 동기화 방식 한 줄이었다

리뷰가 찾은 세 가지와 닫은 방법

  • 모두 “종류는 막았는데 내용은 열려 있다” 는 같은 모양이었다
    • 허용된 Deployment 안의 privileged
    • 허용된 Ingress 안의 internet-facing
    • 새 검사와 어긋난 Terraform 출력
  • 앞의 둘: 앱 저장소가 바꿀 수 없는 자리에 규칙을 두는 것으로 닫았다
  • 마지막: 메모를 실제 방식에 맞추는 것으로 닫았다

남은 일: 앱 쪽

  • ArgoCD 에 kukie-manifest 저장소 등록
  • member 이미지와 digest PR 자동화
  • kukie-dev/member Secret 값
  • DB 5432 허용
  • member 의 SES 발송용 IRSA 역할
  • 다 끝나면 kukie-dev-apps 에 자동 동기화 한 줄을 더한다

핵심 메시지#

두 저장소
플랫폼은 kukie-infra 에서 자동으로, 앱은 kukie-manifest 에서 아직 수동으로
읽기 앱
조직 소유 GitHub App. 클러스터에 놓이는 열쇠는 읽기만 한다
동기화
감지, 렌더링, 비교, 적용. 자동과 수동의 차이는 마지막 단계뿐
이어받는 컨트롤러
ArgoCD 는 객체까지. ALB 와 Secret 은 컨트롤러가 만든다
입구 검사
종류는 프로젝트가, 내용은 API 서버가 거른다

ArgoCD 는 Git 과 클러스터를 맞추는 일만 한다. 굽기는 앞에서, ALB 와 Secret 은 뒤에서 다른 것이 한다. 앱이 쓸 수 있는 자리와 규칙이 놓이는 자리를 나눴다. 규칙은 리뷰를 거치는 저장소에만 있다. 다음 편은 앱 쪽 — 자동 동기화를 켜기 전에 채워야 할 이미지, Secret, DB 다.
