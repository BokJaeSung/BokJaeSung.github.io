1. Overview#

사람이 하는 일은 ① 의 버튼 하나다. 번호를 누르면 해당 절로 이동하고, 칸을 누르면 설명이 열린다

이 글의 범위

  • 화면의 [시작] 버튼부터 vLLM 이 요청을 받을 때까지 GB 단위 데이터가 지나는 길
  • 이미지와 가중치가 각각 어느 디스크에 놓이고, 언제 사라지는지
  • 어느 구간이 시간을 쓰는지와 그 근거. 줄이는 방법은 아직 하나도 적용하지 않았다

2. Timeline — 준비 시간의 구성#

구간 이름

구간옮기는 것하는 쪽다시 일어나는 때
이미지 받기vLLM 이미지: Docker Hub → NAT → 노드의 루트 EBSkubelet 이 시키고 containerd 가 받는다노드가 새로 뜰 때
다운로드 Job가중치: Hugging Face → NAT → PVC EBS다운로드 파드PVC 에 파일이 없을 때. 있으면 확인만 하고 끝난다
가중치 적재가중치: PVC EBS → 노드 메모리 → GPU 메모리vLLM 파드vLLM 파드가 뜰 때마다
엔진 초기화옮기는 것 없음. GPU 메모리 측정, KV 캐시 자리 잡기, CUDA 그래프 준비vLLM 파드vLLM 파드가 뜰 때마다
행 이름을 누르면 그 시험의 상황이 열린다

두 모델의 공통점

  • 사람 개입 없이 끝까지 간다. 노드가 없어 Pending 이던 파드는 노드가 뜨면 이어서 진행한다
  • 가중치를 다시 받지 않는 경우에도 5분 이상 걸린다. 남는 시간은 노드, 이미지, 가중치 적재다

120b 에서 보이는 것

  • 가중치 적재 496초는 세 시험 모두 같다. 파일이 있든 없든, 노드가 켜져 있든 아니든 변하지 않는다
  • 파일이 있어도 21분 42초가 걸린 시험이 있다. 이 차이는 4절의 “다운로드 노드와 서빙 노드가 다른 경우"에서 나온다

20b 의 184초와 171초는 가중치 적재와 엔진 초기화를 나누어 재지 않은 값이다(점선 칸). 파드만 재시작하면 이미지와 가중치 파일이 이미 있어 이 두 구간만 남는다. 120b 는 vLLM 로그로 둘을 나누었다.

3. Storage — 루트 EBS 와 PVC EBS#

두 볼륨은 같은 EBS 제품이지만 서로 관계가 없다. 같은 인스턴스에 따로 붙어 있을 뿐이다. 다른 것은 만드는 쪽과 수명이다. 이미지는 노드와 함께 사라져도 다시 받으면 되고, 가중치는 다시 받지 않으려고 노드보다 오래 사는 볼륨에 둔다.

루트 EBS: Karpenter EC2NodeClass

# kukie-gpu-infra kubernetes/karpenter/gpu.yaml
# Serving images are about 10 GB. The default is 20 GiB, so the size must be set.
blockDeviceMappings:
  - deviceName: /dev/xvda
    ebs:
      volumeSize: 100Gi
      volumeType: gp3
      encrypted: true
      deleteOnTermination: true

PVC EBS: 오븐이 만드는 Deployment

// kukie-gpu-operator oven/internal/controller/resources.go (발췌)
WithEnv(
    corev1ac.EnvVar().WithName("HF_HOME").WithValue(modelsMountPath),      // "/models"
    // The files are on the PVC already; never reach for the Hub from the engine.
    corev1ac.EnvVar().WithName("HF_HUB_OFFLINE").WithValue("1"),
).
WithVolumeMounts(
    corev1ac.VolumeMount().WithName("models").WithMountPath(modelsMountPath),
    corev1ac.VolumeMount().WithName("shm").WithMountPath("/dev/shm"),
)
// ...
corev1ac.Volume().WithName("models").
    WithPersistentVolumeClaim(corev1ac.PersistentVolumeClaimVolumeSource().WithClaimName(pvcName(sm))),
  • 다운로드 Job 도 같은 HF_HOME=/models 에 쓴다. 다운로드 파드가 허깅페이스 캐시 형식으로 쓴 파일을 vLLM 이 같은 형식으로 찾는다
  • PVC 는 클래스를 비워 클러스터 기본 클래스를 쓴다. kukie-gpu 에서는 EBS CSI 애드온의 기본 클래스이고, 만들어진 볼륨은 gp3 다
  • PVC EBS 는 ReadWriteOnce 다. 다시 받아야 하면 오븐이 vLLM 을 0대로 내린 뒤 다운로드 파드를 띄운다

볼륨이 붙는 순서는 PersistentVolume 위키에 정리했다.

4. Image Pull — 노드마다 받는 엔진 이미지#

받기의 시작점

이미지를 미리 받으라는 명령은 없다. 그 이미지를 쓰는 파드가 노드에 배정되는 순간이 시작점이다.

  • 오븐은 imagePullPolicy 를 적지 않는다. 이미지가 latest 가 아닌 태그와 digest 로 고정돼 있어 기본값 IfNotPresent 가 된다. 노드에 있으면 다시 받지 않는다
  • 받기는 파드 단위가 아니라 노드 단위다. 같은 노드의 두 번째 파드부터는 containerd 가 있는 이미지를 쓴다

다운로드 파드가 vLLM 이미지를 쓰는 이유

// kukie-gpu-operator oven/internal/controller/resources.go
func (c Config) downloadImage(sm *servingv1alpha1.ServedModel) string {
	if c.DownloadImage != "" {
		return c.DownloadImage
	}
	return sm.Spec.Engine.Image
}
  • 따로 정하지 않으면 다운로드 파드도 vLLM 이미지로 뜬다. 그 안의 Python 과 hf 명령을 도구로 쓴다
  • 같은 노드에서는 이득이다. 다운로드 파드가 이미지를 받는 동안 노드에 깔리고, 뒤의 vLLM 파드는 10초 만에 시작했다(657초 → 667초)

다운로드 노드와 서빙 노드가 다른 경우

다운로드 파드는 GPU 를 요청하지 않아 Karpenter 가 가장 싼 g6e.xlarge 를 고른다. GPU 4장을 요청하는 vLLM 파드는 g6e.12xlarge 를 따로 띄운다. 이미지는 노드마다 받으므로, 두 노드가 모두 새로 뜨면 같은 이미지를 두 번 받는다.

231초의 구성 (추정)

단계일의 양속도계산
네트워크 (Docker Hub → NAT → 노드)약 10GBNAT 단일 연결 실측 104MB/s약 96초
압축 풀기풀린 크기 미측정레이어 하나에 CPU 코어 하나미측정
루트 EBS 쓰기압축본 + 풀린 파일gp3 기본 125MiB/s (설정값 미확인)풀린 크기를 20GB 로 잡으면 약 240초
  • NAT 는 2026-10 클러스터 생성 때 같은 GPU 노드에서 gpt-oss-20b 조각 4,792,272,488 바이트를 45.95초에 받아 쟀다. 네트워크만으로는 231초가 나오지 않는다
  • 남는 시간은 압축 풀기와 루트 EBS 쓰기에 있을 가능성이 크다. 두 값 모두 재지 않았다. 풀린 크기 20GB 는 가정이다

5. Weight Load — PVC 에서 GPU 메모리까지#

마운트와 준비의 차이

마운트가 끝나면 파드는 /models 의 파일을 바로 열 수 있다. 다만 vLLM 은 요청을 받기 전에 가중치 전부를 GPU 메모리에 올려야 해서, Ready 까지는 이 적재 시간이 더 걸린다.

120b 의 496초

항목값
가중치65.3GB (다운로드 Job 이 받은 크기)
가중치 읽기약 496초 (세 시험 모두)
계산한 속도65.3GB ÷ 496초 = 약 131.7MB/s = 약 125.6MiB/s
gp3 기본 처리량125MiB/s
  • 읽기 속도가 gp3 기본 처리량과 맞는다. PVC EBS 의 처리량 상한이 이 구간을 정한 것으로 본다
  • 같은 계산으로 RAM 에서 GPU 로 옮기는 PCIe 구간은 수 초다. L40S 는 PCIe 4.0 x16 이다
  • 엔진 초기화 59초는 별도다. 메모리 측정, CUDA 그래프 준비 같은 일이다

로컬 디스크와의 비교

위치읽기 속도65.3GB
PVC EBS (gp3 기본)125MiB/s약 496초 (실측)
노드 로컬 NVMe초당 수 GB수십 초 (추정)
  • 노드의 루트 디스크도 EBS 다. 루트에 두어도 같은 상한을 받는다
  • 노드에 붙은 NVMe(instance store)만 로컬이다. 노드가 꺼지면 내용이 사라진다

20b 의 184초

  • 가중치가 약 14GB 라면 같은 속도로 100초 남짓이다. 나머지는 초기화로 보인다. 나누어 재지 않았다
  • 같은 노드에서 파드만 재시작한 171초가 13초밖에 줄지 않았다. page cache 가 가중치를 들고 있지 않았거나, 초기화가 더 큰 몫이다. g6e.xlarge 의 메모리는 32GiB 이고 vLLM 이 적재하며 메모리를 많이 쓴다

6. Lifecycle — 중지 뒤에 남는 것#

화면의 [중지] 는 서버가 고객 클러스터의 ServedModel 을 지우는 DELETE 한 번이다. 그 뒤의 정리는 가비지 컬렉터와 Karpenter 가 나눠 한다.

PVC EBS 가 남을 때의 성질

  • 같은 모델을 다시 시작하면 같은 이름의 PVC 를 다시 쓴다. 이름이 모델 이름에서 나온다(openai/gpt-oss-20b → gpt-oss-20b-models)
  • 다른 모델을 시작하면 새 PVC 가 생긴다. 예전 모델의 볼륨은 그대로 남는다. 지우는 기능은 아직 없다
  • 볼륨은 AZ 하나에 묶인다. 다음 GPU 노드가 다른 AZ 에 뜨면 vLLM 파드가 Pending 에 머문다
  • 볼륨은 고객 AWS 계정에 생긴다. 고객 클러스터의 EBS CSI 드라이버가 고객 권한으로 만든다

PVC 를 지울 때와 클러스터를 지울 때

상황PVC EBS
클러스터가 있을 때 PVC 를 지운다CSI 드라이버가 볼륨을 지운다 (reclaimPolicy Delete 일 때)
클러스터를 통째로 지운다볼륨을 지울 드라이버가 함께 사라져 계정에 남을 수 있다

7. Options — 줄일 수 있는 구간#

모두 적용 전이다. 2절의 120b “파일 있음, 작은 노드 새로” 막대를 기준으로 각 방법이 줄이는 구간을 붙였다.

우리 클러스터 kukie-gpu 의 설정이다. 고객 클러스터의 노드와 스토리지 클래스는 고객 몫이고, 애드온이 할 수 있는 일은 이미지 주소를 바꿀 수 있게 하는 정도다.

8. Limits — 확인 못 한 것#

  • 이미지 실제 크기와 받기 시간: 파드 이벤트의 Successfully pulled image ... Image size 줄을 보지 않았다
  • 231초의 나눔: NAT NetworkIn, 노드 CPU, 루트 EBS VolumeThroughputPercentage 를 같이 보지 않았다
  • StorageClass 와 루트 EBS 의 실제 처리량 설정: 기본값으로 가정했다
  • 20b 의 184초에서 가중치 적재와 초기화의 나눔
  • 볼륨과 다른 AZ 에 뜬 노드에서의 재사용
  • reclaimPolicy 가 Delete 인지
