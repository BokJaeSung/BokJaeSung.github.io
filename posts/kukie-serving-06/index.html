1. Overview#

번호와 아래 띠를 누르면 해당 절로 이동한다

이 글의 범위

  • kukie-counter 가 모델 서버마다 동시 수 한도를 정하는 두 방식: 측정 기준선에서 한 번 정하는 한도와, 지나가는 응답의 꼬리 지연으로 계속 고치는 한도
  • 한도와 따로 그 순간의 새 요청을 막는 브레이크
  • 우리 클러스터 kukie-gpu(L40S 1장, gpt-oss-20b)에서 두 번 돌린 부하 시험의 결과와 아직 모르는 것

카운터를 앞단 게이트웨이·커넥터 뒤에 두는 구조는 Serving.07 에서 다룬다. 이 글의 시험은 모두 클러스터 안에서 카운터 Service 로 직접 보냈다.

2. Background — 04 이후 남은 결정#

Serving.02 의 6절은 “측정 → 기준선 → 429” 루프를 설계로 그렸고, Serving.04 의 8절은 문을 닫는 기준 후보 넷과 입구 위치를 정하지 않은 채로 남겼다. 이 글은 그 뒤에 고른 것과 실제 코드다.

04 의 후보 중 고른 것

04 의 후보지금근거
처리 중인 요청 수한도의 단위. 모델 서버마다 자리 수로 센다카운터가 직접 세고, 넘으면 줄 세우지 않고 바로 429
처리 중인 입력 토큰 양쓰지 않는다. 첫 토큰을 아직 못 받은 요청 수만 지표로 잰다막는 데 쓸 숫자의 근거가 아직 없다
대기 수, KV 사용률브레이크로만 쓴다(6절)꾸준한 부하에서는 동시 40 까지 대기가 0 이었다(3.2절)
실제 첫 토큰 시간으로 자동 조절주된 방법. TTFT 와 ITL 의 p95 로 한도를 움직인다(5절)조합(GPU·모델·설정)마다 미리 잴 수 없다
입구 위치이미 요청 경로에 있는 kukie-counter Deployment(Pod 1개)파드마다 붙는 사이드카는 만들지 않았다

02 의 설계와 달라진 것

  • 02 는 대기 수와 KV 사용률로 판단하고, 닫는 값과 여는 값을 다르게 두는 여유 폭(hysteresis)을 그렸다
  • 지금은 한도를 꼬리 지연으로 움직이고, 깜빡임은 “SLA 의 80~100% 면 그대로” 구간과 내린 뒤의 쿨다운으로 막는다(5절)
  • 대기와 KV 는 한도를 움직이지 않는다. 걸린 브레이크는 다음 읽기에서 조건이 풀리면 바로 푼다(6절)

3. Baseline Limit — 측정 기준선에서 정하는 한도#

처음 만든 방식이다. 오븐이 측정으로 status.baseline.maxConcurrency 를 채우면 카운터가 그 값의 0.8 배를 한도로 쓴다. 사람이 숫자를 옮겨 적던 단계를 없앤 것이 목적이었다.

3.1 Discovery — ServedModel 주기 읽기#

카운터는 watch 없이 30초마다 목록 전체를 다시 읽는다. 기준선이 바뀐 지 25초 뒤 한도가 12 가 됐다

watch 대신 30초 list

  • 카운터는 client-go 없이 net/http 로 GET /apis/serving.kukie.io/v1alpha1/namespaces/<ns>/servedmodels 를 보낸다. Pod 의 ServiceAccount 토큰은 매번 파일에서 다시 읽는다
  • client-go 는 의존성 수십 개를 끌고 오고, 끊긴 watch 를 다시 잇는 상태가 생긴다. 기준선은 사람이 측정을 눌러야 바뀌어 30초 늦어도 된다
  • 매번 목록 전체를 보므로 놓친 이벤트가 없다. 권한은 그 namespace 의 servedmodels get·list 하나다
  • 오븐의 Go 타입은 가져오지 않고 필요한 필드(generation, spec.engine.args, status.phase, status.baseline)만 읽는다
  • 읽기에 실패하면(API 오류, 403, CRD 없음) 직전 모델과 한도를 그대로 쓴다

기준선 상태별 한도

// kukie-gpu-operator counter/limits.go
func (d *discoveryConfig) limitFromBaseline(m servedModel) (int, string, string) {
	b := m.Baseline
	if b == nil || b.MaxConcurrency < 1 {
		return d.DefaultMaxConcurrent, sourceDefault, reasonNoBaseline
	}
	// The epsilon keeps 0.29 × 100 from landing on 28.999… and rounding down to 28.
	measured := int(math.Floor(float64(min(b.MaxConcurrency, maxBaselineConcurrency))*d.SafetyFactor + 1e-9))
	measured = max(1, measured)
	if b.Generation < m.Generation {
		// The numbers describe an older model or engine setting. They may still say the
		// server is small, so the lower of the two is kept.
		return min(d.DefaultMaxConcurrent, measured), sourceDefault, reasonStaleBaseline
	}
	if b.Partial {
		// The run stopped early, so the numbers are a lower bound: safe to use as they are.
		return measured, sourceBaseline, reasonPartial
	}
	return measured, sourceBaseline, reasonMeasured
}
  • 기준선이 없으면 기본값 4, 측정 뒤 스펙이 바뀌었으면 4 와 옛 값 중 작은 값이다
  • 설정 파일에 사람이 maxConcurrent 를 적은 모델은 이 함수를 거치지 않는다. 사람이 적은 값이 언제나 이긴다
  • 한 ServedModel 의 여러 이름(--served-model-name)은 limiter 하나를 같이 쓴다. 한도는 이름이 아니라 모델 서버 단위다
  • 한도를 낮추면 이미 자리를 잡은 요청은 끝까지 가고, 처리 중 수가 새 한도 아래로 내려갈 때까지 새 요청만 429 다

같은 날 시험용 키로 스트림 12개를 열어 자리를 채우자 13번째 요청이 429, Retry-After: 2 를 받았다.

3.2 Safety Factor — 0.8 의 근거#

0.8 은 코드, 문서, 기록 어디에도 근거가 없는 출발값이었다. 같은 날 오븐 측정보다 촘촘하게, 동시 8 부터 40 까지 단계마다 새 seed 로 vllm bench serve 를 돌리며 vLLM /metrics 를 0.5초마다 읽었다. 입력 1,000·출력 200 토큰, SLA 는 TTFT p95 1초·ITL p95 50ms 다.

2026-11-10 탐침. 대기는 단계 시작의 몰림 순간에만 생기고, 꾸준한 부하에서는 동시 40 까지 0 이었다
  • 실제 한계는 24 였다. 오븐 측정은 단계가 1·2·4·…로 두 배씩이라 16 을 내고, 거기에 0.8 을 곱한 한도 12 는 실제의 절반이다
  • 깨지는 것은 꼬리다. ITL p50 은 15 → 17ms 로 거의 그대로였고 p95 만 24 에서 30ms, 28 에서 52ms 로 뛰었다
  • 대기 수는 SLA 를 넘은 28 이상에서도 꾸준한 구간에서는 0 이었다. 이 조합에서 대기 신호로는 SLA 를 지키지 못한다
  • 측정을 촘촘히 해도 그 값은 이 GPU·모델·vLLM 설정·요청 모양 하나의 값이다. 고객 클러스터의 조합을 우리가 다 잴 수 없다

그래서 목표를 “측정을 촘촘히 해서 고정 한도"에서 “조합마다 재지 않고 카운터가 스스로 맞추는 한도"로 바꿨다. 기준선은 버리지 않고 시작값으로 쓴다.

4. Stream Timing — 카운터가 재는 TTFT 와 ITL#

스스로 맞추려면 카운터가 지나가는 응답의 TTFT 와 ITL 을 직접 재야 한다. vLLM 의 지표는 서버 안의 값이라 요청이 실제로 겪은 시간과 다를 수 있다.

카운터는 읽기 안의 시간만 더한다. 느리게 받는 클라이언트가 모델을 느려 보이게 하지 못한다
  • 스트리밍 요청("stream": true 이고 응답이 text/event-stream 인 2xx)만 잰다. 비스트리밍 요청은 첫 토큰을 알 수 없다
  • 본문은 바꾸지 않는다. 받은 바이트를 그대로 보내며, 지나가는 조각에서 표지만 찾고 내용은 남기지 않는다
  • 입력 길이는 응답의 usage.prompt_tokens 를 쓰고, 없으면 본문 4바이트를 1토큰으로 어림한다. 대부분의 클라이언트는 include_usage 를 보내지 않는다

vllm bench 와의 대조

같은 부하를 카운터를 거쳐 보내고, vllm bench serve 가 잰 값과 카운터 지표를 나란히 놓았다(2026-11-11 새벽 KST, 카운터 0.11.0 의 observe).

  • 간격 수의 2% 차이는 한 번 읽을 때 조각이 여러 개 온 경우를 하나로 센 몫이다
  • vLLM 채팅 스트림의 역할만 든 첫 조각은 글이 든 첫 조각보다 17ms 먼저 왔다. 그 조각을 TTFT 로 치지 않는 방식이 맞다

5. Adaptive Limit — 꼬리 지연 되먹임 한도#

조절기는 모델 서버마다 5초에 한 번, 최근 30초 안에 끝난 스트리밍 요청으로 한도를 판단한다. 조금씩 올리고 크게 내리는 AIMD(additive increase, multiplicative decrease) 다.

5초마다 위에서부터 처음 맞는 갈래 하나를 고른다. 내리는 조건이 올리는 조건보다 먼저다

숫자를 고른 이유

  • 한도가 너무 높으면 이미 들어온 요청 모두가 느려지고, 너무 낮으면 일부가 잠깐 429 를 받는다. 넘쳤을 때 잃는 쪽이 더 커서 내릴 때 크게 내린다
  • 0.7 과 +1 은 증명된 숫자가 아니다. TCP 혼잡 제어는 0.5, Netflix concurrency-limits 의 기본은 0.9 이고, 0.7 은 그 사이의 시작값이다
  • ITL 은 모든 간격을 한 데 모은 p95 가 아니라 요청별 p95 의 중앙값이다. 긴 응답 하나나 멈춘 요청 하나가 판단을 좌우하지 못한다
  • TTFT 는 요청마다 하나라 표본 20개부터 본다. 10개면 p95 가 가장 느린 하나가 되어, 쉬고 난 뒤 첫 요청(1.5초) 하나가 한도를 30% 깎는 판단을 냈다

여유 폭과 hysteresis

  • 02 의 hysteresis 는 상태 신호에 닫는 값과 여는 값 두 개를 두어 문을 여닫는다
  • 조절기는 문 대신 한도의 크기를 움직인다. 꼬리 지연은 한도를 바꾼 뒤에야 바뀌므로 한 번 움직이고 새 표본을 기다린다(⑦)
  • 경계에서 깜빡이지 않게 하는 일은 SLA 의 80~100% 구간(③)과 내린 뒤 15초(④)가 맡는다

모드와 한도의 주인

mode판단실제 한도브레이크
off안 함기준선 한도(3절)없음
observe(차트 기본)지표와 로그로만기준선 한도계산만
on함조절기의 한도(source adaptive)429
  • on 에서는 30초 list 가 기준선 한도를 다시 쓰지 않는다. 시작값의 근거(다시 측정, 스펙 변경, 사람이 적은 값)가 바뀔 때만 시작값으로 돌아간다
  • 시작값은 쓸 만한 기준선이면 maxConcurrency 그대로(× 0.8 없이), 없으면 기본값 4 다. 너무 높으면 조절기가 내린다
  • 사람이 maxConcurrent 를 적은 서버는 판단하지 않는다. 카운터가 다시 뜨면 배운 한도를 잃고 시작값부터다
  • observe 에서는 실제 한도가 손님을 막아 “한도까지 찼음”(⑤)이 그 위로 채워지지 않는다. 올라가는 판단은 on 에서만 볼 수 있다

6. Brake — 대기 수와 KV 사용률 기준 거절#

조절기는 30초 창을 5초마다 보고, 동시 도착 몰림은 1~2초 안에 온다. 브레이크는 그 사이를 맡는다. 2초마다 오븐이 만든 Service 의 vLLM /metrics 를 읽어 대기 수(엔진 합)와 KV 사용률(가장 높은 엔진)을 본다. 브레이크를 두는 이유는 Serving.02 의 6절과 같다.

브레이크는 한도를 바꾸지 않는다. 그 순간의 새 요청만 막는다
// kukie-gpu-operator counter/brake.go
func (w *brakeWatch) decide(load upstreamLoad, cfg *adaptiveConfig) string {
	if load.waiting > 0 {
		w.waitingStreak++
	} else {
		w.waitingStreak = 0
	}
	switch {
	case w.waitingStreak >= cfg.BrakeWaitingScrapes:
		return brakeWaiting
	case load.kv >= cfg.BrakeKVRatio:
		return brakeKV
	}
	return ""
}

// kukie-gpu-operator counter/limits.go
func (l *limiter) tryAcquire() bool {
	l.mu.Lock()
	defer l.mu.Unlock()
	if l.brake != "" || l.inFlight >= l.limit {
		return false
	}
	l.inFlight++
	l.peak = max(l.peak, l.inFlight)
	return true
}
  • 대기는 2번 연속일 때만 건다. 한 번은 손님이 같이 들어온 순간일 수 있고, 3.2절에서 그런 순간은 SLA 가 멀쩡한 동시 12·20 에서도 있었다
  • KV 캐시 는 0.9 에서 한 번에 건다. 차는 순간 vLLM 이 이미 들어온 요청까지 밀어내고(preemption) 다시 계산한다
  • 브레이크와 한도는 같은 tryAcquire 에서 본다. 둘 다 같은 429 rate_limit_exceeded 와 Retry-After 를 돌려주고, 지표 kukie_counter_rejected_total 의 reason 만 brake 와 limit 으로 나뉜다
  • 오븐이 만든 Service 주소(http://<name>.<ns>.svc:8000)만 읽는다. 다른 upstream 의 /metrics 는 vLLM 것이라는 보장이 없다
  • 사람이 한도를 적은 서버에도 브레이크는 건다. 한도와 따로 노는 보호다

7.1 Raise — 동시 40 에서 오른 한도#

1차 시험은 짧은 요청만 5분 보냈다.

80% 경계(40ms)를 39.985ms 로 겨우 밑돌아 20 에서 한 번 더 올랐다. 21 의 41ms 는 여유 폭 안이라 머물렀다
  • 21 에 머문 동안 받은 요청은 TTFT p95 215222ms, ITL 40.841.8ms 로 SLA 안이었고, 넘친 요청은 429 였다. 오류는 0 이다
  • 기준선 한도 12 에 비해 동시 수는 1.75배, 출력은 초당 약 1,000 토큰이었다
  • 한 번 올리면 그 한도에서 시작한 요청이 10개 이상 끝나야 다음 판단을 해서, 대략 10초에 1씩 올랐다
  • 첫 10초 몰림의 느린 TTFT 는 판단에 쓰이지 않았다. 그 세대의 TTFT 표본이 20개가 안 됐고, ITL 만 넉넉해 한도가 오르면서 표본째 비워졌다. 이 구멍은 8절에서 고쳤다
  • 브레이크는 걸리지 않았다. 시작 순간 대기 7 이 한 번 보였고, 그 뒤 대기는 0, KV 는 최대 2.1% 였다

탐침(3.2절)에서는 같은 조합이 24 까지 SLA 안이었다. 무작위 토큰 프롬프트와 영어 단어 프롬프트의 차이로 보며, 한계가 요청 모양에 따라 달라진다는 점이 고정 한도 대신 되먹임을 쓰는 근거가 하나 더 된다.

7.2 Lower and Brake — 긴 입력에서 내린 한도#

2차 시험은 1차에서 일어나지 않은 내리기와 브레이크를 보려고 긴 입력을 섞었다.

내린 뒤의 새 표본도 앞 한도로 들어온 긴 요청과 GPU 를 같이 써서 한 번 더 내렸다(DURO-237)

내리기

  • 2,900단어 입력에서는 긴 프리필이 디코드 사이에 끼어 ITL 이 87~102ms 로 올랐고, 한도는 decrease_itl 로 10초 간격 세 번 연속 내려갔다
  • 9,000단어 입력에서는 한도 2 에서도 ITL 이 122ms 였다. 이 길이의 프리필이 끼면 동시 수와 상관없이 ITL 50ms 를 지키지 못한다
  • 쿨다운은 올리기만 막는다. 내리기 사이의 간격은 새 표본 10개가 차는 시간(약 10~15초)뿐이다
  • 짧은 요청으로 돌아오자 한도는 2 → 9 까지 10초에 1씩 올랐다. 회복은 느리다

브레이크

  • 2,900단어에서는 대기가 몰림 시작 3초(최대 16)와 중간 3초에만 생겨 2번 연속 조건에 걸리지 않았다
  • 9,000단어에서는 대기 14 로 waiting 브레이크가 약 8초 걸렸고, 한 번 더 짧게 걸렸다. rejected_total{reason="brake"} 는 74 다. 풀린 뒤 바로 다시 받았다
  • KV 는 최대 16% 였다. 이 모델·노드의 KV 캐시는 86만 5천 토큰이라 0.9 는 닿기 어렵다
  • 9,000단어 첫 10초의 TTFT p95 는 9.4초였지만 입력이 4,096 토큰을 넘어 TTFT 표본에서 빠졌다

7.3 ITL Jump — 카운터 경로의 간헐 지연#

1차 시험의 한도 19 → 20 에서 ITL 이 19ms 에서 40ms 로 두 배가 됐다. 처음에는 vLLM 의 배치 크기 경계로 봤다. vLLM v0.32.0 의 CUDA graph 크기는 1, 2, 4, 8, 16, 24, 32 … 라 17~24 는 같은 24 크기로 돈다. 2차 시험 앞부분에서 카운터를 빼고 vLLM 에 직접, 동시 수를 고정해 단계마다 40초 보냈다.

GPU 속도는 그대로이고 일부 간격만 약 20ms 늦게 온다. 늦어지는 곳은 vLLM → 카운터 구간이나 카운터 안으로 본다(DURO-238)
  • vLLM 에서는 절벽이 없었다. 25 까지 ITL 이 완만하게 오르고 대기는 0 이다
  • 같은 요청을 카운터를 거쳐 보내자 한도 23 에서 ITL 이 40ms 를 넘었다. 경계가 1차의 20 과 다르다
  • 카운터도 23 에서 2분 동안 hold 했다. 카운터가 잰 값도 80% 를 넘었다는 뜻이라, 늦어지는 곳은 클라이언트 쪽이 아니라 vLLM → 카운터 구간이나 카운터 안이다
  • 원인은 확정하지 못했다. 후보는 TCP 지연 ACK 와 Nagle(40ms 단위), 카운터의 스트림 전달(flush) 방식이다

이 지연은 조절기의 판단에도 들어간다. 지금의 한도 21~23 은 GPU 의 한계가 아니라 이 경로 지연이 정한 값일 수 있다.

8. Review — 리뷰에서 고친 것#

출처문제수정
리뷰(#29)한 서버의 여러 이름이 다른 한도를 받아, 맵 순서에 따라 한도가 바뀌었다limiter 키를 upstream 으로 정하고 같은 키는 한 한도로 맞췄다
리뷰(#29)경로가 다시 생길 때 in_flight 지표를 0 으로 덮어, 끝나는 요청이 음수를 만들었다처음 보는 이름만 초기화한다
리뷰(#34)“한도까지 찼음"이 창이 아니라 마지막 변경 뒤의 누적 최댓값을 봤다주기마다 최고 처리 중 수를 시각과 함께 남기고 30초 창 안의 것만 본다
리뷰(#34)values 파일의 따옴표 없는 mode: off 를 YAML 1.1 이 false 로 읽어 설치가 실패했다차트가 bool 을 off·on 으로 되돌린 뒤 검사한다
리뷰(#36)브레이크 루프가 잠금 없이 지표를 써서, 그 사이 사라진 모델의 지표가 되살아났다읽기는 잠금 밖에서 병렬로, 반영은 잠금 안에서 지금 경로에 남은 이름에만 한다
observe 실측(#36)쉬고 난 뒤 첫 요청 하나(TTFT 1.5초)가 p95 가 되어 16 → 11 판단이 나왔다TTFT 판단은 표본 20개부터
1차 실측(#43)TTFT 표본이 20개 미만이면 몰림의 느린 TTFT 를 보지 않고 ITL 만으로 올렸다20개 미만이어도 SLA 80% 를 넘은 TTFT 가 둘 이상이면 올리지 않는다. 하나뿐이면 그대로 올린다

#43 은 카운터 0.14.0 에 들어가 kukie-gpu 에 설치됐다. 다만 설치 뒤 부하를 다시 보내 몰림 첫 구간에서 한도가 멈추는지는 아직 보지 않았다.

9. Limits — 확인 못 한 것과 남은 일#

  • 내리기 연쇄(DURO-237): 내린 뒤 앞 한도로 들어온 요청이 빠질 때까지, 또는 처리 중 수가 새 한도 아래로 내려갈 때까지 다시 내리지 않는 규칙을 후보로 두었다. 구현 전이다
  • 경로 지연(DURO-238): 7.3절의 약 20ms 지연의 위치와 원인. 고친 뒤 직접 경로와 카운터 경로의 ITL p95 를 같은 부하로 다시 비교한다
  • Retry-After 전달(DURO-221): 카운터는 429·503 에 Retry-After 를 붙이지만, 커넥터 → 게이트웨이 터널의 응답 메시지에는 상태와 Content-Type 만 있어 사용자에게 가지 않는다. 앞단을 거친 사용자는 언제 다시 보낼지 모른다
  • 다른 조합(DURO-233): L40S 1장의 gpt-oss-20b 하나만 봤다. 다른 GPU·모델, 길이가 섞인 실제 요청 모양, #43 의 부하 확인은 표준 도구(inference-perf) 재측정 계획에 넣었다
  • 비스트리밍 요청은 재지 않는다. 비스트리밍만 오는 모델의 한도는 시작값에 머문다
  • 모델별 SLA 가 없다. 모든 모델이 TTFT 1초·ITL 50ms 를 쓴다
  • 카운터가 다시 뜨면 배운 한도를 잃는다. Pod 는 1개로 고정이라 여러 카운터가 한도를 나누는 경우는 다루지 않았다
  • 처리 중 프리필 수는 지표로만 잰다. 막는 기준으로 쓸 숫자는 정하지 않았다
