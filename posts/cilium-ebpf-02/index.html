1. Overview#

굵은 선 위는 유저 공간, 아래는 커널 · 숫자는 일이 일어나는 순서 · 아래 칸은 해당 절로 이동

01편에서는 eBPF가 커널 안에서 사용자의 코드를 실행한다고 설명했습니다. 그렇다면 그 코드는 실제로 어떻게 생겼고, 어떤 과정을 거쳐 커널에 올라가며, 실행 결과는 어떻게 꺼낼까요?

이번 글에서는 BCC의 Python 라이브러리로 가장 작은 eBPF 애플리케이션을 만들어 보겠습니다. execve 시스템 콜이 불릴 때마다 실행되는 프로그램 하나에서 출발해 다음 두 가지를 차례로 바꿔 가며 살펴봅니다.

  • 결과를 꺼내는 통로 — trace_pipe, 해시 테이블, perf 버퍼
  • 프로그램을 나누는 방법 — 함수 호출, 꼬리 호출

컴파일과 로드의 세부 과정은 BCC가 대신 처리하므로 이번 글에서는 드러나지 않습니다.

2. Hello World — BCC로 쓴 첫 프로그램#

2.1 두 부분으로 된 애플리케이션#

먼저 전체 코드부터 보겠습니다.

#!/usr/bin/python3
from bcc import BPF

program = r"""
int hello(void *ctx) {
    bpf_trace_printk("Hello World!");
    return 0;
}
"""

b = BPF(text=program)                           # 컴파일 + 커널에 로드
syscall = b.get_syscall_fnname("execve")        # 아키텍처별 커널 함수 이름
b.attach_kprobe(event=syscall, fn_name="hello") # 이벤트에 붙인다
b.trace_print()                                 # 출력을 계속 읽는다

eBPF 애플리케이션은 두 부분으로 나뉩니다.

  • eBPF 프로그램 hello() — 커널에서 실행됩니다. C로 작성해 Python 코드 안에 문자열로 넣습니다.
  • 유저 공간 코드 — 이 프로그램을 커널에 올리고 결과를 읽는 Python 스크립트입니다.

BPF(text=program) 한 줄이 문자열을 컴파일하고 커널에 로드하는 일까지 함께 처리합니다.

프로그램 안에서 호출하는 bpf_trace_printk()는 ‘헬퍼 함수’입니다. eBPF 프로그램은 커널 기능이 필요할 때 헬퍼 함수를 호출하며, 여기서는 메시지 한 줄을 출력하는 데 사용했습니다.

BCC는 eBPF 프로그램을 작성하는 가장 쉬운 방법이라 첫 예제로 적합합니다. 다만 다른 사용자에게 배포하는 운영 도구에는 잘 쓰지 않습니다. 2026년 기준 — BCC 저장소에도 같은 도구를 libbpf와 CO-RE로 다시 작성한 libbpf-tools 디렉터리가 있고, 배포용 도구는 이쪽으로 옮겨 가는 추세입니다.

2.2 execve에 붙이기#

eBPF 프로그램은 이벤트에 연결해야 실행됩니다. 이 예제에서는 새 프로그램을 실행하는 시스템 콜인 execve에 연결했으므로, 머신에서 누가 무엇을 실행하든 hello()가 실행됩니다.

  • 함수 이름 찾기 — execve는 Linux의 표준 인터페이스이지만, 이를 구현하는 커널 함수의 이름은 CPU 아키텍처마다 다릅니다(x86-64에서는 __x64_sys_execve). get_syscall_fnname()이 현재 머신의 이름을 찾아 줍니다.
  • 연결 방식 — 커널 함수의 진입점에 프로그램을 거는 kprobe를 사용했습니다. 커널 5.5부터는 같은 일을 더 빠르게 처리하는 fentry(반환 쪽은 fexit)도 쓸 수 있습니다.
  • 출력 읽기 — 마지막 줄의 trace_print()는 사용자가 멈출 때까지 출력을 계속 읽어 화면에 표시합니다.

2.3 실행 결과와 권한#

스크립트를 실행한 뒤 다른 터미널에서 아무 명령이나 실행하면 한 줄씩 출력됩니다. 아래는 GitHub Actions의 x86-64 러너에서 ls, sudo -u runner true, timeout 0.2 sleep 1을 반복해 실행했을 때의 출력입니다.

sudo ./hello.py
$ sudo ./hello.py

b'<...>-2645 [001] ...31 220.313333: bpf_trace_printk: Hello World!'

GitHub Actions 러너 출력 · x86-64 · Ubuntu 24.04 · 커널 7.0 · 실행 기록
  • 문맥 정보 — 앞부분의 프로세스 이름과 PID, CPU 번호, 시각은 eBPF 프로그램이 넣은 값이 아니라 커널의 추적 기능이 덧붙인 정보입니다.
  • <...> — 추적 기능은 기록할 때 PID만 저장하고, 출력할 때 PID로 프로세스 이름을 찾아 붙입니다. ls처럼 금방 끝난 프로세스는 이름을 찾지 못해 <...>로 표시됩니다.
  • 같은 PID의 네 줄 — timeout은 sleep을 실행할 때 PATH의 디렉터리를 차례로 시도합니다. 파일이 없어 실패한 execve도 커널 함수의 입구는 지나므로 모두 잡힙니다.
  • echo처럼 셸에 내장된 명령은 새 프로그램을 실행하지 않으므로 execve가 호출되지 않고, 아무것도 출력되지 않습니다.

눈여겨볼 점은 프로그램을 연결하자마자 이미 실행 중이던 셸과 스크립트의 이벤트도 잡힌다는 것입니다. 셸이나 실행되는 프로그램은 전혀 수정하지 않았습니다. 01편 4.4에서 설명한 동적 로딩이 바로 이것입니다.

eBPF는 커널을 다루므로 권한이 필요합니다. 가장 간단한 방법은 root로 실행하는 것이고, Operation not permitted 오류가 나면 먼저 권한을 확인해야 합니다. 같은 러너에서 일반 사용자로 실행하면 프로그램을 로드하는 단계에서 거부됩니다.

python3 hello.py
$ python3 hello.py
bpf: Failed to load program: Operation not permitted
…
Exception: Need super-user privileges to run
일반 사용자(UID 1001) 실행 결과 · 실행 기록

커널 5.8부터는 root 대신 필요한 capability만 부여할 수도 있습니다. 다만 CAP_BPF만으로는 부족한 경우가 많습니다.

  • 추적 프로그램 — CAP_BPF + CAP_PERFMON
  • 네트워크 프로그램 — CAP_BPF + CAP_NET_ADMIN

2.4 trace_pipe의 한계#

Python 스크립트는 출력을 어디에서 읽어 오는 걸까요?

bpf_trace_printk()는 항상 정해진 의사 파일 하나에 메시지를 쓰고, Python 쪽은 그 파일을 읽을 뿐입니다. /sys/kernel/debug/tracing/trace_pipe를 cat으로 열어 보면 같은 내용을 확인할 수 있습니다. 2026년 기준 — 커널 4.1부터 추적 파일은 tracefs가 담당하며 기본 위치는 /sys/kernel/tracing입니다. debugfs 아래의 경로는 호환성을 위해 남아 있습니다. 실습한 러너에는 debugfs가 마운트되어 있지 않아 /sys/kernel/tracing/trace_pipe만 있었습니다.

이 방식은 디버깅에는 충분하지만, 운영 환경에서 데이터를 주고받는 통로로 쓰기에는 한계가 분명합니다.

trace_pipe 는 디버깅용 출구 · 프로그램이 여럿이거나 구조가 있는 데이터에는 맵

그래서 실제로는 프로그램마다 따로 만드는 맵을 사용합니다.

3. BPF Maps — 커널과 유저 공간의 공유 자료구조#

3.1 맵의 종류#

‘맵’은 eBPF 프로그램과 유저 공간이 함께 읽고 쓰는 자료구조입니다. eBPF를 classic BPF와 구분하는 가장 큰 차이 중 하나이며, eBPF 맵과 BPF 맵은 같은 뜻으로 쓰입니다.

맵은 주로 세 가지 용도로 사용합니다.

  • 설정 전달 — 유저 공간이 설정 값을 써 두면 eBPF 프로그램이 읽어 갑니다.
  • 상태 보관 — eBPF 프로그램이 남긴 상태를 다른 프로그램이나 같은 프로그램의 다음 실행이 읽습니다.
  • 결과 수집 — eBPF 프로그램이 결과나 지표를 기록하면 유저 공간이 읽어 보여 줍니다.

맵은 모두 키-값 저장소이고, 종류는 다음과 같이 나눌 수 있습니다. 전체 목록은 커널 헤더 uapi/linux/bpf.h에 정의되어 있습니다.

  • 배열과 해시 테이블 — 배열은 키가 4바이트 인덱스로 고정되고, 해시 테이블은 임의의 자료형을 키로 씁니다.
  • 특정 연산용 — FIFO 큐, 스택, LRU, 최장 접두사 일치(LPM), 블룸 필터
  • 특정 객체용 — sockmap과 devmap은 소켓과 네트워크 장치를 담아 트래픽을 다른 곳으로 보냅니다. 프로그램 배열은 eBPF 프로그램을 담아 꼬리 호출에 쓰고, 맵을 담는 map-of-maps도 있습니다.

일부 맵에는 CPU별(per-CPU) 변형이 있습니다. CPU 코어마다 메모리를 따로 두므로 여러 코어가 동시에 접근하는 문제를 신경 쓰지 않아도 됩니다. 여러 코어가 함께 쓰는 맵에는 커널 5.1부터 스핀 락을 적용할 수 있습니다.

3.2 해시 테이블 맵#

이번에는 execve가 호출될 때마다 사용자 ID(UID)별로 횟수를 세어 보겠습니다. 키는 UID, 값은 실행 횟수입니다.

BPF_HASH(exec_count);                       // BCC 매크로 — 해시 테이블 맵 정의

int hello(void *ctx) {
    u64 uid = bpf_get_current_uid_gid() & 0xFFFFFFFF;  // 하위 32비트가 UID
    u64 count = 0;
    u64 *p = exec_count.lookup(&uid);       // 값의 포인터, 없으면 0
    if (p != 0) {
        count = *p;
    }
    count++;
    exec_count.update(&uid, &count);
    return 0;
}

이 코드에서 짚어 볼 점은 두 가지입니다.

  • NULL 확인 — lookup()이 돌려준 포인터가 0인지 확인하는 부분은 생략할 수 없습니다. 맵에 없는 키를 읽을 수 있기 때문에, 확인하지 않으면 검증기가 로드를 거부합니다.
  • BCC 문법 — exec_count.lookup(&uid)는 C 문법이 아닙니다. C의 구조체에는 메서드가 없습니다. BCC는 C와 비슷한 자체 문법을 받아서, 컴파일러에 넘기기 전에 올바른 C 코드로 다시 작성합니다.

컴파일과 로드, kprobe 연결은 2.1과 같습니다. 유저 공간에서는 2초마다 맵 전체를 읽어 출력합니다.

while True:
    sleep(2)
    print("\t".join(f"ID {k.value}: {v.value}" for k, v in b["exec_count"].items()))

다른 터미널에서 ls와 sudo ls를 번갈아 실행하면 맵의 값은 다음과 같이 바뀝니다.

파랑은 일반 사용자(UID 1000), 주황은 root(UID 0) · 오른쪽은 유저 공간이 2초마다 읽는 맵 상태

sudo ls를 실행하면 execve가 두 번 호출됩니다. 사용자가 sudo를 실행하고, sudo가 다시 root 권한으로 ls를 실행하기 때문입니다. 그래서 UID 1000과 0의 값이 함께 늘어납니다.

러너에서는 다음과 같이 출력됩니다.

sudo ./hello_map.py
$ sudo ./hello_map.py
ID 1001: 3	ID 0: 25
ID 1001: 3	ID 0: 26
ID 1001: 3	ID 0: 26
ID 1001: 3	ID 0: 27
GitHub Actions 러너 출력 · x86-64 · Ubuntu 24.04 · 커널 7.0 · 실행 기록
  • UID 1001 — sudo -u runner true를 세 번 실행했으므로 3에서 멈춥니다.
  • UID 0 — 스크립트의 ls와 timeout, 러너의 백그라운드 작업이 모두 root로 실행되어 계속 늘어납니다.
  • 누적 — 맵은 2초마다 읽어도 값이 그대로 남아 있습니다. 읽으면 비워지는 trace_pipe와 다른 점입니다.

이 예제는 키가 정수이므로 배열 맵을 써도 됩니다. 해시 테이블은 키의 자료형이 자유로운 대신, 유저 공간이 주기적으로 맵을 확인해야 합니다. 이벤트가 생길 때마다 바로 받으려면 버퍼 맵을 사용합니다.

3.3 링 버퍼#

Linux에는 원래 커널에서 유저 공간으로 데이터를 보내는 perf 서브시스템이 있었습니다. eBPF는 perf 버퍼와 그 후속인 BPF 링 버퍼를 맵으로 쓸 수 있게 했는데, 둘 다 ‘링 버퍼’ 구조입니다.

링 버퍼는 메모리 한 덩어리를 고리처럼 다루면서 쓰기 포인터와 읽기 포인터를 따로 관리합니다.

읽을 때 drop 카운터도 함께 수신 → 마지막 읽기 이후 놓친 데이터 확인

쓰기와 읽기의 속도는 일정하지 않으므로, 버퍼 크기는 그 차이를 감당할 수 있도록 정해야 합니다.

커널 5.8 이상이라면 perf 버퍼보다 BPF 링 버퍼를 권장합니다.

  • perf 버퍼 — CPU마다 버퍼를 따로 둡니다.
  • BPF 링 버퍼 — 모든 CPU가 버퍼 하나를 함께 써서 메모리를 덜 쓰고, 여러 CPU에서 일어난 이벤트의 순서도 보장합니다. BCC에서는 BPF_RINGBUF_OUTPUT으로 사용합니다.

3.4 perf 버퍼로 구조체 보내기#

이번에는 trace_pipe 대신, 이 프로그램만 쓰는 perf 버퍼 맵으로 구조체를 보내 보겠습니다.

BPF_PERF_OUTPUT(events);                    // 커널 → 유저 공간 메시지용 맵

struct event_t {
    int  pid;
    int  uid;
    char comm[16];
    char msg[12];
};

int hello(void *ctx) {
    struct event_t e = {};
    char msg[12] = "Hello World";

    e.pid = bpf_get_current_pid_tgid() >> 32;
    e.uid = bpf_get_current_uid_gid() & 0xFFFFFFFF;
    bpf_get_current_comm(&e.comm, sizeof(e.comm));
    bpf_probe_read_kernel(&e.msg, sizeof(e.msg), msg);

    events.perf_submit(ctx, &e, sizeof(e));
    return 0;
}

유저 공간 코드는 다음과 같습니다.

def on_event(cpu, data, size):
    e = b["events"].event(data)
    print(f"{e.pid} {e.uid} {e.comm.decode()} {e.msg.decode()}")

b["events"].open_perf_buffer(on_event)      # 데이터가 오면 on_event 를 부른다
while True:
    b.perf_buffer_poll()
  • 문자열 복사 — C에서는 문자열을 =로 대입할 수 없으므로, bpf_get_current_comm()처럼 값을 쓸 위치의 주소를 헬퍼 함수에 넘깁니다.
  • 전달 흐름 — 구조체를 다 채우면 perf_submit()이 이를 맵에 넣고, 유저 공간은 버퍼를 폴링하다가 데이터가 도착하면 콜백 함수를 호출합니다.

러너에서는 다음과 같이 출력됩니다.

sudo ./hello_perf.py
$ sudo ./hello_perf.py
2712 0 bash Hello World
2713 0 bash Hello World
2714 0 bash Hello World
2715 1001 sudo Hello World
2716 0 bash Hello World
2717 0 timeout Hello World
2717 0 timeout Hello World
2717 0 timeout Hello World
2717 0 timeout Hello World
GitHub Actions 러너 출력 · x86-64 · Ubuntu 24.04 · 커널 7.0 · 실행 기록
  • 이름 — bpf_get_current_comm()은 이벤트가 일어난 순간의 이름을 읽어 오므로, 2.3과 달리 <...>가 나오지 않습니다.
  • ls인데 bash — kprobe는 execve의 입구에서 실행됩니다. 이 시점에는 아직 실행 이미지가 바뀌기 전이라, ls를 실행한 셸의 이름이 찍힙니다.
  • UID 1001 — sudo -u runner true에서는 sudo가 UID를 바꾼 뒤 true를 실행하므로 sudo와 1001이 함께 찍힙니다.

이제 데이터는 공용 파일이 아니라 이 프로그램이 만든 맵을 거쳐 전달되므로, trace_pipe를 열어 보면 아무것도 나오지 않습니다. 같은 구조체를 BPF_RINGBUF_OUTPUT과 ringbuf_output()으로 링 버퍼에 보내도 출력은 같습니다.

3.5 헬퍼 함수로 얻는 문맥#

앞의 코드에서 쓴 >> 32와 & 0xFFFFFFFF는 무슨 의미일까요? 두 헬퍼 함수는 64비트 값 하나에 두 가지 정보를 담아 돌려줍니다.

헬퍼 한 번 호출에 두 값 · 시프트와 마스크로 필요한 쪽만 추출
  • bpf_get_current_pid_tgid() — 상위 32비트는 TGID로, 사용자가 ps에서 보는 프로세스 ID입니다. 하위 32비트는 커널이 스레드마다 부여하는 ID이며, 스레드가 하나인 프로세스에서는 두 값이 같습니다.
  • bpf_get_current_uid_gid() — 상위에 GID, 하위에 UID를 담습니다.

이처럼 eBPF 프로그램은 이벤트가 일어났다는 사실뿐 아니라, 누가 어떤 명령으로 일으켰는지까지 커널 안에서 바로 수집합니다. 유저 공간으로 동기 전환할 필요가 없으므로 빠르고, 이것이 eBPF가 관측에 강한 이유입니다.

사용할 수 있는 문맥 정보와 헬퍼 함수는 프로그램 유형과 연결한 이벤트에 따라 다릅니다. 문맥을 읽는 데 그치지 않고 값을 바꾸거나 이벤트 자체를 막는 프로그램도 있습니다.

4. Program Split — 함수 호출과 꼬리 호출#

4.1 인라인 함수#

코드가 길어지면 공통 부분을 함수로 나누고 싶어집니다. 하지만 초기의 eBPF 프로그램은 헬퍼 함수 외에는 함수를 호출할 수 없었습니다. 그래서 개발자들은 컴파일러에 함수를 항상 인라인하도록 지시했습니다.

static __always_inline void record(void *ctx, int val)
초기 eBPF 의 함수 호출 · 헬퍼 외 호출 X → 모든 함수를 오른쪽처럼 인라인
  • 일반 함수 — 점프 명령으로 함수 본체에 갔다가 돌아옵니다.
  • 인라인 함수 — 점프하지 않고, 호출하는 자리마다 본체의 명령이 복사됩니다. 여러 곳에서 호출하면 그만큼 복사본이 생깁니다.

컴파일러가 최적화 과정에서 커널 함수를 인라인하기도 하는데, 이렇게 인라인된 함수에는 kprobe를 연결할 수 없습니다.

4.2 BPF 서브프로그램#

커널 4.16과 LLVM 6.0부터는 인라인하지 않은 함수 호출이 가능해졌습니다. 이를 ‘BPF to BPF 함수 호출’ 또는 ‘BPF 서브프로그램’이라고 부릅니다.

다만 BCC는 이 기능을 지원하지 않으므로, BCC에서는 인라인 함수만 사용할 수 있습니다.

4.3 꼬리 호출#

프로그램을 나누는 또 다른 방법은 ‘꼬리 호출’입니다. 꼬리 호출은 다른 eBPF 프로그램을 호출하면서 실행 문맥을 넘기는 방식으로, 일반 프로세스의 execve()처럼 호출한 쪽으로 돌아오지 않습니다.

long bpf_tail_call(void *ctx, struct bpf_map *prog_array_map, u32 index)
  • ctx — 호출받는 프로그램에 넘길 문맥
  • prog_array_map — 프로그램들의 파일 디스크립터를 담은 BPF_MAP_TYPE_PROG_ARRAY 맵
  • index — 그중 몇 번째 프로그램을 호출할지

호출 결과에 따라 동작이 달라집니다.

  • 성공하면 현재 프로그램이 스택에서 호출된 프로그램으로 바뀌고, 원래 프로그램으로 돌아오지 않습니다.
  • 실패하면(해당 위치에 프로그램이 없으면) 원래 프로그램이 다음 줄부터 계속 실행됩니다.

꼬리 호출은 eBPF에만 있는 개념이 아닙니다. 재귀 호출이 스택 프레임을 계속 쌓다가 넘치는 문제를 막기 위한 기법입니다. eBPF는 스택이 512바이트밖에 되지 않으므로 이 기법이 더욱 유용합니다.

예제로 모든 시스템 콜의 공통 진입점인 sys_enter 원시 트레이스포인트에 프로그램을 연결하고, 시스템 콜 번호에 따라 꼬리 호출로 처리를 나누어 보겠습니다.

BPF_PROG_ARRAY(syscall, 500);               // 프로그램 배열 맵

int hello(struct bpf_raw_tracepoint_args *ctx) {
    int nr = ctx->args[1];                  // 시스템 콜 번호
    syscall.call(ctx, nr);                  // BCC 가 bpf_tail_call() 로 바꾼다
    bpf_trace_printk("Another syscall: %d", nr);   // 꼬리 호출이 없을 때만 실행
    return 0;
}

int hello_exec(void *ctx) {
    bpf_trace_printk("Executing a program");
    return 0;
}

int hello_timer(struct bpf_raw_tracepoint_args *ctx) {
    if (ctx->args[1] == 222)      bpf_trace_printk("Creating a timer");
    else if (ctx->args[1] == 226) bpf_trace_printk("Deleting a timer");
    else                          bpf_trace_printk("Some other timer operation");
    return 0;
}

int ignore_nr(void *ctx) {
    return 0;
}

유저 공간에서는 각 프로그램을 로드한 뒤 프로그램 배열 맵을 채웁니다.

b = BPF(text=program)
b.attach_raw_tracepoint(tp="sys_enter", fn_name="hello")

ignore_fn = b.load_func("ignore_nr", BPF.RAW_TRACEPOINT)
exec_fn   = b.load_func("hello_exec", BPF.RAW_TRACEPOINT)
timer_fn  = b.load_func("hello_timer", BPF.RAW_TRACEPOINT)

prog_array = b.get_table("syscall")
prog_array[ct.c_int(59)] = ct.c_int(exec_fn.fd)        # execve
for nr in range(222, 227):                             # timer_create … timer_delete
    prog_array[ct.c_int(nr)] = ct.c_int(timer_fn.fd)
for nr in (21, 22, 25):                                # 너무 잦은 시스템 콜은 무시
    prog_array[ct.c_int(nr)] = ct.c_int(ignore_fn.fd)

b.trace_print()
한 프로그램이 여러 칸에 · 222~226번 다섯 칸 모두 hello_timer()
  • 시스템 콜 번호 — x86-64 기준으로 59가 execve, 222~226이 타이머 관련 시스템 콜입니다.
  • 빈 칸 — 맵을 모든 번호로 채울 필요는 없습니다. 빈 칸의 번호가 들어오면 꼬리 호출이 실패하고 hello()의 기본 메시지가 출력됩니다.
  • 한 프로그램, 여러 칸 — 한 프로그램을 여러 칸에 넣을 수 있어서, hello_timer()는 다섯 칸이 함께 가리킵니다.
  • 독립된 프로그램 — 꼬리 호출로 실행되는 프로그램도 각각 독립된 eBPF 프로그램입니다. 유저 공간이 하나씩 로드하면 load_func()가 파일 디스크립터를 돌려주고, 이 값으로 맵을 채웁니다.

러너에서 실행한 출력 중 꼬리 호출된 프로그램이 찍은 줄만 골라 보면 다음과 같습니다.

grep -E 'Executing|timer' out.txt

  • 222번과 223번 — timer_create는 Creating a timer, timer_settime은 Some other timer operation을 출력합니다. timeout은 타이머를 지우지 않고 끝나므로 226번은 보이지 않습니다.

  • 대처 — 무시 목록에 0번(read)과 1번(write)을 넣거나, 프로그램 안에서 자기 PID를 걸러 내야 합니다.

4.4 꼬리 호출의 제약#

  • 같은 프로그램 유형 — 꼬리 호출로 실행할 프로그램은 호출하는 프로그램과 유형이 같아야 합니다. 이 예제에서는 모두 BPF.RAW_TRACEPOINT입니다.
  • 서브프로그램과의 조합 — 꼬리 호출은 커널 4.2부터 지원되었지만 오랫동안 BPF 서브프로그램과 함께 쓸 수 없었고, 이 제한은 커널 5.10에서 풀렸습니다. JIT 컴파일러의 지원이 필요해서 처음에는 x86에서만 가능했고, ARM64는 커널 6.0부터 지원합니다.
  • 최대 33번 — 한 번의 실행에서 꼬리 호출은 최대 33번까지 이어질 수 있습니다.

프로그램 하나당 검증기가 처리하는 명령어 100만 개라는 한도가 별도로 있으므로, 둘을 합치면 커널 안에서 상당히 복잡한 로직도 실행할 수 있습니다.

5. Discussion#

이번 글에서는 BCC로 만든 Hello World에서 출발해 맵으로 데이터를 꺼내고, 함수 호출과 꼬리 호출로 프로그램을 나누는 과정을 살펴봤습니다.

BCC 덕분에 몇 줄의 Python 코드만으로 커널 이벤트를 관찰할 수 있었지만, 그만큼 컴파일과 로드, 이벤트 연결 과정은 감춰져 있었습니다.

핵심 메시지#

두 부분으로 된다
커널에서 도는 eBPF 프로그램과, 그것을 올리고 결과를 읽는 유저 공간 코드가 하나의 애플리케이션을 이룹니다.
이벤트에 붙여야 돈다
kprobe로 execve에 붙이면 누가 실행하든, 이미 실행 중이던 셸에서 실행하든 프로그램이 실행됩니다.
맵이 출구다
trace_pipe는 머신에 하나뿐인 문자열 통로입니다. 맵은 프로그램마다 따로, 정해 둔 구조 그대로 데이터를 옮깁니다.
문맥은 커널에서 모은다
헬퍼가 pid, uid, 명령 이름을 돌려주므로 유저 공간으로 넘어가지 않고도 누가 일으켰는지 알 수 있습니다.
꼬리 호출은 돌아오지 않는다
프로그램 배열에서 번호로 다음 프로그램을 골라 실행을 넘깁니다. 빈 칸이면 원래 프로그램이 이어서 실행됩니다.
BCC는 C를 다시 쓴다
lookup(), call() 같은 문법은 BCC가 컴파일 전에 올바른 C와 헬퍼 호출로 바꿔 준 것입니다.
