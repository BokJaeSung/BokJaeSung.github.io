1. Overview#

세트 칸의 색은 역할이다. 번호와 아래 띠를 누르면 해당 절로 이동한다

이 글의 범위

  • Kukie Model 은 쿠버네티스 고장 진단에 쓰는 자체 작은 모델이다. 이 글은 학습 결과가 아니라 그 결과를 재는 방법을 다룬다
  • 한 문제의 흐름: kind 에 고장을 심고 증상을 확인한 뒤 에이전트가 읽기 도구로 원인을 답하고, 채점기가 원인 일치만으로 점수를 낸다
  • 판정은 결과를 보기 전에 얼린 규칙으로 낸다. 세트마다 역할(주 지표, 지킴, 방향만, 확인·거부권)이 다르다
  • 이 설계로 낸 2회차 판정과 학습 과정은 Serving.09 에서 다룬다

2. Background — 측정부터 만든 이유#

위 줄은 정해 둔 순서, 아래는 실제 날짜다(KST)

2026-11-14 에 진단 기능의 폐쇄 모드를 정했다(DURO-266). 온프레미스 고객의 클러스터 정보는 외부 모델 제공자로 나가지 않는다. 그러면 진단을 맡을 모델은 둘 중 하나다. 우리가 만든 작은 모델이거나, 고객 사내의 OpenAI 호환 주소다.

  • 진단은 좁은 작업이다. 읽기 도구 8개로 클러스터를 보고, 정해진 답 양식에 원인을 적는다
  • 그래서 큰 범용 모델이 아니라 작은 모델로 충분할 수 있다는 가설을 세웠다
  • 작업 순서는 “프롬프트 먼저, 학습은 실패 모양이 숫자로 보일 때"로 정했다. 숫자 없이 학습하면 무엇이 좋아졌는지 가를 수 없다
  • 이 모델은 Serving.06·Serving.07 의 고객 GPU 서빙 경로 위에서 돌 모델이다

평가표를 먼저 만들고, 상용 모델 루나로 상한선에 가까운 기준 점수를 낸 뒤, 학습 없이 원본 오픈 모델을 비교했다. 측정을 준비하면서 판정 세트를 두 번 열었고, 그 순서가 뒤의 설계(6절, 8절)를 바꿨다.

3. Task — 문제 하나의 실행#

3.1 Harness 실행 순서#

빨간 갈래는 장비 실패, 회색 점선은 평가 전용 보조 단계다
  • 문제마다 반복마다 처음부터 다시 한다. 반복끼리 상태가 섞이지 않는다
  • 증상 확인은 측정의 전제다. 증상이 재현되지 않은 문제에서 모델이 틀리면 모델 탓인지 장비 탓인지 가를 수 없다. 그래서 에이전트를 돌리지 않고 실패로 센다
  • 장비 실패는 같은 문제·같은 모델만 한 번 다시 돌린다. 모델 답을 보고 다시 돌리지 않는다
  • 에이전트는 제품 agent 를 커밋 51b380f 로 고정해 그대로 부른다. Private 스킬이라 변경 도구가 없다

3.2 Answer 스키마#

답 양식은 화면에 그리는 글 칸 셋에 채점용 구조 칸 셋을 더한 것이다(DURO-264).

# durokukie/agent kukie_agent/skills/base.py (발췌·줄임, 51b380f)
CauseCategory = Literal[
    "bad-command", "image-not-found", "oom", "probe-misconfig", "selector-mismatch", "missing-config",
    "unschedulable", "quota", "rbac", "network-policy",
    "volume-permission", "port-conflict", "admission-rejected",   # DURO-268
    "other", "healthy",
]

class Finding(BaseModel):
    cause: str
    evidence: str
    recommendation: str
    cause_object: CauseObject | None   # kind · namespace · name, 고쳐야 할 오브젝트
    cause_category: CauseCategory
    fix_commands: list[str]            # 제안만 하고 실행하지 않는다
  • cause_object 는 증상이 보인 오브젝트가 아니라 고쳐야 할 오브젝트다. 이 구분이 채점의 핵심이다(4.1절)
  • 분류는 15개다. 처음 12개에서 volume-permission·port-conflict·admission-rejected 를 더했다(DURO-268). 루나 기준을 재기 전에 더해서 모든 비교가 같은 목록을 쓴다
  • 확실하지 않으면 other, 조사했는데 고장이 없으면 healthy 다
  • harness 는 분류 목록을 따로 적지 않고 고정한 agent 의 CAUSE_CATEGORIES 에서 읽는다. 시나리오 정답 분류가 그 목록에 없으면 실행하지 않고 멈춘다

4. Grading — 원인 일치와 근거#

4.1 원인 일치#

왼쪽 번호와 오른쪽 상자가 짝이다

판정에 쓰는 점수는 원인 정답률 하나다. 분류와 원인 오브젝트가 모두 맞아야 정답이다.

  • 사람이나 LLM 이 답 글을 읽고 맞다고 판단하지 않는다. 일치 채점이라 같은 기록이면 언제 다시 채점해도 같은 점수가 나온다(--rescore)
  • 정답은 시나리오의 task.yaml 에 적힌 것만 인정한다. 인정 분류(cause_category_also_accepted)와 인정 오브젝트(cause_object_also_accepted, cause_objects_all)도 정답을 만들 때 미리 적는다
  • 주 지표에서는 요청 상한에 걸려 답이 없거나 서버 오류로 끝난 실행도 오답이다. 끝까지 답하는 것도 진단 능력에 든다
  • 전체 점수는 문제별 반복 평균의 평균이다. 고장·정상·주입 시나리오는 따로 낸다

4.2 근거 기준 v2#

v1은 경로 1만 인정했다. 출력 예시의 이름은 일반 값이다

원인이 맞아도 찍어서 맞혔을 수 있다. 그래서 근거를 보조 지표로 함께 남긴다.

  • 근거 조사: 정답이 요구한 오브젝트를 실제 도구 호출로 봤는가
  • 근거 인용: 답의 evidence 글이 실제 도구 출력에 있는가. 영문·숫자 낱말 80% 이상과 따옴표 안 글 전부가 출력에 있어야 통과다
  • 맞혔지만 근거 없음: 원인은 맞았는데 근거 조사가 실패한 횟수

v1 은 원인 오브젝트를 직접 describe·list 한 것만 인정했다. 교사 풀이에서 근거 조사 실패가 432회로 가장 많이 나오자 기준이 너무 좁은지 봤다.

  • 떨어진 풀이를 다시 읽기 전에 원칙부터 적어 커밋했다(datagen/rules/evidence-principle.md). 통과율을 보고 원칙을 고치지 않기 위해서다
  • 원칙: 근거는 원인 값을 설정으로 보여 준 출력이다. 실행 결과(로그 줄, 종료 코드, 프로브 실패)는 설정 때문에 생긴 일이라 근거가 아니다
  • 원칙에서 규칙마다 인정 경로를 끌어내 v2 를 만들고 얼렸다. 공개 세트를 v2 로 다시 채점했을 때 바뀐 실행은 0회였다

근거 v2 는 판정에도, 지킴에도 쓰지 않는다. 결과 문서에 원인 정답률과 나란히 적을 뿐이다. 원인이 맞았는데 근거가 없는 실행이 늘면 그 증가를 해석 표시로 남긴다.

5. Baselines — 루나 기준과 원본 모델#

학습 전에 두 가지를 쟀다. 상한선에 가까운 기준 점수(루나)와, 학습할 후보 원본 모델이 그 기준에 얼마나 못 미치는가다.

  • 루나는 47문제 × 3 = 141회를 약 $0.71 에 돌렸다. 근거 인용은 처음 41% 로 나왔다가 채점기를 고친 뒤 89% 가 됐다(10절)
  • 루나 출력은 기준 점수에만 쓴다. 약관상 학습 데이터로 쓰지 않는다
  • 9B 는 루나에 크게 못 미쳤고, 27B 는 공개 세트에서 루나와 구간이 겹쳤다. 이 차이가 이후 세트 설계를 바꿨다(6절)
  • 공개된 쿠버네티스 LoRA 둘은 원본보다 낮았다(Qwen3-Coder-30B 67% → 44%, Gemma 3 12B 44% → 0%, k8s-ai-bench 1회)

샘플링 규칙. agent 는 temperature 를 보내지 않으므로 vLLM 서버 기본값이 곧 실험 조건이다. HF 저장소에 generation_config.json 이 없는 모델은 vLLM 중립 기본값(temperature 1.0)으로 돈다. 9B 가 그랬고, 판정 세트 점수가 18% 와 48% 로 갈렸다. 그 뒤로 설정 파일이 없는 모델은 카드 권장값을 --override-generation-config 로 꼭 적고, 결과의 meta.sampling 에 남긴다.

세트는 측정이 지름길이나 천장을 드러낼 때마다 역할을 바꿨다.

  • 판정 세트 격하: 처음에는 합격 판정용이었다. 첫 열람(루나)과 둘째 열람(9B, 문제별 오답 분류까지 봄)이 생성기 규칙 v1 을 얼린 것보다 먼저였다. 열람한 사람이 규칙을 만든 셈이라 합격 판정에 쓸 수 없다. “크게 무너지지 않았는지” 확인과 최종 거부권으로 내렸다
  • 공개 원본 → decoy-v1: LLM 없이 “가장 최근 오브젝트가 원인"이라고 찍는 기준선 recent 가 공개 원본에서 67.7% 를 맞혔다. 찍기로 20% 넘게 맞히는 세트는 주 지표가 될 수 없다. 원본 뒤에 멀쩡한 미끼를 2~3개 더 만든 decoy-v1 에서 recent 는 0/33 이다(DURO-285)
  • decoy-v1 → 지킴: 27B 는 학습 전에 decoy-v1 에서 이미 93.3% 였다. 오를 자리가 없어 개선은 잴 수 없고, 나빠지지 않았는지만 본다
  • ITBench → 따로 보고: 외부 시험으로 쓴 ITBench 14문제에서 27B 학습 전 점수는 54.8% 였다. decoy-v1 과의 차이가 커서, 생성기 쪽 점수가 외부로 옮겨 가지 않는다는 것이 보였다. 그 실패에서 약점 셋(W1 컨텍스트 초과, W2 증상과 원인 오브젝트가 다름, W3 분류 실수)을 골랐다. 약점을 고르는 데 쓴 문제라 개선 주장에는 쓰지 않는다
  • A: 아직 어떤 모델 점수도 보지 않은 새 외부 문제다. 옮기는 원칙은 7.1절, 얼린 순서는 8.1절에 있다
  • 얼림 뒤 공개 이슈: 작성자가 고르지 않은 세트를 만들려고 규칙 얼림 뒤 올라온 공개 이슈(GitHub 12개 레포, k8s.af)를 정한 검색어로 모았다. 후보 1건이 재현에서 탈락해 0문제다(DURO-282)

7. Contamination — 오염 경로와 차단#

7.1 네 가지 경로#

초록은 막은 경로, 빨간 점선은 막지 못한 경로다
  • ①~③은 경로를 끊었다. ④는 사람의 기억이라 끊을 수 없다. 생성기 규칙마다 출처(문서 URL, k8s.af 글, 본 14문제 번호)를 적어 줄였을 뿐이다
  • 그래서 A 의 결과에는 “본 적 있을 수 있는 종류"라는 한계를 꼭 붙인다
  • A 의 정답은 원 벤치마크의 정답을 쓰고, 우리 분류로는 문제를 보기 전에 만든 고장 종류 단위 대응표(MAPPING.md)로만 바꾼다. 원 정답에 오브젝트 종류가 없으면 주입 코드가 바꾸는 오브젝트의 종류를 쓰고, 해석이 필요하면 넣지 않는다

7.2 공개 세트 변형 검사#

공개 세트는 인터넷에 있으니 원본 모델이 문제를 외웠을 수 있다. 이름·문장·질문만 바꾼 변형 35개를 만들어 원본과 비교했다(DURO-275).

모델원본변형차이 [95% 구간]
Qwen3.8-27B86.9%90.9%+4.0%p [−2.0, +11.1]
Qwen3.5-9B51.5%65.7%+14.1%p [+2.0, +26.3]

외웠다면 변형에서 떨어져야 한다. 두 모델 모두 떨어지지 않아 암기 걱정은 낮게 봤다. 그래도 공개 세트는 개발용으로만 두고, 판정은 비공개나 새 외부 문제로 한다는 원칙은 그대로 뒀다.

7.3 생성기 흔적#

생성기는 난이도 미끼(멀쩡한 이웃 Deployment 등)를 고장보다 먼저 만들었다. 그러면 “가장 최근에 바뀐 오브젝트"가 늘 원인이 된다. 학습한 모델이 진단 대신 이 흔적을 배울 수 있다.

  • 같은 이름·같은 고장으로 옛 순서와 새 순서 짝을 만들었다(사전 등록 §5). 새 순서는 미끼를 고장 뒤에 만들고 rollout restart 하며, field manager 와 어노테이션도 미끼와 맞춘다
  • 새 순서가 실제로 다른 문제는 hard 41개다. easy 는 미끼가 없어 대조군이다
왼쪽은 흔적의 크기, 오른쪽은 모델이 그 흔적을 쓰는 정도다
  • 흔적은 실제로 있다. recent 가 옛 순서에서 60%, 새 순서에서 0% 다
  • 학습 전 모델은 그 흔적에 기대지 않았다. 지름길 크기 구간이 두 모델 모두 0을 지난다
  • 그래서 학습 뒤 지름길 크기가 학습 전보다 커지면 흔적을 배운 것으로 적는다. 2회차 학습 기록은 옛 순서 기록을 모두 거른다

8. Pre-registration — 사전 등록#

8.1 얼림#

결과를 본 뒤 기준을 고르면 원하는 결론이 나온다. 그래서 무엇을 재고 무엇을 보고 채택할지를 결과 전에 얼렸다(DURO-280, 얼림 커밋 3132719).

  • eval/FROZEN.md 에 얼린 파일과 sha256 을 적고, datagen/tests/test_prereg_frozen.py 가 해시와 파일을 대 본다
  • 얼린 파일은 고치지 않는다. 바꿀 일이 생기면 새 부록을 만들고 표에 줄을 더한다. 지금 부록 1~4 와 정정 1 이 있다
  • 얼림 커밋이 측정보다 먼저인 이력을 남기려고, 이 PR 들은 squash 대신 merge commit 으로 합쳤다
  • 2회차는 두 번에 나눠 얼렸다. 얼림 1 은 A 를 옮기기 전(판정·지킴·멈춤·칸 정의, 생성기 규칙 v2), 얼림 2 는 수집 전(학습 문제 784개, D 20문제, 씨앗)이다

8.2 판정 규칙#

지킴을 통과한 뒤 1번부터 차례로 대 본다. 지킴 2(자신 있게 틀림)는 점 추정끼리 비교라 그림에 없다
  • 비교는 학습 전 27B 와 2회차 27B 두 모델뿐이다. 측정은 한 번 하고, 결과를 보고 세트·반복·기준을 바꾸지 않는다
  • 주장은 “A 에서 학습 전보다 좋아졌다” 하나만 걸었다. 하한 > −5%p 는 개선이 아니라 “나빠지지 않음"이다
  • 지킴 C 의 −7%p 는 1회차 같은 세트의 구간 반폭(약 4.5%p)만큼 −5%p 에서 넓힌 값이다. −5%p 로 두면 실제 차이가 0 이어도 약 40% 확률로 떨어진다. 결과 문서에 점 추정을 함께 적는다
  • 지킴 2 는 “자신 있게 틀림 증가 ≤ 맞음 증가"다. “틀림 ≤ 0"으로 두면 HTTP 400 으로 끝나던 “판단 못 함"이 맞음과 틀림으로 함께 옮겨 가는 겨냥한 성공까지 벌한다
  • 칸은 하나만 둔다. 겨냥 유형 / 나머지다. 겨냥 유형만 오르면 “겨냥 유형만”, D 가 오르지 않으면 “본 종류만"이라는 해석 표시를 판정과 별개로 붙인다

9B 때의 판정 규칙(사전 등록 §8)은 더 엄격했다. 채택은 하한 > 0 이면서 점 차이가 최소 검출 차이(8.5절) 이상이어야 했고, 탈락은 상한 < 0, 그 밖은 판단 보류였다.

8.3 멈춤 조건#

멈춤 조건은 비용과 시간을 지키는 장치이고 판정에는 쓰지 않는다(부록 3 §6).

  • A 가 20문제 미만이거나 군집이 15개 미만이면 수집 전에 멈추고 묻는다. 그 크기로는 “구분 못 함"이 될 가능성이 높다
  • 새 기록이 400개 미만이거나, 큰 앱 기록·1~2단계 기록이 칸마다 150개 미만이면 학습하지 않는다
  • 학습 중 1에폭 체크포인트로 D 일부를 재서 학습 전보다 5%p 넘게 떨어지면 멈춘다
  • 누적 비용이 예산 상한 $600 을 넘을 것 같으면 다음 단계를 시작하지 않는다
  • 지킴 실패면 채택하지 않고 데이터도 키우지 않는다. A 하한 > 0 이어도 데이터 2배 키우기는 사용자가 정한다

8.4 어긴 것의 기록#

얼린 계획을 어긴 일은 숨기지 않고 결과 문서와 부록에 적었다.

어긴 것처리
얼린 execfix.py 를 탈출 시험 작업(DURO-269)이 직접 고침얼린 원본을 eval/frozen/execfix.py.20261116 에 바이트 그대로 보관하고 해시를 그 사본으로 옮김
부록 2·4 는 앞 결과를 본 뒤에 씀부록 첫머리에 그 사실을 스스로 적음
부록 3 자체가 ITBench 결과를 보고 쓴 것그 14문제를 주장에서 빼고 새 외부 문제 A 를 주 시험으로 둠
A 시범에서 PodSecurity 가 원 고장보다 먼저 거부해 원 증상을 잃음A 모델 점수를 보기 전, oracle 시범만 보고 정정 1 을 얼림(A 만 privileged, PSA 가 곧 고장인 2문제는 restricted)
얼림 2 설명의 “모든 문제가 새 순서"가 틀림(80문제가 옛 순서)틀린 문장을 정정으로 남김
멈춤 조건 6(1에폭 점검 9문제)에 걸린 학습을 이어 감더 크게 다시 재고 사용자 결정으로 넘김. 판정 규칙은 그대로 두고 넘긴 사실을 판정과 함께 적음(Serving.09)

8.5 잡음 바닥#

문제 부트스트랩 구간은 “어떤 문제를 골랐나"의 흔들림만 센다. 같은 모델을 다시 돌렸을 때의 흔들림은 따로 재야 한다.

  • 학습 전 9B 를 공개 원본에서 4회차 쟀다: 64.1%, 51.5%, 54.5%, 61.6%. 회차 사이 표준편차 s = 5.9%p 다
  • 최소 검출 차이(양쪽 5%, 검정력 80%) = 2.80 · s · √(1/kₐ + 1/k_b) 이다. 1회 대 1회면 23.4%p, 4회 대 3회면 12.6%p 다
  • 최소 검출 차이가 5%p 보다 크면 “하한 < −5%p 면 탈락” 같은 기준은 장식이 된다. 사전 등록에 그 문장을 미리 적었다
  • 27B 의 잡음 바닥은 재지 않았다(11절)

9. Statistics — 구간과 문제 수#

점 하나가 문제 하나, 칸이 함께 뽑히는 묶음이다

흔들림은 두 가지로 나눈다. 모델 무작위성은 반복으로 줄이고, 문제 선택에서 오는 흔들림은 문제를 다시 뽑는 부트스트랩으로 구간을 낸다. 반복을 늘려도 문제 선택의 흔들림은 줄지 않는다.

  • 같은 고장 종류의 변형(예: targetPort 3변형)은 독립이 아니다. A 는 (출처, 원 고장 종류)를 군집으로 묶어 함께 뽑는다
  • 0건 지표(예: 위험 명령 0번)는 구간이 한 점으로 무너지므로 Clopper-Pearson 과 rule of three(3/n)로 상한을 적는다
  • 계산은 표준 라이브러리만 쓰고 씨앗을 고정한다(stats.py, prereg.py). 같은 입력이면 같은 구간이 나온다

세트 크기가 가릴 수 있는 차이를 정한다. 공개 33문제는 ±15%p, 판정 12문제는 ±25%p, 지름길 41문제는 ±15%p 쯤이다. 짝지은 차이에서 하한 > 0 을 80% 확률로 얻는 데 필요한 문제 수는 N = (2.8 · sd / 효과)² 다(sd = 문제별 차이의 표준편차).

sd \ 실제 효과+10%p+15%p+20%p
0.2032148
0.25492213
0.35974325

20~30문제면 sd ≤ 0.29 일 때만 +15%p 를 가린다. +10%p 는 가리지 못한다. 군집이 문제보다 적으니 실제로 가릴 수 있는 크기는 이 표보다 크다. 이 한계는 A 의 목표(20문제, 군집 15개 이상)와 멈춤 조건 1 의 근거다.

11. Limits — 남은 한계#

  • 설계자 머릿속(④): 막지 못했다. A 결과는 “본 적 있을 수 있는 종류"라는 한계와 함께만 쓴다
  • D 의 공개: 2회차 모델과 학습 데이터를 Hugging Face 에 올렸으므로 D 는 이제 모르는 시험이 아니다. 다음 회차에는 새 보류 종류가 필요하다
  • 순서 효과: 판정 세트를 규칙 얼림 전에 열었고, 부록 2·3·4 는 앞 결과를 본 뒤에 썼다. 기록으로 남겼을 뿐 되돌릴 수 없다
  • 문제 수: A 44문제·30군집으로는 +10%p 를 가리지 못한다. 판정 세트 12문제는 ±25%p 라 확인용으로만 쓴다
  • 27B 잡음 바닥: 재지 않았다. 지킴 C 의 −7%p 는 1회차 구간 반폭으로 정한 값이고, 회차 사이 흔들림은 들어 있지 않다
  • 채점기 관례: 사람이 다시 읽는 확인도 같은 사람이 하면 채점기와 같은 관례가 들어간다

이 설계로 낸 2회차 판정은 Serving.09 에서 다룬다.
