1. Overview#

05-1이 바뀌는 Pod 앞의 접점을 봤다면, 05-2는 그 접점으로 들어오는 바깥 길과 L7 분기를 본다.

05-1에서 이어지는 것

  • 05-1은 API 객체를 요청서로, 컨트롤러를 처리 주체로, 노드의 커널 규칙을 실제 전달 경로로 나눴다. Service가 있다는 사실과 앱까지 닿는다는 사실은 달랐다
  • 이번에는 바깥에서 시작한다 — 외부 주소를 누가 주고, 그 주소로 온 패킷이 어느 노드에 도착하며, HTTP 요청은 누가 읽어 나누는가
  • LoadBalancer는 바깥 문, Ingress와 Gateway API는 그 문 뒤의 L7 분기 규칙이다. 함께 쓸 수 있고, 어느 하나를 적었다고 나머지가 자동으로 설치되지는 않는다

이번 글의 범위

  • 원서 5장의 LoadBalancer·Ingress와 개정 원고의 Gateway API를 한 흐름으로 묶는다. 내부 서비스 사이의 mTLS·관측과 Linkerd는 다음 글에서 다룬다
  • 그림의 주소·노드 배치는 설명용이다. 아래 YAML과 명령은 개념 확인 및 조건부 실습용이며, 이 글을 작성하면서 실제 클러스터에서 실행한 결과는 아니다
  • 2026년 11월 5일 공식 문서 확인 기준이다. 특정 구현의 설치 옵션은 사용하는 버전의 문서와 맞춘다

2. LoadBalancer — 외부 주소와 전달은 다른 일#

2.1 주소를 주는 쪽과 패킷을 나르는 쪽#

  • type: LoadBalancer는 바깥 접속점을 요청한다 — 공급자 컨트롤러가 외부 주소·장치를 준비하고, 결과를 status.loadBalancer.ingress에 보고한다. 주소는 IP일 수도, 호스트명일 수도 있다
  • EXTERNAL-IP <pending>은 그 결과가 아직 없다는 뜻이다 — 컨트롤러 부재, 클래스 불일치, 주소 풀 고갈, 공급자 오류를 이벤트와 로그로 가른다. 이것만으로 안쪽 ClusterIP의 고장을 뜻하지는 않는다
  • 주소가 생긴 다음에도 그 주소로 패킷이 들어올 길과 백엔드로 보낼 구현이 필요하다. 인터넷용 LB인지 사설망용 LB인지도 공급자의 구성에 달려 있다

이 경계를 가장 잘 보여 주는 것이 MetalLB다. 새 LB 장비를 사 오는 대신, 외부 IP를 배정하고 기존 노드로 도착하게 만든다. 다음 절에서는 그 두 일을 나눠 본다.

2.2 NodePort는 기본 할당이지 필수 경유지가 아니다#

설명구분해서 읽을 것
LoadBalancer는 보통 NodePort도 할당한다API의 기본 할당 동작
외부 LB가 노드의 NodePort로 보낸다여러 구현 중 하나의 데이터 경로
LB가 Pod로 직접 보낸다이를 지원하는 구현의 다른 경로
ClusterIP가 함께 있다모든 패킷이 그 IP를 중간 장비처럼 통과한다는 뜻은 아니다
  • allocateLoadBalancerNodePorts: false는 NodePort 없이 전달할 수 있는 구현에서만 선택한다. 기존 Service에서 false로 바꿔도 이미 배정된 nodePort는 자동 회수되지 않는다
  • 05-1 5.1의 “타입이 쌓인다”는 설명은 기본 접속점 구성으로 읽는다. 실제 패킷 경로를 LB → NodePort → ClusterIP → Pod 한 줄로 고정하지 않는다

2.3 필드와 책임의 경계#

필드의미확인할 점
loadBalancerClass처리할 LB 구현 선택이름에 맞는 구현이 있는가. 설정 후 변경할 수 없다
externalTrafficPolicy외부 트래픽의 endpoint 후보 정책Local의 제약은 05-1 6.2와 같다
loadBalancerIP과거의 고정 IP 요청 필드v1.24부터 deprecated. 구현별 주소 요청 기능을 확인한다
status.loadBalancer.ingress컨트롤러가 보고한 주소주소 할당과 실제 도달성을 따로 본다

프로토콜 지원도 구현의 계약이다. Service YAML에 포트를 적는 것만으로 공급자의 TCP·UDP 지원 제한이 사라지지 않는다. Pod 수를 늘리는 HPA 역시 별도 컨트롤러다 — 문을 열고 연결을 나누는 것과 방을 더 만드는 것은 다른 일이다.

3. MetalLB — 주소 배정과 광고를 나누기#

3.1 Controller와 Speaker#

EXTERNAL-IP가 채워졌다는 증거와 그 IP로 패킷이 도착한다는 증거는 따로 확인한다.
구성요소맡는 일하지 않는 일
controller주소 풀에서 IP 배정, Service status 갱신HTTP 경로 분기
speakerL2의 ARP/NDP 또는 BGP로 도달 경로 알림사용자 공간에서 모든 요청 중계
Service 데이터패스노드에 온 트래픽을 endpoint로 전달외부 주소 풀 관리

한 문장으로 나누면 이렇다 — controller가 주소를 고르고, speaker가 어디로 보내면 되는지 알리고, 노드의 데이터패스가 앱까지 보낸다. 외부 IP가 인터페이스에 보이지 않는다는 이유만으로 광고 실패를 단정하지 않는다. L2 광고는 그 IP에 대한 ARP/NDP 응답으로 동작한다.

3.2 L2와 BGP#

구분L2 모드BGP 모드
바깥에 알리는 것이 IP로 갈 MAC 주소이 IP로 가는 라우트
상대같은 L2의 이웃피어링한 라우터
유입Service IP 하나에 광고 노드 하나라우터·ECMP 구성에 따라 여러 노드
병목·장애한 노드의 대역폭, 이웃 캐시 갱신라우터의 경로·다중 경로 동작
필요한 지식LAN, ARP/NDP, 주소 충돌ASN, 피어링, 경로 정책
  • L2에서 “백엔드 Pod가 셋”과 “진입 노드가 셋”은 같은 말이 아니다. 한 진입 노드에 도착한 뒤 여러 Pod로 전달될 수 있다
  • 노드가 바뀔 때는 이웃의 MAC 캐시도 바뀌어야 한다. 그래서 광고 노드 장애 뒤의 복구 시간과 기존 연결의 지속성을 별개로 본다
  • BGP라고 언제나 모든 노드로 똑같이 나뉘는 것도 아니다. 실제 분산은 라우터와 트래픽 정책에 달려 있다

3.3 주소 풀과 광고 리소스#

IPAddressPool은 배정 가능한 주소, L2Advertisement는 그 주소의 L2 광고 설정이다. 장부에 주소를 적는 것과 이웃에게 알리는 것을 서로 다른 리소스로 관리한다.

# 14-metallb-pool.yaml — 구조 설명용
# ★ 자신의 L2 대역·DHCP 풀·사용 중인 주소를 확인하기 전에는 적용하지 않는다
apiVersion: metallb.io/v1beta1
kind: IPAddressPool
metadata:
  name: lab-pool
  namespace: metallb-system
spec:
  addresses:
    - 192.168.1.240-192.168.1.250
---
apiVersion: metallb.io/v1beta1
kind: L2Advertisement
metadata:
  name: lab-advertisement
  namespace: metallb-system
spec:
  ipAddressPools:
    - lab-pool

여기서 두 가지 함정.

  • 풀을 만들고 광고 설정을 빠뜨리면 IP가 생겨도 외부 요청이 못 올 수 있다. 다른 Advertisement가 이미 같은 풀을 광고하는지도 함께 본다
  • 원서의 ConfigMap 안 address-pools는 지금 설정 형식이 아니다. 오래된 PodSecurityPolicy 설치 예시도 복사하지 않는다. 설치는 현재 MetalLB Installation의 버전 고정 지침을 따른다

Cilium을 쓴다면 MetalLB가 필수는 아니다. 다만 LB IPAM의 주소 배정, L2/BGP의 광고, Service 데이터패스는 여전히 다른 기능이다. 한 Service를 두 LB 구현이 동시에 관리하게 두지 않고 클래스·선택 범위를 구분한다.

4.2 주소를 고르는 순서#

kind get clusters
docker network inspect kind
kubectl -n metallb-system get ipaddresspools,l2advertisements -o yaml
  • docker network inspect kind에서 Subnet·Gateway와 컨테이너 주소를 읽는다. 출력에 안 나온다고 미사용 주소가 보장되는 것은 아니다 — 기존 풀과 다른 사용자·클러스터의 사용 범위도 확인한다

4.3 LoadBalancer Service 만들기#

# 13-loadbalancer.yaml
apiVersion: v1
kind: Service
metadata:
  name: web-lb
  namespace: netlab

  type: LoadBalancer

kubectl apply -f 13-loadbalancer.yaml

확인하는 증거는 셋이다 — status에 주소가 생겼는가, 이벤트에 할당·광고 문제가 없는가, ready endpoint가 있는가. 어느 하나도 나머지를 대신하지 않는다.

4.4 요청 출발지를 고정해서 시험하기#

kind 내부의 성공과 호스트의 성공을 나눠 기록한다 — 고정된 172.18.x.x 대역을 모든 PC에 복사하지 않는다.

아래는 Docker의 kind 네트워크 안에서 보내는 요청이다. 호스트의 브라우저에서 시험한 결과와 구분한다.

LB_IP=$(kubectl -n netlab get svc web-lb -o jsonpath='{.status.loadBalancer.ingress[0].ip}')
# IP가 비어 있으면 여기서 멈추고 Service 이벤트·controller 로그를 본다
if [ -n "$LB_IP" ]; then
  docker run --rm --network kind busybox:1.36 \
    wget -T 5 -qO- "http://${LB_IP}/"
fi
  • nginx HTML이 나오면 그 출발지에서 앱까지 도달한 것이다. 같은 환영 페이지가 열 번 나왔다고 Pod 셋에 균등 분배됐다는 뜻은 아니다 — 응답한 Pod는 로그·식별 응답으로 확인한다
  • kubectl port-forward는 API server·kubelet을 거치는 다른 경로다. 앱 확인에는 쓸 수 있지만 ARP 광고나 외부 LB를 검증한 것으로 세지 않는다
  • 실패하면 <pending>부터 볼지, ARP·라우팅부터 볼지 가른다. 이미 IP가 배정됐다면 할당 설정을 계속 고치기보다 광고와 요청 출발지를 먼저 본다

5. Ingress — HTTP 요청을 읽는 자리#

5.1 객체와 Controller와 Proxy#

컨트롤러와 프록시는 한 Pod에 함께 있을 수도, 서로 다른 위치에 있을 수도 있다 — 역할을 구분해 그린다.

Ingress에는 세 이름이 있다 — 규칙 객체 Ingress, 그 규칙을 맡을 구현을 가리키는 IngressClass, 실제 프록시를 설정하는 Controller. 바깥에서 프록시까지 가는 노출 방법은 또 따로다.

컨트롤러가 클라우드 LB를 설정하는 구현도 있고, 클러스터 안 프록시를 관리하는 구현도 있다. 따라서 그림의 프록시 위치는 구조를 설명하는 예다. “Ingress Controller Pod가 반드시 모든 요청을 직접 받는다”로 일반화하지 않는다.

5.2 Host와 Path와 Default Backend#

# 15-ingress.yaml — 구조 설명용
# ★ class 이름과 api-web Service가 준비되어야 동작한다
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web-ingress
  namespace: netlab
spec:
  ingressClassName: installed-ingress-class
  defaultBackend:
    service:
      name: web
      port:
        number: 80
  rules:
    - host: web.example.com
      http:
        paths:
          - path: /api
            pathType: Prefix
            backend:
              service:
                name: api-web
                port:
                  number: 80
          - path: /
            pathType: Prefix
            backend:
              service:
                name: web
                port:
                  number: 80
요청 경로/api Exact/api Prefix
/api일치일치
/api/불일치일치
/api/v1불일치일치
/apix불일치불일치
  • Prefix는 /로 나눈 경로 요소 단위다. 더 긴 일치 경로가 우선하고, 동률이면 Exact가 Prefix보다 우선한다. ImplementationSpecific은 구현 문서를 따로 읽는다
  • web.example.com/api는 api-web, 같은 호스트의 /apix는 / 규칙으로 web을 고른다. defaultBackend는 규칙에 일치하지 않은 요청의 처리 대상이다
  • /api가 일치한다고 그 문자열을 지우지는 않는다. 경로 선택과 rewrite는 다른 설정이다 — 백엔드가 /api를 모르면 올바른 대상으로 갔어도 404가 날 수 있다

이 YAML은 분기 구조를 읽는 예제다. 4절의 nginx만 배포한 상태에는 api-web이 없다. 두 백엔드를 실제로 만들고, 현재 지원되는 컨트롤러와 클래스·외부 주소를 준비한 뒤 시험한다.

kubectl get ingressclass -o wide
kubectl -n netlab get ingress
kubectl -n netlab describe ingress web-ingress
# 실제 진입점 IP를 넣고, 요청할 호스트를 맞춘다
# curl -H 'Host: web.example.com' http://<INGRESS_IP>/api

5.3 인증서 이름과 Host는 연결 주소와 다르다#

curl http://<IP>/는 IP로 연결하면서 Host도 IP로 보낸다. web.example.com 규칙을 시험하려면 Host를 맞춰야 한다. DNS에 레코드가 없다면 HTTP는 -H 'Host: …', HTTPS는 아래 --resolve 방식으로 이름과 연결 주소를 나눌 수 있다.

Ingress를 만든다고 공개 DNS 레코드가 생기지는 않는다. DNS 제공자에 직접 설정하거나 ExternalDNS 같은 별도 구현이 필요하다. 이름이 풀려도 프록시가 그 Host를 처리하는지는 다시 확인한다.

6. TLS — 종료 지점 뒤의 연결은 별개#

6.1 Secret과 TLS 종료#

TLS Secret을 만들었다고 발급·갱신까지 자동화되지는 않는다 — 인증서 수명은 별도 관리 대상이다.
# 15-ingress.yaml의 spec에 추가하는 조각 — 단독 적용 파일이 아니다
spec:
  tls:
    - hosts:
        - web.example.com
      secretName: web-example-tls
  • 일반적인 Ingress TLS 설정은 같은 namespace의 kubernetes.io/tls Secret을 참조한다. tls.crt와 tls.key에는 해당 이름의 인증서와 개인 키를 넣는다
  • Secret을 생성하는 것과 인증서 발급·갱신은 다르다. 만료 전에 갱신하고 프록시까지 반영되는 경로를 운영한다
  • 표준 Ingress의 TLS 종료만으로 프록시→앱까지 암호화되지는 않는다. 백엔드 HTTPS는 구현별 별도 설정을 본다. Gateway API에서도 프런트 TLS와 백엔드 TLS 정책은 나뉜다

6.2 HTTPS를 IP만 바꿔 시험하면 생기는 일#

# 준비한 실제 인증서·키를 사용한다
# kubectl -n netlab create secret tls web-example-tls \
#   --cert=fullchain.pem --key=privkey.pem

# INGRESS_IP에는 실제 진입점 IP를 넣는다
# curl --resolve "web.example.com:443:${INGRESS_IP}" \
#   https://web.example.com/
# 사설 CA라면: --cacert lab-ca.pem 옵션을 함께 쓴다
  • --resolve는 연결할 IP를 지정하면서 URL의 이름을 유지한다. 따라서 TLS SNI·인증서 이름 검사·HTTP Host를 같은 이름으로 시험할 수 있다
  • https://<IP>/에 Host 헤더만 바꾸는 방법은 TLS 이름 문제를 해결하지 못한다. HTTP 헤더를 보내기 전에 TLS 핸드셰이크가 먼저다
  • 인증서 검증을 끄고 통과한 결과로 정상 TLS를 확인했다고 쓰지 않는다. 어느 구간을 무엇으로 검증했는지 적는다

  • 호스트·경로·TLS 요구사항은 옮길 수 있지만 annotation·snippet·rewrite·인증 연동이 자동 변환된다고 기대하지 않는다
  • 새 컨트롤러의 기본 타임아웃, 전달 헤더 신뢰, 요청 크기 제한도 비교한다. 리소스 문법만 바꾸면 같아지는 것은 아니다
  • Gateway API는 이런 기능을 역할별 리소스로 표현할 수 있는 틀이다. 특정 제품의 모든 확장을 표준이 대신 지원한다는 약속은 아니다

8. Gateway API — 진입점과 라우팅의 소유권#

8.1 세 객체는 세 장비가 아니다#

GatewayClass → Gateway → HTTPRoute는 패킷이 차례로 통과하는 세 장비가 아니다.
리소스적는 내용주된 소유자
GatewayClass컨트롤러 구현과 공통 구성플랫폼 관리자
Gateway리스너·TLS·주소·Route 연결 범위인프라 팀
HTTPRoute호스트·경로·헤더와 백엔드앱 팀

운영자가 공동 현관의 포트와 인증서를 관리하고, 앱 팀은 자기 길 안내를 적는다. 이 구분은 리소스를 더 만드는 수고를 들여 변경 권한을 나누는 설계다. 실제 권한 경계는 RBAC와 namespace 정책도 함께 구성해야 한다.

CRD가 없으면 API server는 Gateway 종류 자체를 모른다. CRD만 있으면 객체 저장까지 가능하고, 컨트롤러가 있어야 구현이 따라온다. 이 점은 05-1 2.1의 요청서와 같다.

8.2 Gateway와 HTTPRoute 읽기#

아래는 edge-class라는 준비된 GatewayClass가 있다는 전제의 예제다. 그 이름은 표준 예약값이 아니다. 설치된 클래스와 필요한 기능을 확인하고 바꾼다.

# 17-gateway.yaml — 구현체·외부 노출이 준비된 클러스터에서 사용
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: lab-gateway
  namespace: netlab
spec:
  gatewayClassName: edge-class
  listeners:
    - name: http
      protocol: HTTP
      port: 80
      allowedRoutes:
        namespaces:
          from: Same
---
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: web-route
  namespace: netlab
spec:
  parentRefs:
    - name: lab-gateway
      sectionName: http
  hostnames:
    - web.example.com
  rules:
    - matches:
        - path:
            type: PathPrefix
            value: /
      backendRefs:
        - name: web
          port: 80
  • parentRefs는 붙을 Gateway, sectionName은 그 Gateway의 리스너 이름이다. allowedRoutes: Same은 같은 namespace의 Route만 받는다
  • backendRefs.port: 80은 Service의 port다 — Pod가 실제로 듣는 targetPort를 여기 적는 것이 아니다
  • Route가 백엔드를 찾는 것과 DNS가 Gateway 주소를 찾는 것은 별개다. 이 YAML에는 공개 DNS나 인증서 발급 설정이 없다
kubectl api-resources --api-group=gateway.networking.k8s.io
kubectl get gatewayclass -o yaml
# CRD·컨트롤러·클래스·노출 방법을 준비하고 class 이름을 바꾼 뒤
# kubectl apply -f 17-gateway.yaml
kubectl -n netlab get gateway,httproute
kubectl -n netlab get gateway lab-gateway -o yaml
kubectl -n netlab get httproute web-route -o yaml

8.3 Accepted와 ResolvedRefs와 Programmed#

관찰 대상확인할 상태말해 주는 것
GatewayClassAccepted구현체가 이 클래스를 수락했는가
Gateway·listenerAccepted, Programmed 등구성이 수락되고 데이터패스에 반영됐는가
HTTPRoute의 각 status.parentsAccepted, ResolvedRefs그 parent에 연결됐는가, 참조가 유효한가
최종 요청HTTP 응답·로그해당 출발지에서 앱까지 동작하는가
  • status는 객체마다, Route에서는 parent마다 읽는다. observedGeneration도 현재 metadata.generation과 맞춰 오래된 결과를 피한다
  • Accepted: False면 연결 제약과 parent·listener를, ResolvedRefs: False면 Service·포트·참조 권한을 우선 살핀다. 정확한 reason과 message가 다음 단서다
  • Programmed: True도 최종 앱의 준비 상태나 외부 DNS를 보장하지 않는다. 외부 주소와 EndpointSlice, 실제 요청이 남는다
# IP 주소를 보고하는 Gateway의 예 — hostname을 보고하면 해당 주소 방식에 맞춘다
GATEWAY_IP=$(kubectl -n netlab get gateway lab-gateway \
  -o jsonpath='{.status.addresses[?(@.type=="IPAddress")].value}')
# 위 결과가 하나의 도달 가능한 IP인 것을 확인한 뒤
# curl -H 'Host: web.example.com' "http://${GATEWAY_IP}/"

8.4 Namespace 경계를 넘는 두 허가#

5-1의 selector가 같은 namespace의 Pod를 고르는 규칙이었다면, 여기서는 namespace를 넘는 참조 권한을 따진다.
  • 다른 namespace의 Gateway에 Route를 붙이는 것은 Gateway의 allowedRoutes가 제어한다. 앱 쪽 parentRefs.namespace만 적는다고 인프라 팀의 문이 열리지 않는다
  • Route가 다른 namespace의 Service를 백엔드로 참조하려면, 그 Service가 있는 namespace에 이를 허용하는 ReferenceGrant가 필요하다
  • 참조 권한은 통신 정책을 대신하지 않는다. Route가 수락돼도 NetworkPolicy·데이터패스·앱 설정 때문에 요청은 실패할 수 있다

위 8.2 예제는 전부 netlab 안이다. 같은 namespace 구성부터 확인하고 경계를 넓혀야 어느 권한에서 막혔는지 보인다.

8.5 기존 Cilium 실습과의 차이#

여기서 앞 장의 환경을 그대로 복사하면 막힌다.

  • 05-1의 cn4는 Cilium을 CNI로 쓰고 Service는 kube-proxy iptables가 나른다. Cilium을 설치했다는 사실만으로 Gateway API가 활성화된 것이 아니다
  • 확인한 Cilium Gateway 공식 문서는 kubeProxyReplacement=true, L7 proxy, 호환 Gateway API CRD와 Gateway 기능 활성화를 요구한다. 기본 노출은 LoadBalancer이며 host network 선택지도 있다
  • 따라서 이 글의 Gateway 예제는 기존 cn4에 바로 적용하는 연속 실습이 아니다. 해당 요건을 갖춘 별도 실습 클러스터나 다른 준비된 Gateway 구현에서 확인한다. 기존 Cilium 설정을 한 줄 Helm 명령으로 덮어쓰지 않는다
  • 같은 HTTPRoute도 구현별 지원 filter·정책이 다르다. Gateway API 버전·채널과 Controller의 conformance·지원 목록을 함께 확인한다

외부 L7 진입점이 완성돼도 내부 서비스 간 mTLS·관측이 자동으로 생기지는 않는다. 다음 글의 Service Mesh는 그 내부 통신을 다룬다.

9. Discussion#

9.1 어느 단계의 증거인가#

05-1의 선언·컨트롤러·데이터패스·앱 진단에 외부 주소와 L7 라우팅의 증거를 더한다.
증상먼저 가를 것볼 증거
외부 IP가 <pending>주소 할당Service 이벤트, 풀, 클래스, LB 컨트롤러 로그
IP는 있는데 연결 timeout광고·라우팅·방화벽 또는 이후 경로출발지, ARP/route, 진입 노드 관측, endpoint
IP 직접 요청은 응답하지만 호스트 규칙 실패이름·Host·SNIDNS, --resolve, 프록시 access log
/api만 404일치 규칙 또는 앱 경로Host·path, rewrite 여부, 응답 주체의 로그
프록시가 503을 반환구현에 따라 백엔드 선택·연결 실패 등Route status, Slice ready, upstream 로그
TLS 인증서 이름 불일치클라이언트가 사용한 이름과 인증서URL·SNI, SAN, 선택된 Secret
Route가 저장됐지만 연결되지 않음제어 영역의 수락·참조parent별 conditions, generation, 클래스

HTTP 상태 코드 하나를 장애 위치와 일대일로 묶지 않는다. 404는 프록시의 기본 응답일 수도 앱의 응답일 수도 있다. status·로그·직접 연결을 함께 봐야 어느 층에서 나왔는지 알 수 있다.

핵심 메시지#

주소는 도착의 증거가 아니다
status의 외부 IP, ARP·라우팅, ready endpoint, 앱 응답은 각각 따로 확인한다.
배정과 광고를 나눈다

L7 규칙은 프록시가 읽는다
Ingress와 HTTPRoute는 API 객체다. Host·Path를 해석하고 백엔드에 연결하는 구현이 따로 필요하다.
TLS의 범위를 그린다
클라이언트와 프록시, 프록시와 앱은 다른 연결이다. 인증서와 갱신도 따로 관리한다.
참조에는 상대의 허가가 필요하다
Gateway 연결은 allowedRoutes, 다른 namespace의 백엔드 참조는 ReferenceGrant로 구분한다.
지원 상태도 구현의 일부다
API의 안정성과 프로젝트의 수명은 다르다. 저장된 객체뿐 아니라 현재 구현의 전제와 status를 읽는다.
