1. Overview#

클러스터를 만들기 전에 VPC 의 서브넷, 경로, 주소 범위가 Pod 수와 트래픽 경로를 먼저 정한다.

05-2에서 이어지는 것

  • 05-2는 type: LoadBalancer의 외부 주소를 누가 주고, 그 주소로 온 패킷을 누가 나르는지를 나눴다. kind에서는 MetalLB가 그 일을 맡았다
  • 클라우드에서는 같은 일을 클라우드의 네트워크 서비스가 맡는다. 외부 주소는 로드 밸런서가, Pod 주소는 VPC의 서브넷이, 나가는 길은 라우트 테이블과 NAT가 정한다
  • 그래서 클러스터를 읽기 전에 VPC를 먼저 읽는다. Pod가 몇 개까지 뜰 수 있는지, 인터넷에서 닿을 수 있는지가 Kubernetes 객체가 아니라 서브넷 크기와 경로에서 먼저 정해진다

이번 글의 범위

  • 원서 6장의 AWS 부분이다 — VPC의 구성 요소, EKS의 네트워크 구조, VPC CNI, 로드 밸런서 컨트롤러, 배포 실습 순서로 읽는다
  • 원서는 2021년 기준이다(EKS 1.20, eksctl 0.54, 컨트롤러 v2.2.0). 지금과 달라진 부분은 해당 절에서 따로 표시했고, 2026년 11월 10일에 AWS 공식 문서로 확인했다
  • 명령과 출력은 원서의 것을 줄여 옮겼다. 이 글을 쓰면서 EKS 클러스터를 실제로 만들어 실행한 결과는 아니다. 그림의 주소와 배치는 설명용이다

2. VPC — 주소와 경로의 틀#

2.1 VPC와 리전과 가용 영역#

  • VPC는 계정 안에 만드는 격리된 가상 네트워크다. 리전 하나에 속하고, 한 리전에 여러 개를 만들 수 있다
  • VPC에는 CIDR을 준다. 원서의 예는 192.168.0.0/16 하나다. VPC 안의 자원은 이 범위에서 사설 IP를 받는다. 나중에 겹치지 않는 CIDR을 더 붙일 수 있다
  • 리전은 물리적으로 떨어진 가용 영역(AZ) 여러 개로 이루어진다. AZ끼리는 직접 연결되어 있지만 한 AZ의 장애가 다른 AZ로 번지지 않게 분리되어 있다
  • 서브넷은 VPC의 CIDR 일부를 잘라 AZ 하나에 둔 범위다. 여러 AZ에 걸친 서브넷은 없다. 고가용성이 필요하면 AZ마다 서브넷을 두고 로드 밸런서로 나눈다

EKS에서 이 구조가 중요한 이유는 주소다. 뒤의 6절에서 보듯 Pod의 IP도 이 서브넷에서 나온다. 노드만 세고 서브넷 크기를 정하면 Pod를 늘릴 때 주소가 먼저 바닥난다.

2.2 서브넷과 라우트 테이블#

서브넷의 퍼블릭·프라이빗은 이름이 아니라 라우트 테이블의 기본 경로가 정한다.
  • 서브넷에는 라우트 테이블이 정확히 하나 연결된다. 따로 연결하지 않으면 VPC의 메인 라우트 테이블을 쓴다
  • 모든 라우트 테이블에는 VPC 범위를 local로 보내는 줄이 있다. VPC 안의 통신은 이 줄로 처리되고, 가장 구체적인 경로이므로 다른 줄보다 먼저 일치한다
  • 경로 한 줄은 목적지(CIDR), 대상(게이트웨이·ENI 등), 상태로 이루어진다. 대상이 사라지면 상태가 blackhole이 되고 그 범위의 패킷은 버려진다
  • 원서 그림의 11.0.0.0/16은 사설 대역이 아니다. 예제 값으로만 읽는다
라우트 테이블의 종류쓰이는 곳
메인명시적으로 연결하지 않은 모든 서브넷. 삭제할 수 없고 다른 테이블로 교체할 수 있다
커스텀특정 서브넷의 흐름을 위해 직접 만든 테이블
게이트웨이인터넷 게이트웨이나 가상 프라이빗 게이트웨이에 연결. 들어오는 트래픽을 어플라이언스로 돌릴 때 쓴다

연결이 안 될 때 라우트 테이블은 보안 그룹보다 먼저 확인할 대상이다. 서브넷이 의도한 테이블에 연결되어 있는지, 기본 경로의 대상이 살아 있는지를 본다.

2.3 ENI와 Elastic IP#

  • ENI(Elastic Network Interface)는 VPC 안의 가상 네트워크 카드다. 인스턴스에서 떼어 다른 인스턴스에 붙일 수 있고, 그때 속성이 함께 옮겨 간다
  • ENI가 가지는 것은 기본 사설 IPv4 하나, 보조 사설 IPv4 여러 개, 보안 그룹, MAC 주소, 출발지/목적지 검사 플래그다
  • 보조 사설 IP가 이 글의 핵심이다. VPC CNI는 ENI의 보조 IP를 Pod에 하나씩 준다
  • Elastic IP는 계정에 고정으로 할당받는 공인 IPv4다. 인스턴스가 아니라 ENI의 사설 IP에 연결된다. 인스턴스가 바뀌어도 주소를 유지해야 하는 NAT 게이트웨이, 배스천, NLB에 쓴다
  • 서브넷이 인스턴스에 자동으로 주는 공인 IP는 재시작하면 바뀔 수 있다. 고정이 필요하면 Elastic IP를 쓴다

2.4 인터넷 게이트웨이와 NAT 게이트웨이#

구분인터넷 게이트웨이NAT 게이트웨이
붙는 곳VPC퍼블릭 서브넷 (AZ 하나)
방향양방향안에서 시작한 연결만

  • 인터넷과 통신하려면 세 가지가 맞아야 한다 — VPC에 인터넷 게이트웨이가 붙어 있고, 서브넷의 라우트 테이블이 그쪽을 가리키고, 보안 그룹과 네트워크 ACL이 허용한다
  • NAT 게이트웨이는 퍼블릭 서브넷에 두고, 프라이빗 서브넷의 기본 경로가 그것을 가리키게 한다. AZ 하나에 속하므로 AZ 장애까지 견디려면 AZ마다 둔다
  • NAT 게이트웨이의 IP는 만든 뒤 바꿀 수 없다. 바깥 서비스가 허용 목록으로 출발지를 제한한다면 이 IP가 등록 대상이다
  • EKS의 노드와 Pod는 이미지를 받고 AWS API를 부르기 위해 VPC 밖으로 나가야 한다. 프라이빗 서브넷의 노드에는 NAT 경로나 VPC 엔드포인트가 필요하다

3. Security — 보안 그룹과 네트워크 ACL#

3.1 적용 위치와 상태 추적#

보안 그룹은 ENI 에, 네트워크 ACL 은 서브넷에 붙는다. 둘 다 통과해야 연결이 된다.
구분보안 그룹네트워크 ACL
붙는 곳ENI (인스턴스)서브넷
규칙허용만허용과 거부
평가모든 규칙을 함께번호가 낮은 규칙부터, 처음 일치한 것 적용
기본값인바운드 전부 거부기본 NACL은 전부 허용, 새로 만든 NACL은 전부 거부
출발지 지정CIDR 또는 다른 보안 그룹CIDR
  • 보안 그룹의 출발지에는 다른 보안 그룹을 적을 수 있다. “노드 보안 그룹에서 오는 것은 허용"처럼 IP가 아니라 소속으로 규칙을 쓴다. EKS가 컨트롤 플레인과 노드 사이에 만드는 규칙이 이 방식이다
  • 보안 그룹은 AZ를 가리지 않고 VPC 전체에서 쓴다. 네트워크 ACL은 서브넷에 붙으므로 AZ 하나에 묶인다
  • 원서는 보안 그룹을 Kubernetes NetworkPolicy와 비슷하다고 설명한다. 다만 적용 단위가 다르다 — 보안 그룹은 ENI, NetworkPolicy는 Pod 레이블이다. 한 ENI의 보조 IP를 쓰는 Pod들은 기본적으로 노드와 같은 보안 그룹을 공유한다

4. Load Balancer — ELB의 종류와 구성 요소#

4.1 네 종류#

종류계층EKS에서의 자리
Classic (CLB)L4와 L7 일부구형이다. 원서는 컨테이너와 함께 쓰지 말라고 적는다

4.2 리스너와 규칙과 대상 그룹#

  • 리스너는 프로토콜과 포트로 연결을 받는다. ALB의 리스너는 HTTP와 HTTPS다
  • 규칙은 ALB에만 있다. 조건(Host, Path, 헤더)과 동작으로 이루어지고, 우선순위가 낮은 번호부터 평가한다
  • 동작은 forward, redirect, fixed-response 중 하나가 반드시 들어가고, HTTPS 리스너에서는 그 앞에 authenticate-oidc나 authenticate-cognito를 둘 수 있다
  • 대상 그룹은 forward가 보내는 곳이다. 대상은 인스턴스, IP, Lambda 중 하나의 유형이고, 대상마다 헬스 체크를 돌려 정상인 대상에만 보낸다

이 네 가지는 05-2의 Ingress와 그대로 대응한다. Ingress의 host·path 규칙이 ALB의 규칙이 되고, backend Service가 대상 그룹이 된다. 그 변환을 하는 것이 7절의 컨트롤러다.

5. EKS — 컨트롤 플레인과 노드의 자리#

5.1 두 VPC와 EKS가 만든 ENI#

  • EKS 클러스터는 VPC 두 개에 걸쳐 있다. API 서버와 etcd는 AWS가 관리하는 VPC에, 노드와 Pod는 고객 VPC에 있다
  • 클러스터를 만들 때 지정한 서브넷에 EKS가 ENI를 2~4개 만든다. 컨트롤 플레인이 kubelet에 접속하는 kubectl exec·logs·port-forward가 이 ENI를 지난다
  • 그래서 클러스터용 서브넷에는 EKS가 쓸 주소가 남아 있어야 한다. 공식 문서의 최소는 서브넷마다 6개, 권장은 16개다
  • 노드가 부팅되면 kubelet이 API 엔드포인트에 접속해 자신을 등록한다. 이 접속이 어느 길로 가는지는 다음 절의 엔드포인트 설정이 정한다

5.2 API 엔드포인트 접근 설정#

엔드포인트 설정은 API 서버로 가는 길을 정한다. 앱 트래픽의 경로와는 별개다.
  • 기본값은 퍼블릭만 켠 상태다. API 서버는 인터넷에서 닿을 수 있고, 인증은 IAM과 RBAC이 맡는다. 접근 가능한 출발지 CIDR을 제한할 수 있다
  • 퍼블릭 접근 CIDR을 좁힐 때는 노드가 나가는 주소(NAT 게이트웨이의 IP)도 포함해야 한다. 빠뜨리면 노드가 API 서버에 등록하지 못한다. 프라이빗을 함께 켜면 이 문제가 없다
  • 프라이빗만 켠 클러스터의 엔드포인트 이름은 공개 DNS에서 VPC의 사설 IP로 풀린다. 이름은 풀리지만 VPC 밖에서는 그 IP로 갈 길이 없다
  • 원서는 이것을 public-only, private-only, mixed의 세 “모드"로 부르고 노드가 놓인 서브넷과 함께 설명한다. 엔드포인트 설정과 노드의 서브넷 배치는 서로 다른 선택이다. 프라이빗 서브넷의 노드에 퍼블릭 엔드포인트를 쓰는 조합도 흔하다

5.3 노드의 세 유형#

유형누가 관리하나네트워크에서 다른 점
관리형 노드 그룹EKS가 Auto Scaling 그룹과 인스턴스를 만든다지정한 서브넷 전체에 걸쳐 인스턴스를 둔다
자체 관리 노드사용자가 Auto Scaling 그룹과 AMI를 관리한다같은 그룹은 인스턴스 유형, AMI, 노드 IAM 역할이 같아야 한다
FargatePod마다 격리된 실행 환경을 AWS가 준다Pod마다 전용 ENI를 받는다. 프라이빗 서브넷에서만 돈다. 로드 밸런서 대상은 ip 유형만 된다

인스턴스 유형은 CPU와 메모리만 정하지 않는다. 붙일 수 있는 ENI 수와 ENI당 IP 수가 유형마다 다르고, 그 값이 노드 하나에 뜰 수 있는 Pod 수를 정한다.

  • 원서는 프라이빗 서브넷에 kubernetes.io/cluster/<이름>: shared 태그가 필요하다고 적는다. 지금 EKS는 새 클러스터에 이 태그를 붙이지 않고, 최신 로드 밸런서 컨트롤러도 요구하지 않는다
  • 지금 필요한 태그는 로드 밸런서를 둘 서브넷을 찾기 위한 것이다 — 퍼블릭 서브넷에 kubernetes.io/role/elb: 1, 프라이빗 서브넷에 kubernetes.io/role/internal-elb: 1. eksctl로 만든 VPC에는 이미 붙어 있다
  • 직접 만든 VPC에서 Ingress를 만들었는데 ALB가 생기지 않으면 이 태그부터 확인한다. 컨트롤러는 라우트 테이블을 읽어 퍼블릭 여부를 추측하지 않는다
  • 원서는 eksctl을 Weaveworks의 도구로 소개한다. 현재 저장소는 eksctl-io/eksctl이다

6. VPC CNI — Pod가 VPC 주소를 받는 방식#

6.1 CNI 바이너리와 ipamd#

① kubelet 이 CNI 를 부른다 ② CNI 바이너리가 ipamd 에서 주소를 받는다 ③ ipamd 는 EC2 API 로 ENI 와 보조 IP 를 미리 채운다.
  • 04-1에서 본 오버레이 방식의 CNI는 Pod에 VPC와 무관한 대역을 주고 노드 사이를 터널로 이었다. VPC CNI는 Pod에 서브넷의 실제 주소를 준다. VPC의 라우팅이 Pod IP를 그대로 알기 때문에 터널이 없다
  • 구성 요소는 둘이다. CNI 바이너리는 kubelet이 Pod를 만들 때 불려 veth와 경로를 설정한다. ipamd는 노드마다 aws-node DaemonSet으로 떠서 ENI와 주소를 관리한다
  • ipamd는 Pod가 생길 때 EC2 API를 부르지 않는다. ENI와 보조 IP를 미리 받아 두고(warm pool), CNI 바이너리의 요청에 그중 하나를 내준다. Pod 시작이 EC2 API 응답 시간에 묶이지 않는다
  • Pod가 지워지면 그 IP는 30초 동안 재사용하지 않는다. 다른 노드의 kube-proxy가 규칙을 갱신하기 전에 같은 IP가 새 Pod에 가는 것을 막는다

6.2 최대 Pod 수#

최대 Pod 수 = ENI 수 × (ENI 당 IP 수 − 1) + 2

m5.large:  3 × (10 − 1) + 2 = 29
  • ENI마다 첫 IP는 ENI 자신이 쓴다. 그래서 1을 뺀다
  • 끝의 2는 호스트 네트워크로 뜨는 aws-node와 kube-proxy다. 이 둘은 노드 IP를 쓰므로 보조 IP를 소비하지 않는다
  • 따라서 m5.large에서 보조 IP를 받는 Pod는 27개까지다. CoreDNS 같은 시스템 Pod도 이 27개 안에서 센다
  • 노드에 CPU와 메모리가 남아 있어도 이 수를 넘는 Pod는 뜨지 않는다. 작은 Pod를 많이 띄우는 워크로드는 인스턴스 유형을 CPU가 아니라 ENI 한도로 고르게 된다

6.3 warm pool과 서브넷 주소#

  • 기본 설정(WARM_ENI_TARGET=1)은 Pod가 쓰지 않는 ENI 하나를 항상 여분으로 붙여 둔다. ENI에 딸린 보조 IP 전체가 함께 예약된다
  • 예약된 주소는 Pod에 배정되지 않았어도 서브넷에서는 사용 중이다. 공식 문서의 예로, c5.large 노드 3대에 CoreDNS Pod 2개만 떠 있어도 서브넷 주소 50개가 소비된다
  • 그래서 서브넷이 고갈되는 시점은 Pod 수가 아니라 노드 수와 warm 설정에 달려 있다. 작은 서브넷에 노드를 많이 두면 Pod가 거의 없어도 주소가 바닥난다
  • 주소를 아껴야 하면 WARM_IP_TARGET과 MINIMUM_IP_TARGET으로 ENI 단위가 아니라 IP 단위로 여분을 정한다. 대신 Pod가 몰릴 때 EC2 API 호출이 늘어난다
kubectl -n kube-system get daemonset aws-node
kubectl -n kube-system describe daemonset aws-node | grep -E 'WARM|MINIMUM|EXTERNALSNAT'
kubectl get nodes -o custom-columns=NAME:.metadata.name,PODS:.status.allocatable.pods

Pod가 ContainerCreating에서 멈추고 이벤트에 주소 할당 실패가 보이면 순서대로 본다 — 노드의 allocatable pods, 서브넷의 남은 주소, aws-node 로그.

7. AWS Load Balancer Controller — Ingress가 ALB가 되는 과정#

7.1 컨트롤러가 만드는 것#

  • 원서의 “AWS ALB Ingress Controller"는 지금 “AWS Load Balancer Controller"다. 옛 이름의 버전은 지원이 끝났고 업그레이드가 아니라 제거 후 재설치 대상이다
  • 05-1의 세 층으로 읽으면 이렇다 — Ingress와 Service는 선언, 이 컨트롤러가 처리 주체, ALB와 NLB가 데이터패스다. 컨트롤러 Pod는 트래픽을 받지 않는다
Kubernetes 객체컨트롤러가 AWS에 만드는 것
IngressALB 하나
Ingress의 포트리스너. 지정하지 않으면 80, 인증서가 있으면 443
Ingress의 host·path 규칙리스너 규칙
backend Service대상 그룹과 헬스 체크
type: LoadBalancer ServiceNLB 하나
Gateway와 HTTPRoute (v2.14 이상)ALB
TargetGroupBinding (CRD)이미 있는 대상 그룹에 Service의 엔드포인트를 등록
  • Ingress마다 ALB가 하나씩 생긴다. 여러 Ingress를 한 ALB로 묶으려면 alb.ingress.kubernetes.io/group.name으로 같은 IngressGroup에 넣는다
  • 컨트롤러는 AWS API를 부르므로 IAM 권한이 필요하다. 노드의 역할에 얹지 않고, ServiceAccount에 IAM 역할을 연결해 컨트롤러 Pod에만 준다

7.2 instance 대상과 ip 대상#

대상 유형은 로드 밸런서가 어디까지 직접 보내는지를 정한다. 기본값은 instance 다.
  • instance 대상의 경로는 05-1 6.2의 NodePort와 같다. externalTrafficPolicy: Cluster면 다른 노드로 넘어가면서 SNAT되어 Pod가 보는 출발지가 노드 IP가 된다
  • ip 대상은 VPC CNI여서 가능하다. Pod IP가 VPC의 주소이므로 로드 밸런서가 직접 보낼 수 있다. 오버레이 CNI를 쓰는 클러스터에서는 instance 대상만 된다
  • ip 대상에서는 로드 밸런서의 헬스 체크가 Pod에 직접 간다. 대상 등록과 해제가 Pod의 생성·종료를 따라가야 하므로, 롤링 업데이트 때 대상 그룹의 등록 지연과 Pod의 종료 유예가 맞지 않으면 일시적인 502가 난다

7.3 Service type LoadBalancer의 처리 주체#

처리 주체만드는 것지금의 상태
Kubernetes에 내장된 AWS 클라우드 프로바이더CLB (기본), 인스턴스 대상 NLB중요한 버그 수정만 받는다
AWS Load Balancer ControllerNLB (instance 또는 ip 대상)권장. CLB는 만들지 않는다
  • 원서 실습의 EXTERNAL-IP는 CLB다. 컨트롤러를 설치하기 전에 Service를 만들었기 때문에 내장 프로바이더가 처리했다
  • 컨트롤러 v2.5부터는 설치하면 새 type: LoadBalancer Service에 loadBalancerClass: service.k8s.aws/nlb를 자동으로 넣어 자신이 맡는다. 05-2 2.3에서 본 그 필드다
  • 컨트롤러가 만드는 NLB의 기본 scheme은 internal이다. 인터넷에서 받으려면 service.beta.kubernetes.io/aws-load-balancer-scheme: internet-facing을 명시한다. 내장 프로바이더의 기본값은 인터넷용이어서, 컨트롤러 설치 전후로 같은 YAML의 결과가 달라진다
  • 로드 밸런서 관련 annotation은 Service를 만든 뒤 고치지 않는다. 바꿔야 하면 Service를 지우고 다시 만든다

  Normal  SuccessfullyReconciled  ingress  Successfully reconciled
  • Address가 채워지고 이벤트에 SuccessfullyReconciled가 있으면 컨트롤러가 ALB를 만든 것이다. ALB가 active가 되고 대상이 healthy가 될 때까지는 몇 분 더 걸린다
  • Address가 계속 비어 있으면 컨트롤러 로그를 본다. 흔한 원인은 IAM 권한 부족, 서브넷 태그 누락, 클래스 불일치다
  • 원서 출력의 Default backend: default-http-backend:80 (<error: endpoints … not found>)는 장애가 아니다. kubectl describe가 기본 백엔드 이름을 찾아 보고 표시한 것이고, ALB에서는 일치하는 규칙이 없으면 404 고정 응답을 낸다

8.6 정리 순서#

# 1. 로드 밸런서를 만든 Kubernetes 객체부터 지운다
kubectl delete -f alb-rules.yml
kubectl delete -f dnsutils.yml,database.yml,web.yml

# 2. AWS에 남은 것이 없는지 확인한다
aws elbv2 describe-load-balancers --query "LoadBalancers[].LoadBalancerArn"
aws elb describe-load-balancers --query "LoadBalancerDescriptions[].DNSName"
aws ec2 describe-volumes --filters "Name=tag-key,Values=kubernetes.io/created-for/pv/name" \
  --query "Volumes[].VolumeId"

# 3. 클러스터를 지운다
eksctl delete cluster --name ${CLUSTER_NAME}

# 4. 직접 만든 IAM 정책을 지운다
aws iam delete-policy \
  --policy-arn arn:aws:iam::<계정 ID>:policy/AWSLoadBalancerControllerIAMPolicy

순서가 중요하다. 클러스터를 먼저 지우면 컨트롤러가 사라져 ALB와 그 보안 그룹을 정리할 주체가 없다. 남은 로드 밸런서의 ENI가 서브넷을 붙잡아 VPC 삭제가 실패한다. PVC가 만든 EBS 볼륨도 reclaim 정책에 따라 남을 수 있다.

9. Discussion#

9.1 증상과 확인할 층#

증상먼저 가를 것볼 증거
Pod가 ContainerCreating에서 멈춘다노드의 Pod 한도 또는 서브넷 주소allocatable pods, 서브넷의 남은 IP, aws-node 로그
노드가 클러스터에 등록되지 않는다API 엔드포인트로 가는 길엔드포인트 설정, 퍼블릭 접근 CIDR, NAT 경로
Ingress의 Address가 비어 있다컨트롤러의 처리컨트롤러 로그, IAM 권한, 서브넷 태그, 클래스
ALB는 있는데 503이다대상 그룹의 상태대상 헬스, 보안 그룹, 헬스 체크 경로
NLB 주소가 VPC 밖에서 안 열린다schemeinternal 여부, 퍼블릭 서브넷 태그
Pod가 인터넷에 못 나간다프라이빗 서브넷의 기본 경로라우트 테이블, NAT 게이트웨이, 네트워크 ACL
Pod가 보는 출발지가 노드 IP다대상 유형과 트래픽 정책target-type, externalTrafficPolicy

kind에서는 문제의 원인이 대부분 클러스터 안에 있었다. EKS에서는 절반이 VPC에 있다. Kubernetes 객체가 정상인데 연결이 안 되면 AWS 쪽 자원의 상태를 같은 순서로 따라간다 — 주소, 경로, 방화벽, 로드 밸런서.

핵심 메시지#

VPC가 먼저 정한다
Pod 수의 한도와 인터넷 도달 여부는 서브넷 크기와 라우트 테이블에서 먼저 정해진다.
퍼블릭은 경로의 이름이다
기본 경로가 인터넷 게이트웨이를 가리키면 퍼블릭 서브넷이다. 프라이빗 서브넷은 NAT로 나가기만 한다.
방화벽은 두 겹이다
보안 그룹은 ENI에서 상태를 추적하고, 네트워크 ACL은 서브넷 경계에서 양방향을 따로 본다.
Pod IP는 ENI의 보조 IP다
VPC CNI는 서브넷의 실제 주소를 Pod에 준다. 터널이 없는 대신 ENI 한도가 Pod 수를 묶는다.
warm 주소도 주소를 쓴다
ipamd가 미리 받아 둔 ENI와 IP는 Pod가 없어도 서브넷에서 사용 중이다.
객체와 로드 밸런서 사이에 컨트롤러가 있다
Ingress는 ALB가, LoadBalancer Service는 NLB가 된다. 어느 컨트롤러가 맡았는지에 따라 결과가 다르다.
지울 때는 객체부터
로드 밸런서를 만든 Ingress와 Service를 먼저 지운 뒤 클러스터를 지운다.
