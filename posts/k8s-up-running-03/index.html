1. Overview#

앞으로 책 전체가 이 그림 위에서 돈다. 3장은 이 모양을 어디에 어떻게 만들지를 고르는 장이다

2장에서 이미지를 만들었다. 이미지 하나는 1장이 말한 분산 시스템이 아니다. 여러 대에 복제하고, 죽으면 되살리고, 늘릴 수 있어야 하는데 그 일을 할 쿠버네티스 클러스터가 아직 없다. 3장은 그 클러스터를 어디에 어떻게 세우는지, 세운 뒤 kubectl 로 무엇을 보는지의 장이다.

책의 입장은 처음부터 분명하다. 처음이라면 클라우드의 관리형으로 시작하라. 나중에 직접 깔 계획이더라도, 쓰는 법과 까는 법을 동시에 배우면 뭐가 안 될 때 어느 쪽 문제인지 모른다. 그래서 이 장의 절반은 클라우드 세 곳의 명령 두 줄이고, 나머지 절반은 그렇게 생긴 클러스터를 kubectl 로 들여다보는 것이다.

이 글은 책의 순서를 따르되 두 가지를 덧붙인다. 책이 2022년 기준이라 지금과 다른 부분, 그리고 책이 한 줄로 지나간 “kubectl 설정이 포함된다” 가 실제로 무슨 뜻인지. 후자는 7장에서 EKS 를 예로 끝까지 따라간다.

실습 환경은 1장과 같다. 로컬은 kind, 클라우드는 EKS 기준으로 적었다.

2. Four Ways — 어디에 세울 것인가#

네 길 모두 결과는 1장 그림과 같은 클러스터다. 다른 건 컨트롤 플레인과 노드를 누가 어디에 두느냐

2.1 책의 권고 — 처음엔 관리형#

클러스터는 결정하는 쪽(컨트롤 플레인)과 일하는 쪽(워커 노드)으로 나뉜다. 네 가지 길은 이 둘을 누가 어디에 두느냐의 차이다.

관리형(GKE, AKS, EKS)은 컨트롤 플레인을 클라우드가 자기 계정 안에 띄우고 숨긴다. 사용자는 API 서버 주소 하나를 받고, 노드는 숫자만 적는다. 책이 1순위로 꼽는 이유는 두 가지다. 클러스터 관리 자체가 복잡한 일이라 대부분은 넘기는 게 맞고, 관리 서비스 요금이 작다. 책이 “대부분 무료” 라고 적은 컨트롤 플레인 요금은 지금 GKE 와 EKS 모두 클러스터당 시간당 0.1달러 수준이다. 노드 VM 요금에 비하면 여전히 작다.

대신 카드를 등록해야 하고, 인터넷이 있어야 하고, 켜 둔 만큼 돈이 나간다. 그래서 로컬이 끌린다.

2.2 로컬 — 노드 하나와 노드 여럿#

책은 로컬 선택지로 minikube 를 먼저 말하고, Docker Desktop 에 묶여 오는 쿠버네티스도 같은 부류로 둔다. 둘 다 VM 하나 안에 컨트롤 플레인과 워커를 같이 넣는다. 노드가 하나다. 책이 이 점을 세 번 반복해서 경고한다. 노드 하나짜리는 분산 클러스터가 아니고, 클라우드 연동이 필요한 기능은 안 되거나 제한된다.

노드가 하나면 못 보는 장면이 있다. 스케줄러가 노드를 고르는 것, 노드가 죽을 때 파드가 옮겨 가는 것, 노드마다 하나씩 뜨는 DaemonSet. 고를 노드가 하나뿐이니 전부 무의미해진다. 그래서 책은 “정말 안 되는 상황이 아니면 클라우드” 라고 못 박는다.

더 최근 대안으로 책이 소개하는 것이 kind 다. VM 대신 도커 컨테이너를 노드로 써서 한 노트북에 노드 셋을 띄운다. 책은 집필 시점에 베타라며 조심스럽게 적었는데, 지금은 쿠버네티스 프로젝트 자체의 CI 에서 쓰일 만큼 안정적이고 로컬 멀티노드의 사실상 표준이다. 4장에서 구조를 본다.

2.3 베어메탈 — 부록으로 밀려난 이유#

베어메탈은 가상화 없이 물리 서버에 직접 까는 것이다. 책은 이걸 본문이 아니라 부록으로 보냈고, 라즈베리 파이 여러 대로 클러스터를 만드는 안내를 두었다. “정말로 고집한다면” 이라는 표현에 입장이 드러난다.

이유는 빈칸 때문이다. kubeadm 으로 init 과 join 을 치면 API 서버, etcd, 스케줄러, kubelet 은 생긴다. 그런데 네트워크(CNI), 로드밸런서, 스토리지(CSI) 자리가 비어 있다. CNI 를 안 깔면 파드끼리 통신이 안 되고 노드가 NotReady 로 남는다. Service 에 로드밸런서를 달라고 하면 만들어 줄 클라우드가 없어 Pending 이다. PVC 를 내도 받아 줄 쪽이 없다. 관리형은 이 빈칸을 클라우드가 채워 준 것이고, 베어메탈은 Calico 나 Cilium, MetalLB, Ceph 나 Longhorn 을 내가 골라서 채운다.

노드를 늘리는 것도 다르다. 관리형은 숫자를 바꾸면 VM 이 생기지만, 베어메탈은 서버를 사 와서 꽂고 join 을 쳐야 한다. 책이 1장에서 “물리 인프라는 새 머신 받는 데 몇 주” 라고 한 상황이다. 그래서 쓰는 법을 먼저 익히고 까는 법은 나중에 하라는 것이다.

3. Managed Cloud — 두 단계면 끝난다#

3.1 GKE, AKS, EKS — 같은 두 단계, 다른 묶음 단위#

세 클라우드의 명령은 전부 같은 두 단계다. 만들기, 그리고 kubectl 에게 주소 알려 주기.

바닐라에서 사람이 치던 init 과 join 을 클라우드 부품이 대신 친다. 그래서 명령이 두 줄이다
# GKE — 존을 정하고, 만들고, 자격 증명
gcloud config set compute/zone asia-northeast3-a
gcloud container clusters create kuar-cluster --num-nodes=3
gcloud container clusters get-credentials kuar-cluster

# AKS — 리소스 그룹(폴더)을 만들고, 만들고, 자격 증명
az group create --name=kuar --location=koreacentral
az aks create --resource-group=kuar --name=kuar-cluster
az aks get-credentials --resource-group=kuar --name=kuar-cluster

# EKS — eksctl 한 줄. kubectl 설정까지 포함
eksctl create cluster

만들기 단계에서 클라우드가 하는 일은 바닐라에서 사람이 치던 것과 같다. 컨트롤 플레인 3대를 자기 계정에 띄우고, 노드 그룹의 VM 을 찍고, 그 VM 이 부팅하면서 kubelet 을 올려 join 한다. 그래서 몇 분 걸린다. EKS 는 VPC, 서브넷, IAM 역할까지 만들어야 해서 15분쯤 걸리고, 그 수고를 한 줄로 묶은 것이 eksctl 이다. 공식 CLI 가 아닌 서드파티 출신 도구를 책이 권하는 이유다.

차이는 각 클라우드가 자원을 묶는 단위가 명령에 어떻게 드러나느냐뿐이다. GKE 는 존, AKS 는 리소스 그룹, EKS 는 VPC. AKS 의 리소스 그룹은 나중에 폴더째 지우면 클러스터, VM, 디스크, 로드밸런서가 한 번에 사라져서 실습 정리에 편하다.

두 가지를 적어 둔다. 책의 GKE 명령에만 --num-nodes=3 이 보이는데, 2.2 의 “노드 하나로는 안 보이는 장면” 을 위한 것이다. 그리고 책에 정리 절이 없다. 세 명령 전부 노드 VM 이 시간당 과금되니, 실습 끝나면 gcloud container clusters delete, az aks delete, eksctl delete cluster 를 쳐야 한다.

3.2 kubeconfig — kubectl 은 주소를 어디서 아나#

두 번째 단계인 get-credentials 가 하는 일이 이 절이다. kubectl 명령은 짧다. kubectl get nodes 어디에도 주소가 없다. kubectl 이 실행될 때마다 ~/.kube/config 를 읽어서 거기 적힌 클러스터로 보내기 때문이다.

get-credentials 류 명령이 하는 일은 이 파일에 묶음 세 개를 적는 것뿐이다

파일에는 묶음이 셋 있다. clusters 는 어디로 갈지, 즉 API 서버 주소와 그 서버가 진짜인지 확인할 CA 다. users 는 내가 누구인지다. kind 와 kubeadm 은 여기에 인증서와 키를 통째로 박아 두고, 클라우드는 “토큰은 이 명령한테 받아와라” 는 쪽지만 둔다. contexts 는 둘의 짝이고, current-context 가 지금 대상이다.

clusters:
- name: my-cluster
  cluster:
    server: https://203.0.113.10:6443
    certificate-authority-data: LS0tLS1CRUdJTi...
users:
- name: admin
  user:
    client-certificate-data: LS0tLS1CRUdJTi...     # kind, kubeadm — 열쇠가 파일에
    client-key-data: LS0tLS1CRUdJTi...
contexts:
- name: my-context
  context: {cluster: my-cluster, user: admin}
current-context: my-context

get-credentials 류 명령은 이 파일에 묶음 셋을 적고 current-context 를 거기로 돌려놓는다. 그래서 그 직후부터 주소 없이 kubectl 이 된다. 클러스터는 있는데 kubectl 이 안 된다면 이 단계를 빼먹은 것이다. 클러스터가 여럿이면 어디를 보고 있는지 확인하는 습관이 필요하다. 로컬 kind 인 줄 알고 delete 를 쳤는데 운영이었던 사고가 흔하다.

kubectl config get-contexts            # 별표가 지금 대상
kubectl config use-context kind-kind   # 이후 모든 명령이 kind 로
kubectl --context=my-eks get nodes     # 이 명령만 다른 곳으로

API 서버는 6443 포트에서 HTTPS 만 받는다. kubectl 뿐 아니라 kubelet, 스케줄러, 컨트롤러, ArgoCD 전부 같은 문으로 같은 REST API 를 부른다. kubectl get nodes -v=8 을 치면 실제로 나가는 GET /api/v1/nodes 와 Authorization 헤더가 찍힌다. kubectl 이 하는 일이 그것뿐이라는 게 보인다.

4. Local — minikube 와 kind#

4.1 minikube — VM 하나, 노드 하나#

minikube start    # VM 만들고, 쿠버네티스 깔고, kubectl 설정까지
minikube stop     # 상태는 남기고 끈다
minikube delete   # VM 째 지운다

클라우드에서 두 단계였던 만들기와 자격 증명이 start 한 줄에 들어 있다. 끝나자마자 kubectl get nodes 가 된다. stop 은 노트북 메모리를 아끼려고 꺼 두는 것이고 다시 start 하면 파드가 그대로 돌아온다. 실습이 꼬이면 delete 가 가장 빠른 복구다.

책이 “클라우드 연동이 필요한 기능은 제한된다” 고 한 지점은 2.3 의 빈칸과 같다. Service 에 LoadBalancer 를 달라고 하면 Pending 으로 멈추고, minikube 는 이걸 위해 minikube tunnel 이라는 가짜 로드밸런서 명령을 따로 둔다.

4.2 kind — 컨테이너가 노드다#

책이 베타라 조심한 kind 가 지금은 로컬 멀티노드의 표준이다. Pending 이 뜨는 그 자리가 5.1 의 빈칸이다

kind 는 Kubernetes IN Docker 다. 이름이 곧 구조다. 노드 하나가 도커 컨테이너 하나이고, docker ps 에 kind-control-plane, kind-worker, kind-worker2 가 보인다. 컨트롤 플레인 컨테이너 안에서는 kubeadm 이 하던 init 이 돌아 API 서버와 etcd 가 static pod 로 뜬다. 워커 컨테이너 안에는 containerd 와 kubelet 이 따로 깔려 있고, 파드의 컨테이너는 그 안에서 또 뜬다. 컨테이너 안의 컨테이너다. 그래서 호스트에서 docker ps 를 쳐도 파드는 안 보이고, 노드 컨테이너에 들어가 crictl ps 를 쳐야 보인다.

kind create cluster --wait 5m     # 기본 노드 1. 멀티노드는 --config 로
kubectl cluster-info
kind delete cluster

멀티노드는 설정 파일에 역할을 적어 넘긴다.

kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes:
- role: control-plane
- role: worker
- role: worker

minikube 와의 차이는 무게다. VM 하나는 무겁지만 컨테이너 셋은 가볍다. 그래서 2.2 에서 말한 “노드가 여럿이어야 보이는 장면” 을 노트북에서 볼 수 있다. 빈칸은 그대로다. 로드밸런서는 Pending 이고, PVC 는 kind 가 기본으로 깔아 주는 local-path 프로비저너가 노드 컨테이너 안의 폴더를 디스크인 척 내준다. 그 Pending 이 뜨는 자리가 1장 5.1 의 “플러그인이 번역한다” 를 몸으로 확인하는 순간이다.

4.3 책과 지금이 다른 것#

책은 2022년 기준이라 명령 셋이 지금과 다르다.

minikube 의 하이퍼바이저
책은 VirtualBox 를 먼저 깔라고 한다. 지금은 도커가 있으면 --driver=docker 가 기본값이라 VM 없이 컨테이너 안에 뜬다. VirtualBox 설치에서 막히면 건너뛴다.
kind get kubeconfig-path
지금은 없는 명령이다. 옛 kind 는 kubeconfig 를 별도 파일로 만들어 KUBECONFIG 로 가리켜야 했는데, 지금은 ~/.kube/config 에 자동으로 합쳐지고 컨텍스트 이름이 kind-kind 로 잡힌다.
"kind 는 베타"
버전은 지금도 0.2x 대지만 쿠버네티스 자신의 CI 가 쓴다. 1.0 을 안 찍는 것뿐이지 성숙도는 충분하다. 이 책을 따라갈 로컬 환경으로는 kind 가 맞다.

5. Looking Inside — kubectl 로 들여다보기#

kubectl 은 API 와 대화하는 도구이면서 클러스터가 건강한지 보는 도구다. 책은 객체를 만들기 전에 클러스터부터 들여다본다.

5.1 version — 버전은 둘이고, 차이는 한 단계까지#

kubectl version

로컬 kubectl 버전과 API 서버 버전이 따로 나온다. 클라이언트와 서버가 별개 프로그램이라는 걸 처음 보여 주는 자리다. 서버 버전이 찍힌다는 건 연결이 된다는 뜻이라 연결 확인용으로도 쓴다. 연결이 안 되면 클라이언트 버전만 찍히고 에러가 난다.

둘이 달라도 된다. 쿠버네티스의 “버전” 은 사실상 가운데 숫자(1.31 의 31)이고, 넉 달마다 하나씩 오른다. 책은 두 단계 차이까지 권장, 세 단계까지 한계라고 적었는데, 지금 공식 정책은 kubectl 이 API 서버보다 한 단계 높거나 낮은 것까지만 보장한다. 책보다 엄격해졌다. 깨지는 경우는 하나다. 옛 클러스터에 새 버전에서 추가된 필드를 보내면 API 서버가 모르는 필드라며 거부한다. 클러스터가 여럿이면 버전별 kubectl 을 바꿔 주는 도구를 쓴다.

5.2 componentstatuses — 세 부품, 그리고 지금 방식#

kubectl get componentstatuses

scheduler, controller-manager, etcd 세 줄이 Healthy 로 나온다. 책이 각각을 한 줄로 정의한다. controller-manager 는 복제본이 전부 살아 있는지 같은 규칙을 지키는 컨트롤러들을 돌리고, scheduler 는 파드를 노드에 배치하며, etcd 는 모든 API 객체가 저장되는 창고다. 1장 3.3 의 “주문서를 벽에 붙여 놓고 계속 쳐다보는” 루프들이 전부 controller-manager 하나의 프로세스 안에서 돌고, etcd 를 잃으면 클러스터를 잃는다. 컨트롤 플레인을 3대로 두는 이유의 절반은 etcd 복제다.

API 서버 자신은 목록에 없다. 이 명령에 답을 하고 있다는 것 자체가 살아 있다는 증거라서다.

이 명령은 1.19 부터 deprecated 다. 지금도 치면 나오긴 하지만 경고가 붙고, 관리형 클러스터에서는 컨트롤 플레인이 숨겨져 있어 Unhealthy 로 잘못 나오기도 한다. 책도 “출력이 책과 똑같지 않아도 걱정하지 마라” 는 박스를 이 자리에 두었다. 지금 방식은 둘이다.

kubectl get pods -n kube-system          # 컨트롤 플레인 파드가 Running 인지
kubectl get --raw /readyz?verbose        # API 서버의 자체 점검

5.3 nodes — 역할, 조건, 용량#

kubectl get nodes

NAME    STATUS   ROLES           AGE   VERSION
kube0   Ready    control-plane   45d   v1.22.4
kube1   Ready    <none>          45d   v1.22.4
kube2   Ready    <none>          45d   v1.22.4
kube3   Ready    <none>          45d   v1.22.4

ROLES 가 비어 있는 것이 워커다. 관리형에서는 첫 줄이 아예 안 보인다. 컨트롤 플레인을 클라우드가 숨기니까. 쿠버네티스는 사용자 파드가 클러스터 운영을 해치지 않도록 컨트롤 플레인 노드에는 일을 올리지 않는데, 메커니즘은 taint 다. kubeadm 이 node-role.kubernetes.io/control-plane:NoSchedule 을 붙여 두고 스케줄러는 그걸 허용한 파드만 거기 올린다. 사용자 파드가 메모리를 다 먹으면 같은 머신의 API 서버가 죽고, 그러면 클러스터 전체가 멈춘다. AGE 는 머신이 켜진 시간이 아니라 노드 객체가 등록된 뒤 경과 시간이다. 재부팅해도 안 바뀌고, 지웠다 다시 join 하면 0 부터다.

kubectl describe nodes kube1 은 노드 하나를 다섯 토막으로 풀어 준다.

Labels 에는 OS 와 CPU 아키텍처, 호스트명이 있다. 스케줄러가 “ARM 노드에만”, “GPU 노드에만” 을 볼 때 쓰는 꼬리표다. 책의 예시 클러스터는 라즈베리 파이라 arch=arm 인데, 2장의 “이미지가 arm64 를 지원해야 한다” 가 그대로 적용된다.

Conditions 는 읽는 요령이 하나다. Pressure 는 False 가 정상, Ready 는 True 가 정상. Reason 이 전부 Kubelet... 으로 시작하는 건 이 보고를 하는 주체가 노드의 kubelet 이기 때문이다. kubelet 이 10초마다 API 서버에 보내고, 40초 동안 안 오면 Ready 가 Unknown 이 되고, 5분 지나면 그 노드의 파드를 다른 곳에 옮기기 시작한다. 노드가 죽으면 파드가 옮겨 간다는 말의 타이머가 이것이다. NetworkUnavailable 의 Reason 에 CNI 이름(책에서는 Flannel)이 보이고, CNI 를 안 깔면 이 줄이 True 로 남아 NotReady 가 된다.

System Info 에서 눈에 띄는 건 둘이다. 책 문장은 “도커 버전” 이라고 하는데 출력은 containerd:// 다. 2장 끝의 “띄우는 건 도커가 아니다” 가 여기서 증거로 나온다. PodCIDR 10.244.1.0/24 는 이 노드에서 뜨는 파드가 받을 IP 대역이고, 노드마다 /24 하나씩 받는다. Network & K8s 02-1 에서 본 파드 IP 10.244.1.3 이 이 대역에서 나온 것이다.

5.4 requests 와 limits — 스케줄러는 requests 만 본다#

5장의 requests 와 limits 가 여기서 처음 나온다. 빈자리는 Allocatable 에서 requests 합을 뺀 것이다

describe 의 나머지 두 토막이 Capacity/Allocatable 과 Non-terminated Pods 다. Capacity 는 머신이 가진 전부, Allocatable 은 그중 파드에 줄 수 있는 양이다. kubelet 과 OS 몫을 빼서 보통 조금 작다. pods: 110 은 노드당 파드 수 상한인데 메모리 882MB 짜리 라즈베리 파이에 110개는 어차피 못 띄우니 의미 없는 숫자다.

Non-terminated Pods 는 지금 이 노드에서 도는 파드와 각각의 CPU, 메모리 requests/limits, 그리고 합계다. 사용자 파드가 하나도 없는 노드인데 셋이 돈다. 전부 kube-system 이고 6장의 주인공들이다. 260m 은 0.26 코어라는 뜻이다. 1000m 이 코어 하나다.

책이 5장을 예고하며 한 줄로 정의한 것이 이 절의 핵심이다. requests 는 노드에 반드시 확보되는 양, limits 는 파드가 쓸 수 있는 최대치. limits 가 requests 보다 클 수 있고 그 초과분은 있으면 주고 없으면 못 주는 best-effort 다. 그래서 스케줄러는 requests 만 보고 자리를 정한다. 출력에 “limits 합은 100% 를 넘을 수 있다” 는 괄호 주석이 붙는 이유다. 실무에서 requests 를 안 적으면 스케줄러가 0 필요로 보고 한 노드에 몰아 넣다가 메모리가 터지고, limits 만 크게 적으면 자리는 잡히는데 실제로 그만큼 못 받는다. 1장 5.2 의 “빈자리를 채운다” 가 가능한 것도 limits 가 requests 보다 커도 된다는 이 규칙 덕분이다.

6. Cluster Components — 자기 부품도 파드로#

DNS 가 이름을 IP 로, Service 가 IP 하나를, kube-proxy 가 그 IP 를 실제 파드로 — 셋이 맞물린다

클러스터를 이루는 부품 상당수가 쿠버네티스 자신 위에 파드로 떠 있다. 집을 짓는 도구가 그 집 안에 들어 있는 구조다. 전부 kube-system 네임스페이스에 있다. 책의 각주대로 네임스페이스는 자원을 정리하는 폴더이고, kube-system 은 시스템 폴더다. 그냥 kubectl get pods 를 치면 안 보이고 -n kube-system 을 붙여야 보인다.

6.1 kube-proxy — 노드마다 하나, DaemonSet#

kubectl get daemonsets -n kube-system kube-proxy

NAME         DESIRED   CURRENT   READY   UP-TO-DATE   AVAILABLE   AGE
kube-proxy   5         5         5       5            5           45d

Service 가 “주소 하나 뒤에 파드 여럿” 을 만드는데, 그 주소로 온 패킷을 파드 중 하나로 보내는 일을 각 노드에서 하는 것이 kube-proxy 다. 이름은 프록시지만 패킷을 직접 받아 넘기지 않고 노드의 iptables 나 IPVS 규칙을 써서 커널이 넘기게 한다. 규칙이 노드 커널에 들어가니 노드마다 하나씩 있어야 하고, 그래서 DaemonSet 이다. DaemonSet 은 “모든 노드에 정확히 하나” 를 보장하는 객체다. 노드가 추가되면 거기에도 자동으로 하나 뜬다. CNI 에이전트, 로그 수집기, 모니터링 에이전트가 전부 이걸로 배포된다. DESIRED 와 READY 가 같으면 정상이고, READY 가 작으면 어느 노드에서 못 뜨고 있다는 신호다.

책이 “DaemonSet 을 안 쓸 수도 있다” 고 여지를 둔 경우가 있다. Cilium 을 CNI 로 쓰면 kube-proxy 를 아예 빼고 Cilium 이 eBPF 로 그 역할을 대신한다. 배포 방식이 뭐든 “노드마다 하나” 라는 요구는 변하지 않는다.

6.2 CoreDNS — 몇 개면 된다, Deployment 와 Service#

kubectl get deployments -n kube-system coredns
kubectl get services -n kube-system kube-dns

NAME      READY   UP-TO-DATE   AVAILABLE   AGE
coredns   2/2     2            2           45d

NAME       TYPE        CLUSTER-IP   PORT(S)                  AGE
kube-dns   ClusterIP   10.96.0.10   53/UDP,53/TCP,9153/TCP   45d

파드 안에서 curl http://order-service 라고 치면 되는 이유가 이 DNS 다. Service 를 만들면 그 이름이 자동으로 등록되고, CoreDNS 가 그 이름을 Service 의 IP 로 풀어 준다. 1장 4.3 에서 Service 를 팀 간 전화번호라고 했는데, 번호부가 이것이다.

kube-proxy 는 DaemonSet, DNS 는 Deployment 인 것이 대비된다. DNS 는 노드마다 있을 필요가 없고 전체에 몇 개만 있으면 된다. Deployment 는 개수만 정하고 어디에 둘지는 스케줄러에 맡긴다. 1장의 replicas: 3 이 바로 이 객체의 필드다. 복제본이 둘이든 셋이든 파드는 Service 주소 10.96.0.10 하나만 안다. Service 가 주소를 고정하고, 그 뒤의 복제본으로 나누는 건 6.1 의 kube-proxy 가 한다. 그러니까 세 부품이 맞물린다. DNS 가 이름을 IP 로, Service 가 IP 하나를, kube-proxy 가 그 IP 를 실제 파드로.

파드가 뜰 때 kubelet 이 그 파드의 /etc/resolv.conf 에 nameserver 10.96.0.10 을 적어 준다. 그래서 파드 안의 프로그램은 아무 설정 없이 서비스 이름을 푼다. 02-1 에서 nsenter 로 컨테이너 방에 들어갔던 것처럼 들어가 cat 하면 바로 보인다. 10.96.0.10 은 kubeadm 과 kind 의 기본값이라 거의 모든 클러스터에서 같은 숫자다. 책은 Deployment 와 Service 둘 다 core-dns 로 적었는데 실제 이름은 Deployment 가 coredns, Service 가 kube-dns 다. 옛 이름이 Service 에 남아 있다.

6.3 UI — 한 문장으로 줄어든 이유#

책은 대시보드를 세 문장으로 끝낸다. 클라우드 콘솔에 있고, 없으면 커뮤니티 대시보드를 깔 수 있고, VS Code 확장으로도 볼 수 있다. 2판까지는 설치와 접근법이 본문에 있었는데 3판에서 줄었다. 인증 없이 열면 클러스터 전체가 노출되는 보안 설정이 까다롭고, 쓰는 사람이 줄어서다. 지금은 k9s(터미널 UI), Lens, Headlamp 쪽이 많이 쓰인다.

7. Discussion#

7.1 kubectl 한 번의 인증 — EKS 를 예로#

책은 “eksctl 이 kubectl 설정까지 포함한다” 로 끝낸다. 그 설정 파일을 열어 보면 3.2 의 users 에 인증서가 없다.

users:
- name: my-eks
  user:
    exec:
      command: aws
      args: ["eks", "get-token", "--cluster-name", "my-cluster"]

“토큰은 aws 한테 받아와라” 는 쪽지뿐이다. 그래서 EKS 의 kubeconfig 는 파일만 복사해 가면 안 된다. 그 컴퓨터에 aws CLI 가 있어야 하고, ~/.aws/credentials 에 IAM 키가 있어야 하고, 그 IAM 신원이 클러스터 명부에 등록돼 있어야 한다. 동료에게 파일을 보내도 동료의 aws CLI 는 동료의 키로 토큰을 만든다. 내 권한이 따라가지 않는다.

kubeconfig 에 열쇠가 없어도 되는 이유. GKE 와 AKS 도 같은 자리에 자기 플러그인을 끼운다

흐름을 끝까지 따라가면 이렇다.

노트북의 aws CLI 는 내 비밀키로 “나 누구야?” 라는 STS 질문서(GetCallerIdentity)에 서명만 하고, 보내지는 않는다. 서명된 URL 을 base64 로 감싸고 k8s-aws-v1. 을 붙인 것이 토큰이다. 비밀키는 노트북 밖으로 안 나간다. kubectl 은 그 토큰을 Authorization 헤더에 붙여 보통의 HTTPS 요청을 보낸다.

API 서버는 토큰을 받고 인증기 목록을 차례로 돈다. 클라이언트 인증서, ServiceAccount 토큰, OIDC 는 “내 거 아님” 이라고 넘기고, 마지막 웹훅 인증기가 받아서 AWS 가 컨트롤 플레인 옆에 띄워 둔 aws-iam-authenticator 에 TokenReview 양식으로 묻는다. 그 프로그램이 토큰을 풀어 질문서를 STS 에 전달한다. STS 호출은 여기 한 번뿐이다. STS 는 서명을 검증하고 ARN 을 돌려준다. arn:aws:iam::123456789012:user/taewon 같은, 계정 번호까지 붙은 AWS 식 이름이다.

쿠버네티스는 ARN 을 모른다. 사용자 객체도 없다. 그래서 변환표가 필요하고, 그 표의 한 줄이 access entry 다. “이 ARN 이 오면 이 그룹으로 취급하라”. 표에 있으면 쿠버네티스 이름과 그룹으로 바꿔 TokenReview 답장에 적어 돌려주고, API 서버는 그 문자열로 RBAC 를 본다. 표에 없으면 토큰이 정상이어도 Unauthorized 다. 표는 클러스터 안이 아니라 AWS API 쪽에 있어서, 클러스터에 못 들어가도 콘솔에서 고칠 수 있다. 옛 방식인 aws-auth ConfigMap 은 클러스터 안의 YAML 이라 관리자 줄을 잘못 지우면 되돌릴 사람도 못 들어가는 사고가 흔했다.

API 서버는 끝까지 ARN 의 의미를 모른다. 통역사(웹훅)가 AWS 에 한 번 확인하고 쿠버네티스 양식으로 답을 적어 줄 뿐이다. 웹훅은 쿠버네티스의 공식 확장 지점이라 GKE 는 같은 자리에 구글 토큰용 플러그인을, AKS 는 애저 AD 용 플러그인을 끼운다. 온프레미스 kubeadm 에도 aws-iam-authenticator 를 붙일 수 있다. EKS 가 나오기 전에 그 용도로 만들어진 오픈소스다.

이 구조 덕에 EKS 의 kubeconfig 에는 비밀이 하나도 없다. 주소와 공개 CA 뿐이다. 비밀은 전부 ~/.aws/credentials 쪽에 있고, 토큰은 15분이면 만료된다. 인증서 파일이 유출되면 만료까지 누구나 쓸 수 있지만, 이 방식은 유출돼도 IAM 키가 없으면 쓸모없고 IAM 키는 AWS 에서 즉시 폐기할 수 있다. Kukie Infra.02 5장에서 “진짜 열쇠는 노트북의 AWS 키다” 라고 쓴 것이 이 흐름이다.

책 따라가기 — kind
4장부터의 실습은 Pod 띄우고, 라벨 붙이고, Deployment 롤아웃하고, Service 만드는 것이다. 만들고 지우기를 수십 번 반복한다.
kind 가 수십 초에 3노드를 만들고 지운다. 돈 안 들고, 인터넷 없어도 되고, 망가지면 delete 로 끝.
진짜 서버 감각 — 무료 VM 에 kubeadm
"노드는 어디서 오나", "컨트롤 플레인은 어디 깔리나" 는 kind 로는 느낌이 안 온다. 컨테이너가 노드인 척하는 거라서.
오라클 Always Free 의 ARM 4코어 24GB 를 VM 셋으로 쪼개 init 과 join 을 직접 치면 책 부록의 라즈베리 파이 실습 그대로다. 로드밸런서 Pending 을 MetalLB 로 푸는 것까지.

주의 하나. 무료 ARM VM 은 이미지가 arm64 를 지원해야 한다. 책의 kuard 는 kuard-arm64 태그가 있고 요즘 공식 이미지는 대부분 멀티아키텍처라 괜찮지만, amd64 만 있는 이미지를 만나면 exec format error 가 난다. 5.3 의 Labels 에서 arch 를 먼저 확인하는 습관이 그래서 필요하다.

핵심 메시지#

네 가지 길
관리형은 컨트롤 플레인을 숨기고, kind 는 컨테이너를 노드로, kubeadm 은 빈칸을 내가 채운다
kubeconfig
어디로, 누구로, 둘의 짝. get-credentials 는 이 파일에 적는 명령이다
requests
스케줄러는 이것만 본다. limits 합은 100% 를 넘어도 된다
DaemonSet 과 Deployment
노드마다 하나면 전자, 몇 개면 되면 후자. kube-proxy 와 CoreDNS 가 그 예
웹훅 인증
API 서버는 ARN 을 모른다. 통역사가 STS 에 한 번 묻고 표에서 바꾼다

클러스터는 어디에 세우든 같은 모양이고, kubectl 은 어디에 세웠든 같은 HTTPS 요청을 보낸다. 다른 건 그 요청에 붙는 신원을 누가 어떻게 증명하느냐, 그리고 빈칸을 누가 채우느냐뿐이다. 책은 그 둘을 클라우드에 맡기고 쓰는 법부터 배우라고 한다. 이 글은 맡긴 것이 정확히 무엇인지까지 따라가 봤다. 다음 편은 4장 — kubectl 명령을 익히는 장이다. 네임스페이스, 컨텍스트, 라벨, 디버깅 명령.
