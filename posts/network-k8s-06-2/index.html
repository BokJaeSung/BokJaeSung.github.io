1. Overview#

이름은 비슷해도 범위가 다르다. AWS 의 서브넷은 AZ 하나에, GCP 와 Azure 의 서브넷은 리전에 묶인다.

06-1에서 이어지는 것

  • 06-1은 EKS를 VPC부터 읽었다. 서브넷과 경로가 도달 범위를 정하고, Pod IP는 ENI의 보조 IP였고, Ingress와 로드 밸런서 사이에는 컨트롤러가 있었다
  • GCP와 Azure도 같은 질문으로 읽는다. 구성 요소의 이름은 비슷하지만 묶이는 범위가 다르다
  • 범위가 다르면 설계가 달라진다. AWS에서는 AZ마다 서브넷을 만들었지만 GCP와 Azure에서는 서브넷 하나가 리전 전체에 걸친다

이번 글의 범위

  • 원서 6장의 GCP·Azure 부분과 장 끝의 비교표다 — 각 클라우드의 네트워크, 관리형 Kubernetes, Pod 주소, 로드 밸런서 순서로 읽는다
  • 원서는 2021년 기준이다(GKE의 Calico, AKS 1.19와 kubenet). 지금과 달라진 부분은 해당 절에서 따로 표시했고, 2026년 11월에 각 공식 문서로 확인했다
  • 원서의 GCP 절에는 실습이 없고, Azure 실습은 포털 화면 위주다. 명령과 출력은 필요한 것만 옮겼고, 이 글을 쓰면서 GKE나 AKS 클러스터를 실제로 만들어 실행한 결과는 아니다

2. GCP Network — 전역 VPC와 리전 서브넷#

2.1 리전과 존과 전역 자원#

  • 리전은 독립된 지리 영역이고 존 여러 개로 이루어진다. 존 하나는 장애가 함께 나는 단위로 본다
  • GCP에는 전역 자원이 있다. VPC 네트워크, 방화벽 규칙, 경로가 전역이다. 프로젝트 안에서 리전을 가리지 않고 같은 것을 쓴다
  • 서브넷은 리전 자원이다. 서브넷 하나가 그 리전의 모든 존에 걸친다
  • AWS와 비교하면 한 단계씩 넓다 — VPC는 리전에서 전역으로, 서브넷은 AZ에서 리전으로

2.2 네트워크 티어#

티어인터넷과 VM 사이의 경로쓰는 곳
프리미엄 (기본값)가능한 한 Google 망 안에서 나른다여러 리전에 걸친 서비스, 전역 로드 밸런서
스탠더드일반 인터넷으로 나른다한 리전 안에서 끝나는 서비스, 비용 우선

티어는 다른 클라우드에 없는 선택지다. 전역 로드 밸런서의 단일 Anycast IP는 프리미엄 티어에서 동작한다.

2.3 VPC와 서브넷#

  • VPC 네트워크는 프로젝트에 속한다. 네트워크 자체에는 CIDR이 없고 서브넷이 범위를 가진다
  • 새 프로젝트에는 auto 모드의 default 네트워크가 있다. 리전마다 서브넷이 하나씩 미리 만들어져 있다
  • custom 모드는 서브넷을 만들지 않고 시작한다. 범위를 직접 정하므로 운영 환경에는 이쪽을 쓴다
  • 서브넷에는 기본 범위 하나와 보조 범위 여러 개가 있다. 3.2에서 이 보조 범위가 Pod와 Service의 주소가 된다

VPC끼리는 피어링으로 잇는다. 범위가 겹치는 네트워크끼리는 피어링할 수 없다. auto 모드 네트워크는 프로젝트가 달라도 같은 범위를 쓰므로 서로 피어링되지 않는다. 팀이나 서비스마다 프로젝트를 나누는 조직에서는 처음부터 custom 모드로 범위를 나눠 둔다. Shared VPC는 한 프로젝트의 서브넷을 다른 프로젝트가 쓰게 하는 방식이다.

2.4 방화벽 규칙과 고정 IP#

  • 방화벽 규칙은 VPC 네트워크에 정의하고 VM 단위로 적용된다. 규칙 하나는 인그레스 또는 이그레스 한 방향만 다룬다
  • 상태 기반이다. 허용된 연결의 응답은 따로 규칙이 없어도 통과한다. AWS의 보안 그룹과 같은 성질이다
  • 규칙의 대상은 네트워크 태그나 서비스 계정으로 고른다. GKE 노드에도 네트워크 태그가 붙으므로 특정 노드 풀에만 규칙을 걸 수 있다
  • 방화벽 규칙은 다른 VPC와 공유되지 않는다. 피어링한 네트워크에도 따로 만든다
  • 내부 IP와 외부 IP 모두 이름을 붙여 예약할 수 있다. 예약한 외부 IP는 로드 밸런서의 주소로 쓴다

2.5 Cloud Load Balancing#

구분받는 트래픽GKE에서 만드는 방법
외부 L4VPC 밖의 TCP·UDPtype: LoadBalancer Service
내부 L4같은 VPC 안의 TCP·UDP내부용 annotation을 단 type: LoadBalancer Service
L7 (HTTP·HTTPS)Host와 Path로 나누는 요청Gateway(권장) 또는 Ingress
  • GKE에는 Service, Ingress, Gateway를 처리하는 컨트롤러가 내장되어 있다. EKS처럼 컨트롤러를 따로 설치하지 않아도 객체를 만들면 Google Cloud 로드 밸런서가 생긴다
  • GKE Ingress는 유지보수 모드다. 버그 수정 외의 새 기능은 들어가지 않고, 문서는 Gateway API를 쓰라고 권장한다. 05-2 7.1에서 본 Ingress API의 동결과 같은 흐름이다. 원서는 Ingress만 다룬다
  • 05-1의 세 층은 그대로다. Ingress는 선언, GKE의 컨트롤러가 처리 주체, Cloud Load Balancing이 데이터패스다. 컨트롤러가 내장되어 눈에 보이지 않을 뿐이다
  • 클러스터 안에 ingress 프록시를 직접 두는 구성도 가능하다. 로드 밸런서는 프록시 Pod가 있는 노드까지만 보내고 프록시가 나눈다. Ingress가 많을 때 로드 밸런서 수를 줄일 수 있지만 한 단계가 더 생긴다

3. GKE — VPC-native와 NEG#

3.1 컨트롤 플레인과 노드 풀#

  • GKE의 컨트롤 플레인은 보이지 않는다. API 서버와 일부 설정에만 접근할 수 있고, kube-apiserver나 kube-controller-manager의 플래그를 직접 줄 수 없다
  • 조정할 수 있는 네트워크 설정은 제한적이다 — Pod 주소 범위, 노드당 최대 Pod 수, NetworkPolicy 사용 여부 정도다
  • 노드는 Compute Engine VM이다. 같은 설정의 노드 묶음이 노드 풀이고, 머신 유형·오토스케일링·서비스 계정·taint를 풀 단위로 정한다
  • 클러스터는 VPC 네트워크 하나에 속한다. 존 클러스터는 컨트롤 플레인이 하나, 리전 클러스터는 여러 존에 복제본을 둔다
  • 원서의 “프라이빗 클러스터"를 지금 문서는 네트워크 격리라고 부르고 둘로 나눈다. 프라이빗 노드는 노드에 공인 IP를 주지 않는 설정이고, 컨트롤 플레인에 누가 접근할 수 있는지는 따로 정한다. 접근에는 DNS 기반 엔드포인트를 권장한다. 06-1 5.2와 같은 종류의 선택이다

3.2 VPC-native 클러스터#

VPC-native 클러스터는 범위 세 개로 읽는다 — 노드, Pod, Service.
  • 이전 방식인 routes-based 클러스터는 노드마다 Pod 대역을 정하고 VPC에 정적 경로를 한 줄씩 추가했다. VPC가 Pod IP를 경로로만 알았고 NEG를 쓸 수 없었다
  • GKE는 Pod용 보조 범위에서 노드마다 /24를 떼어 준다. 주소 256개로 Pod를 최대 110개까지 띄운다. 주소를 Pod 수의 두 배 이상 잡는 것은 Pod가 교체될 때 옛 주소와 새 주소가 잠시 함께 필요하기 때문이다
  • EKS의 VPC CNI와 결과는 같다 — Pod IP가 VPC의 주소다. 방식이 다르다. EKS는 ENI에 보조 IP를 하나씩 붙이고, GKE는 노드에 범위를 통째로 준다. 그래서 GKE에는 ENI 한도 같은 인스턴스 유형별 제약이 없고, 노드당 Pod 수는 설정값이다
  • 원서의 표 6-3은 만드는 방법(콘솔, gcloud 버전, REST API)에 따라 모드가 갈린다고 적는다. 지금은 새 클러스터가 모두 VPC-native로 만들어진다

3.3 서브넷 크기와 노드 수#

기본 범위 /S 가 받을 수 있는 노드 수:   N = 2^(32 − S) − 4
노드 N 대에 필요한 넷마스크:            S = 32 − ⌈log2(N + 4)⌉
노드 수의 한도는 범위 두 개가 함께 정한다.
  • 4를 빼는 것은 서브넷마다 예약된 주소다
  • 노드당 최대 Pod 수를 줄이면 노드마다 떼는 범위도 작아진다. 작은 Pod 범위로 노드를 더 많이 두는 방법이다
  • 범위는 클러스터를 만들 때 정한다. Pod 범위는 나중에 보조 범위를 추가할 수 있지만 처음 범위를 바꾸지는 못한다

3.4 컨테이너 네이티브 로드 밸런싱#

06-1 의 instance 대상과 ip 대상이 GKE 에서는 인스턴스 그룹과 NEG 다.
  • NEG(network endpoint group)는 로드 밸런서의 백엔드로 쓰는 엔드포인트 목록이다. 엔드포인트가 Pod의 IP와 포트다
  • NEG 컨트롤러가 EndpointSlice를 따라 Pod IP를 NEG에 넣고 뺀다. 05-1의 EndpointSlice가 클라우드 로드 밸런서의 백엔드 목록으로 복사되는 셈이다
  • 로드 밸런서가 Pod를 직접 헬스 체크한다. Pod의 Ready와 로드 밸런서가 본 상태가 따로 있으므로, GKE는 readiness gate로 로드 밸런서가 정상으로 본 뒤에야 Pod를 Ready로 표시한다
  • 얻는 것은 셋이다 — 한 단계가 줄어 지연이 낮아지고, 지연과 오류를 Pod 단위로 볼 수 있고, Cloud Armor·Cloud CDN·Identity-Aware Proxy 같은 L7 기능을 Pod 앞에 바로 붙일 수 있다
# Service에 NEG를 요청하는 annotation — 구조 설명용
apiVersion: v1
kind: Service
metadata:
  name: web
  annotations:
    cloud.google.com/neg: '{"ingress": true}'
spec:
  type: ClusterIP
  selector:
    app: web
  ports:
    - port: 80
      targetPort: 8080

NEG를 쓰면 Service가 NodePort일 필요가 없다. 로드 밸런서가 노드의 포트를 거치지 않기 때문이다. 05-2 2.2의 “NodePort는 필수 경유지가 아니다"가 여기서 실제 구현으로 나타난다.

3.5 원서 이후 달라진 것#

원서의 서술지금
만드는 방법에 따라 routes-based가 기본새 클러스터는 모두 VPC-native

구조는 그대로다. Pod IP는 서브넷의 범위에서 나오고, 로드 밸런서는 NEG로 Pod에 직접 닿는다.

4. Azure Network — 리소스 그룹과 VNet#

4.1 배포 모델과 리소스 그룹#

  • Azure에는 배포 모델이 둘 있었다. 클래식 모델은 자원을 하나씩 따로 만들고 지웠다. 2014년에 나온 Azure Resource Manager(ARM)가 지금의 모델이다. 클래식 모델의 자원은 2024년 8월까지 단계적으로 종료됐다
  • ARM의 핵심은 리소스 그룹이다. 관련된 자원을 한 묶음으로 만들고, 태그를 붙이고, 권한을 주고, 한 번에 지운다
  • 계층은 구독 → 리소스 그룹 → 자원이다. 권한은 위에서 아래로 상속된다
  • AKS는 리소스 그룹을 두 개 쓴다. 5.1에서 이 구분이 실제 운영에 영향을 준다

4.2 VNet과 서브넷과 가용 영역#

  • VNet은 Azure의 가상 네트워크다. 리전 하나에 속하고 CIDR을 가진다. 원서의 예는 192.168.0.0/16이다
  • 서브넷은 VNet의 범위를 나눈 것이고 자원은 서브넷에서 사설 IP를 받는다
  • Azure의 서브넷은 리전의 모든 가용 영역에 걸친다. 영역마다 서브넷을 만들지 않는다. 같은 서브넷 안에서 VM을 영역별로 나눠 배치한다
  • 리전에 따라 가용 영역이 없는 곳도 있다. 영역에 걸친 AKS 클러스터를 계획한다면 리전부터 확인한다

4.3 라우트 테이블과 기본 아웃바운드#

경로의 종류만드는 주체예
시스템 경로Azure가 서브넷마다 자동으로VNet 범위, 0.0.0.0/0 → Internet, 사설 대역 → None
선택적 시스템 경로기능을 켜면 추가VNet 피어링, 서비스 엔드포인트
사용자 정의 경로 (UDR)사용자0.0.0.0/0 → 방화벽 어플라이언스
BGP 경로온프레미스 게이트웨이VPN·ExpressRoute 너머의 대역
  • 시스템 경로는 지우거나 고칠 수 없다. 같은 목적지에 UDR을 만들어 덮는다. 우선순위는 더 긴 접두사가 먼저이고, 같으면 UDR, BGP, 시스템 순이다
  • 포털의 라우트 테이블 화면에는 시스템 경로가 보이지 않는다. 원서의 그림 6-20이 그 상태다. 실제로 적용되는 경로는 NIC의 유효 경로(effective routes)에서 본다
  • 라우트 테이블 하나를 여러 서브넷에 연결할 수 있다. 서브넷 하나에는 테이블 하나만 붙는다
  • 경로의 목적지와 NSG 규칙에는 IP 범위 대신 서비스 태그를 쓸 수 있다. Storage.EastUS처럼 Azure 서비스의 주소 묶음을 이름으로 가리킨다

원서는 Azure의 큰 차이로 “새로 만든 자원이 기본으로 인터넷에 나갈 수 있다"는 점을 든다. AWS의 프라이빗 서브넷이 NAT 없이는 못 나가는 것과 반대였다. 이 기본값이 바뀌고 있다.

  • 명시적인 아웃바운드 수단이 없는 VM에 Azure가 공인 IP를 암묵적으로 붙여 주던 동작이 “기본 아웃바운드 액세스"다
  • 2026년 3월 31일 이후의 API 버전에서는 새 VNet의 서브넷이 프라이빗으로 만들어진다. 이 서브넷의 VM은 NAT 게이트웨이, 로드 밸런서의 아웃바운드 규칙, 공인 IP 중 하나를 명시해야 나갈 수 있다
  • 기존 VNet은 바뀌지 않는다. 같은 템플릿이라도 API 버전에 따라 결과가 달라지므로 “예전에는 됐는데"의 원인이 될 수 있다

4.4 공인 IP와 NAT#

  • Azure에서 IP 주소는 독립된 자원이다. 어디에도 붙이지 않은 공인 IP를 만들어 두고 나중에 연결할 수 있다
  • 자원은 VNet 안에서 사설 IP로만 통신한다. 공인 IP와 사설 IP의 변환은 VNet 경계에서 일어난다. 그래서 NSG 규칙에는 자원의 사설 IP를 적는다
  • NAT 게이트웨이를 서브넷에 연결하면 그 서브넷의 자원은 공인 IP 없이 밖으로 나간다. 연결하면 로드 밸런서나 공인 IP 같은 다른 아웃바운드 방법보다 우선한다
  • NAT 게이트웨이의 Standard SKU는 영역 하나에 속하고, 새로 나온 StandardV2 SKU는 영역 중복이다. 06-1 2.4의 리전 NAT 게이트웨이와 같은 방향의 변화다
  • VNet 피어링은 다른 리전의 VNet도 잇는다. 다만 로드 밸런서 같은 일부 자원은 전역 피어링 너머에서 제약이 있다

4.5 네트워크 보안 그룹#

NSG 하나가 AWS 의 보안 그룹과 네트워크 ACL 의 성질을 함께 가진다.
  • NSG는 서브넷과 NIC 두 곳에 붙일 수 있다. 둘 다 붙어 있으면 둘 다 통과해야 한다
  • 같은 방향에 같은 우선순위의 규칙을 둘 수 없다
  • 규칙은 방향(인바운드·아웃바운드)별로 따로 평가하고, 프로토콜은 TCP·UDP·ICMP·Any, 포트는 단일 값이나 범위로 적는다

4.6 로드 밸런서와 Application Gateway#

Azure Load Balancer는 IP와 포트로 나누는 L4이고 type: LoadBalancer Service가 쓴다. Application Gateway는 URI와 Host 헤더로 나누는 L7이고 TLS 종료와 웹 방화벽(WAF)을 겸하며, Ingress 컨트롤러의 데이터패스가 된다. 06-1 4.1의 NLB와 ALB에 대응한다.

  • 구성 요소의 이름은 AWS와 대응된다 — 프런트엔드 IP, 백엔드 풀(대상 그룹), 상태 프로브(헬스 체크), 리스너와 규칙
  • SKU가 기능을 정한다. Basic SKU는 2025년 9월 30일에 종료됐다. 표준 SKU의 로드 밸런서는 기본이 닫혀 있다. NSG가 허용하지 않은 트래픽은 로드 밸런서를 지나지 못한다
  • 그래서 “Service에 외부 IP는 생겼는데 연결이 안 된다"면 NSG를 본다. AKS가 관리하는 NSG에는 규칙이 자동으로 들어가지만, 직접 가져온 서브넷의 NSG는 직접 연다

5. AKS — kubenet에서 Azure CNI로#

5.1 클러스터와 노드 리소스 그룹#

  • AKS는 컨트롤 플레인을 Azure가 운영하고 사용자는 노드만 관리한다. 원서는 컨트롤 플레인이 무료이고 노드와 주변 자원에만 요금이 든다고 적는다. 지금은 Free·Standard·Premium 세 티어이고 Standard부터 가동률 SLA가 붙는다
  • 클러스터를 만들면 리소스 그룹이 둘이다. 하나는 AKS 자원을 넣은 그룹, 다른 하나는 AKS가 자동으로 만든 노드 리소스 그룹(MC_<그룹>_<클러스터>_<리전>)이다
  • 노드 리소스 그룹에 VM 스케일 세트, 로드 밸런서, 공인 IP, NSG, 라우트 테이블이 들어 있다. AKS가 관리하는 자원이므로 직접 고치지 않는다. Service나 클러스터 설정으로 바꾼다
  • 기본 구성에서 표준 SKU 로드 밸런서가 함께 만들어지고, 노드의 아웃바운드도 이 로드 밸런서를 지난다. 원서 출력의 "outboundType": "loadBalancer"가 그 뜻이다
  • 프라이빗 클러스터는 API 서버에 공인 주소를 두지 않는다. VNet 안에서만 접근한다

5.2 오버레이와 플랫#

AKS 의 CNI 선택은 Pod 에 VNet 주소를 줄지 말지의 선택이다.

원서가 설명하는 kubenet의 규칙은 넷이다.

  • 노드는 VNet 서브넷에서 IP를 받는다
  • Pod는 노드와 논리적으로 다른 주소 공간에서 IP를 받는다
  • Pod가 밖으로 보내는 트래픽의 출발지는 노드의 IP로 바뀐다
  • VNet에서 라우팅되는 주소는 노드의 것뿐이다

이것이 오버레이 모델이다. Azure CNI(원서 시점의 것, 지금의 Node Subnet 방식)는 반대로 Pod에 VNet 서브넷의 주소를 준다. EKS의 VPC CNI, GKE의 VPC-native와 같은 쪽이다. Pod를 VNet에서 직접 볼 수 있는 대신 Pod 수만큼 VNet 주소가 든다. 노드당 최대 Pod 수만큼 주소를 미리 잡으므로 서브넷 계획이 먼저다.

5.3 지금의 CNI 선택지#

새 클러스터는 위쪽 줄에서 고른다. 아래쪽 줄은 옮겨 갈 대상이다.
  • 원서 실습의 클러스터는 kubenet이다. 지금 새로 만든다면 Azure CNI Overlay가 같은 자리에 있다. Pod에 별도 대역을 주고 나갈 때 노드 IP로 바꾸는 구조는 같고, 라우트 테이블을 사용자가 관리하지 않는다는 점이 다르다
  • 플랫이 필요한 경우는 정해져 있다. VNet이나 온프레미스의 다른 시스템이 Pod IP로 먼저 연결을 걸어야 할 때, 출발지 IP로 Pod를 구분해야 하는 방화벽이 있을 때다. 그렇지 않으면 오버레이로 주소를 아낀다

5.4 Application Gateway Ingress Controller#

  • AGIC는 클러스터 안에 Pod로 뜬다. Ingress와 Service의 변화를 감시하다가 Application Gateway의 설정을 ARM으로 갱신한다
  • 트래픽은 AGIC Pod를 지나지 않는다. 클러스터 밖의 Application Gateway가 받아서 Pod로 보낸다. 06-1 7.1의 AWS Load Balancer Controller와 같은 구조다
  • Application Gateway의 SKU는 Standard_v2와 WAF_v2만 지원한다. TLS 종료, URL 라우팅, 웹 방화벽을 Ingress로 설정한다
설치 방법차이
AKS 애드온Azure가 관리하고 자동으로 업데이트한다. 배포 값을 직접 고칠 수 없다
Helm직접 업데이트한다. 값을 고칠 수 있고, 게이트웨이를 다른 백엔드와 함께 쓰는 설정(Prohibited Target)을 지원한다

원서 이후에 Application Gateway for Containers가 나왔다. Gateway API와 Ingress를 받는, Kubernetes용으로 따로 만든 서비스다. kubenet 클러스터에서는 지원되지 않는다. AGIC도 종료 일정 없이 계속 지원되고, 옮겨 가는 안내서가 따로 있다. 원서 비교표의 Azure ingress 칸은 Nginx-Ingress인데, 커뮤니티 ingress-nginx는 05-2 7.1에서 본 대로 유지보수가 끝났다. AKS의 application routing 애드온이 제공하는 관리형 NGINX도 보안 패치 지원이 2026년 11월까지이고, 문서가 권하는 대체는 Gateway API 구현이다.

5.5 원서 실습 출력에서 읽을 것#

원서의 순서는 이렇다 — 이미지를 Azure Container Registry(ACR)에 올리고, 포털에서 클러스터를 만들고, CLI로 접속해 ACR을 연결하고, 앱을 배포한다.

az aks get-credentials --resource-group go-web --name go-web
az aks update --resource-group go-web --name go-web --attach-acr <ACR 이름>
kubectl get nodes -o wide

az aks update가 돌려주는 JSON에서 네트워크 부분만 보면 클러스터의 구조가 읽힌다.

"networkProfile": {
  "networkPlugin": "kubenet",
  "podCidr": "10.244.0.0/16",
  "serviceCidr": "10.0.0.0/16",
  "dnsServiceIp": "10.0.0.10",
  "loadBalancerSku": "Standard",
  "outboundType": "loadBalancer"
},
"nodeResourceGroup": "MC_go-web_go-web_westus",
"agentPoolProfiles": [{ "count": 3, "maxPods": 110, "vmSize": "Standard_DS2_v2", "vnetSubnetId": null }]
  • networkPlugin: kubenet과 podCidr가 5.2의 오버레이다. Pod 대역 10.244.0.0/16은 VNet의 주소가 아니다
  • serviceCidr와 dnsServiceIp는 ClusterIP 대역과 그 안의 CoreDNS 주소다. VNet·Pod 대역과 겹치지 않게 잡는다
  • vnetSubnetId: null은 VNet을 직접 지정하지 않았다는 뜻이다. AKS가 노드 리소스 그룹에 VNet을 만들었다
  • maxPods: 110은 노드당 최대 Pod 수다. 플랫 모델에서는 이 값만큼 서브넷 주소가 노드마다 예약된다
NAME     TYPE           CLUSTER-IP   EXTERNAL-IP     PORT(S)          AGE
go-web   LoadBalancer   10.0.3.75    203.0.113.117   8080:31728/TCP   21h
  • EXTERNAL-IP가 IP다. AWS는 호스트명을 줬다. Azure의 로드 밸런서는 공인 IP 자원을 프런트엔드로 쓰기 때문이다
  • 이 IP는 AKS가 Service를 위해 만든 공인 IP 자원이다. 주소를 유지하려면 공인 IP를 미리 만들어 annotation으로 Service에 지정한다
  • 원서는 ACR 접근에 서비스 주체(service principal)의 ID와 비밀값을 쓴다. 지금의 기본은 관리 ID이고 --attach-acr이 그 ID에 pull 권한을 준다. 비밀값을 보관할 필요가 없다

7. Discussion#

7.1 클러스터를 만들기 전에 정할 것#

정할 것나중에 바꾸기 어려운 이유
노드·Pod·Service의 주소 범위범위는 클러스터 생성 시 고정되고, 다른 네트워크와 겹치면 피어링과 VPN이 막힌다
Pod에 가상 네트워크 주소를 줄지CNI 모델을 바꾸는 것은 노드를 다시 만드는 작업이다
노드당 최대 Pod 수노드마다 예약하는 주소 수가 여기서 정해진다
API 서버를 공개할지사람과 CI의 접근 경로, 노드의 등록 경로가 함께 바뀐다
나가는 길바깥 서비스가 보는 출발지 IP가 정해진다. 허용 목록에 등록되는 주소다
L7 진입의 구현annotation과 기능이 구현마다 달라서 옮길 때 다시 적는다

1장에서 5장까지는 노드 안과 클러스터 안의 이야기였다. 6장은 그 클러스터가 놓이는 자리를 본다. kind에서 Docker 브리지가 하던 일을 VPC가 하고, MetalLB가 하던 일을 클라우드 로드 밸런서가 한다. 처리 주체가 바뀌어도 확인 순서는 같다 — 주소가 있는가, 경로가 있는가, 막는 규칙이 없는가, 백엔드가 준비됐는가.

핵심 메시지#

이름보다 범위를 본다
VPC와 서브넷이라는 이름은 같아도 묶이는 범위가 다르다. GCP의 VPC는 전역이고, GCP와 Azure의 서브넷은 리전이다.
GKE는 범위 세 개로 읽는다
노드는 서브넷의 기본 범위, Pod와 Service는 보조 범위에서 주소를 받는다. 노드마다 /24가 나간다.
NEG는 Pod를 백엔드로 등록한다
로드 밸런서가 NodePort를 거치지 않고 Pod IP로 보낸다. VPC-native여서 가능하다.
AKS의 CNI는 주소의 선택이다
오버레이는 VNet 주소를 아끼고 나갈 때 노드 IP로 바꾼다. 플랫은 Pod를 VNet에서 직접 보이게 한다.
기본값은 바뀐다
kubenet은 종료 일정이 있고, Azure의 새 VNet은 명시적 아웃바운드가 필요하다. 원서의 기본값을 그대로 믿지 않는다.
내장과 설치를 구분한다
같은 Ingress도 GKE에서는 내장 컨트롤러가, EKS와 AKS에서는 설치한 컨트롤러가 처리한다.
주소 범위는 처음에 정한다
노드·Pod·Service 범위와 CNI 모델은 클러스터를 만든 뒤에 바꾸기 어렵다.

원서 6장의 “Google Compute Cloud (GCP)”, “Azure”, “Conclusion” 절(275~309쪽)을 바탕으로 재구성했다. 원서 이후 바뀐 내용은 아래 공식 문서로 확인했다.

새 GKE 클러스터의 네트워크 모드는 VPC-native다.
"VPC-native is the default network mode for all new clusters in any available version"
[해석] VPC-native는 지원되는 모든 버전에서 새 클러스터의 기본 네트워크 모드다. — 3.2와 3.5의 근거다. 원서의 표 6-3(만드는 방법에 따라 routes-based)은 지금의 동작이 아니다.
→ Google Kubernetes Engine — VPC-native clusters
GKE는 Pod용 보조 범위에서 노드마다 /24를 떼어 준다.
"GKE allocates a /24 alias IP range (256 addresses) to each node for the Pods running on it."
[해석] GKE는 노드마다 그 노드의 Pod를 위한 /24 alias IP 범위(주소 256개)를 할당한다. — 3.2의 gke62 그림과 3.3의 sz62 그림에서 Pod 범위 쪽 계산의 근거다. 같은 문서에 이 256개로 Pod를 최대 110개까지 지원한다는 설명이 있다.
→ Google Kubernetes Engine — VPC-native clusters · IP address ranges
컨테이너 네이티브 로드 밸런싱은 Pod를 직접 백엔드로 삼는다.
"Container-native load balancing is the practice of load balancing directly to Pod endpoints in GKE."
[해석] 컨테이너 네이티브 로드 밸런싱은 GKE에서 Pod 엔드포인트로 직접 부하를 나누는 방식이다. — 3.4와 neg62 그림의 근거다. 인스턴스 그룹 방식의 kube-proxy 추가 홉과 readiness gate도 같은 문서에 있다.
→ Google Kubernetes Engine — Container-native load balancing
AKS의 오버레이 모델은 클러스터를 나가는 트래픽을 노드 IP로 바꾼다.
"Traffic that leaves the cluster is Source Network Address Translated (SNAT'd) to the node's IP address."
[해석] 클러스터를 나가는 트래픽은 노드의 IP 주소로 SNAT된다. — 5.2와 aks62 그림의 근거다. 플랫 모델에서 목적지가 보는 출발지가 IPAM 방식에 따라 다르다는 설명도 같은 절에 있다.
→ Azure Kubernetes Service — CNI networking overview · Networking models
kubenet은 종료 일정이 정해져 있다.
"Retires on March 31, 2028; migrate to Azure CNI Overlay before the retirement date"
[해석] 2028년 3월 31일에 종료된다. 그 전에 Azure CNI Overlay로 옮긴다. — 5.3의 opt62 그림의 근거다. Azure CNI Overlay를 대부분의 경우에 쓰라는 권장, Pod Subnet이 플랫의 권장이고 Node Subnet이 레거시라는 구분, kubenet의 Windows 노드 풀 미지원, Application Gateway for Containers가 kubenet에서 지원되지 않는다는 표도 이 문서에 있다.
→ Azure Kubernetes Service — CNI networking overview · Use case comparison
Azure의 새 VNet은 기본으로 인터넷에 나가지 않는다.
"For the API released after March 31, 2026, new virtual networks default to using private subnets."
[해석] 2026년 3월 31일 이후에 나온 API에서는 새 가상 네트워크가 프라이빗 서브넷을 기본으로 쓴다. — 4.3의 근거다. 원서가 Azure의 특징으로 든 "기본 인터넷 경로"는 새 VNet에서는 명시적 아웃바운드 수단을 요구하는 쪽으로 바뀌었다. 기존 VNet은 바뀌지 않는다.
→ Azure Virtual Network — Default outbound access
추가 근거 — GCP의 전역·리전 자원과 서브넷 모드는 VPC networks, 방화벽 규칙은 VPC firewall rules, GKE Dataplane V2는 GKE Dataplane V2, Azure의 시스템 경로와 우선순위는 Virtual network traffic routing, NSG의 기본 규칙은 Network security groups, AGIC는 Application Gateway Ingress Controller에 있다.

원서 이후에 생긴 것 — GKE Ingress의 유지보수 모드와 Gateway 권장은 GKE — Ingress, 네트워크 격리와 DNS 기반 엔드포인트는 GKE — Network isolation, Application Gateway for Containers는 Application Gateway for Containers — Overview, 관리형 NGINX의 지원 종료는 AKS — Application routing add-on, AKS 티어는 AKS — Pricing tiers, NAT 게이트웨이 SKU는 Azure NAT Gateway — Overview에서 2026년 11월 14일에 확인했다.

원서에서 고쳐 읽은 곳 — VPC-native의 장점 목록 중 "Pod IP address ranges are dependent on custom static routes"는 반대다. VPC-native의 Pod 범위는 정적 경로에 의존하지 않는다. Azure 실습은 ACR 주소가 azurecr.io와 azure.io로, 클러스터 이름이 go-web과 tjbakstest로 섞여 있고, 본문은 Deployment와 Service를 만든다고 하지만 예제 6-2는 Pod 하나의 매니페스트다. 5.5의 명령은 한 가지 이름으로 맞췄고 공인 IP는 문서용 주소로 바꿨다.
