1. Overview#

유저 공간 = 파일과 도구 · 커널 = 핀 · 프로그램 · 맵 · XDP 연결 · 번호 클릭 → 해당 절로 이동

02편에서는 BCC의 BPF()와 attach_kprobe() 몇 줄로 프로그램을 커널에 올렸습니다. 컴파일과 로드, attach가 그 안에서 한꺼번에 일어났기 때문에, 커널에 실제로 무엇이 올라갔는지는 보이지 않았습니다. 그렇다면 C 코드 한 줄은 커널에서 어떤 모습이 될까요?

이번 글에서는 같은 과정을 clang과 bpftool로 한 단계씩 나눠 실행하고, 단계마다 결과물을 직접 열어 봅니다.

  • 무엇으로 바뀌나 — C 소스, 오브젝트 파일, 바이트코드, 기계어
  • 커널에 무엇이 남나 — 프로그램, 맵, 핀, attach
  • 어떻게 정리하나 — detach와 unload

예제는 네트워크 장치로 패킷이 들어올 때마다 실행되는 XDP 프로그램입니다. 실습은 02편과 같은 GitHub Actions의 x86-64 러너에서 했습니다.

2. eBPF Virtual Machine — 바이트코드가 도는 가상 CPU#

eBPF 프로그램은 eBPF 바이트코드 명령어의 묶음입니다. 어셈블리처럼 바이트코드를 직접 쓸 수도 있지만, 대부분은 C로 쓰고 컴파일러가 바이트코드로 바꿉니다. 2026년 기준 — Rust 컴파일러도 eBPF 바이트코드를 출력할 수 있어서, Aya 같은 Rust 라이브러리로 쓰는 경우가 늘었습니다.

2.1 인터프리터와 JIT#

바이트코드는 ’eBPF 가상 머신’이라는 소프트웨어 CPU를 기준으로 쓰인 명령어입니다. 실제 CPU가 바로 실행할 수 없으므로 한 번 더 바꿔야 합니다.

초기 eBPF는 인터프리터였고, 지금은 대부분 JIT입니다.

JIT은 빠르기도 하고, 인터프리터가 Spectre 계열 CPU 취약점의 공격 경로가 될 수 있기 때문입니다. JIT은 커널 설정 CONFIG_BPF_JIT으로 넣고, sysctl net.core.bpf_jit_enable로 켜고 끕니다.

2.2 레지스터#

가상 머신의 레지스터는 r0부터 r10까지 11개입니다. 실제 CPU의 레지스터가 아니라 소프트웨어로 만든 칸이고, 커널 헤더 include/uapi/linux/bpf.h에 BPF_REG_0부터 BPF_REG_10까지 정의되어 있습니다.

  • 시작과 끝 — 프로그램이 시작될 때 r1에는 ctx가 들어 있습니다. 02편 4.3의 hello(ctx)가 받은 그 값입니다. 끝날 때는 r0의 값이 반환값이 됩니다.
  • 헬퍼 호출 — 인자를 r1~r5에 넣고 부르면, 호출 뒤에는 r1~r5를 다시 읽을 수 없습니다. 호출 뒤에도 써야 하는 값은 r6~r9에 둡니다.

레지스터의 수와 역할을 x86-64, arm64 같은 64비트 CPU의 함수 호출 규칙에 맞춰 정했기 때문에, JIT은 eBPF 레지스터를 실제 레지스터로 거의 1대1로 옮깁니다(4.4).

2.3 명령어#

명령어 하나는 구조체 bpf_insn 하나이고, 크기는 8바이트로 고정입니다. opcode가 정하는 연산은 대부분 다음 네 갈래에 속합니다.

  • 레지스터에 값 넣기 — 상수, 메모리의 값, 다른 레지스터의 값
  • 레지스터의 값을 메모리에 쓰기
  • 산술 — 레지스터 값에 더하기 등
  • 조건 점프 — 조건이 맞으면 다른 명령으로 이동

64비트 상수를 넣는 명령은 8바이트 안에 상수를 다 담을 수 없어서, 8바이트를 하나 더 붙인 16바이트 ‘와이드 명령어’를 씁니다. 3.4의 바이트코드에 두 번 나옵니다. 2026년 기준 — eBPF 명령어 집합은 2024년 IETF RFC 9669로 표준화되었습니다.

3. XDP Hello World — 소스에서 오브젝트 파일까지#

3.1 프로그램#

패킷이 들어올 때마다 Hello World와 카운터 값을 trace_pipe에 쓰고, 패킷은 그대로 통과시키는 프로그램입니다.

#include <linux/bpf.h>
#include <bpf/bpf_helpers.h>

// 전역 변수 — 커널에서는 hello.bss 맵이 된다
int counter = 0;

// 오브젝트 파일의 xdp 섹션 = XDP 프로그램
SEC("xdp")
int hello(struct xdp_md *ctx)
{
    bpf_printk("Hello World %d", counter);
    counter++;
    // XDP_PASS(2) — 패킷을 커널로 그대로 넘긴다
    return XDP_PASS;
}

char LICENSE[] SEC("license") = "Dual BSD/GPL";
  • counter — 전역 변수입니다. 실행할 때마다 1씩 늘고, 다음 실행까지 값이 남습니다(5.3).
  • SEC("xdp") — 바로 뒤의 함수를 오브젝트 파일의 xdp 섹션에 넣으라는 표시입니다. 매크로를 펼치면 컴파일러 속성 __attribute__((section("xdp"), used))이고, 섹션 이름이 곧 프로그램 종류가 됩니다.
  • 함수 이름 — eBPF에서는 함수 이름이 프로그램 이름입니다. 이 프로그램의 이름은 hello입니다.
  • XDP_PASS — 패킷을 커널 네트워크 스택으로 넘기라는 판정입니다(5.5).
  • LICENSE — 일부 헬퍼는 GPL과 호환되는 라이선스를 선언한 프로그램만 쓸 수 있고, 검증기가 이 값을 확인합니다.

bpf_printk()는 libbpf 쪽의 이름이고, 02편 BCC의 bpf_trace_printk()와 같은 커널 헬퍼를 부릅니다. 파일 이름 끝의 .bpf.c는 같은 폴더의 유저 공간 C 코드와 구분하려는 관례입니다.

XDP는 네트워크 드라이버가 패킷을 받자마자 실행되는 자리입니다. 커널이 패킷을 정리하기 전이라 넷필터보다 앞에 있고, 버리거나 다른 곳으로 보내는 판단을 가장 먼저 내릴 수 있습니다. kprobe가 커널 함수에, tracepoint가 정해진 지점에 붙는다면, XDP는 네트워크 장치에 붙습니다.

3.2 clang 컴파일#

clang -target bpf \
      -I/usr/include/$(uname -m)-linux-gnu \
      -g -O2 -c hello.bpf.c -o hello.bpf.o
  • -target bpf — 내 컴퓨터 CPU의 기계어가 아니라 eBPF 바이트코드를 만듭니다. 02편에서는 BPF(text=...)가 이 일을 대신했습니다.
  • -I — asm/types.h처럼 아키텍처마다 다른 헤더의 위치입니다.
  • -g — 디버그 정보와 BTF(타입 정보)를 넣습니다. 없어도 프로그램은 돌지만, 바이트코드 옆에 소스가 보이지 않고 맵 내용이 바이트로만 보입니다(5.3).
file hello.bpf.o
$ file hello.bpf.o
hello.bpf.o: ELF 64-bit LSB relocatable, eBPF, version 1 (SYSV), with debug_info, not stripped
GitHub Actions 러너 출력 · x86-64 · Ubuntu 24.04 · 커널 7.0 · 실행 기록

결과물은 ELF 형식의 오브젝트 파일이고, 안에 든 코드는 x86-64가 아니라 eBPF입니다.

3.3 오브젝트 파일의 섹션#

ELF 파일은 ‘섹션’이라는 칸으로 나뉩니다. llvm-objdump -h로 섹션 목록을 보면 소스의 각 부분이 서로 다른 섹션에 들어 있습니다.

llvm-objdump -h hello.bpf.o
$ llvm-objdump -h hello.bpf.o

  2 .text                  00000000 0000000000000000 TEXT
  3 xdp                    00000060 0000000000000000 TEXT
  4 .relxdp                00000020 0000000000000000
  5 .bss                   00000004 0000000000000000 BSS
  6 .rodata                0000000f 0000000000000000 DATA
  7 license                0000000d 0000000000000000 DATA
  8 .debug_abbrev          000000f7 0000000000000000 DEBUG
…
 16 .BTF                   0000032b 0000000000000000
…
GitHub Actions 러너 출력 · x86-64 · Ubuntu 24.04 · 커널 7.0 · 실행 기록
  • xdp 섹션의 크기 0x60은 96바이트, 곧 명령어 12개 분량입니다.
  • .rodata에는 소스에 따로 선언하지 않은 데이터가 들어 있습니다. bpf_printk()에 넘긴 형식 문자열 "Hello World %d"가 15바이트(0xf) 상수로 저장된 것입니다.
  • .relxdp는 xdp 섹션 안에서 나중에 채워야 할 자리의 목록입니다. 3.4의 빈칸 두 곳이 여기에 적혀 있습니다.

3.4 바이트코드 읽기#

llvm-objdump -S는 xdp 섹션의 바이트코드를 소스 줄과 함께 보여 줍니다.

llvm-objdump -S hello.bpf.o

  • 왼쪽 번호 — 명령어의 위치를 8바이트 단위로 센 값입니다. 0번과 3번이 16바이트 와이드 명령어라서 1번과 4번이 없습니다.
  • 0x0 ll — 맵의 주소가 들어갈 빈칸입니다. 컴파일할 때는 맵이 아직 없으므로 0으로 두고, 로드할 때 채웁니다(4.3).
  • call 0x6 — 커널 헤더에 6번으로 정해진 헬퍼 bpf_trace_printk를 부릅니다.

바이트코드를 한 줄씩 외울 필요는 없습니다. 다만 레지스터의 역할을 알면 C 한 줄이 명령어 몇 개로 바뀌는지 따라갈 수 있습니다.

4. bpftool — 커널에 올리고 들여다보기#

4.1 로드와 핀#

sudo bpftool prog load
$ bpftool prog load hello.bpf.o /sys/fs/bpf/hello
$ ls /sys/fs/bpf
hello
GitHub Actions 러너 출력 · x86-64 · Ubuntu 24.04 · 커널 7.0 · 실행 기록

명령 한 줄이지만, 안에서는 bpf() 시스템 콜이 32번 불립니다. 23번은 이 커널이 어떤 기능을 지원하는지 확인하는 시험 호출이고, 나머지 9번이 실제 로드입니다. 러너에서 strace로 기록한 순서는 다음과 같습니다.

  • 맵이 먼저 — 프로그램보다 맵을 먼저 만듭니다. 3.4의 빈칸에 채울 맵 번호가 있어야 프로그램을 올릴 수 있기 때문입니다.
  • 로드 — BPF_PROG_LOAD에서 검증과 JIT이 일어납니다. 프로그램 종류(XDP)는 섹션 이름 xdp에서 정해졌습니다.
  • 핀 — 커널의 프로그램을 /sys/fs/bpf 아래의 파일 이름에 고정합니다. /sys/fs/bpf는 BPF 전용 파일 시스템(bpffs)이고, 핀은 그 안의 의사 파일입니다.

핀이 필요한 이유는 프로그램의 수명에 있습니다.

  • 02편의 Python 스크립트는 프로그램의 파일 디스크립터를 쥐고 있다가, 스크립트가 끝나면 프로그램도 함께 정리했습니다.
  • bpftool은 명령 하나를 처리하고 바로 끝나는 도구입니다. 핀으로 붙잡아 두지 않으면 명령이 끝나는 순간 프로그램도 사라지므로, bpftool prog load에는 핀 경로가 반드시 필요합니다.

2026년 기준 — bpftool prog load에 autoattach를 붙이면, kprobe나 tracepoint처럼 붙일 자리를 섹션 이름에서 알 수 있는 종류는 로드와 attach를 한 번에 합니다. XDP는 장치를 따로 정해야 하므로 해당하지 않습니다.

  • id — 커널이 올릴 때마다 새로 매기는 번호입니다.
  • tag — 명령어로 계산한 해시입니다. 같은 바이트코드면 언제 올려도 같습니다. 실습에서 -g 없이 컴파일한 것도 tag가 같았습니다. 디버그 정보는 명령어가 아니기 때문입니다.
  • bytes_xlated · bytes_jited — 검증을 거친 바이트코드와 JIT 기계어의 크기입니다(4.3, 4.4).
  • map_ids — 소스에 맵을 선언하지 않았는데 맵이 두 개 있습니다. 전역 변수와 문자열 상수가 맵이 된 것입니다(5.3).
  • btf_id — -g로 넣은 타입 정보 블록의 번호입니다.

bpftool은 프로그램을 id, 이름, tag, 핀 경로 중 어느 것으로든 가리킬 수 있습니다. 이름과 tag는 다른 프로그램과 겹칠 수 있지만, id와 핀 경로는 겹치지 않습니다.

4.3 검증 뒤의 바이트코드#

sudo bpftool prog dump xlated name hello
$ bpftool prog dump xlated name hello

   3: (18) r1 = map[id:15][0]+0

   6: (85) call bpf_trace_printk#-137776
; counter++;
   7: (61) r1 = *(u32 *)(r6 +0)
   8: (07) r1 += 1
   9: (63) *(u32 *)(r6 +0) = r1
; return XDP_PASS;

  11: (95) exit
GitHub Actions 러너 출력 · x86-64 · Ubuntu 24.04 · 커널 7.0 · 실행 기록
  • 맵 주소 — 빈칸이던 0x0 ll이 map[id:14], map[id:15]로 채워졌습니다. 로드할 때 libbpf가 맵을 먼저 만들고, .relxdp에 적힌 자리에 그 맵을 가리키는 값을 넣었습니다.
  • 헬퍼 — call 0x6이 call bpf_trace_printk로 보입니다.
  • 나머지 — 명령어의 개수와 위치, 연산은 그대로입니다.

이 예제는 거의 그대로 통과했지만, 검증기는 안전을 위해 명령어를 고치거나 더하기도 합니다. 그래서 오브젝트 파일의 바이트코드와 xlated는 다를 수 있습니다.

  • 크기 — 바이트코드 96바이트가 기계어 65바이트가 되었습니다. 바이트코드는 명령어마다 8바이트로 고정이지만, x86-64 기계어는 명령어마다 길이가 다릅니다.
  • 1대1 대응 — r2 = 15가 movl $15, %esi가 되는 식으로 소스 줄마다 대응합니다. eBPF의 r1·r2·r3가 x86-64의 함수 인자 레지스터 rdi·rsi·rdx로 옮겨졌기 때문에, 헬퍼 호출이 callq 한 줄로 끝납니다.
  • 맵 주소 — movabsq로 넣는 큰 숫자가 맵 값이 놓인 커널 메모리 주소입니다. xlated의 map[id:14]가 실제 주소로 바뀐 것입니다.
  • 앞뒤 — pushq와 popq, leave는 스택을 준비하고 정리하는 부분입니다.

같은 프로그램을 다른 러너에서 올렸을 때는 기계어가 68바이트였고, 마지막 retq 대신 jmp로 커널의 공용 반환 코드에 뛰었습니다. CPU 취약점에 대응하는 방식이 커널 빌드마다 다르기 때문입니다. 바이트코드와 tag는 두 러너에서 같았습니다. 오브젝트 파일 하나를 여러 머신에 쓸 수 있는 이유가 이것입니다.

dump jited를 쓰려면 bpftool이 LLVM이나 libbfd의 디스어셈블러와 함께 빌드되어 있어야 합니다. 실습에서는 bpftool v7.5.0을 LLVM과 함께 빌드했습니다.

5. Attach and Detach — 장치의 XDP 자리#

5.1 XDP Attach#

XDP 프로그램은 네트워크 장치에 붙습니다. 러너의 바깥 인터페이스에 붙이면 러너 자체의 통신에 영향을 줄 수 있으므로, veth 한 쌍을 만들어 실습했습니다.

러너의 연결은 그대로 · 실습 패킷만 veth 한 쌍으로 · 응답 = 같은 veth 로 복귀
ip netns add lab
ip link add veth0 type veth peer name veth1 netns lab
ip addr add 10.10.0.1/24 dev veth0 && ip link set veth0 up
ip -n lab addr add 10.10.0.2/24 dev veth1 && ip -n lab link set veth1 up
sudo bpftool net attach xdp
$ bpftool net attach xdp id 90 dev veth0

$ bpftool net list

tc:

enp39s0(2) clsact/egress tc_egress_traffic id 79

flow_dissector:

netfilter:

  • net attach xdp — 프로그램 종류(xdp)와 붙일 자리(장치)가 맞아야 붙습니다. 장치는 소스에 적을 수 없으므로 이때 정합니다.
  • driver — 드라이버 안에서 실행되는 네이티브 모드로 붙었다는 뜻입니다. 드라이버가 XDP를 지원하지 않으면 커널 쪽에서 흉내 내는 generic 모드를 씁니다.
  • tc 줄 — 러너의 바깥 인터페이스에 원래 붙어 있던 eBPF 프로그램입니다. 클라우드 머신에서는 eBPF가 이미 쓰이고 있습니다.
  • ip link — 장치 쪽에서도 prog/xdp id 90이 보입니다.

5.5 반환값과 패킷의 판정#

XDP 프로그램의 반환값은 그 패킷을 어떻게 할지에 대한 판정입니다.

반환값 = 패킷의 판정 · 통과시키려면 XDP_PASS(2)

C에서는 보통 0이 성공이지만, XDP에서 0은 XDP_ABORTED입니다. 0을 돌려주는 프로그램을 veth0에 붙이고 ping을 보냈습니다.

// 0 = XDP_ABORTED — 성공이 아니라 패킷 버림
SEC("xdp")
int abort_all(struct xdp_md *ctx)
{
    return 0;
}

$ ip netns exec lab ping -c 3 -W 1 10.10.0.1

$ bpftool net detach xdp dev veth0
$ ip netns exec lab ping -c 3 -W 1 10.10.0.1

같은 프로그램을 SSH로 접속한 머신의 바깥 인터페이스에 붙이면 SSH 패킷도 버려져서 접속이 끊깁니다. 다시 들어갈 방법이 없으면 재부팅해야 하므로, veth나 컨테이너 안에서 시험합니다.

6. BPF to BPF Calls — 함수가 따로 남는 호출#

02편 4.2에서 커널 4.16부터는 인라인하지 않은 함수 호출이 가능하다고 했습니다. BCC는 이 기능을 쓰지 않았지만, clang으로 직접 컴파일하면 바이트코드에서 그 모습을 볼 수 있습니다.

// 인라인을 막아 바이트코드에 함수가 따로 남게 한다
// args[1] = sys_enter 의 두 번째 인자 = 시스템 콜 번호
static __attribute((noinline)) int get_opcode(struct bpf_raw_tracepoint_args *ctx)
{
    return ctx->args[1];
}

SEC("raw_tp")
int hello(struct bpf_raw_tracepoint_args *ctx)
{
    int opcode = get_opcode(ctx);
    bpf_printk("Syscall: %d", opcode);
    return 0;
}
  • noinline — 이렇게 작은 함수는 컴파일러가 보통 인라인합니다. 함수가 바이트코드에 따로 남도록 일부러 막았고, 실제 코드에서는 컴파일러에 맡기는 편이 낫습니다.
  • SEC("raw_tp") — 02편 4.3과 같은 raw tracepoint 종류입니다. 이번에는 올려서 바이트코드만 봅니다.

  • opcode — 0번 명령의 85는 헬퍼 호출과 같은 opcode입니다. 헬퍼는 번호로, BPF 함수는 상대 위치(pc+7)로 가리키는 점이 다릅니다.
  • args[1] — r1 +8은 ctx 구조체에서 8바이트 떨어진 칸, 곧 두 번째 인자인 시스템 콜 번호입니다.
  • 스택 — 호출할 때마다 새 스택 프레임이 생기므로 호출을 깊이 겹칠 수 없습니다. 호출 깊이는 8단계까지이고, 꼬리 호출과 섞어 쓰면 함수마다 쓸 수 있는 스택이 512바이트에서 256바이트로 줄어듭니다.

7. Discussion#

이번 글에서는 BCC가 한 줄로 처리하던 과정을 clang과 bpftool로 단계마다 나눠 보았습니다. C 소스는 clang이 바이트코드로 바꿔 오브젝트 파일의 섹션에 담고, bpftool이 커널에 올리면 맵이 만들어지고 빈칸이 채워진 뒤 검증과 JIT을 거쳐 기계어가 됩니다. 프로그램은 핀으로 커널에 남고, 장치에 attach하면 패킷마다 실행되며, 핀을 지우면 unload됩니다.

같은 바이트코드라도 커널 빌드에 따라 기계어는 달랐습니다. 바이트코드는 가상 머신을 기준으로 쓰여 있으므로 오브젝트 파일 하나를 여러 머신에서 쓸 수 있고, 머신마다 다른 부분은 JIT이 맡습니다.

핵심 메시지#

바이트코드는 가상 CPU 기준이다
레지스터 11개와 8바이트 명령어로 쓰인 바이트코드를, JIT이 실제 CPU의 기계어로 거의 1대1로 옮깁니다.
섹션 이름이 종류를 정한다
SEC("xdp") 함수는 오브젝트 파일의 xdp 섹션에 들어가고, bpftool은 그 이름으로 프로그램 종류를 정합니다.
전역 변수는 맵이다
.bss와 .rodata 섹션이 칸 하나짜리 배열 맵이 되어, 실행과 실행 사이에 값이 남습니다.
빈칸은 로드할 때 채운다
오브젝트 파일의 맵 주소는 0입니다. 로드할 때 맵이 만들어지고 그 번호가 명령어에 채워집니다.
핀이 수명을 붙잡는다
장치에서 detach해도 프로그램은 핀이 붙잡고 있습니다. 핀 파일을 지워야 프로그램과 맵이 정리됩니다.
XDP에서 0은 버림이다
반환값이 패킷의 운명입니다. C의 관례와 달리 0은 성공이 아니라 XDP_ABORTED입니다.

"After an in-kernel function call, R1 - R5 are reset to unreadable and R0 has a return value of the function. Since R6 - R9 are callee saved, their state is preserved across the call."
[해석] "커널 함수를 호출한 뒤 R1~R5는 읽을 수 없는 상태가 되고 R0에 함수의 반환값이 들어갑니다. R6~R9는 호출된 쪽이 보존하므로 호출 전후로 값이 유지됩니다" — 2.2의 근거입니다
→ kernel.org — Classic BPF vs eBPF
명령어 집합 문서는 64비트 상수를 담는 인코딩을 따로 둡니다.
"the wide instruction encoding, which appends a second 64 bits after the basic instruction for a total of 128 bits."
[해석] "와이드 명령어 인코딩은 기본 명령어 뒤에 64비트를 하나 더 붙여 모두 128비트가 됩니다" — 2.3과 3.4의 근거입니다
→ kernel.org — BPF Instruction Set Architecture
bpftool 매뉴얼은 로드와 핀을 한 명령으로 묶고, 최근에는 attach까지 넣을 수 있게 했습니다.
"If autoattach is specified program will be attached before pin."
[해석] "autoattach를 지정하면 핀을 만들기 전에 프로그램을 attach합니다" — 4.1의 근거입니다
→ bpftool-prog(8)
eBPF Docs는 전역 변수를 맵으로 바꾸는 방식을 이렇게 설명합니다.
"The loader will take these sections and turn them into array maps with a single key ( max_entries set to 1) and its value the same size as the binary blob in the ELF section."
[해석] "로더는 이 섹션들을 가져와, 키가 하나뿐이고(max_entries = 1) 값의 크기가 ELF 섹션의 데이터 크기와 같은 배열 맵으로 만듭니다" — 5.3의 근거입니다
→ eBPF Docs — BPF_MAP_TYPE_ARRAY, Global data
XDP 반환값 중 0에 해당하는 것은 오류 처리용입니다.
"XDP_ABORTED - Signals that a unrecoverable error has taken place."
[해석] "XDP_ABORTED는 복구할 수 없는 오류가 일어났다는 신호입니다" — 5.5의 근거입니다
→ eBPF Docs — BPF_PROG_TYPE_XDP
BPF to BPF 호출의 깊이에는 한도가 있습니다.
"Functions are limited to a maximum call depth of 8, so recursion of any meaningful depth is not possible."
[해석] "함수 호출 깊이는 최대 8로 제한되므로, 의미 있는 깊이의 재귀는 불가능합니다" — 6의 근거입니다
→ eBPF Docs — Functions
추가 근거 — 명령어 집합 표준은 RFC 9669 — BPF Instruction Set Architecture, JIT 설정은 kernel.org — /proc/sys/net (bpf_jit_enable), Rust로 eBPF 프로그램을 쓰는 라이브러리는 Aya, 실습 코드와 출력 원본은 GitHub — BokJaeSung/Cilium-and-eBPF ch03.
