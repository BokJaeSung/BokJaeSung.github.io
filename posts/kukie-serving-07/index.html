1. Overview#

주황 점선은 커넥터가 먼저 여는 연결이다. 번호와 아래 띠를 누르면 해당 절로, 칸을 누르면 설명으로 이동한다

이 글의 범위

  • 고객 GPU 클러스터의 모델을 Kukie 공개 주소 하나와 개인 키로 부르게 하는 경로
  • 역할 분담: Kotlin(member)은 계정·권한·키·사용량, Go 게이트웨이는 중계, 커넥터는 고객 클러스터 안에서 바깥으로 연결
  • 경계: Kukie 쪽은 입구·게이트웨이·member 이고, 고객 쪽은 커넥터·카운터·vLLM 이다. 추론은 고객 GPU 에서 돈다
  • 카운터의 어드미션은 Serving.06 에서 다루고, 여기서는 커넥터 뒤의 문 하나로만 본다

본문을 대하는 방식

  • 질문과 답은 게이트웨이를 지난다. 그래서 “데이터가 고객 환경 밖으로 나가지 않는다"고 안내하지 않는다
  • 게이트웨이는 본문을 저장하지 않는다. 사용량 기록에는 키 ID·모델·시각·상태·확인된 토큰 수만 남는다

2. Background — 다시 연 외부 API#

Serving.02 에서 우리 GPU 로 모델을 올려 파는 외부 API 를 접었다. 품질과 비용에서 상용 API 와 겨룰 수 없다는 판단이었다. 그 뒤 만든 것은 고객 클러스터에 까는 애드온이다.

애드온이 고객 GPU 에 모델을 띄우고 나면, 그 모델을 고객 회사의 개발자에게 API 로 열어 줄 방법이 필요하다. 2026-11-05 에 이 일을 Kukie 기존 회원과 키로 하기로 정했다(DURO-193).

  • 별도 회원 DB 와 고객별 로그인 사이트는 만들지 않는다
  • 키를 가진 사람은 Kukie 회원이고, 어느 클러스터를 쓸지는 그 클러스터 관리자가 허용한다
  • 사용자 앱은 OpenAI 호환 주소 하나만 안다. 목적지는 키가 정한다

3. Path Changes — 중계 경로의 변경#

3.1 Kotlin 직접 중계#

첫 구현은 11월 5일 member 안에 넣은 중계였다(DURO-196). 관리자가 고객 카운터의 공개 HTTPS 주소와 카운터 서비스 키를 등록하면, member 가 개인 키를 확인하고 그 주소로 요청을 넘긴다.

  • 허용 호스트 목록, 공개 IP 검사, TLS 이름 검증, redirect 금지로 엉뚱한 곳으로 가는 요청을 막았다
  • 카운터 서비스 키는 AES-GCM 으로 암호화해 저장했다
  • 로컬 종단 시험(가짜 카운터 2개)은 통과했다

문제는 고객 쪽 준비물이다. 고객이 카운터를 공개 주소로 내놓고 인증서와 인바운드 허용까지 준비해야 했다. 사설망에 있는 클러스터는 쓸 수 없다.

3.2 Go 게이트웨이 분리#

다음 날인 11월 6일, 중계를 member 에서 떼어 Go 서버(kukie-serving-gateway)로 옮기고 고객 쪽에는 커넥터를 두는 구조로 바꿨다.

  • 부하와 장애 범위를 나눈다. 관리 API 는 짧은 요청이고, LLM 중계는 수십 초씩 열려 있는 스트림이다. 같은 프로세스에 두면 한쪽 부하가 다른 쪽을 흔든다
  • 고객이 포트를 열지 않는다. 커넥터가 고객 클러스터 안에서 Kukie 로 연결을 먼저 연다. 공개 주소, 인증서, 인바운드 허용이 필요 없다
  • 카운터를 거친다. 모든 요청이 고객 카운터의 어드미션을 지난다

“Go 가 Kotlin 보다 빠르다"는 이유로 정한 것은 아니다. 나눈 이유는 책임과 부하의 모양이 다르다는 점이다. 같은 날 dev 에 실제로 배포했고, 기존 dev 입구(CloudFront → ALB → web Caddy) 뒤에 게이트웨이를 붙였다(DURO-206).

3.3 보류한 경로#

  • EKS Service 프록시 자동 연결(DURO-199). Kukie 가 이미 FULL 권한으로 붙어 있는 EKS 라면, 쿠버네티스 API 서버의 Service 프록시로 vLLM 에 바로 닿을 수 있다. 구현과 로컬 시험(872개 테스트)까지 했지만 보류했다. 카운터를 건너뛰고, EKS 와 API 서버 접근이라는 전제가 붙는다
  • 카운터 공개 입구. 카운터 앞의 ALB Ingress(IdleTimeout 660초)는 우리 클러스터용 키 포털이 쓰려던 경로다. 포털 확장(DURO-191)을 보류하면서 함께 멈췄다

4. Permission and Keys — 팀 권한과 API 이용 권한#

두 권한은 서로를 바꾸지 않는다. 화면 칸을 누르면 설명이 열린다

두 권한의 분리

  • 팀 권한은 기존 Kukie 팀 기능의 권한이다. 클러스터의 팀 ADMIN 이 그 클러스터의 키 관리자도 맡는다
  • API 이용 권한(ServingAccess)은 이메일 초대와 수락으로 생긴다. 수락해도 팀에 들어가지 않는다
  • 관리자가 팀 권한을 잃으면 키 관리도 못 한다. 별도로 받은 API 이용 권한은 따로 처리하고, 한쪽이 다른 쪽을 바꾸지 않는다
  • 권한을 회수하면 그 뒤의 새 요청은 막힌다. 이미 인증을 지난 스트림은 끝까지 간다

키와 그 키가 갈 곳

// kukie-server serving/infrastructure/ServingKeyTokens.kt (발췌)
fun generate(): String = "kk_" + encoder.encodeToString(ByteArray(32).also(random::nextBytes))
fun hash(token: String): String = sha256Hex(token)
  • 키 원문은 발급 응답에 한 번만 나온다. DB 에는 SHA-256 해시와 앞 12글자만 남는다
  • 이용 권한 하나에 키는 최대 5개, 유효 기간은 1~365일(기본 90일)이다
  • 키 → 이용 권한 → 클러스터가 한 줄로 이어진다. A 용 키는 B 로 갈 수 없다
  • 키로 부를 수 있는 모델은 커넥터 자격을 발급할 때 정한 모델 목록에서 관리자가 끈 모델을 뺀 것이다

사용량

  • 요청 한 건이 한 행이다: 키·이용 권한·클러스터·사용자 ID, 모델, 시작·끝 시각, 상태, 결과(COMPLETED, FAILED, TIMEOUT, CANCELLED …), 확인된 입력·출력 토큰
  • 거절은 행을 만들지 않고 키·모델·이유별로 분 단위 개수만 센다
  • 토큰을 확인하지 못한 요청은 0 으로 채우지 않고 “누락"으로 표시한다. 과금이나 토큰 한도에는 쓰지 않는 통계다

5. Gateway — Go 중계 코어#

5.1 요청 한 건의 순서#

공개 경로는 둘뿐이다. GET /serving/v1/models 와 POST /serving/v1/chat/completions 이다. dev 에서는 web Caddy 가 /member/serving/v1/* 의 /member 를 떼고 게이트웨이로 넘긴다.

Authorize · Begin · Finish 는 이름만 남은 인터페이스다. 구현(internal/local)은 네트워크를 쓰지 않는다
  • 순서의 기준은 비싼 일을 늦게다. ①~④ 는 메모리 안에서 끝나고, 거절은 여기서 대부분 난다
  • ④ 의 예약이 ⑤ 사용량 메모보다 앞에 있는 것은 7.3절의 측정에서 고친 결과다
  • ⑦ 은 응답을 모으지 않는다. 32 KiB 를 읽을 때마다 바로 쓰고 flush 한다. 그 바이트를 지나가며 usage 필드만 읽는다
  • 스트림이 중간에 끊기면 핸들러를 중단시킨다. 잘린 본문을 정상 응답으로 받는 일을 막는다

한도는 코드에 고정값으로 있다: 요청 본문 1 MiB, 응답 64 MiB, 요청 전체 300초, 동시 32.

5.2 키 목록과 사용량 묶음#

처음에는 ②·⑤ 와 끝 기록이 모두 member 호출이었다. 7.2절의 측정 뒤, 같은 인터페이스를 두고 구현만 메모리로 바꿨다.

// kukie-serving-gateway internal/local/keys.go (발췌)
func (k *Keys) Lookup(token string) (relay.Identity, error) {
	sum := sha256.Sum256([]byte(token))
	hash := hex.EncodeToString(sum[:])
	now := k.now()
	k.mu.RLock()
	defer k.mu.RUnlock()
	if k.loadedAt.IsZero() || now.Sub(k.loadedAt) > k.maxAge {
		return relay.Identity{}, ErrUnavailable
	}
	e, ok := k.byHash[hash]
	if !ok || !now.Before(e.ExpiresAt) {
		return relay.Identity{}, relay.ErrUnauthorized
	}
	return relay.Identity{KeyID: e.KeyID, ClusterID: e.ClusterID, Models: slices.Clone(k.models[e.ClusterID])}, nil
}
  • 게이트웨이는 5초마다 member 에서 쓸 수 있는 키 전체의 해시 목록을 받는다. 바뀐 것만 받지 않는다. “목록에 없으면 무효” 규칙 하나로 폐기·만료·권한 회수가 모두 처리된다
  • 목록이 60초 넘게 갱신되지 않으면 모든 요청을 503 control_unavailable 로 막는다. 낡은 목록으로 계속 받지 않는다
  • 첫 목록을 받기 전에는 /healthz 가 503 이다. 새 파드가 준비되지 않은 채 요청을 받는 일을 막는다
  • 사용량은 메모리 대기열에 쌓았다가 2초마다(200건이 차면 바로) 묶어 보낸다. 대기열 상한은 10,000건이고 넘치면 오래된 것부터 버린다

받아들인 것은 두 가지다. 키 폐기는 평소 몇 초 늦게 반영되고, 게이트웨이가 갑자기 죽으면 마지막 몇 초분의 사용량을 잃는다. 사용량이 통계에만 쓰이기 때문에 가능한 선택이다. 토큰 한도나 과금이 생기면 그때 한도만 따로 빠르게 확인하는 길을 둔다.

6. Connector — 고객 클러스터의 커넥터#

6.1 바깥으로 여는 연결#

{…} 는 텍스트 프레임(JSON)이다. 연결 하나는 요청 하나만 나르고, id 는 응답이 그 요청의 것인지 맞춰 보는 데만 쓴다
  • 커넥터에게 필요한 것은 Kukie 연결 주소로 나가는 TCP 443 하나다. 사설 서브넷이면 고객이 쓰던 NAT 를 그대로 탄다
  • 접속할 때 커넥터는 자격과 클러스터 ID 를 헤더로 보낸다. 게이트웨이는 자격의 SHA-256 을 member 에서 5초마다 받은 바인딩과 비교한다. 연결마다 member 를 부르지 않는다
  • 세션은 자격 만료 시각까지만 산다. 만료되면 게이트웨이가 닫는다
  • 끊기면 1초부터 두 배씩 최대 30초까지 기다렸다 다시 연다(지터 50%). 30초 넘게 붙어 있었으면 다시 1초부터다

6.2 Protocol: WebSocket v1#

// kukie-serving-gateway internal/tunnel/protocol.go
const StatusProtocol = "kukie.connector.v2"
const Protocol = "kukie.connector.v1"
const ConnectPath = "/connector/v1/connect"
const MaxRequest = 1 << 20
const ChunkSize = 32 << 10
const MaxResponse = 64 << 20

type message struct {
	Type        string `json:"type"`
	ID          string `json:"id"`
	Path        string `json:"path,omitempty"`
	Body        []byte `json:"body,omitempty"`
	TimeoutMS   int64  `json:"timeoutMs,omitempty"`
	Status      int    `json:"status,omitempty"`
	ContentType string `json:"contentType,omitempty"`
}
  • 연결 하나가 요청 하나를 나른다. 다중화는 없다. 동시 처리 수는 커넥터 워커 수(기본 4, 1~8)다
  • 취소는 별도 메시지가 아니라 연결을 닫는 것이다. 생존 확인은 WebSocket ping(15초, 5초 안에 답 없으면 끊음)으로 한다
  • v2 는 v1 에 model_status 프레임 하나를 더한 것이다. 유휴 연결에서 15초마다 카운터가 본 준비된 모델 목록을 보낸다

WebSocket 을 유지한 이유와 바꿀 기준. 11월 11일 측정 뒤 gRPC 와 비교했다.

  • 병목은 “연결당 요청 하나"라는 구조였고, 전송 방식과는 관계없었다. gRPC 로 바꿔도 연결당 요청 하나면 결과가 같다
  • 역방향 요청: WebSocket 은 연결 뒤 양쪽 모두 보낼 수 있다. gRPC 는 커넥터가 클라이언트라서 게이트웨이 → 커넥터 요청을 긴 양방향 스트림 위에 따로 얹어야 한다
  • 고객망 통과: WebSocket 은 HTTP/1.1 업그레이드라 회사 프록시를 통과하기 쉽다. gRPC 는 HTTP/2 가 필요하고 TLS 검사 프록시에서 깨질 수 있다
  • gRPC 의 실질 이점은 스트림별 흐름 제어다. 이것이 필요해지는 때는 다중화를 도입할 때다

그래서 지금 결정은 임시다. 다중화로 갈 때 다시 고른다. 후보는 WebSocket 위 자체 구현, WebSocket 위 검증된 다중화 라이브러리(yamux 등), gRPC 셋이다. 판단 근거는 고객망의 HTTP/2 통과율과 느린 소비자 시험(DURO-218) 결과다. 전송 계층은 인증·사용량과 분리한 어댑터로 두었고, 바꿀 때는 버전 협상과 구·신 병행 기간이 필요하다.

6.3 자격 자동 갱신#

처음 dev 커넥터는 사람이 발급한 24시간 자격 하나로 돌았다. 11월 7일 만료된 뒤 3일 동안 아무도 몰랐다. 파드는 Running 이었고, 게이트웨이와 커넥터 모두 401 을 로그 없이 넘겼다. 그래서 커넥터가 스스로 갱신하게 했다(DURO-210).

// kukie-server serving/application/RenewConnectorCredentialService.kt (발췌)
val current = row.tokenHash == command.tokenSha256 && row.expiresAt.isAfter(now)
// 직전 자격으로 다시 오면 앞선 갱신 응답을 잃은 것이다. 직전 자격은 그대로 두고 새 자격을 다시 준다.
val retry = !current && row.previousTokenHash == command.tokenSha256 && row.previousActive(now)
if (!current && !retry) throw ServingAccessException(ServingErrorCode.SERVING_CONNECTOR_CREDENTIAL_INVALID)
// ...
val previousExpires = if (current) minOf(row.expiresAt, now.plus(properties.overlap)) else row.previousExpiresAt
val previousHash = if (current) row.tokenHash else row.previousTokenHash
credentials.save(ConnectorCredential(row.clusterId, tokens.hash(token), row.models, expires, previousHash, previousExpires, now))
  • 서버는 클러스터마다 현재 자격과 직전 자격 두 개를 둔다. 직전 자격은 30분 동안만 유효하다
  • 갱신 응답을 잃어도 괜찮다. 직전 자격으로 다시 오면 새 자격을 다시 준다
  • 갱신하면 워커들이 새 자격으로 먼저 연결을 열고, 게이트웨이는 그 뒤 옛 자격의 빈 연결을 0.5초에 하나씩 닫는다. 진행 중인 스트림은 끊지 않는다
  • 커넥터는 새 자격을 메모리에 바로 쓰고, 자기 Secret 에도 다시 쓴다(resourceVersion 으로 충돌 확인). 파드가 다시 떠도 새 자격으로 붙는다
  • 다른 방향도 검토했다. Kukie 서버가 고객 Secret 에 밀어 넣는 방식은 고객 클러스터 쓰기 권한이 필요해서 버렸다. 수명 연장은 근본 해결이 아니어서 버렸다

6.4 설치: Secret 하나와 helm 한 줄#

kubectl create namespace kukie-gpu
read -rs CREDENTIAL   # 대시보드가 발급한 자격을 붙여 넣는다
kubectl -n kukie-gpu create secret generic kukie-connector --from-literal=credential="$CREDENTIAL"
unset CREDENTIAL
helm upgrade --install kukie-gpu oci://ghcr.io/durokukie/charts/kukie-gpu --version <버전> -n kukie-gpu \
  --set oven.enabled=true --set counter.enabled=true --set counter.discovery.enabled=true \
  --set connector.enabled=true \
  --set connector.gateway=https://<Kukie 연결 호스트>/connector/v1/connect \
  --set connector.clusterId=<등록된 클러스터 ID>
  • 자격은 일부러 helm 값으로 받지 않는다. 값으로 받으면 Helm 릴리스 Secret 에 원문이 남는다
  • 커넥터 ServiceAccount 는 그 Secret 하나만 get·update 할 수 있다(resourceNames)
  • Deployment 는 Recreate 다. 파드 두 개가 같은 Secret 의 자격을 각자 갱신해 서로를 밀어내는 일을 막는다
  • 카운터 서비스 키는 차트가 만든다. 사용자의 개인 키는 고객 클러스터로 가지 않는다

7. Load Test — 게이트웨이 경로 시험#

Serving.01 에서 정한 SLA(TTFT p95 1초, ITL p95 50ms)는 카운터 → vLLM 에서 재는 값이다. 사용자는 게이트웨이를 지나므로, 경로가 얹는 지연과 경로가 받아 주는 동시 수를 따로 쟀다.

시험 조건

  • 가짜 모델: TTFT 200ms, 토큰 사이 20ms, 128토큰을 SSE 로 낸다. GPU 없이 반복할 수 있다
  • 부하 도구: 스트림마다 TTFT·ITL 을 재는 작은 Go 프로그램(cmd/loadgen). 동시 수를 고정해 60초씩 유지한다
  • 거절되면 Retry-After 를 무시하고 50ms 뒤 다시 보낸다. 재시도를 막 하는 클라이언트라는 최악 조건이다
  • dev 의 member, 게이트웨이, web Caddy 는 vCPU 2개 노드 하나에 함께 있다

7.1 경로 오버헤드#

  • 카운터가 얹는 값(B − A)은 TTFT p95 기준 1~6ms 다
  • 게이트웨이 경로가 얹는 값(C − B)은 약 20~25ms 다. 공개 인터넷 왕복(CloudFront)이 들어 있다
  • 처음 측정은 +33~38ms 였다. 부하 도구가 [DONE] 뒤 본문을 비우지 않아 연결을 다시 쓰지 못한 탓이었고, 고친 도구로 다시 쟀다

7.2 요청 경로의 member 호출#

동시 수가 커넥터 워커 수를 넘자 두 문제가 같이 나왔다. 넘친 요청이 502 로 떨어졌고(7.3절), 받은 요청까지 느려졌다. 동시 32 에서 받은 요청의 ITL p95 는 72.5ms 로 SLA 를 넘었다.

원인을 CPU 로 나눠 봤다. 거절 한 건에 member 약 5ms, 게이트웨이 약 3ms, Caddy 약 1ms 를 썼다. 노드 전체는 2코어 중 1.8코어가 찼다. 가장 비싼 것은 거절할 요청의 키를 확인하려고 member 를 부르는 일이었다.

  • member 가 요청 경로에서 빠졌다. 사이드카 Caddy 의 CPU 도 0 이다
  • 같은 시간에 거절을 더 빨리 처리하면서 받은 요청 수(거절 포함)는 동시 32 에서 7.6천에서 22.5천으로 늘었다. 그래도 전체 32 자리가 차는 일은 거의 없어졌다
  • 키 폐기는 실측 약 2.2초 뒤 막혔다. 5초 주기 안 어디서 폐기했는지에 따라 0~5초가 나온다
  • 동시 64 에서는 노드가 다시 1.7코어까지 찬다. 거절이 초당 약 570건이고, 이번에는 web Caddy 와 게이트웨이가 쓴다(거절 1건당 약 0.8ms, 0.6ms). 남은 병목은 dev 단일 노드의 자원이다

7.3 커넥터 포화와 429#

처음 측정에서는 빈 커넥터 연결이 없으면 게이트웨이가 502 upstream_unavailable 을 돌려줬다. 그 전에 키 확인, 사용량 시작 기록, 실패 기록까지 거쳐서 거절 한 건에 member 호출 3번과 DB 쓰기 2번이 붙었다. 502 는 클라이언트에게 “서버 고장"이지 “잠시 뒤 다시"가 아니다.

고친 것(DURO-220)은 순서다. 커넥터 자리를 사용량 기록보다 먼저 예약하고, 바쁘면 429 connector_busy 와 Retry-After: 1 을 준다. 같은 조건(워커 4)에서 다시 쟀다.

동시완료 (전 → 후)거절 (전 → 후)거절 응답 p50 ms (전 → 후)
1660 → 84502 ×2,404 · 503 ×238 · 끊긴 스트림 4 → 429 ×6,739158 → 43
3210 → 83502 ×887 · 503 ×173 → 429 ×7,8821,007 → 150
  • 고치기 전 동시 32 에서는 60초 동안 10건만 끝났다. 거절에 붙은 호출이 member 를 밀어 503 이 나고, 받은 요청까지 멈췄다
  • 고친 뒤에는 동시 수와 관계없이 워커 4개 몫(60초에 약 84건)이 끝났다. 끊긴 스트림과 사용량 토큰 불일치는 0 이다
  • 카운터의 429 는 Serving.06 의 문이다. 이 시험에서 카운터 한도 16 에는 한 번도 닿지 않았다. 워커 1·4·8 의 처리량이 22·84·168 건/분으로 정확히 비례했다. 경로의 동시 한도는 커넥터 워커 수가 정한다

8. Incident — 자격 다시 발급과 31시간 단절#

시각은 UTC. 대시보드 상태는 그동안 '만료'로 보였다
  • 증상: dev GPU 클러스터의 커넥터가 2026-11-11 11:01 UTC 부터 11-12 18:44 UTC 까지 약 31시간 게이트웨이에 붙지 못했다. 그동안 대시보드의 클러스터 상태와 모델 목록이 갱신되지 않았고, 모델 켜기·끄기도 전달되지 않았다
  • 원인: 관리자 화면의 “다시 발급"은 IssueConnectorCredentialService 가 처리한다. 새 행을 저장하면서 직전 자격을 남기지 않는다. 같은 시간대에 다른 시험 클러스터에서 다시 발급 화면을 시험했고, dev 클러스터에서도 누른 것으로 보인다. 누가 눌렀는지는 접근 로그에 남지 않는다
  • 확인: dev Loki 의 게이트웨이 로그와 대시보드 발급 요청(201) 시각이 맞았다. 자동 갱신은 문제가 없었다. 11-10 에 두 번 성공했고, 복구 직후에도 바로 갱신해 Secret 에 저장했다
  • 복구: 다시 발급한 값을 사람이 Secret 에 넣었다. 커넥터는 파일이 바뀌면 재시작 없이 새 값을 읽는다
// kukie-server serving/application/IssueConnectorCredentialService.kt (발췌, develop 기준)
val token = tokens.generate()
val expires = now.plus(properties.lifetime)
val models = command.models.distinct()
val hash = tokens.hash(token)
credentials.save(ConnectorCredential(command.clusterId, hash, models, expires))   // 직전 자격 칸은 비어 있다

고칠 거리는 정해 두었지만 아직 하지 않았다(DURO-232). 다시 발급할 때도 직전 자격을 30분 살려 두고, 연결된 커넥터가 있으면 “지금 연결이 끊길 수 있다"는 확인을 띄운다.

9. Limits — 남은 일#

  • 장애 주입(DURO-218): 커넥터 파드 삭제, 게이트웨이 재배포, 네트워크 차단, 자격 회수, 느린 소비자, 클라이언트 취소. 지금은 재시작 때 진행 중인 요청이 모두 끊긴다는 것만 코드로 안다
  • 실제 GPU 확인(DURO-219): 7절의 숫자는 모두 가짜 모델로 잰 값이다
  • Retry-After 전달(DURO-221): 터널의 response 메시지에 필드가 없어 카운터의 Retry-After 가 게이트웨이에서 사라진다. 게이트웨이와 커넥터 양쪽, 프로토콜 버전을 같이 바꿔야 한다
  • 다시 발급 겹침(DURO-232): 8절의 고칠 거리 그대로다
  • 게이트웨이 여러 대: 커넥터 연결이 한 대에 붙어 있어 라우팅을 따로 만들어야 한다. 전체 한도(32)도 한 대 기준이다
  • CloudFront 60초: 응답 바이트 사이가 60초 넘게 비면 입구에서 끊긴다. 긴 프리필이나 대기열 대기는 아직 시험하지 않았다
  • 다중화: 고객 클러스터가 수백 개가 되면 연결 수가 문제가 된다. 그때 6.2절의 기준으로 전송 방식을 다시 고른다
