1. Overview#

Elastic Scale: 세 축으로, 실측에 반응해 스스로 커지고 작아진다

26장과 29장의 차이

  • 26장: 한 문에서 요청을 검문하는 이야기
  • 29장: 그 문 안쪽의 시스템이 스스로 몸집을 바꾸는 이야기
  • 앞 장까지는 “Pod 3개를 유지해라"고 적으면 Kubernetes가 3개를 지켰다
  • 이 장은 그 3이라는 숫자 자체를 누가 정하느냐를 묻는다

확장기들의 관계: 대화 없는 릴레이

  • 이 장의 재미는 확장기들이 서로 대화하지 않는다는 데 있다
    • HPA는 Pod만 보고, CA는 Pending Pod와 빈 노드만 본다
    • VPA는 HPA가 있는지조차 모른다
  • 그런데 결과적으로 맞물려 돌아간다
    • HPA가 Pod를 늘리면 자리가 모자라고
    • 자리가 모자라면 Pending이 생기고
    • Pending이 생기면 CA가 노드를 산다
  • 아무도 다음 사람에게 전화하지 않았는데 릴레이가 이어지는 구조다
  • 그 릴레이의 출발점은 언제나 실제 측정값이지 사람의 예상이 아니다

2. Problem#

2.1 숫자를 미리 알 수 없다 — 예측이 아니라 실측#

원하는 상태에 적을 숫자

  • Kubernetes는 원하는 상태(desired state)를 적어두면 그대로 유지해준다
  • 문제는 그 상태에 적을 숫자를 사람이 미리 알기 어렵다는 것이다
적을 숫자미리 알기 어려운 이유
replicas: ?점심시간엔 손님이 몰리고 새벽엔 텅 빈다
requests.cpu: ?앱이 실제로 얼마 쓰는지 배포 전엔 감으로 적는다
노드: ? 대이번 주 세일 트래픽이 10배일지 3배일지 아무도 모른다

맞추기 어려운 이유: 계속 변하는 워크로드

  • 너무 크게 잡으면 돈 낭비, 너무 작게 잡으면 SLA를 못 지킨다
  • 어렵게 맞춰놔도 워크로드는 시간대·요일·계절에 따라 계속 변한다
  • 책의 표현을 빌리면 “정확히 파악하는 데 시간과 노력이 든다” — 한 번이 아니라 계속

이 장의 전환 한 문장: 예측에서 실측으로

예성격
예측(anticipated)“아마 점심에 100명 올 거야”사람이 짐작, 틀리기 쉽다
실측(actual usage)“지금 문 앞에 47명 줄 서 있다”측정값에 반응, 정확하다

정할 것은 값이 아니라 규칙

  • 다행히 Kubernetes에서는 이 숫자들 — 복제본 수, requests, 노드 수 — 을 바꾸기가 쉽다
  • 그러니 “얼마로 적을지"를 고민하는 대신 “언제 바꿀지"의 규칙만 정한다
  • 실제 값은 측정에 맡기자는 것이다

2.2 세 축 — 개수, 크기, 서버#

확장의 세 방향

  • 확장은 세 방향이 있고, 이 장은 셋을 다 다룬다
축뭘 바꾸나도구식당으로
수평Pod 개수HPA, Knative, KEDA요리사를 더 고용
수직Pod 하나의 CPU/메모리VPA요리사 한 명에게 더 큰 주방
클러스터노드 개수CA식당 건물을 넓힘

수평이 기본, 수직은 예외

  • 수평은 “똑같은 거 하나 더"라 기존 Pod를 건드리지 않는다
  • 수직은 “있는 걸 고치기"라 Pod를 죽였다 살려야 한다
    • 상태 없는 웹 서버는 옆 Pod가 받아주니 괜찮다
    • DB처럼 하나뿐인 것은 재시작이 곧 다운타임이다

함정: 따로는 쉽고 같이는 어렵다

  • 개발자가 자주 빠지는 함정 — 셋을 따로 배우면 각각은 쉬운데, 같이 돌리면 어렵다
  • 공유 클러스터에서 내 서비스가 자동으로 확 늘어나면 옆 팀이 쓸 자리가 없어진다
  • 책이 “종이 위에서는 간단해 보이지만 상당한 시행착오가 필요하다"고 못 박는 이유다

2.3 안티프래질 — 부하를 먹고 커지는 시스템#

장의 처음과 끝을 잇는 단어

  • 책이 이 장 첫 부분에 꺼내고 마지막에 다시 가져오는 단어가 antifragile이다
충격을 받으면예
취약(fragile)깨진다유리잔
튼튼(robust)버틴다돌
안티프래질더 강해진다운동으로 단련되는 근육

앞 장들과 이 장: 버티기에서 커지기로

  • 앞 장들까지의 Kubernetes는 두 번째였다 — 안 무너지기
    • Pod가 죽으면 다시 띄우고, 노드가 죽으면 다른 노드에서 살린다
  • 이 장은 세 번째를 만든다 — 부하를 먹고 커지기
    • 트래픽이 몰리면 Pod가 늘고 노드가 늘어난다

이 장의 목표

  • 사람이 예측한 숫자가 아니라 실제 측정값에 반응해서, 개수·크기·서버 세 축으로 시스템이 스스로 커지고 작아지게 만드는 것

3. 수동 확장 — 사람이 숫자를 바꾼다#

수동을 먼저 보는 이유: 자동 확장은 뒷북

  • CPU가 80%를 넘는 것을 본 다음에 늘리기 시작한다
    • 그 사이 몇 십 초는 이미 느려진 상태다
  • 반면 사람은 미래를 안다
    • “금요일 밤 11시 세일 시작"을 알면 목요일에 미리 늘려둘 수 있다
    • 손님이 몰리기 전에 계산대를 미리 여는 것이다
자동 확장수동 확장
반응 시점부하가 오른 후부하가 오르기 전에 가능
적합한 상황예측 불가능한 트래픽예측 가능한 이벤트, 최적값 찾는 튜닝 단계

3.1 명령형 — 빠르지만 파일에 남지 않는다#

ReplicaSet: 숫자 하나를 지키는 감시자

  • ReplicaSet은 “Pod가 N개여야 해"라는 숫자를 항상 지켜보는 감시자다
  • 그러니 사람이 할 일은 그 숫자 하나를 바꾸는 것뿐이다
kubectl scale deployment random-generator --replicas=4

책 예제와의 차이: 리소스 종류

  • 책의 예제는 deployment가 빠진 kubectl scale random-generator --replicas=4로 적혀 있다
  • 실제로는 리소스 종류를 명시해야 동작한다

한계: 파일에 남지 않는다

  • 빠르고 직관적이지만 파일에 남지 않는다
  • 원래 YAML에는 여전히 replicas: 2라고 적혀 있다

3.2 선언형 — 파일이 진실이다#

명령형이 만드는 사고: 설정 드리프트(configuration drift)

  • 명령형이 만드는 사고에는 이름이 있다 — 설정 드리프트(configuration drift)
설정 드리프트: 파일에 적힌 것과 실제 돌아가는 것이 어긋난다

해법: YAML 을 고쳐서 apply

  • “파일에 적힌 것"과 “실제 돌아가는 것"이 어긋난 상태다
  • 해법은 YAML의 replicas를 고쳐서 kubectl apply하는 것
    • 클러스터도 4, Git도 4
    • 히스토리에 누가 언제 왜 바꿨는지도 남는다

운영 규칙: 역반영(backporting)

  • 책이 말하는 **역반영(backporting)**은 운영 규칙이다
  • 급하면 scale로 먼저 하되, 상황이 정리되면 반드시 YAML에도 따라 적어 커밋하라는 것
  • 26장에서 RBAC가 파일이 아니라 리소스라서 GitOps에 올라탈 수 있었던 것과 같은 자리
    • 여기서도 진실은 Git에 있어야 한다

3.3 리소스마다 다르다 — StatefulSet 의 비대칭과 Job 의 parallelism#

확장할 수 있는 리소스

  • Deployment, ReplicaSet, StatefulSet, Job
  • 이 중 두 개가 조금 다르게 행동한다

StatefulSet: 늘릴 땐 만들고, 줄일 땐 안 지운다

  • 12장에서 본 대로 각 Pod가 자기 전용 디스크(PVC)를 갖는다
StatefulSet: 늘릴 땐 만들고, 줄일 땐 디스크를 안 지운다

디스크를 남기는 이유와 비용

  • 디스크를 같이 지우면 데이터가 날아가기 때문이다
  • 다시 5개로 늘리면 남아 있던 디스크가 그대로 다시 붙는다
  • 다만 안 쓰는 디스크도 비용이 나가니 정말 필요 없으면 수동으로 지워야 한다

Job: 이름만 다르다

  • 7장의 Job은 “계속 도는 서비스"가 아니라 “일 끝내면 종료되는 작업"이다
  • 그래서 복제본이라는 말 대신 동시 실행 수라고 부른다
spec:
  parallelism: 4      # replicas 가 아니라 이것

같은 뜻: 일꾼을 늘려 처리량을 키운다

  • 이름은 다르지만 뜻은 같다
  • 이미지 1만 장 변환을 1개로 돌리면 10시간, 4개로 돌리면 2.5시간
리소스확장 필드축소 시 특이점
Deployment / ReplicaSetreplicas없음
StatefulSetreplicasPVC는 남김
Jobparallelism작업 완료 시 종료

4. HPA — 판단은 내장, 숫자는 설치#

사람이 하던 세 단계

  • 명령형이든 선언형이든 사람이 세 단계를 해야 한다
    1. 부하가 변하는 걸 알아채고
    2. 몇 개로 늘릴지 판단하고
    3. 명령을 실행
  • 지금까지는 실행만 쉬웠다
  • HPA는 앞의 둘까지 Kubernetes에 맡긴다

4.1 정의 하나 — 울타리와 목표#

kubectl autoscale deployment random-generator --cpu-percent=50 --min=1 --max=5

명령 한 줄이 만드는 YAML

  • 이 한 줄이 아래 YAML을 만든다
# Example 29-4. HPA 정의
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: random-generator
spec:
  minReplicas: 1                  # ❶ 아무리 한가해도 1개는 유지
  maxReplicas: 5                  # ❷ 아무리 바빠도 5개까지만
  scaleTargetRef:                 # ❸ 조절할 대상
    apiVersion: apps/v1
    kind: Deployment
    name: random-generator
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 50    # ❹ 목표 CPU 사용률

❶❷ 울타리

  • min: 갑자기 트래픽이 왔을 때 0에서 시작하는 것보다 1개라도 있어야 바로 응답할 수 있어서
  • max: 버그나 공격으로 Pod가 무한히 늘어나 클러스터를 잡아먹는 걸 막는 비용 안전장치

❸ 붙이는 곳: ReplicaSet 이 아니라 Deployment

  • ❸에서 HPA는 ReplicaSet이 아니라 Deployment에 붙여야 한다
  • Deployment는 배포할 때마다 새 ReplicaSet을 만들고 옛것을 비운다
HPA 는 ReplicaSet 이 아니라 Deployment 에 붙인다

ReplicaSet 에 붙였을 때의 결과

  • HPA를 ReplicaSet v1에 붙여뒀다면 배포 한 번에 자동 확장이 조용히 꺼진다
  • 회사 정책을 “이번 분기 TF팀"에 걸어두면 TF가 해체될 때 정책도 사라지는 것과 같다
    • 부서에 걸어야 TF가 바뀌어도 유지된다

붙일 수 있는 대상과 내장 여부

  • HPA는 /scale 서브리소스가 있는 리소스에만 붙는다
    • Deployment, ReplicaSet, StatefulSet은 된다
    • 단일 Pod나 DaemonSet은 안 된다
  • HPA 리소스 자체는 Kubernetes 코어에 내장되어 있다
    • kubectl api-resources | grep autoscal에 아무것도 안 깔아도 나온다
  • 이 장에서 내장인 것은 이것 하나뿐이라는 점을 미리 적어둔다

4.2 숫자는 어디서 오나 — kubelet 에서 API 자리까지#

지표가 HPA 까지 오는 길

  • HPA가 “지금 CPU 75%“라는 숫자를 얻기까지의 길은 생각보다 길다
  • 어디까지가 내장이고 어디부터 설치인지가 실무에서 자주 헷갈린다
측정은 내장, 수집기는 설치, 판단은 내장 — 가운데 한 칸만 사람이 깔아야 한다
단계누가내장?
컨테이너 사용량 측정kubelet 안의 cAdvisor✅ 노드마다 있다
노드별 값을 모아 API로 노출metrics-server❌ 클러스터에 1개 설치
API 그룹 이름과 위임 메커니즘metrics.k8s.io, APIService✅ 내장
그 API를 읽어서 판단HPA 컨트롤러✅ 내장

없는 것: 값을 모아주는 Pod 하나

  • 측정 자체는 이미 되고 있다
    • Kubernetes를 설치한 순간부터 모든 노드의 kubelet이 자기 노드 컨테이너의 CPU·메모리를 재고 있다
    • 앱마다 뭘 만들 필요가 없다
  • 없는 것은 흩어진 값을 한곳에 모아주는 Pod 하나뿐이고, 그게 metrics-server다

metrics-server 설치 여부

  • metrics-server가 “기본 제공"처럼 느껴지는 건 GKE·AKS 같은 관리형 클러스터가 미리 깔아주기 때문이다
  • EKS, minikube, kubeadm은 직접 깔아야 한다
  • 확인은 간단하다
kubectl top pods              # 값이 나오면 있는 것
# error: Metrics API not available   → 없는 것

등록: APIService 리소스

  • 등록은 APIService 리소스로 한다
  • “이 API 경로로 오는 요청은 저 Service에게 넘겨라"고 API 서버에 알려주는 것이다
apiVersion: apiregistration.k8s.io/v1
kind: APIService
metadata:
  name: v1beta1.metrics.k8s.io          # <버전>.<그룹> — 이 이름은 고정

service 의 정체: 일반 ClusterIP Service

  • 여기서 service는 일반 Kubernetes Service 리소스이고 타입은 ClusterIP다
    • 외부 IP가 아니다
  • API 서버가 클러스터 내부에서 그 Service로 프록시하고, 뒤의 Pod가 실제 값을 만든다
  • Pod IP는 재시작하면 바뀌지만 Service 이름은 고정이라 이 구조가 필요한 것이다
    • 일반 앱 간 통신에서 Service를 쓰는 이유와 같다

설치 방식: 한꺼번에 딸려온다

  • 보통 이 YAML을 손으로 쓰지 않는다
  • kubectl apply -f components.yaml이나 Helm으로 설치하면 Deployment + Service + APIService가 한꺼번에 딸려온다

4.4 분자와 분모 — requests 가 기준이다#

퍼센트에 필요한 두 숫자

  • HPA가 “50%“라는 퍼센트를 만들려면 숫자 두 개가 필요하다
  • 사용률 = 실제로 쓰고 있는 양 ÷ requests 에 적은 양
    • 분자: 실제로 쓰고 있는 양 ← metrics-server 가 재서 줌
    • 분모: requests 에 적은 양 ← Pod spec 에 이미 있음
어디서 오나성격
분자 — 실제 사용량 (지금 150m)metrics-server측정값, 매초 변함
분모 — requests (200m)Pod spec, API 서버에 저장됨선언값, 내가 YAML에 적은 것

둘 중 하나만 없어도 HPA 가 멈춘다

  • metrics-server는 분자만 준다
  • 분모는 2장 “Predictable Demands"에서 적은 requests를 그냥 읽는다
  • 그래서 둘 중 하나만 없어도 HPA가 안 돈다
    • metrics-server가 없으면 분자가 없다
    • requests가 없으면 분모가 없다

기준은 limits 가 아니라 requests

  • 여기서 헷갈리기 쉬운 것 — 기준은 limits가 아니라 requests다
같은 300m 라도 HPA 눈에는 300%, limits 대비는 60%

requests 값이 HPA 동작을 좌우한다

  • limits 대비로는 여유가 있는데 HPA는 “엄청 바쁘다"고 판단해 늘린다
  • 즉 requests 값 자체가 HPA 동작을 좌우한다
    • requests를 감으로 낮게 적으면 HPA가 과민 반응한다
    • 높게 적으면 둔감해진다
  • 이 문제의 답이 뒤에 나올 VPA다(6.1)

4.5 지표 선택 — Pod 를 늘리면 내려가는가#

가장 중요한 결정: 지표 선택

  • 책이 “가장 중요한 결정"이라고 부르는 것이 지표 선택이다
  • HPA의 계산식은 이런 믿음 위에 서 있다

“Pod 를 2배로 늘리면 → 지표가 절반으로 내려갈 것이다”

판단 기준 하나

  • 이 믿음이 깨지면 HPA는 엉뚱한 짓을 한다
  • 그러니 판단 기준은 하나다 — Pod를 늘리면 그 숫자가 내려가는가?
요청은 나눠 갖고, 메모리는 Pod 마다 자기 몫이다

요청은 나눠 갖고, 메모리는 자기 몫

  • 요청은 나눠 갖는 성질이다
  • 메모리는 Pod 하나가 혼자 쓰는 고정 비용이다
    • 옆에 Pod가 몇 개 생기든 자기 800MB는 그대로다

메모리로 HPA 를 걸면 벌어지는 일

  1. HPA: “메모리 80%네, 목표 50%니까 늘리자” → 3개
  2. 15초 뒤: “여전히 80%? 더 늘리자” → 5개
  3. 15초 뒤: “아직도 80%?!” → 8개
  4. … maxReplicas 도달할 때까지

결과: 상한에 걸려 멈춘다

  • 돈은 돈대로 쓰고 사용률은 1도 안 내려가고, 결국 상한에 걸려 멈춘다
  • Pod를 아무리 늘려도 내려가지 않는 숫자를 내리겠다고 애쓰는 것이다
지표Pod 늘리면 내려가나HPA 적합?
초당 요청 수✓매우 좋음
CPU✓ (요청 처리에 쓰니까)좋음, 기본 선택
큐 길이✓ (소비자가 늘면 빨리 빠짐)좋음
메모리✗ (대부분)피할 것

메모리 문제의 답과 여러 지표의 처리

  • 메모리가 문제라면 HPA가 아니라 VPA나 앱 튜닝이 답이다
  • 지표가 여러 개면 각각 따로 계산해서 가장 큰 값을 택한다
    • 어느 하나라도 한계에 걸리면 안 되니, 가장 많이 필요하다는 쪽을 따른다

4.6 공식은 비례식, 나머지는 안전장치#

계산: 비례식 하나

  • 계산은 비례식 하나다

$$\text{원하는 개수} = \left\lceil \text{현재 개수} \times \frac{\text{현재 사용률}}{\text{목표 사용률}} \right\rceil$$

지금 상태계산결과
Pod 1개, CPU 90%, 목표 50%1 × (90/50) = 1.8올림해서 2개
Pod 4개, CPU 25%, 목표 50%4 × (25/50) = 22개로 줄임

공식의 뜻

  • “부하가 목표의 몇 배인가"를 구해서 Pod 개수에 곱한다
  • 소수점은 올림 — 부족한 것보다 남는 게 안전하니까

HPA 가 하는 일: replicas 에 숫자 하나

  • HPA는 계산 결과 숫자 하나를 Deployment의 replicas에 써넣기만 한다
    • 직접 Pod를 만들지 않는다
  • 그 뒤는 Deployment → ReplicaSet → 스케줄러의 기존 흐름 그대로다
  • 사람이 kubectl scale로 하던 일을 HPA가 대신 치는 것뿐이고, 그 아래 메커니즘은 동일하다

공식 위의 안전장치: 스래싱(thrashing) 방지

  • 책이 “단순화한 공식"이라고 한 이유는 그 위에 안전장치가 얹히기 때문이다
  • 이름은 스래싱(thrashing) 또는 플래핑
    • 3 → 5 → 3 → 5를 15초마다 반복하는 나쁜 상태를 막는 것이다

늘릴 때: 갓 뜬 Pod 의 CPU 는 안 믿는다

  • Java·Node 는 시작할 때 몇십 초간 CPU 100% 를 찍는다
  • 그걸 넣으면 “새 Pod 가 바쁘네 → 더 늘려 → 그것도 바쁘네 → 더” 의 폭주가 된다

줄일 때: 최근 5분간 계산 결과 중 최댓값을 따른다

  • 70% 72% 30% 68% … 에서 30% 순간에 줄이면 15초 뒤 다시 늘려야 한다
  • 5분 내내 “3개면 충분” 이 나와야 비로소 3개로 줄어든다

의도된 비대칭: 늘릴 땐 빨리, 줄일 땐 천천히

  • 줄일 때만 이렇게 보수적인 이유
    • 늘리는 게 늦으면 서비스가 느려진다(사용자가 바로 느낀다)
    • 줄이는 게 늦으면 돈이 조금 더 나간다(5분어치)

조절 손잡이: .spec.behavior

  • 이 안전장치는 .spec.behavior로 조절한다
  • 손잡이는 둘이다
# Example 29-5. 축소는 5분 지켜본 뒤 1분에 10% 씩, 확장은 15초에 4개씩
spec:
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 300    # 얼마나 참고 — 5분
      policies:
      - type: Percent
        value: 10                        # 얼마나 빨리 — 현재의 10%
        periodSeconds: 60                #             1분마다
    scaleUp:
      policies:
      - type: Pods
        value: 4                         # 15초에 4개씩
        periodSeconds: 15
질문비유
stabilizationWindowSeconds결정하기 전에 얼마나 지켜보나대기 시간
policies한 번에 몇 개까지 바꿀 수 있나속도 제한

이 설정의 효과

  • Pod 20개가 5개까지 내려오려면 약 15분
  • 2개가 20개까지 올라가려면 1분
  • scaleDown.selectPolicy: Disabled로 축소 자체를 끌 수도 있다

책의 오류 하나: kubectl autoscale 과 behavior

  • 책에는 “모든 behavior 매개변수를 kubectl autoscale로도 설정할 수 있다"고 적혀 있다
  • 실제 kubectl autoscale이 받는 건 --min, --max와 목표치 플래그 정도다
    • 지금 kubectl 레퍼런스에는 --cpu·--memory가 올라 있다(--cpu-percent는 목록에서 빠졌다)
    • behavior를 정하는 플래그는 없다
  • behavior를 쓰려면 YAML로 작성해 apply해야 한다

쌓이는 지연: 보통 1~3분

  • 지연은 어쩔 수 없이 쌓인다
    • cAdvisor 주기 + metrics-server 주기 + HPA 주기 + 안정화 창 + 새 Pod가 뜨는 시간
  • 보통 1~3분이고, 주기를 줄이면 API 서버 부하와 스래싱이 늘어난다
자동 확장의 지연은 단계마다 쌓인다: 보통 1~3분

현실적인 대응

  • 주기가 아니라 ④→⑤ 구간(이미지 크기, 앱 시작 시간, readiness probe)을 줄인다
  • 목표치를 낮게 잡아 여유분을 둔다
  • 예측 가능한 이벤트는 3장의 수동 사전 확장으로 처리한다

5. Scale to Zero — 0 에서 깨우는 일은 누가 하나#

HPA 가 못 하는 한 가지: 0개로 줄이기

  • HPA는 강력하지만 한 가지를 못 한다 — 아무도 안 쓸 때 Pod를 0개로 줄이는 것
  • 밤에 아무도 안 쓰는 내부 도구, 한 달에 한 번 쓰는 리포트 생성기
    • Pod 1개씩 계속 떠 있으면 비용이 계속 나간다

5.1 HPA 는 왜 0 에서 못 깨어나나#

까다로운 쪽: 0에서 다시 깨우기

  • 0으로 줄이는 것 자체는 어렵지 않다
  • 까다로운 건 0에서 다시 깨우는 것이다

HPA 의 막다른 길

  • HPA 는 Pod 의 CPU 를 보고 판단한다
  • Pod 가 0개면 볼 CPU 가 없다
  • Pod 0개 → 요청 들어옴 → 받을 Pod 가 없어서 실패 → CPU 도 0 → HPA 는 조용함

결론: HPA 는 애초에 0으로 안 내려간다

  • Pod가 없으면 “바쁘다"는 신호를 영영 받을 수 없다
  • 그래서 HPA는 애초에 0으로 안 내려간다
  • 예외는 HPAScaleToZero 기능 게이트다
    • custom(object)·external 지표를 걸면 minReplicas: 0을 허용한다
    • v1.36까지는 알파(기본 꺼짐), v1.37부터 베타로 기본 켜짐
    • CPU·메모리 같은 리소스 지표로는 여전히 0으로 못 내린다

해법: Pod 앞쪽을 지켜보는 무언가

  • 해법은 하나다 — Pod가 아니라 Pod 앞쪽을 지켜보는 무언가를 두는 것
    • Knative: HTTP 요청이 오면 잠깐 붙잡아두고 Pod를 띄운 뒤 넘겨준다
    • KEDA: 큐에 메시지가 쌓이는 걸 보고 Pod를 띄운다

대체재가 아니라 보완재

  • 책이 강조하는 것 — 둘은 대체재가 아니라 보완재다
  • 트리거가 뭐냐에 따라 쓰는 게 다르다
KnativeKEDA
깨우는 신호HTTP 요청외부 이벤트 (큐, DB, cron)

5.2 Knative — 문지기, 카운터, 결정권자#

Knative Serving: 리소스 넷을 하나로

  • Knative는 세 조각(Serving, Eventing, Functions)짜리 애드온이다
  • 이 장에서 중요한 건 Serving뿐이다
  • 일반 Kubernetes에서 웹 앱 하나 띄우려면 Deployment + Service + Ingress + HPA 넷을 써야 한다
  • Knative Serving은 이걸 리소스 하나로 줄인다
# Example 29-6. Knative Service
apiVersion: serving.knative.dev/v1        # ❶ 코어 Service 와 이름만 같은 다른 리소스
kind: Service
metadata:
  name: random
  annotations:
    autoscaling.knative.dev/target: "80"   # ❷ Pod 당 동시 요청 80개
    autoscaling.knative.dev/window: "120s" # ❸ 최근 2분 평균으로 판단
spec:
  template:
    spec:
      containers:
      - image: k8spatterns/random          # ❹ 유일한 필수 항목

❶ kind: Service 지만 코어 Service 가 아니다

  • apiVersion이 serving.knative.dev/v1이고, 설치해야 생긴다
  • 헷갈려서 보통 ksvc라고 부른다
  • 이걸 만들면 그 안에서 코어 Service, Deployment, Ingress가 자동 생성된다
    • 외부 접속 URL(http://random.default.example.com)까지 생긴다
  • Knative Service는 코어 Service를 포함하는 상위 개념이다

❷ 지표: CPU 가 아니라 동시 요청 수

  • Knative는 CPU를 보지 않는다
  • 동시 요청 수 — 지금 이 Pod가 병렬로 처리 중인 요청 수 — 를 본다
지표식당으로문제
CPU요리사가 얼마나 땀 흘리나외부 API 기다리는 동안은 땀 안 흘림. 실제론 바쁜데 한가해 보임
rps1초에 손님 몇 명 들어오나라면 손님 10명과 코스 손님 10명이 같아 보임
동시 요청지금 테이블에 앉아 있는 손님 수—

  • 테이블에 앉아 있는 손님 수 = (들어오는 속도) × (머무는 시간)
  • rps에 없던 “요청 하나가 얼마나 오래 걸리나"가 자동으로 들어간다
  • 느린 요청이 많으면 동시 요청이 쌓이니 늘려야 한다는 걸 정확히 잡는다

Knative 의 기본은 HPA 가 아니라 KPA

  • 처음엔 커스텀 지표 어댑터로 만들어 HPA가 판단하게 했다
  • 그런데 4.3의 “그룹마다 자리 하나” 제약에 걸렸다
    • Knative가 그 자리를 차지하면 사용자는 Prometheus Adapter를 못 붙인다
  • 게다가 0에서 깨우기, 요청 붙잡아두기는 HPA 공식으로 불가능하다
  • 그래서 숫자 공급도 판단도 전부 자기가 하는 자체 컨트롤러를 만들었다
    • 이름은 **KPA(Knative Pod Autoscaler)**다
  • KPA가 기본값일 뿐 HPA를 아예 버린 건 아니다
    • autoscaling.knative.dev/class: hpa.autoscaling.knative.dev로 HPA 클래스를 고를 수 있다

  • Activator는 밖에 따로 있으니 살아 있다

6.1 VPA — 재시작이 문제였고, 제자리 수정이 답이 되고 있다#

감으로 적은 requests 의 대가

  • 4.4에서 requests가 HPA의 분모라고 했다
  • 그런데 대부분 그 requests를 감으로 적고 그대로 둔다
  • 잘못 적으면 양쪽으로 터진다
requests 를 감으로 적으면 양쪽으로 터진다

VPA: 실제 사용량으로 requests 를 정한다

  • VPA는 실제 사용량을 보고 requests를 대신 정해주는 도구다
  • HPA가 “몇 개?“를 모르는 문제를 자동으로 풀었듯, VPA는 “얼마나 크게?“를 같은 방식으로 푼다
  • 4.5에서 메모리는 HPA로 못 푼다고 했는데, 그 답이 이것이다
# Example 29-8. VPA
apiVersion: autoscaling.k8s.io/v1         # 설치해야 생기는 그룹
kind: VerticalPodAutoscaler
metadata:
  name: random-generator-vpa
spec:
  targetRef:                              # HPA 의 scaleTargetRef 와 같은 역할
    apiVersion: apps/v1
    kind: Deployment
    name: random-generator
  updatePolicy:
    updateMode: "Off"                     # 추천만 해라, 손대지 마라
VPA — 추천하는 쪽, 쫓아내는 쪽, 끼워 넣는 쪽이 나뉘어 있다

HPA 와 닮았지만 설치가 필요하다

  • HPA YAML과 거의 똑같이 생겼고 차이는 updateMode 하나다
  • 그리고 HPA와 달리 VPA는 설치해야 한다
    • autoscaling.k8s.io/v1 처럼 k8s.io 도메인이 붙어 있어도 내장이라는 뜻은 아니다(apiVersion)
  • 세 부품으로 되어 있다

  • Recommender가 평균이 아니라 높은 쪽을 고르는 이유 — 평균으로 잡으면 피크 때 모자란다
  • Admission plugin은 26장 3.4에서 본 Mutating 어드미션 그대로다
    • 내가 낸 YAML은 100m인데 실제로 뜬 Pod는 350m
    • Deployment YAML은 그대로인데 VPA 웹훅이 생성 시점에 고쳐서 돌려준 것이다

  • Kubernetes는 “고치지 말고 버리고 새로 만들어라"로 설계됐다
    • Pod의 resources 필드는 불변이었다
  • 수평 확장은 이 철학과 딱 맞는다(똑같은 거 하나 더)
  • 수직 확장은 정반대다(있는 걸 고쳐야 함)
  • 그래서 VPA가 requests를 바꾸려면 Pod를 죽였다 살려야 했다

  • 이 문제가 지금은 풀리고 있다
  • 리눅스 cgroup 자체는 원래 실행 중에도 값을 바꿀 수 있었다
    • 막고 있던 건 Kubernetes 쪽이었다
  • In-Place Pod Vertical Scaling이 들어오면서 /resize 서브리소스로 resources를 수정할 수 있게 됐다
  • kubelet이 컨테이너 런타임에 “cgroup 값 바꿔"를 요청한다
  • 프로세스는 죽지 않고 CPU 배정만 늘어난다

Initial 이 “부분적으로 파괴적"인 이유

  • 이유가 미묘하다
  • 재시작은 안 시키지만 requests가 바뀌면 자리 크기가 바뀐다
  • 100m 자리 → 350m 자리로 커지면 원래 노드에 빈자리가 없어 다른 노드로 간다
  • 어느 노드에도 없으면 Pending으로 멈춘다
  • 배포했는데 Pod가 안 뜨고, 이유를 찾아보면 VPA가 requests를 올려놔서 자리가 없는 것이다

Auto 는 이제 쓸 이유가 없다

  • Auto는 이제 굳이 쓸 이유가 없다
  • 책 쓸 땐 “나중에 좋아질 거야"였는데 실제로는 InPlaceOrRecreate라는 다른 이름으로 나왔다

모드 고르는 순서

  1. Off: 추천값이 말 되는지 며칠 확인
  2. Initial: 다음 배포 때 자연스럽게 반영
  3. InPlaceOrRecreate: 더 자동화하고 싶으면, 재시작 최소화

실무에서 흔한 조합

  • HPA는 요청 수로, VPA는 Off로 추천만 보고 사람이 반영

6.4 CA — CPU 가 아니라 Pending 을 본다#

CA: 노드를 사고 반납한다

  • HPA가 Pod를 늘리려는데 노드에 자리가 없으면 CA가 노드(서버)를 더 산다
  • 노드는 곧 VM이고 VM은 시간당 요금이다
    • 밤에 Pod가 줄어 노드가 텅 비면 반납해서 요금을 아낀다
    • 낮에 다시 필요하면 새로 산다

CA 의 신호: 자리 없어서 못 뜬 Pod

  • CA의 신호는 CPU가 아니다
  • 4.2의 HPA가 “자리 없어서 못 뜬 Pod"를 만들면 그것이 신호다
kubectl get pods
NAME          STATUS
worker-xxx    Pending       ← 만들긴 했는데 놓을 데가 없어서 기다리는 중

kubectl describe pod worker-xxx
Events:
  FailedScheduling   0/3 nodes are available: insufficient memory
  TriggeredScaleUp   pod triggered scale-up: [{node-group-1 3->4}]   ← CA 가 반응
분리되어 있지만 보완적 — HPA 는 Pod 만 보고, CA 는 Pending 과 빈 노드만 본다

노드를 늘리기 전의 계산

  • CA는 “노드 하나 추가하면 Pod가 들어갈까?“를 먼저 계산한다
  • Pod가 메모리 64Gi를 요구하는데 노드 종류가 16Gi짜리면 100개를 추가해도 못 들어간다
    • 이런 경우 CA는 노드를 안 늘린다

노드 그룹과 expander

  • CA는 아무 서버나 사지 않는다 — 노드 그룹 중 하나에서 한 대 더 산다
  • AWS의 Auto Scaling Group, GKE의 node pool이 이것이다
  • 그룹 안은 다 같은 크기라고 가정한다
    • 그래야 “기존 노드 하나와 똑같이 생겼겠지"로 계산할 수 있다
  • 여러 그룹이 후보면 expander가 고른다
    • random(기본), least-waste, most-pods, price, priority
    • 실무에선 least-waste나 priority를 많이 쓴다

Node 리소스: 관찰용이지 생성용이 아니다

  • 여기서 짚어둘 것 — Node 리소스는 내장이지만 “관찰용"이지 “생성용"이 아니다
PodNode
YAML 만들면컨테이너가 생김아무것도 안 생김
관계리소스 → 실체실체 → 리소스

CA 가 클라우드 API 를 부르는 이유

  • 서버가 먼저 있고 그게 붙으면 Node 객체가 생기는 순서다
  • 그래서 CA는 Kubernetes API가 아니라 클라우드 API를 직접 호출해 VM을 만든다
  • 그 VM의 kubelet이 등록하면 Node가 생긴다
  • 노드 그룹, 노드를 사고 반납하는 것은 전부 클라우드 쪽 개념이다

빈틈을 메우는 Cluster API 와 Karpenter

  • 이 빈틈을 메우려는 게 Cluster API다
    • MachineDeployment라는 리소스를 만들어 YAML로 노드를 생성할 수 있게 한다
    • 클라우드별 차이는 machine controller가 흡수한다
    • Pod ↔ Deployment 관계를 노드에 적용한 것이다
  • 2026년 기준 AWS, Azure, GCP, vSphere, OpenStack 등 주요 공급자는 다 있다
    • 다만 EKS·GKE·AKS 같은 관리형 서비스를 쓰면 각자 노드 자동 확장이 이미 있어 만날 일이 거의 없다
    • 자체 관리 클러스터의 표준으로 자리잡았지 관리형까지 대체하진 않았다
  • AWS의 Karpenter도 알아둘 만하다
    • 노드 그룹 없이 “이 Pod에 딱 맞는 크기의 VM"을 그때그때 고르는 대안이다
    • EKS에서는 CA 대신 이걸 쓰는 경우가 많다

CA 의 정체: 리소스 없는 애드온

  • CA도 설치해야 하는 애드온이다
  • HPA와 달리 kind: ClusterAutoscaler 같은 리소스가 없다
  • 백그라운드에서 도는 Pod 하나고, 설정은 실행 옵션과 노드 그룹 태그로 한다

6.5 노드를 빼는 네 조건과 10분#

네 가지를 다 통과해야 뺀다

  • 노드를 빼는 건 그 위 Pod를 전부 쫓아내는 거라 네 가지를 다 통과해야 뺀다
조건내용

② 쫓겨난 Pod 가 갈 데 있나CA 가 머릿속으로 시뮬레이션 — 안 들어가면 안 지움

실무 함정: 대부분 ④

  • “노드가 텅 비었는데 왜 안 줄어들지?“는 대부분 ④다
  • kubectl run으로 띄운 Pod 하나, 로컬 볼륨 쓰는 Pod 하나가 노드를 붙잡고 있다

10분 뒤의 축소 절차

  • 넷을 통과한 상태가 10분 유지되면 아래 순서로 뺀다
    1. cordon: 새 Pod 받지 마
    2. drain: 위의 Pod를 하나씩 쫓아냄, 다른 노드에서 다시 뜸
    3. 다 비면 VM 반납
  • 10분 기다리는 이유는 HPA의 5분 안정화 창과 같다
    • 잠깐 비었다고 바로 빼면 다시 사야 한다
  • 그리고 Pending Pod가 있으면 축소는 아예 안 본다
    • 늘려야 할 때 줄이면 안 되니까

CA 가 특히 빛나는 경우: 새벽 배치

  • 밤 2시에 배치 작업이 노드 5개 분량을 쓰고 30분 만에 끝난다면
    • CA 없이는 그 5개를 24시간 내내 켜둬야 한다
    • CA가 있으면 30분어치만 낸다

7.1 확장 수준 — 앱 튜닝이 맨 위인 이유#

작은 것부터 큰 것 순서로

  • 책은 장을 닫으며 확장 기법을 작은 것부터 큰 것 순서로 다시 세운다
층뭘 조절누가언제

VPAPod 크기자동 (Off로 추천만도 가능)처음 한 번 + 이후
HPA / Knative / KEDAPod 개수자동이제부터 계속
CA노드 개수자동자리 모자랄 때

앱 튜닝이 맨 위인 이유: 밑에서 안 쓰면 낭비

  • 이 장에서 다루지 않은 앱 튜닝이 맨 위에 있는 이유 — 밑에서 안 쓰면 위에서 아무리 줘도 낭비이기 때문이다

앱스레드 1개만 씀—

CA노드 3개 추가다 놈

반대 방향의 위험: 잘못된 설정도 복제된다

  • 힙을 컨테이너 limit보다 크게 잡으면 OOM이다
    • 이건 Pod를 100개로 늘려도 100개가 다 똑같이 죽는다
  • 수평 확장은 “같은 걸 복제"하니 잘못된 설정도 같이 복제된다

전형적인 함정: 노드 전체를 자기 몫으로 착각

  • 앱이 노드 전체를 자기 몫으로 착각하는 것이 전형적인 함정이다
  • 컨테이너에 CPU 2개를 줬는데 nproc은 노드 전체(64코어)를 돌려준다
    • 그래서 스레드 64개를 만든다
  • 최신 JVM은 cgroup을 읽어서 알아서 한다
  • 오래된 런타임은 시작 스크립트에서 “내 몫은 2개"를 계산해 넘겨줘야 한다

한 걸음 더: 앱 내 자동 확장

  • Netflix Adaptive Concurrency Limits처럼 앱이 자기 응답 시간을 재면서 동시성을 실시간으로 조절하는 앱 내 자동 확장도 있다
  • Knative가 Pod 밖에서 동시 요청을 조절했다면, 이건 Pod 안에서 스스로 하는 것이다

쌓는 순서

  1. 앱 튜닝: 처음 한 번. 앱이 자기 몫을 제대로 쓰게
  2. VPA (Off): 처음 한 번. requests 값 찾기
  3. HPA 켜기: 이제부터 자동
  4. CA: 자리 모자라면 노드 추가

보이는 패턴: 판단은 내장, 공급은 설치

  • “판단하는 쪽”(HPA)은 내장, “숫자를 공급하는 쪽”(metrics-server 등)은 설치
  • Kubernetes는 “HPA는 metrics.k8s.io에 물어본다"는 규칙과 빈 자리만 갖고 있다
    • 그 자리를 채우는 건 세 종류 다 애드온이다
  • cAdvisor처럼 측정 자체는 필수라 kubelet에 넣었다
  • “어떻게 모아서 노출할지"는 환경마다 원하는 게 달라서 코어에서 빼고 교체 가능하게 둔 것이다
    • Prometheus로 대체하는 곳도 많다

HPA 가 반응하지 않을 때: 지표 공급부터

  • HPA YAML을 만들었는데 아무 반응이 없다면 HPA 문제가 아니다
  • 지표 공급이 없는 경우가 대부분이다
kubectl describe hpa random-generator
# unable to get metrics ...   → metrics-server 부터 확인

7.3 서로 모르는데 맞물린다#

각자 자기 신호만 보는 확장기들

  • 이 장의 확장기들은 서로 대화하지 않는다
    • HPA는 Pod만 본다
    • CA는 Pending Pod와 빈 노드만 본다
    • VPA는 HPA가 있는지조차 모른다
    • KEDA는 HPA를 만들어놓고 0↔1만 챙긴다
  • 그런데 결과적으로 릴레이가 이어진다

릴레이 순서

  1. HPA/VPA: “Pod 가 더 필요해”
  2. 자리 없으면 Pending → CA: “노드 하나 더”
  3. 한가해지면 HPA: Pod 줄임 → 노드 비어감
  4. 10분 후 CA: 노드 반납

분리되어 있지만 보완적(decoupled but complementary)

  • 책의 표현은 “분리되어 있지만 보완적(decoupled but complementary)“이다
  • 아무도 다음 사람에게 전화하지 않았는데 각자 자기 신호(CPU, Pending, 빈 노드)만 보고 움직이니 전체가 맞물린다
  • 24장의 컨트롤 플레인·데이터 플레인 분리, 26장의 인증·인가 분리와 같은 설계
    • 정해진 신호로만 소통하고 서로의 내부는 모른다

분리가 독이 되는 경우: 같은 신호

  • 다만 6.3에서 봤듯 같은 신호를 둘이 보면 이 분리가 독이 된다
  • HPA와 VPA가 둘 다 CPU를 보면 이중 확장이다
  • 분리는 신호가 겹치지 않을 때만 안전하다

릴레이의 출발점: 실측

  • 이 릴레이의 출발점은 언제나 실측이다
    • 사람이 “아마 100명 올 거야"라고 짐작한 숫자가 아니다
    • 지금 문 앞에 47명 서 있다는 측정값이다
  • 그것이 2.3의 antifragile — 부하가 올수록 시스템이 커지는 성질 — 을 만든다

핵심 메시지#

Elastic Scale 의 몫

  • 예측이 아니라 실측에 반응해서, 세 축으로 스스로 커지고 작아지는 것

전제

  • 숫자를 미리 알 수 없다
    • 규칙만 정하고 값은 측정에 맡긴다
  • 수동은 예측적(미리), 자동은 반응적(뒷북) — 둘 다 자리가 있다

수동

  • scale 은 빠르지만 파일에 안 남는다
  • 급하면 쓰되 반드시 YAML 에 역반영

HPA

  • 이 장에서 유일하게 내장
  • Deployment 에 붙인다 (ReplicaSet 아님)
  • 분자(측정값)는 metrics-server, 분모(requests)는 Pod spec — 둘 다 있어야 %
  • 지표는 “Pod 를 늘리면 내려가는가” 로 고른다
    • 메모리는 대부분 아니다
  • 늘릴 땐 빨리 줄일 땐 천천히 — behavior 는 YAML 로만

자리

  • APIService 는 그룹마다 하나
  • 두 개 붙이면 에러 없이 덮어써진다

0 으로

  • Pod 가 없으면 HPA 는 볼 게 없다
    • Pod 앞에 문지기를 둔다
  • Knative: HTTP, 푸시, 기본은 KPA(HPA 클래스도 지원)
    • Activator 가 요청을 붙잡아둔다
  • KEDA: 이벤트, 풀, HPA 위에 얹음
    • 0↔1 만 직접

VPA

  • requests 를 실측으로
  • 재시작이 문제였고 InPlaceOrRecreate 가 답이 되는 중
  • Off 로 시작
  • HPA 와 같은 지표 보면 이중 확장

CA

  • CPU 가 아니라 Pending 을 본다
  • 노드를 빼려면 네 조건 + 10분
  • 리소스가 아니라 Pod 하나
    • 클라우드 API 를 직접 부른다

수준

  • 앱 튜닝이 맨 위
    • 밑에서 안 쓰면 위에서 아무리 줘도 낭비
  • 앱 튜닝 → VPA(Off) → HPA → CA 순으로 쌓는다

Elastic Scale 은 “숫자를 맞추는 패턴이 아니라, 숫자를 맞추지 않아도 되게 만드는 패턴” 이다. 사람은 울타리와 목표만 정하고, 측정은 kubelet 이, 판단은 HPA 가, 자리는 CA 가 각자 맡으며, 서로 대화하지 않는데도 신호가 이어진다. 그러면 트래픽이 몰릴수록 시스템은 약해지는 대신 커진다.

Pod 리소스 resize 서브리소스와 제자리 수정(6.1)은 "Resize CPU and Memory Resources assigned to Containers" 문서에, VPA 의 InPlaceOrRecreate 모드는 autoscaler 저장소의 VPA 문서에 있다.
Knative 의 Activator·Queue-proxy·Autoscaler 구조와 autoscaling.knative.dev/ annotation 목록(5.2)은 Knative Serving 의 "Autoscaling" 문서에, KEDA 가 ScaledObject 로부터 HPA 를 생성하고 0↔1 만 직접 처리한다는 점(5.3)은 KEDA 의 "Concepts" 문서에 정리되어 있다. Cluster Autoscaler 의 축소 조건 네 가지와 10분 대기, expander 종류(6.4~6.5)는 autoscaler 저장소의 FAQ 가 가장 정확하다.
책 예제에서 눈에 띈 것 — Example 29-1 의 kubectl scale random-generator 는 리소스 종류(deployment)가 빠져 있어 실제로는 동작하지 않는다. "모든 behavior 매개변수를 kubectl autoscale 로 구성할 수 있다"는 문장은 실제와 다르며, 해당 명령이 받는 건 --min·--max 와 목표치 플래그(지금 레퍼런스 기준 --cpu·--memory) 정도이고 behavior 를 정하는 플래그는 없다. VPA 의 Auto 모드가 "미래에 제자리 수정을 지원할 예정"이라는 서술(2023 기준)은 이후 InPlaceOrRecreate 라는 별도 모드로 실현되었고, Auto 는 여전히 Recreate 와 같이 동작한다. Google Stackdriver 는 현재 Google Cloud Monitoring 으로 이름이 바뀌었다.
