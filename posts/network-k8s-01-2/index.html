1. Overview#

IP 줄은 끝까지 같고, MAC 줄은 칸마다 바뀌고, 길은 라우터마다 이정표로 정한다

01-1 이 컴퓨터 한 대 안에서 curl 을 뜯어본 이야기였다면, 이 글은 그 상자가 밖으로 나가는 이야기다. 01-1 의 캡처는 루프백(lo0)이라 MAC 주소도 라우터도 없었다. 이번엔 실제 와이파이에서 공유기, 통신사, 인터넷을 건너간다.

볼 것은 네 가지다. 노트북은 상대가 같은 동네인지 어떻게 판단하나. 동네 밖으로 나간 패킷은 어떻게 길을 찾나. 이번 칸에서 건넬 기기의 MAC 은 어떻게 알아내나. 그리고 쿠버네티스는 이 모든 걸 어떻게 다시 조합하나.

2. IP — 끝까지 바뀌지 않는 주소#

IP 의 일은 상자에 주소를 붙여 목적지까지 보내는 것이다. 다만 도착을 약속하지는 않는다. 잃어버려도, 순서가 바뀌어도 IP 는 신경 쓰지 않는다. 그 뒷수습은 TCP 가 한다.

2.1 IPv4 헤더 — 캡처 값으로 읽기#

01-1 에서 뜯어본 IP 헤더 20바이트를 실제 모양대로 그리면 이렇다. 색이 있는 칸만 보면 된다.

IPv4 헤더 20바이트 — 색이 있는 칸만 알면 된다. 값은 01-1 에서 캡처한 5번 패킷

TTL 은 라우터를 하나 지날 때마다 1씩 준다. 0 이 되면 버려진다. 길을 잃은 패킷이 영원히 떠도는 걸 막는 장치다. 4장의 traceroute 가 이걸 이용한다.

2.2 MTU — 짐칸보다 크면 사라진다#

MTU 는 한 번에 보낼 수 있는 패킷의 최대 크기다. 보통 1500바이트다.

이보다 큰 데이터는 보통 TCP 가 처음부터 잘게 나눠 보낸다. 문제는 경로 중간에 MTU 가 더 작은 구간이 있을 때다. 그러면 패킷이 버려지고, 원래는 “너무 크다” 는 ICMP 알림이 돌아온다.

실무에서 자주 겪는 증상이 있다. 중간 방화벽이 그 ICMP 알림까지 막아 버리면, 보내는 쪽은 패킷이 왜 사라지는지 모른다. 작은 요청은 잘 되는데 큰 응답만 멈춘다. 쿠버네티스에서 VXLAN 을 쓸 때 특히 자주 나오는데, 6.2 에서 다시 본다.

2.3 NAT — 공유기는 출발 주소를 바꿔 쓴다#

집 안의 192.168.x.x 주소는 집 안에서만 쓰는 사설 주소다. 이 주소로는 인터넷에 나갈 수 없다. 그래서 공유기가 나가는 패킷의 출발 주소를 자기 공인 주소로 바꿔 쓴다. 이게 NAT 다.

주황이 바뀐 칸 — 출발 주소와 포트가 바뀌고, 도착 주소는 그대로다

공유기는 바꾼 내용을 장부에 적어 두었다가, 답장이 오면 다시 노트북의 주소로 돌려준다. 도착 주소는 그대로다.

여기서 기억할 것. 받는 서버는 노트북의 진짜 주소를 모른다. 출발 주소는 중간에 바뀔 수 있다. 7장에서 쿠버네티스 Service 가 이 NAT 를 반대 방향으로 쓴다.

2.4 CIDR — 마스크는 패킷에 실리지 않는다#

노트북은 패킷을 보낼 때마다 한 가지를 판단한다. 이 주소가 같은 동네인가, 아닌가. 같은 동네면 직접 보내고, 아니면 공유기에 맡긴다.

그 기준이 /24 다.

ifconfig en0 | grep "inet "
# inet 192.168.0.112 netmask 0xffffff00 broadcast 192.168.0.255

netmask 0xffffff00 이 /24 다. 뜻은 하나다. 주소의 앞 세 칸(192.168.0)이 같으면 같은 동네다. 이 동네에는 기기를 254대까지 붙일 수 있다.

보낼 때마다 노트북은 마스크로 동네를 비교해 직접 보낼지 공유기에 맡길지 정한다

꼭 기억할 건 하나다. 이 /24 는 패킷 어디에도 적혀 있지 않다. 2.1 의 그림을 다시 보면, IP 헤더의 주소 칸은 출발과 도착 두 개뿐이다. 마스크는 노트북 혼자 들고 있는 설정이다.

그래서 생기는 일이 둘 있다.

  • 같은 IP 라도 마스크가 다르면 동네가 달라진다. 192.168.1.2/24 에게 192.168.5.9 는 다른 동네지만, /16 이면 같은 동네다. 그래서 같은 동네의 기기들은 마스크를 똑같이 맞춰야 한다. 한 기기만 틀리면 그 기기만 판단이 어긋나고, 패킷에는 흔적이 남지 않는다. 원인은 ifconfig 를 봐야 찾는다.
  • 마스크가 맞는지 장비가 스스로 검사하지는 않는다. 사람이 정하거나, 공유기가 DHCP 로 주소와 함께 나눠 준 값을 그대로 믿고 쓴다.

참고로 쿠버네티스도 같은 방식을 쓴다. Pod 전체에 /16 을 잡고, 노드마다 /24 씩 나눠 준다.

2.5 LAN 과 서브넷 — 선이 정하는 범위, 주소가 정하는 범위#

지금까지 “같은 동네” 라고 부른 건 정확히는 같은 서브넷이다. “같은 와이파이”, “같은 LAN” 과 비슷하게 쓰지만 둘은 다른 것이다. 아래 그림의 브로드캐스트는 같은 LAN 의 모두에게 한 번에 보내는 것을 말한다(5.2).

같은 기기가 아래 판(선)에서는 몸으로, 위 판(주소)에서는 IP 로 존재한다

둘을 짝지어 주는 게 DHCP 다. 와이파이에 막 붙은 노트북이 주소를 받는 과정을 보면, LAN 이 IP 보다 먼저 있다는 것도 함께 보인다.

주황 점선은 브로드캐스트, 파랑 실선은 공유기의 답 — 이 네 번의 교환이 LAN 과 서브넷을 짝지어 준다

DHCP 메시지 자체는 이렇게 생겼다. 아직 IP 가 없는데도 IP 패킷으로 보낸다는 점이 재미있다. 출발 주소를 0.0.0.0 으로 비워 두고, 도착을 255.255.255.255(이 LAN 의 모두)로 적는다.

IP 를 받기 전에도 IP 패킷으로 보낸다 — 출발을 비워 두고 모두에게 브로드캐스트할 뿐이다

짝이 맞아야 노트북의 판단(2.4)이 맞는다. 어긋나면 이렇게 된다. 예시 주소는 모두 사설 대역이다.

점선 상자는 선이 정하는 LAN, 색 띠는 주소가 정하는 서브넷 — 둘이 겹쳐야 노트북의 판단이 맞는다

실무에서 가장 흔한 어긋남은 VPN 이다. 공유기 기본값이 대개 192.168.0.x 나 192.168.1.x 라서, 집과 회사 내부가 같은 사설 대역을 쓰는 일이 잦다.

노트북은 192.168.1.20 이 어느 쪽인지 서브넷으로 구분하지 못한다 — 집 서브넷을 흔하지 않은 대역으로 바꾸면 피할 수 있다

3. Routing and BGP — 이정표는 누가 세우나#

3.1 라우팅 테이블 — 가장 길게 맞는 줄#

패킷은 스스로 길을 모른다. 라우터마다 있는 라우팅 테이블을 보고 다음 칸으로 넘어갈 뿐이다. 이정표라고 생각하면 된다.

노트북에도 라우팅 테이블이 있다.

netstat -rn -f inet           # Linux: ip -4 route show
route -n get 1.1.1.1          # Linux: ip route get 1.1.1.1

중요한 줄은 셋이다. 주소 두 개를 넣어 보면 어느 줄을 타는지 보인다.

여러 줄이 맞으면 가장 구체적인 줄, 아무 줄도 안 맞으면 default 로 간다

어떤 주소가 여러 줄에 맞으면, 가장 구체적인 줄을 따른다. 아무 줄에도 안 맞으면 default 로 간다. 구글이든 네이버든 우리 동네가 아니면 전부 공유기로 가는 이유다.

2.4 와 이어지는 부분이다. /24 같은 숫자는 패킷이 아니라 이 테이블의 줄에 붙어 있다. 패킷의 도착 주소는 처음부터 끝까지 그대로이고, 라우터마다 자기 테이블과 비교할 뿐이다. 편지 봉투의 주소는 그대로인데, 먼 우체국은 “서울” 까지만 보고 가까운 우체국은 “역삼동” 까지 보는 것과 같다.

그래서 공인 IP 하나가 여러 크기의 덩어리에 동시에 속하는 것도 정상이다. 멀리 있는 라우터는 /16 같은 큰 덩어리로, 가까운 라우터는 /24 로 알고 있다.

3.2 default 의 사슬 — 통신사가 공유기에, 공유기가 노트북에#

그럼 노트북의 default 줄은 누가 적었을까. 공유기가 알려 줬다. 공유기의 default 는 통신사가 알려 줬다.

공유기는 안쪽에선 DHCP 서버, 바깥쪽에선 DHCP 클라이언트다 — default 는 이렇게 한 칸씩 위에서 내려온다

아래쪽 기기들은 “모르면 위로 넘긴다” 한 줄이면 충분하다. 진짜 길을 아는 건 맨 위의 통신사 라우터들이다.

통신사의 큰 라우터는 전 세계 경로를 들고 있다. IPv4 만 약 100만 줄이다. 주소가 43억 개인데 100만 줄로 되는 건, 주소를 큰 덩어리로 묶어서 적기 때문이다.

3.3 BGP — 대역의 도달 경로를 광고한다#

통신사 라우터의 100만 줄은 사람이 쓰지 않는다. 라우터끼리 서로 알려 줘서 채운다. 그 방법이 BGP(Border Gateway Protocol)다.

왜 알려 줘야 할까. KT 라우터에는 케이블이 여러 개 꽂혀 있다. 142.250.1.1 로 가는 패킷이 오면 어느 케이블로 보내야 할지 정해야 하는데, 그 주소가 구글 것이라는 걸 KT 는 원래 모른다. 주소의 주인인 구글이 알려 줘야 이정표에 적을 수 있다.

BGP 는 이정표를 미리 세워 두는 대화다 — 사용자 패킷 안에 들어 있지 않다

이 소식이 이웃에서 이웃으로 퍼지면서 전 세계 이정표가 채워진다. 받은 라우터는 여러 길 중 하나를 골라 테이블에 적는다. 사용자 패킷 안에 BGP 가 들어 있는 건 아니다. BGP 는 이정표를 미리 세워 두는 일만 하고, 사용자 패킷은 세워진 이정표만 보고 지나간다.

그럼 KT 와 구글이 “이어져 있다” 는 건 실제로 무슨 뜻일까.

인터넷은 상자(라우터)와 상자 사이에 꽂은 케이블이고, BGP 는 케이블로 이미 이어진 두 상자의 대화다

말 그대로 라우터 포트끼리 광케이블을 꽂아 둔 것이다. 여러 회사가 한 건물(IX)에 라우터를 모아 두고 서로 케이블을 연결한다. 그 케이블 위에서 TCP 179 번으로 BGP 대화를 한다.

무선은 생각보다 아주 짧은 구간에만 쓰인다. 노트북에서 공유기까지, 폰에서 기지국까지뿐이고, 나머지는 전부 광케이블이다. 그래서 온프레미스로 서버를 운영하는 회사도 무선이 아니라 고정 IP 가 붙은 기업용 회선을 쓰거나, 서버를 데이터센터에 맡긴다.

BGP 를 쓰는 건 통신사만이 아니다. 여러 망과 직접 이어진 곳, 구글 같은 큰 서비스나 클라우드도 쓴다. 집은 길이 하나뿐이라 BGP 없이 DHCP 로 받은 default 한 줄이면 된다.

3.4 Kubernetes 에서 — 알리거나 감싸거나#

쿠버네티스에서도 같은 문제가 생긴다. Pod 주소(10.244.x.x)는 쿠버네티스가 만든 주소라서, 바깥 라우터들은 모른다. 그럼 다른 노드에 있는 Pod 에게는 어떻게 보낼까. 방법은 크게 둘이다.

알리기
노드가 자기 Pod 대역을 BGP 로 라우터에 알린다 · 예: Calico
감싸기
Pod 패킷을 노드 주소가 적힌 봉투에 넣어 보낸다 · 예: Flannel (VXLAN)

어느 방법을 쓸지는 CNI 플러그인이 정한다. 감싸기는 6장에서 뜯어본다.

4. ICMP — IP 계층의 진단과 오류 통지#

ICMP 는 네트워크 상태를 알려 주는 짧은 메시지다. 01-1 의 6.2 에서 닫힌 UDP 포트의 거절을 전해 준 게 ICMP 였다.

ICMP 는 TCP 나 UDP 를 거치지 않고 IP 안에 바로 들어간다. TCP, UDP 와 나란히 있는 별도의 프로토콜이다. 포트가 없어서, 프로그램이 아니라 OS 가 답한다.

IP 헤더의 Protocol 칸이 안에 든 것을 알려 준다

자주 보는 종류는 셋이다.

Echo Request / Reply
ping 의 질문과 답
Destination Unreachable
갈 수 없을 때 · 01-1 의 닫힌 UDP 포트
Time Exceeded
TTL 이 다 됐을 때 · traceroute

4.1 ping — 포트가 없어서 OS 가 답한다#

ping 은 상대 주소까지 패킷이 갔다 오는지 확인한다. 공유기에 보내 봤다.

ping -c 3 192.168.0.1
# 3 packets transmitted, 3 packets received, 0.0% packet loss
# round-trip avg = 9.2 ms

바로 옆 공유기인데 9ms 다. 와이파이 구간 때문이다. 유선이면 보통 1ms 도 안 걸린다.

ping 을 해석할 때 두 가지를 주의하자.

  • 답이 없다고 서버가 죽은 건 아니다. 방화벽이 ICMP 만 막았을 수 있다.
  • 답이 와도 웹 서버가 살아 있다는 뜻은 아니다. ping 은 주소까지만 확인한다. 포트는 TCP 로 직접 확인해야 한다.
nc -zv 127.0.0.1 8080   # 8080 포트에 TCP 연결만 시도해 본다

4.2 traceroute — TTL 을 하나씩 늘려 길을 그린다#

traceroute 는 목적지까지 거쳐 가는 라우터를 보여 준다. 원리는 2.1 의 TTL 이다. TTL 을 1 로 보내면 첫 라우터에서 수명이 다해 Time Exceeded 가 돌아온다. 그걸로 첫 칸이 누군지 안다. TTL 을 2, 3 으로 늘려 가면 경로 전체가 그려진다.

traceroute -n -q 1 -w 2 1.1.1.1
9장의 집 → 통신사 → … → 목적지 그림의 실물. 중간 통신사 주소는 가렸다

3장에서 그림으로 본 “집 → 통신사 → … → 목적지” 가 실제로 이렇게 찍힌다.

결과를 읽을 때 두 가지를 보자.

  • 3~6번의 * 는 길이 끊긴 게 아니다. 패킷은 잘 넘겨 주면서 Time Exceeded 답만 안 보내는 라우터다. 9번까지 도착한 게 그 증거다.
  • 1.1.1.1 은 미국 회사 주소인데 16ms 만에 답이 왔다. 미국까지 다녀오면 150ms 는 걸려야 한다. 같은 주소를 세계 여러 곳에서 동시에 알리는 방식(애니캐스트, BGP) 덕분에 가까운 서버가 답한 것이다.

5. Ethernet and ARP — 이번 한 칸의 주소#

5.1 MAC 과 IP — 최종 주소와 이번 칸#

패킷에는 주소가 두 종류 붙는다. IP 주소와 MAC 주소. 둘의 차이를 알면 이 장은 끝이다. 노트북에서 구글까지 가는 동안 두 주소가 어떻게 되는지 보자.

노트북이 ARP 로 찾는 건 구글 서버가 아니라 첫 칸, 공유기의 MAC 이다

IP 는 최종 목적지라 끝까지 같고, MAC 은 이번 한 칸에서 받을 옆 기기라 칸마다 바뀐다. 택배로 치면 IP 는 송장에 적힌 최종 받는 사람이고, MAC 은 지금 이 구간에서 상자를 넘겨받을 사람이다.

MAC 주소를 붙이는 규칙이 Ethernet 이다. IP 가 하나의 프로토콜인 것처럼 Ethernet 도 IP 한 층 아래의 프로토콜이고, Ethernet 헤더가 IP 헤더에 해당한다. 프레임 모양은 이렇다.

Ethernet 헤더는 IP 헤더와 같은 역할을 한 층 아래에서, 이번 한 칸에 대해 한다

5.2 ARP — 같은 링크에서 IP 를 MAC 으로#

노트북이 공유기에게 보내려면 공유기의 MAC 을 알아야 한다. 그런데 노트북이 아는 건 IP(192.168.0.1)뿐이다. 이걸 MAC 으로 바꿔 주는 게 ARP 다.

방법은 단순하다. 같은 동네 전체에 물어보고, 해당 기기만 답한다. 이렇게 같은 LAN 의 모두에게 한 번에 보내는 걸 브로드캐스트라고 한다. 받는 MAC 칸에 ff:ff:ff:ff:ff:ff 를 적으면 된다.

질문은 동네 전체에 브로드캐스트하고, 답은 그 IP 의 주인만 묻는 쪽에게 직접 보낸다

한 번 알아낸 MAC 은 한동안 저장해 두고(ARP 캐시) 다시 묻지 않는다. arp -a 로 볼 수 있다.

ARP 메시지 안에는 네 칸이 핵심이다. 보내는 쪽 MAC 과 IP, 찾는 쪽 MAC 과 IP. 질문할 때는 찾는 쪽 MAC 이 빈칸이고, 답하는 기기가 그 빈칸을 채워 돌려준다. 안에 IP 주소가 들어 있지만 배달 주소가 아니라 질문 내용이다.

그래서 ARP 는 IP 헤더 없이 Ethernet 에 바로 실린다. 보통 L2(링크 계층)로 분류하고, IP 주소를 다루니 L2 와 L3 사이라고도 한다. IP 헤더가 없다는 게 중요한데, 라우터는 IP 헤더를 보고 넘겨 주는 장비라서 ARP 는 라우터를 넘어가지 못한다. ARP 질문은 항상 같은 동네 안에서만 들린다.

실제 와이파이에서 캡처해 봤다.

sudo tcpdump -i en0 -nn arp
# ARP, Request who-has 192.168.0.35 tell (집의 다른 PC), length 46
# ARP, Request who-has 192.168.0.35 tell (집의 다른 PC), length 46
# … 약 1초 간격으로 계속, 답은 없음

두 가지를 알 수 있다. 첫째, 노트북과 상관없는 다른 PC 의 질문도 다 보인다. 동네 전체에 묻는 방식이라서다. 둘째, 답이 없으니 그 PC 는 계속 묻는다. .35 기기가 꺼져 있는 것으로 보인다. MAC 을 모르면 패킷을 보낼 수 없어서, 그 PC 의 통신은 시작도 못 하고 있다.

이제 이 장에서 가장 중요한 내용이다. 노트북이 구글로 보낼 때, ARP 로 찾는 건 구글 서버의 MAC 이 아니다. 공유기의 MAC 이다. 5.1 의 그림에서 첫 칸의 MAC 이 “노트북 → 공유기” 였던 이유다.

  • MAC 은 이번 한 칸에서만 쓰는 주소다. 멀리 있는 기기의 MAC 은 알아도 쓸 데가 없다.
  • ARP 질문은 라우터를 넘어가지 못한다. 동네 밖으로는 물어볼 방법이 없다.

각 장비는 바로 옆 이웃의 MAC 만 안다. 공유기도 구글 MAC 은 모르고 통신사 라우터의 MAC 만 안다. 같은 동네면 상대의 MAC 을, 다른 동네면 공유기의 MAC 을 찾는다. 2.4(같은 동네인지 판단), 3.1(default 는 공유기), 5.2(공유기 MAC 찾기)가 여기서 하나로 이어진다.

5.3 라우터 한 칸 — 벗기고, 보고, 새로 붙인다#

그럼 공유기는 받은 패킷을 어떻게 다음 칸으로 넘길까.

주황이 바뀐 칸 — MAC 라벨은 칸마다 새로 붙고, 도착 IP 와 HTTP 는 그대로 간다

공유기는 받은 MAC 라벨을 떼고, IP 를 보고 다음 칸을 정한 뒤, 다음 칸의 MAC 을 ARP 로 찾아 새 라벨을 붙여 내보낸다. 인터넷의 모든 라우터가 칸마다 이 일을 반복한다.

그림에서 주황색이 바뀐 칸이다. MAC 은 매번 바뀌고, NAT 때문에 출발 IP 와 포트도 바뀐다. 도착 IP 와 HTTP 내용은 끝까지 그대로다.

라벨 종류 자체가 바뀌기도 한다. 노트북에서 공유기까지는 와이파이 라벨, 공유기에서 통신사까지는 Ethernet 라벨이다. IP 는 아래가 무엇이든 신경 쓰지 않는다. 층끼리 서로의 속을 몰라도 된다는 게 바로 이것이다.

5.4 라우터의 두 표 — 길은 크게, 이웃은 작게#

패킷마다 ARP 를 하지는 않는다. 그리고 인터넷 라우터가 전 세계 MAC 을 기억하는 것도 아니다. 내 패킷이 건너는 라우터는 열몇 개(4.2 의 traceroute 는 9칸)이고, 각 라우터 안에는 크기가 전혀 다른 표가 두 개 있다.

멀리는 서브넷 단위의 큰 표로 길을 찾고, 바로 옆은 작은 표로 MAC 을 찾는다 — 그래서 패킷마다 ARP 를 하지 않는다

6. VLAN and VXLAN — 나누는 것과 잇는 것#

6.1 VLAN — 라벨 사이의 4바이트 스티커#

VLAN 은 스위치 하나를 여러 동네로 나누는 기술이다. 5.2 에서 본 것처럼, 같은 스위치에 꽂힌 기기들은 서로의 ARP 질문이 다 들린다. 회사에서 직원 PC 와 서버를 섞어 두면 곤란하다. 그래서 칸막이를 친다.

방법은 새 상자를 씌우는 게 아니라, Ethernet 라벨 중간에 4바이트 표시를 끼워 넣는 것이다.

VLAN 은 새 상자를 씌우지 않고, 보내는 MAC 과 EtherType 사이에 4바이트를 끼운다

알아 둘 건 두 가지다.

  • 다른 VLAN 으로 가려면 라우터를 거쳐야 한다. 다른 동네가 되기 때문이다.
  • 이 표시는 보통 스위치가 붙이고 뗀다. PC 쪽에서는 거의 안 보이고, 쿠버네티스가 직접 쓰지도 않는다.

6.2 VXLAN — 프레임을 UDP 봉투에 통째로#

VXLAN 은 반대로 떨어져 있는 네트워크를 하나처럼 잇는 기술이다. 쿠버네티스에서 중요한 쪽은 이것이다.

3.4 의 문제로 돌아가자. 노드 1 의 Pod A 가 노드 2 의 Pod B 에게 보내고 싶다. 그런데 중간 네트워크는 Pod 주소를 모른다. 해법은 봉투다. Pod 패킷을 통째로, 노드 주소가 적힌 봉투에 넣어 보낸다.

바깥 네트워크는 노드 주소만 보고 배달하고, Pod 주소는 봉투를 싸고 뜯는 노드끼리만 안다

중간 네트워크는 봉투에 적힌 노드 주소만 보고 배달한다. 받은 노드가 봉투를 뜯어 Pod B 에게 넘긴다. 봉투를 싸고 뜯는 일은 CNI 가 노드마다 만들어 둔 가상 장치(flannel.1 같은)가 한다.

봉투는 IP 와 UDP 다. 표준 포트는 4789 이고, Flannel 은 8472 를 쓰는 경우가 많다. 바깥이 UDP 라고 Pod 끼리의 통신이 UDP 가 되는 건 아니다. 안쪽은 원래대로 TCP 다. 봉투 하나를 잃어버리면 안쪽 TCP 가 알아채고 다시 보낸다. 바깥까지 TCP 로 싸면 같은 확인을 두 번 하게 되니, 바깥은 가벼운 UDP 로 운반만 한다.

그래서 노드에서 캡처하면, Pod 끼리 HTTP 를 주고받아도 바깥에는 UDP 로 보인다.

주의할 점이 하나 있다. 봉투를 씌운 만큼(약 50바이트) 안에 담을 수 있는 크기가 줄어든다. 그래서 CNI 는 Pod 의 MTU 를 1450 정도로 낮춰 둔다. 이게 어긋나면 2.2 에서 말한 “작은 요청은 되는데 큰 응답만 멈추는” 증상이 나온다.

VLAN — 나눈다
라벨에 동네 번호를 끼워 스위치 하나를 여러 동네로 · 쿠버네티스는 직접 안 씀
VXLAN — 잇는다
프레임을 UDP/IP 봉투에 통째로 넣어 노드 사이를 잇는다 · CNI 가 씀

7. Kubernetes — 새 네트워크가 아니라 조합#

7.1 회사로 보는 부품 — 대표 번호와 교환원#

쿠버네티스의 네트워크 부품을 회사에 비유하면 한 번에 정리된다. 주문 Pod 가 결제 서비스에 전화를 거는 장면이다.

Service 는 기기가 아니라 번호이고, 실제로 전화를 돌리는 건 노드 커널이다
  • Pod 는 직원이다. 내선 번호(Pod IP)가 있고 자주 바뀐다.
  • Service 는 부서 대표 번호다. 직원이 바뀌어도 그대로다.
  • EndpointSlice 는 대표 번호 뒤의 담당자 명단이다.
  • 노드 커널(kube-proxy 가 설정)은 교환원이다. 대표 번호로 온 전화를 명단을 보고 담당자에게 돌린다.
  • CoreDNS 는 전화번호부, CNI 는 내선 번호를 주고 건물 사이 선을 까는 공사 업체다.

하나만 기억하자. yaml 은 주문서다. Service 를 만드는 건 “대표 번호를 만들어 달라” 는 신청서를 내는 것이고, 실제로 전화를 돌리는 건 각 노드의 리눅스 커널이다. 3.3 에서 BGP 가 이정표를 세우고 패킷은 이정표만 보고 지나간 것과 같은 구조다.

7.2 Service IP — 어떤 기기에도 없는 주소#

Service IP 에는 특이한 점이 있다. 어떤 기기에도 붙어 있지 않다. 그럼 어떻게 동작할까. 2.3 의 NAT 를 반대 방향으로 쓴다. 공유기는 나가는 패킷의 출발 주소를 바꿨다. 노드 커널은 Pod 가 보낸 패킷의 도착 주소를, Service IP 에서 실제 Pod IP 로 바꾼다. 받을 기기가 없으니 Service IP 로 ping 을 하면 보통 답이 없다.

대표 번호가 필요한 이유는 Pod 가 자주 바뀌기 때문이다. Pod 가 죽고 다시 뜨면 IP 도 바뀐다. 그래서 바뀌지 않는 번호를 앞에 두고, 뒤의 명단(EndpointSlice)만 쿠버네티스가 자동으로 고친다.

Service IP 는 클러스터 안에서 쓰는 번호다. 바깥과 통하는 길은 따로 있다.

Service IP 는 안에서 쓰는 번호다 — 들어올 땐 Ingress·LB, 나갈 땐 노드가 집 공유기처럼 주소를 바꾼다

7.3 요청 하나 — 앞의 장들이 일곱 단계에#

Pod 하나가 my-svc 에 요청할 때 일어나는 일이다. 오른쪽이 앞에서 본 절이다.

8.1 층은 디버깅 도구다#

1장을 다 읽고 남는 건 일곱 층의 이름이 아니라 질문 하나다. 지금 몇 층이 고장 났나. 두 편에서 직접 본 장면들을 그 질문으로 다시 묶으면 이렇다.

쿠버네티스는 새로운 네트워크를 만들지 않는다. Service 는 NAT 이고, Pod 사이의 길은 라우팅이나 봉투이고, 그 아래는 여전히 TCP 와 ARP 다. 추상화는 평소 일을 덜어 주지만, 장애의 원인까지 감춰 주지는 않는다. curl 한 번을 끝까지 따라가 본 경험이 yaml 몇 장을 더 외우는 것보다 오래 쓸모 있는 이유다.

VXLAN 봉투의 UDP 목적지 포트는 RFC 7348 의 패킷 형식 설명에 정해져 있다.
"IANA has assigned the value 4789 for the VXLAN UDP port, and this value SHOULD be used by default as the destination UDP port."
[해석] "IANA 는 VXLAN UDP 포트로 4789 를 할당했으며, 이 값을 기본 목적지 UDP 포트로 사용해야 한다(SHOULD)." — 6.2 의 4789 의 근거다. SHOULD 라서 Flannel 처럼 다른 포트(8472)를 쓰는 구현도 있다. ARP 는 RFC 826 이 원본이고, RFC 1122 는 ARP 를 링크 계층 절(2.3.2)에서 다룬다 — 5.2 의 분류 근거다.
