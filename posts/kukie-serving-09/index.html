1. Overview#

위 줄은 데이터, 아래 줄은 모델 쪽이다. 번호와 아래 띠를 누르면 해당 절로 이동한다

이 글의 범위

  • Kukie Model 의 학습 1회차와 2회차다. 학습 전 Qwen3.8-27B 가 스스로 푼 풀이 중 맞혔고 근거가 있는 것만 골라 27B 자신을 학습했다(rejection-sampling fine-tuning)
  • 측정 방법, 세트의 역할, 판정 규칙은 Serving.08 에서 다뤘다. 이 글은 그 설계 위에서 나온 숫자와 그 과정에서 걸린 멈춤 조건을 다룬다
  • 결과: 2회차 모델은 새 외부 문제 A 에서 학습 전보다 좋아졌다(+6.1%p, 95% 구간 +0.8 ~ +12.0). Hugging Face 에 Kause-K8s-27B v0.2 로 올렸다

2. Background — 9B 학생에서 27B 자기 학습으로#

처음 계획은 작은 학생 모델(Qwen3.5-9B)을 큰 교사(Qwen3.8-27B)의 풀이로 학습하는 것이었다. 11-16 하루에 SFT 를 세 번 했다.

회차무엇을 바꿨나결과읽은 것
SFT 1차교사 기록 421개공개 원본 58.0 → 47.0%, 판단 보류상한 걸림은 30% → 2% 로 줄었지만, 답의 35~43% 가 namespace 를 빼먹음
SFT 2차기록 파일의 인자 순서 고침58.0 → 75.7%, +17.7%p [+3.0, +31.6]끝까지 답한 실행끼리는 −9.4%p. “상한 안에 끝내는 습관으로 설명됨”
SFT 3차단독 파드 기록 84개 더함decoy-v1 조건부 +5.0%p [−4.4, +15.5]겨냥한 유형만 고침. 나머지는 −4.2%p
  • 1차의 namespace 빠짐은 기록 파일을 sort_keys=True 로 써서 생겼다. 학습 정답의 인자가 알파벳순이 됐는데, 서빙은 strict 도구 스키마 문법이 순서를 강제한다. 둘이 어긋나 모델이 namespace 를 건너뛰었다
  • 9B 가 배운 것은 대부분 “요청 상한 안에 답을 끝내는 습관"이었다. 진단 자체가 나아졌다는 증거는 나오지 않았다
  • 교사 27B 는 학습 없이 공개 세트에서 루나 대비 0.98배였다. 작은 학생을 끌어올리는 것보다 27B 를 그대로 다듬는 쪽이 빨랐다

11-17 새벽 사용자가 9B 를 멈추고 27B 자체를 학습하기로 정했다. 교사와 학생이 같은 모델이 되므로 기록은 “27B 가 스스로 맞힌 풀이"가 된다. 루나 출력은 이때도 학습에 쓰지 않았다.

3. Round 1 — 자기 정답 505개#

1회차(RFT1)의 목표는 하나였다. 자기 풀이로 학습해도 아무것도 망가지지 않는지 확인하는 것이다(DURO-289). 판정 기준은 학습 전에 커밋했다.

데이터와 학습

  • 기록: 9B 때 모은 27B 교사 기록 421개 + 단독 파드 기록 84개 = 505개. 모두 학습 전 27B 가 생성기 문제를 풀고 근거 v2 로 거른 것이다
  • 27B 토크나이저로 다시 렌더링했다. 27B 템플릿은 참·거짓을 true/false 로 적고 지난 턴에 빈 생각 블록을 남겨서, 9B 토큰 파일과 505개 중 319개만 같다
  • LoRA rank 32, alpha 16, 모든 선형층, lr 1e-4 하나, 2에폭 64스텝, 마지막 체크포인트. 학습률이나 체크포인트를 고르지 않았다
  • 장비: g6e.12xlarge(L40S 4장). bf16 27B 를 2장에 층 단위로 나눈 벌 2개가 배치를 반씩 나눠 기울기를 구한다. 125분, GPU 당 최대 38.8 GiB

FP8 합치기. 서빙은 공식 Qwen/Qwen3.8-27B-FP8 과 같은 형식이어야 L40S 1장에 들어간다. LoRA 가 걸린 층만 bf16 원본에 (α/r)·B·A 를 더하고, 공식과 같은 128×128 블록 e4m3 로 다시 양자화한다. 나머지 텐서는 공식 FP8 을 그대로 쓴다. LoRA 없이 같은 스크립트로 다시 만든 400개 층이 공식 FP8 과 바이트까지 100% 같은 것을 먼저 확인했다.

주황 점선은 1회차의 채택 기준(하한 > −5%p)이다. 세 줄 모두 개선을 주장하지 않았다
  • decoy-v1: 하한 −4.4%p > −5%p, 자신 있게 틀림 −1.7%p 로 채택 조건을 넘었다. 하한이 0 이하라 “나빠지지 않음"까지만 쓴다
  • 학습 전이 이미 93.3% 였다. 오를 자리가 6~7%p 뿐이라 이 세트로는 27B 의 개선을 잴 수 없다
  • 평균 뒤에서 한 문제는 크게 쏠렸다. Ingress 고장 문제에서 RFT1 은 9번 모두 멀쩡한 미끼 Service 를 원인으로 골랐다(학습 전 5/9 → 0/9). 거른 기록에 Ingress 고장이 적은 탓으로 본다
  • ITBench: 학습 전과 RFT1 모두 외부 시험에서 decoy-v1 보다 크게 낮았다. 학습 전 기준 차이는 −38.5%p [−63.3, −14.7] 다. 생성기 쪽에서 본 실력이 바깥 문제로 옮겨 가지 않는다

4. Weaknesses — 외부 시험에서 고른 약점#

ITBench 14문제에서 두 모델이 틀린 풀이를 읽고 약점 셋을 골랐다(DURO-291). 이 14문제는 이제 “본 문제"라 2회차의 개선 주장에는 쓰지 않는다(Serving.08 의 7.1절).

처방은 생성기와 거름에만 들어간다
  • W1 은 읽기 도구가 출력을 자르지 않아서 생긴다. 26개 서비스짜리 앱에서 넓은 조회를 몇 번 하면 컨텍스트 64k 를 넘는다. 에이전트를 고치지 않기로 했으므로 “처음부터 좁게 묻는” 풀이만 남기는 쪽으로 가르친다. 32k 를 넘는 풀이는 거름에서 빠진다
  • 큰 앱의 서비스 이름·구조는 생성기의 낱말 목록으로 만들고, ITBench 앱의 출력 크기를 맞추지 않았다. 같은 앱을 외우는 효과(오염 경로 ②)를 막기 위해서다
  • W2 는 증상이 난 서비스와 원인 오브젝트가 다른 문제다. 큰 앱 안에서 하위 서비스를 고장 내 부르는 쪽 로그와 readiness 에 증상이 나게 만들었다
  • W3 는 전용 데이터를 만들지 않았다. 분류 설명이 이미 두 경우를 가르고, 생성기에도 같은 규칙이 있다

5.2 거름과 멈춤 3#

빨간 줄이 두 거름의 가장 큰 차이다

부록 3 의 거름으로 222개가 남았다. 멈춤 3(새 기록 400개, 큰 앱 150개, 1~2단계 150개 이상) 셋 모두 미달이라 학습하지 않았다.

  • 32k 거름은 원인이 아니었다. 32k 단계까지 온 풀이의 99.8% 가 통과했다
  • 원인 정답률도 주 원인이 아니었다. 한 번이라도 맞힌 문제가 669개(85%)였다
  • 원인은 맞힌 풀이가 기록 조건을 채우지 못한 것이다. 원인 직접 조회 검사에서 159문제가 빠졌다. 컨테이너 설정 고장에서 27B 는 Deployment 를 describe 하지 않고, 그 Deployment 가 만든 파드를 describe 해서 고장 필드를 읽고 Deployment 를 답했다
  • 옛 순서 80문제(5규칙)는 거름에서 전부 빠졌다. 순서를 바꾸면 고장이 재현되지 않는 규칙이라 생성기가 옛 순서로 남겼는데, 얼림 2 설명은 “모든 문제가 새 순서"라고 잘못 적었다. 얼림을 지키기로 해서 거름은 바꾸지 않았다

5.3 부록 4: 직접 조회 완화와 추가 수집#

사용자 결정으로 부록 4 를 추가 수집 전에 얼렸다. 판정과 멈춤 기준은 그대로 두고 수집과 거름만 바꾼다.

  • 거름 한 줄: 원인이 워크로드 컨트롤러이고 직접 조회가 없을 때만, 그 컨트롤러가 만든 Pod·Job(<원인 이름>-…)의 describe 를 직접 조회로 본다. 근거 원칙의 “복사본 describe” 경로와 같은 생각이다
  • 추가 문제: 큰 앱만 256문제(32규칙 × 씨앗 8), 그중 192문제가 1~2단계
  • 두 수집을 합쳐 다시 거르니 새 기록 470개, 큰 앱 260개, 1~2단계 200개로 멈춤 3 을 통과했다. 784문제만으로는 약 360개라, 완화만으로는 400 에 못 미쳤다
  • 부록 4 는 결과(멈춤 3 미달)를 본 뒤 썼다. 부록 첫머리에 그 사실을 적었다

6. Training — 2회차 학습과 멈춤 조건#

학습 설정은 1회차와 같다(rank 32, alpha 16, lr 1e-4, 배치 16, 2에폭, 씨앗 279, 마지막 체크포인트). 1회차 LoRA 에서 이어 하지 않고 학습 전 bf16 에서 새로 시작했다. 대화 최대 길이는 32k 로, 551개 토큰 650만 중 loss 토큰은 66만이다.

× 는 멈춤 6으로 멈춘 자리다. 멈춤 조건은 판정 규칙이 아니라 비용 안전장치다
  • 멈춤 5: 첫 스텝이 9.2분이라 약 11시간이 예상됐다(기준 10시간). 알렸고, 사용자가 계속으로 정했다
  • 멈춤 6: 1에폭 체크포인트로 D 의 작은 앱 10문제를 --exec-fix 로 1번씩 풀었다. verify.sh 가 있는 9문제 중 통과가 4개에서 3개로 줄었다(−11%p, 기준 5%p). 규칙대로 44스텝에서 멈추고 장비를 껐다
  • 9문제 × 1번이라 1문제가 11%p 다. 차이는 한 문제에서 원인을 맞히고도 고치기 명령을 내지 않은 것이었다
  • 다시 재기: 돌리기 전에 해석 규칙을 적었다. D 20문제 × 3번, 모델마다 kind 를 따로 새로 만들었다. “−10%p 보다 낮으면 실제로 나빠졌다"가 규칙이었다. 결과는 verify +3.7%p, 원인 +10.0%p 로 나빠졌다는 증거가 없었다. 이 숫자도 판정에는 쓰지 않는다
  • 이어 학습: 사용자가 멈춤 6 을 넘기고 35스텝부터 잇기로 정했다. 35스텝 저장본에는 옵티마이저 상태가 없어 AdamW 를 새로 시작하고 워밍업 3스텝을 다시 했다. 원래 계획과 다른 점은 이것 하나다

멈춤 조건은 비용 안전장치다. 넘겨도 측정 세트·지킴·판정 규칙은 부록 3 그대로라, 판정 자체는 바뀌지 않는다. 넘긴 사실은 판정과 함께 적었다.

7. Results — 2회차 판정#

70스텝 어댑터를 FP8 로 합쳐 학습 전 모델과 같은 조건으로 한 번 쟀다. 계산은 얼린 eval/round2/report.py 다.

부트스트랩 10,000번 · 씨앗 292. 판정 세트 구간은 참고값이다

판정: 좋아졌다. 지킴 둘을 통과했고, A 의 구간 하한이 0 보다 크다.

  • 지킴 1: C 하한 −1.3%p > −7%p
  • 지킴 2: A 의 자신 있게 틀림이 −5.3%p 로 늘지 않았다. 맞음 증가(+6.1%p)보다 작다
  • 해석 표시: A 는 “본 적 있을 수 있는 종류"다. 44문제·30군집으로는 +10%p 를 가리지 못한다
  • B 의 +14.3%p 는 약점을 고른 문제를 고친 것이라고만 적는다. D 는 방향만 본다(구간이 0 을 지난다)
  • 판정 세트는 2회차 모델과 학습 전 모델을 한 번씩 쟀다. 전체 점수 78.8% → 75.8%, 33번 중 1번 차이로 무너짐 기준(−25%p)보다 훨씬 작다. 좋아지지도 않았다. 정상 문제의 헛경보는 두 모델 모두 0/3 이다

근거는 늘지 않았다. 근거 v2(보조 지표)로 보면 A 에서 근거 있게 맞힌 실행이 학습 전과 2회차 모두 36/132 다. 늘어난 정답 8번은 모두 근거 검사를 통과하지 못한 쪽이었다.

  • 2회차가 새로 맞힌 A 문제 4개의 풀이를 읽었다. 짐작으로 맞힌 것은 없었다
  • 둘은 파드 describe·로그에서 고장 값을 정확히 인용하고 컨트롤러를 답했다. 부록 4 가 학습에 허용한 모양이지만, 평가의 근거 v2 는 원인 오브젝트 직접 조회를 요구해 “근거 조사 실패"가 된다
  • 둘은 웹훅 설정을 직접 조회했지만, 인용 문구 중간을 “…“로 줄여 원문 대조에서 빠졌다
  • 거름(부록 4)과 평가(근거 v2)가 인정하는 경로가 한 줄 다르다. 표본이 4개뿐이라 숫자로 말하지 않고 한계로 둔다

8. Release — Hugging Face v0.2#

판정 뒤 모델과 학습 데이터를 Hugging Face 에 Apache-2.0 으로 올렸다.

  • 모델 Kukie-AI/Kause-K8s-27B-FP8 태그 v0.2. 이름은 K + cause 다. L40S 1장(48GB)에서 평가와 같은 vLLM 설정으로 돈다
  • 데이터 Kukie-AI/Kause-K8s-train-v0.2, 대화 551개
  • 모델 카드에 A·B·C·D·판정 세트 표와, 학습 전에 정한 판정 규칙을 그대로 실었다. 판정 세트는 문제를 싣지 않고 전체 점수만 적었다
  • FP8 합치기 코드(code/merge_lora_fp8.py)를 같이 올렸다
묶음 이름은 모델 카드의 표를 따른다
  • 기록이 많은 쪽은 컨테이너 설정과 NetworkPolicy 다. Service·저장소 쪽은 규칙마다 0~8개로 적다
  • VAP·웹훅·쿼터 고장은 0개다. 옛 순서 규칙이 거름에서 모두 빠졌기 때문이다. 그런데 A 에는 이 종류가 있다
  • 학습 데이터를 공개했으므로 D(생성기 보류 종류)는 이제 모르는 시험이 아니다

10. Review — 시행착오#

증상원인처리
1회차 학습이 18스텝에서 죽음두 벌이 triton 자동튜너를 동시에 불러 충돌자동튜너에 잠금을 걸고 같은 설정으로 처음부터
L40S 1장 vLLM 이 뜨지 않음기본 max_num_seqs 256 이 Mamba 캐시 칸(172)을 넘음--max-num-seqs 64 를 학습 전·후 서버 모두에
1회차 기록 “334개"가 84개로 줄어듦설계는 순서 검사 없이 셌고, 얼린 거름은 order 칸 없는 기록을 뺌결과를 보기 전에 84개만 쓰기로 정함
1에폭 점검의 첫 결과가 학습 전과 같음실행이 안 됐는데 스크립트가 직전 기록을 새 기록으로 읽음“새 실행 폴더가 생겼나” 검사를 점검·본 측정 스크립트에 넣음
실행한 명령 없이 verify 통과다시 풀 때 kind 를 새로 만들지 않아 앞 실행의 고친 상태가 남음다시 재기부터 모델마다 kind 를 새로 만듦
모델 받기가 35분 멈춤Hugging Face 내려받기 정지시간 제한을 걸고 이어받음. 두 번 멈춘 GPU 는 버리고 서버 4개로 줄임
C 의 한 문제가 늘 장비 실패로 보임원본 setup 이 kind 에서 OOM 이벤트를 못 찾아 rc=1얼린 세트라 고치지 않음. 학습 전 기록도 같았고 증상 확인은 통과

11. Limits — 남은 한계#

  • 오염 ④: A 는 설계자가 출처 목록 일부를 읽은 세트다. “본 적 있을 수 있는 종류"라는 한계와 함께만 쓴다
  • 크기: A 44문제·30군집으로는 +10%p 를 가리지 못한다. +6.1%p 는 하한이 0.8 로 겨우 0 을 넘었다
  • 순서 효과: A·D 는 같은 kind 에서 학습 전 → 2회차 순서로 풀었다. B·C 의 학습 전 값은 다른 날 잰 기록이다
  • 멈춤 6 을 넘김: 35스텝부터 옵티마이저 없이 이어 학습했다. 원래 계획대로 한 번에 70스텝을 학습한 모델과 같지 않다
  • 근거: 늘어난 정답이 근거 v2 를 통과하지 못했다. 거름과 평가가 인정하는 경로를 맞추는 일이 남았다
  • 빠진 종류: VAP·웹훅·쿼터 고장 기록이 없다
  • 고치기 명령: 거름이 fix_commands 를 검사하지 않는다. 검토에서 애매로 나온 9개 중 대부분이 실제로는 실패하는 명령이었다
  • 영어: 한국어 프롬프트로 학습했다. 영어 질문은 재지 않았다
  • 판정 세트: 무너지지 않았을 뿐 좋아지지 않았다. 12문제라 작은 차이는 볼 수 없다
