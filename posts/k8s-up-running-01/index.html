1. Overview#

책이 꼽는 다섯 이점. 이 글은 그 다섯을 하나씩 쉬운 말로 다시 쓴다

『Kubernetes: Up and Running』 3판을 한 장씩 정리하는 시리즈다. 책은 구글이 Borg 를 10년 운영하며 배운 것을 오픈소스로 다시 만든 것이 쿠버네티스라고 소개하고, 1장에서는 코드 한 줄 없이 “왜 써야 하는가” 만 설득한다. 그 설득의 뼈대가 다섯 이점 — 속도, 확장, 추상화, 효율, 생태계 — 이고, 이 글은 그 다섯을 쉬운 말과 그림으로 다시 쓴다.

읽기 전에 하나만 잡아 두면 된다. 다섯 이점은 결국 한 문장으로 모인다. 운영에 쓰던 사람 시간을 개발로 돌린다. 불변 이미지도 선언적 설정도 자가 치유도, 새벽에 사람이 깨어 서버를 만지는 일을 없애려는 장치다. 뒷장에서 Pod, Deployment, Service 가 나올 때 “이건 다섯 중 어느 것을 위한 부품인가” 를 물으면서 읽으면 길을 잃지 않는다.

이 편은 개념 장이라 실습이 없다. 2장부터 컨테이너 이미지를 만들고 띄운다.

2. Distributed Systems — 쿠버네티스가 풀려는 문제#

2.1 API 하나 뒤의 머신들#

책은 쿠버네티스를 “안정적이고 확장 가능한 분산 시스템을 만들기 위한 도구” 라고 정의한다. 그 말이 무슨 뜻인지부터 풀어야 뒤가 읽힌다.

지도 앱에서 가장 가까운 병원을 찾는다고 하자. 손에 든 앱은 API 하나를 부른다. 그런데 그 API 뒤에는 서버 한 대가 아니라 수십, 수백 대가 있다. 지도 타일을 주는 머신, 경로를 계산하는 머신, 병원 데이터를 가진 머신이 네트워크로 이어져 같이 일한다. 사용자는 문 하나만 보고, 문 뒤의 머신들은 서로 통신하며 답을 만든다. 이것이 분산 시스템이다.

API 하나 뒤에 여러 머신이 있는 것이 분산 시스템이고, 책은 그 시스템에 세 가지를 요구한다

2.2 세 가지 요구 — 죽지 않고, 배포 중에도, 커질 수 있게#

사람들이 일상의 거의 모든 일을 이런 API 에 맡기게 되면서, 분산 시스템에는 세 가지가 요구된다.

첫째, 일부가 죽어도 전체가 멈추면 안 된다. 머신 한 대가 꺼졌다고 길 찾기가 안 되면 곤란하다.

둘째, 새 버전을 올리는 동안에도 서비스가 살아 있어야 한다. 예전에는 자정에 점검 공지를 띄우고 서비스를 내리는 게 허용됐다. 지금은 소프트웨어가 매시간 바뀌는데도 사용자는 항상 켜져 있기를 기대한다.

셋째, 사용자가 늘면 구조를 갈아엎지 않고 용량을 키울 수 있어야 한다. 많은 경우 그 키우고 줄이는 일을 자동으로 하는 것까지 포함한다.

쿠버네티스가 이 셋에 대응하는 방식을 미리 적어 두면 — 죽으면 다시 띄우는 자가 치유, 무중단 롤링 업데이트, 복제본 수를 숫자 하나로 바꾸는 확장이다. 셋 다 3장과 4장에서 나온다.

3. Velocity — 안 깨뜨리며 배포하는 횟수#

책이 첫 번째로 꼽는 이점은 속도다. 소프트웨어는 CD 에 담아 1년에 한 번 팔던 물건에서 매시간 업데이트되는 웹 서비스로 바뀌었다. 경쟁자와의 차이는 새 기능을 얼마나 빨리 만들어 내보내느냐, 남의 혁신에 얼마나 빨리 대응하느냐로 갈린다.

그런데 책은 바로 단서를 단다. 속도는 빠르기가 아니다. 하루에 기능 열 개를 내보냈는데 서비스가 세 번 깨졌다면 그건 속도가 아니다. 사용자는 점진적 개선보다 안 끊기는 서비스를 더 원한다. 그래서 속도는 “시간당 몇 개를 내보냈나” 가 아니라 “서비스를 깨뜨리지 않으면서 몇 개를 내보냈나” 로 잰다.

배포가 두려운 이유는 망하면 되돌리기 힘들기 때문이다. 되돌리기가 공짜가 되면 배포가 두렵지 않고, 두렵지 않으면 자주 할 수 있고, 그게 속도다. 아래 세 개념 — 불변성, 선언적 설정, 자가 치유 — 는 전부 되돌리기를 공짜로 만드는 장치다.

3.1 Immutability — 고치지 말고 새로 찍는다#

서버를 다루는 방식은 두 가지다.

고쳐 쓰는 방식. 서버 한 대를 두고 그 위에 계속 변경을 덧댄다. apt 로 패키지를 올리고, 설정 파일 몇 줄을 바꾸고, 급할 때 누군가 ssh 로 들어가 손으로 고친다. 이러면 지금 이 서버가 어떤 상태인지는 “처음 설치 + 그동안의 업데이트 + 누군가의 손 수정” 의 합인데, 그 합을 아무도 설명하지 못한다. 큰 팀일수록 여러 사람 손을 거쳤고, 대부분 기록이 없다. 똑같이 세팅했다는 서버 두 대가 미묘하게 다르게 동작하는 이유가 여기 있다.

새로 찍는 방식. 바꿀 게 있으면 새 이미지를 통째로 만들고, 돌아가는 것을 내리고, 새것을 띄운다. 점진적 변경이 없다. 설계도(Dockerfile)를 고쳐서 집을 새로 찍는 것이지, 살면서 고치는 게 아니다.

왼쪽 서버는 지금이 어떤 상태인지 아무도 설명 못 한다. 오른쪽은 v13 이라고 답하면 끝이다

두 방식은 언뜻 비슷해 보인다. 컨테이너에 들어가 새 버전을 받아서 프로세스를 재시작하는 것과, 새 이미지를 빌드해 레지스트리에 올리고 컨테이너를 갈아 끼우는 것은 결과만 보면 같다. 차이는 두 가지다.

기록이 남는다. 새 이미지를 빌드하면 Dockerfile 의 변경과 이미지 태그가 남는다. “v13 에서 뭐가 바뀌었지” 에 git diff 한 번으로 답할 수 있다. 컨테이너 안에서 wget 으로 받아 덮어쓰면 그 사실은 그 사람 머릿속에만 있다.

되돌릴 수 있다. 옛 이미지가 레지스트리에 그대로 있으니 문제가 생기면 v11 로 다시 띄우면 끝이다. 바이너리를 덮어썼으면 이전 버전은 이미 없다.

실무 규칙 하나. 새벽에 운영이 터져서 컨테이너에 들어가 급히 고치는 것은 책도 허용한다 — 다른 방법이 없을 때의 응급처치로. 다만 불을 끈 뒤에는 반드시 같은 변경을 Dockerfile 이나 설정 파일에 반영해야 한다. 안 그러면 다음 배포에서 새 이미지가 뜨는 순간 응급처치가 사라지고 같은 장애가 재발한다. 3.3 에서 이 함정이 한 번 더 나온다.

3.2 Declarative — 레시피가 아니라 주문서#

불변성은 컨테이너에서 끝나지 않고, 앱을 쿠버네티스에 설명하는 방식까지 간다. 쿠버네티스의 모든 것은 “원하는 상태” 를 적은 선언적 설정 객체이고, 현재 상태를 거기에 맞추는 것이 쿠버네티스의 일이다.

명령형과 선언형의 차이는 복제본 셋을 만드는 예로 보면 바로 잡힌다.

명령형 — 레시피
A 를 띄워라, B 를 띄워라, C 를 띄워라.
행동을 적는다. 순서대로 실행해야 결과가 나오고, 실행한 뒤에는 지금 몇 개인지 레시피만 봐서는 모른다.
kubectl run, kubectl scale, 셸 스크립트의 docker run 세 번.
선언형 — 주문서
replicas: 3
상태를 적는다. 어떻게 만들지는 주방이 알아서 한다. 읽기만 해도 결과가 뭔지 안다.
YAML 파일을 kubectl apply -f 로 넣는다.

주문서 방식의 장점은 두 가지다.

읽기만 해도 결과를 안다. 주문서에 셋이라고 적혀 있으면 실행하지 않아도 결과가 셋인 걸 안다. 레시피는 끝까지 따라가 봐야 뭐가 나오는지 알고, 조건문이 있으면 머릿속으로 실행해야 한다. 그래서 YAML 을 눈으로 검토하는 것이 스크립트를 검토하는 것보다 훨씬 안전하다.

코드처럼 다룰 수 있다. 주문서는 텍스트 파일이니 git 에 넣고, PR 로 리뷰받고, 자동 검사를 돌릴 수 있다. 복제본을 3 에서 5 로 바꾸는 PR 은 diff 가 한 줄이라 누구나 리뷰한다. 반면 kubectl scale 을 누가 쳤는지는 git 에 남지 않는다. 설정을 git 에 넣고 코드처럼 관리하는 것을 Infrastructure as Code 라고 부른다.

여기서 한 발 더 나간 것이 GitOps 다. 운영 클러스터에는 아무도 직접 손대지 않는다. 바꾸고 싶으면 git 에 YAML 을 고쳐 푸시하고, ArgoCD 나 Flux 같은 도구가 그것을 보고 클러스터를 맞춘다. kubectl apply 조차 사람이 치지 않는다. 책은 이것을 “운영 클러스터를 읽기 전용으로 본다” 고 표현한다.

그러면 롤백이 공짜가 된다. 레시피는 A 에서 B 로 가는 길만 적어 두고, 돌아오는 길은 따로 짜야 하며 보통 안 짠다. 주문서는 “B 여야 한다” 고 적은 것이라 되돌리려면 “A 여야 한다” 로 바꾸면 끝이다. git 에서는 git revert 한 번이고, 어떻게 돌아갈지는 쿠버네티스가 알아서 한다. 이미지는 불변이고, 설정은 선언이고, 그 설정은 git 에 있다 — 그러면 “지금 운영이 어떤 상태인가” 의 답이 main 브랜치 그 자체가 된다.

3.3 Self-Healing — 한 번이 아니라 계속#

주문서를 받은 보통의 주방은 셋을 내놓으면 일이 끝난다. 쿠버네티스는 다르다. 주문서를 벽에 붙여 놓고 계속 쳐다본다.

주문서를 벽에 붙여 놓고 계속 쳐다보는 주방. 셋이 아니면 어느 쪽이든 셋으로 돌린다

replicas: 3 은 “지금 셋 띄워라” 가 아니라 “항상 셋이어야 한다” 다. 하나가 죽어서 둘이 되면 말없이 하나를 더 띄운다. 누가 손으로 하나를 더 띄워서 넷이 되면 하나를 없앤다. 많아도 틀린 것이다. 선언과 다른 상태는 방향에 상관없이 되돌린다. 이 “계속 비교하고 맞추는 동작” 을 조정 루프(reconciliation loop)라고 하고, 그것을 돌리는 구성 요소가 컨트롤러다. 뒷장의 ReplicaSet 과 Deployment 는 전부 이 루프를 돌리는 컨트롤러다.

사람이 고치는 방식과 비교하면 왜 이게 속도와 이어지는지 보인다. 알람이 울리고, 사람이 깨고, 노트북을 켜고, VPN 을 붙이고, 로그인하고, 상황을 파악하고, 명령을 친다. 비싸다 — 당직을 세워야 한다. 느리다 — 최소 몇 분에서 수십 분이다. 믿을 수 없다 — 졸린 사람이 새벽에 치는 명령은 틀릴 수 있고, 뭘 쳤는지 기록도 없다. 3.2 에서 명령형의 문제로 꼽은 것이 복구 상황에서는 더 심하게 나타난다. 쿠버네티스는 수 초 안에 다시 띄우고, 사람은 “계속 죽어서 재시작이 반복된다” 처럼 시스템이 스스로 못 고치는 패턴만 본다.

여기서 3.1 의 함정이 돌아온다. 트래픽이 몰려서 kubectl scale --replicas=5 로 급히 늘렸는데 YAML 에는 여전히 3 이라고 적혀 있으면, 다음에 누가 그 YAML 을 apply 하는 순간 쿠버네티스가 둘을 조용히 없앤다. 응급처치를 YAML 에 반영하지 않으면 자가 치유가 응급처치를 되돌린다.

3.4 Operator — 앱을 아는 자가 치유#

위의 자가 치유는 범용이다. 쿠버네티스는 “컨테이너가 살았나, 몇 개 있나” 까지만 본다. 그 안에서 뭐가 돌아가는지는 모른다. 셋이 있는지는 세지만, 그 셋이 제대로 일하는지는 모른다.

MySQL 같은 것은 “컨테이너가 살아 있다” 와 “DB 가 정상이다” 가 다르다. 복제가 끊겼을 수도 있고, 프라이머리가 죽어서 레플리카 하나를 승격시켜야 할 수도 있다. MySQL 을 아는 사람만 할 수 있는 판단이다. 오퍼레이터는 그 사람의 지식을 코드로 짜서 클러스터 안에 컨테이너로 띄운 것이다. 쿠버네티스의 조정 루프와 같은 방식으로 돌면서 “DB 상태가 선언과 다르면 맞춘다” 를 수행한다. 사람 운영자가 하던 일을 소프트웨어가 대신하니 이름이 오퍼레이터다.

두 층으로 기억하면 된다. 쿠버네티스 기본 자가 치유는 모든 앱에 공통인 것 — 죽으면 다시 띄우기, 개수 맞추기. 오퍼레이터는 특정 앱에만 해당하는 것 — DB 승격, 샤드 재배치, 버전 업그레이드 절차. 직접 짜는 일은 드물고 Prometheus Operator, Strimzi(Kafka), CloudNativePG 같은 것을 가져다 쓴다. 책은 17장에서 다룬다.

4. Scaling — 서버도 팀도#

제품이 커지면 소프트웨어도 커져야 하고 그것을 만드는 팀도 커져야 한다. 책은 쿠버네티스가 둘 다 돕는다고 하고, 비결을 한 단어로 짚는다. 분리(decoupling). 결합을 끊어 놓은 구조를 선호하기 때문이다.

4.1 Decoupling — 로드밸런서는 기계 쪽, API 는 사람 쪽#

분리된 구조에서 컴포넌트는 두 가지 장치로 서로 격리된다. 둘은 층이 다르다.

사람 10명이 100명이 될 때 먼저 터지는 건 서버가 아니라 회의 시간이다. 그걸 막는 게 API 선이다

로드밸런서는 기계 쪽 분리다. 주문 서비스 뒤에 서버가 셋이든 서른이든, 앞에 있는 결제 서비스는 로드밸런서 주소 하나만 안다. 그래서 주문을 늘릴 때 결제를 재배포하거나 설정을 고칠 필요가 없다. 이것이 소프트웨어 확장이다.

API 는 사람 쪽 분리다. 주문 팀과 결제 팀이 “이 엔드포인트에 이 JSON 을 보내면 이 응답이 온다” 만 합의하면 서로 내부 코드를 몰라도 된다. 결제 팀이 DB 를 바꾸든 언어를 바꾸든 주문 팀은 상관없다. 회의가 줄고, 팀을 더 쪼개도 된다. 이것이 팀 확장이다. 책은 팀 사이의 의사소통 비용이 팀을 키울 때 가장 큰 제약이라고 말한다. 사람 열 명이 백 명이 될 때 먼저 터지는 것은 서버가 아니라 회의 시간이다.

쿠버네티스 용어로 대응시키면 로드밸런서 역할은 Service 객체가, 인스턴스 늘리기는 Deployment 의 replicas 가 맡는다. 둘 다 뒷장에서 나온다.

4.2 머신과 예측 — 합치면 매끈해진다#

확장은 두 층이다. 앱 확장은 3장에서 다진 것 덕에 아주 간단하다. 컨테이너는 불변이고 복제본 수는 설정 파일의 숫자 하나이니, 3 을 10 으로 고쳐서 넘기면 나머지는 쿠버네티스가 한다. 자동 확장을 켜 두면 그 숫자조차 사람이 안 바꾼다. 이미지가 가변이었다면 열 대를 똑같이 만들 수 있다는 보장이 없었을 것이다.

앱을 늘리려면 올릴 자리가 있어야 하니 때로는 클러스터 자체, 즉 머신을 늘려야 한다. 클러스터 안의 머신은 서로 똑같고 앱은 컨테이너 덕에 머신 세부사항과 분리돼 있으니, 같은 종류 머신을 하나 더 찍어 붙이면 된다.

책이 길게 다루는 것은 용량 예측이다. 물리 서버는 새 장비를 받는 데 몇 주가 걸리고, 클라우드든 물리든 특정 앱이 얼마나 커질지 맞히기는 어렵다. 그런데 쿠버네티스는 이 예측을 쉽게 만든다.

컨테이너가 가벼워서가 아니라, 변동을 한 곳에 모아서 상쇄하기 때문에 서버가 준다

팀별로 전용 머신을 사면 각 팀의 최대 예상치로 사야 한다. A 팀의 남는 자리를 B 팀이 못 쓰기 때문이다. 쿠버네티스로 팀과 머신을 분리하면 세 팀의 합산 성장률로 예측하면 된다. 변동이 큰 곡선 셋을 합치면 통계적 잡음이 줄어 예측이 정확해지고, 팀들이 서로의 머신을 조각으로 나눠 쓰니 낭비도 준다. 보험 원리다. 한 사람의 병원비는 예측이 안 되지만 만 명을 모으면 평균이 안정된다. 쿠버네티스가 비용을 아끼는 진짜 이유는 컨테이너가 가벼워서가 아니라 이 통계 효과다.

실무에서는 HPA(Horizontal Pod Autoscaler)가 Pod 를 늘리려는데 노드에 자리가 없으면 Pod 가 Pending 으로 멈추고, 그것을 보고 Cluster Autoscaler 나 Karpenter 가 노드를 추가한다. 이 두 단계 연동이 책이 말하는 “앱과 클러스터 양쪽의 자동 확장” 이다.

4.3 Two-Pizza Team — 쪼개되 띄우는 법은 하나로#

여러 연구가 말하는 이상적인 팀 크기는 피자 두 판으로 먹일 수 있는 여섯에서 여덟 명이다. 이 크기면 지식 공유, 빠른 결정, 공통 목표 의식이 되고, 더 커지면 위계, 낮은 가시성, 내부 다툼이 생긴다. 문제는 제품이 그보다 훨씬 많은 사람을 필요로 한다는 것이다. 업계의 해법은 여든 명을 여덟 명짜리 열 팀으로 쪼개고, 팀마다 마이크로서비스 하나씩 맡기고, 팀 사이에는 API 만 두는 것이었다. 4.1 의 분리가 조직도에 그대로 적용된 모습이다. MSA 를 하는 진짜 이유는 기술이 아니라 사람이다.

쿠버네티스는 이 구조를 만들기 쉽게 하는 부품을 준다.

Pod
다른 팀이 만든 컨테이너들을 하나의 배포 단위로 묶는다
Service
팀 간 전화번호. 로드밸런싱과 이름, 디스커버리로 서비스를 서로 격리한다
Namespace
팀별 사무실 칸막이. 다른 서비스가 얼마나 끼어들 수 있는지 통제한다
Ingress
회사 대표 번호. 여러 마이크로서비스를 외부에 하나의 API 로 묶어 노출한다

그런데 열 팀이 각자 알아서 배포하면 열 가지 배포 방식이 생긴다. A 팀은 셸 스크립트, B 팀은 Ansible, C 팀은 수동. 장애가 나면 팀마다 대응법이 다르고, 사람이 팀을 옮기면 처음부터 다시 배운다. 쿠버네티스가 하는 일은 쪼개는 것은 자유지만 띄우는 방식은 하나로 강제하는 것이다. 모든 팀이 Deployment YAML 을 쓰고, 헬스체크도 같은 자리에 적고, 롤아웃도 같은 명령으로 한다. 팀 수가 늘어도 운영 방식은 하나다. 컨테이너와 머신이 분리돼 있으니 여러 마이크로서비스가 같은 머신에 함께 올라가도 서로 간섭하지 않는 것도 MSA 의 비용을 줄인다.

4.4 Separation of Concerns — 내 층 문제가 아니다#

4.3 이 개발 팀 쪼개기였다면 여기는 운영 팀 쪼개기다. 쿠버네티스 API 는 책임의 경계선이 된다. 책은 이 선을 “not my monkey, not my circus” — 내 원숭이도 아니고 내 서커스도 아니다, 즉 내 소관이 아니다 — 라고 부른다.

각 층은 아래층의 약속만 믿고 위층에 자기 약속만 지킨다. 그래서 관리사무소 다섯 명이 천 세대를 감당한다

아파트로 보면 이렇다. 입주민(앱 개발자)은 수도 틀면 물 나오고 전기 켜면 불 들어오면 된다. 배관이 어떻게 깔렸는지 모른다. 관리사무소(클러스터 운영)는 수도와 전기가 끊기지 않게만 책임진다. 입주민이 집에서 뭘 하는지 모른다. 한국전력(OS 운영)은 아파트 변압기까지 전기가 오게만 책임진다. 그 아파트에 누가 사는지 모른다.

각 층이 아래층의 약속(SLA)만 믿고 위층에 자기 약속만 지키면 된다. 그래서 관리사무소 직원 다섯이 천 세대를 감당하고, 한전 직원 몇이 아파트 수백 동을 감당한다. 책의 숫자로는 클러스터 운영 팀 하나가 그 위에서 앱을 돌리는 수백, 수천 팀을 지원하고, 또 다른 작은 팀이 전 세계 수십 개 클러스터를 맡는다. 선이 없으면 입주민이 변압기 걱정까지 해야 하고, 그러면 아무도 자기 일에 집중하지 못한다.

관리사무소를 외주 주는 것이 관리형 쿠버네티스(KaaS)다. EKS, GKE, AKS 가 그것이다. 컨트롤 플레인을 클라우드가 운영해 주고 사용자는 앱만 올린다. 대신 관리사무소 규정은 외주 업체가 정하니, 많은 관리형 서비스가 안정성을 위해 알파 기능을 꺼 둔다. 책의 조언은 상황에 따라 다르다는 것이다. 작은 조직은 관리형으로 클러스터 관리 대신 제품에 집중하는 쪽이 낫고, 전담 팀을 둘 수 있는 큰 조직은 직접 운영하는 쪽이 유연하다. 학습이나 소규모 프로젝트라면 전자다. 클러스터를 직접 세우는 것은 내부를 이해하는 공부로는 좋지만, 서비스를 만드는 게 목적이면 관리형을 쓰고 그 시간을 앱에 쓰라는 뜻이다.

5. Abstraction, Efficiency, Ecosystem#

5.1 Abstraction — 쿠버네티스 말로 적으면 갈아탈 수 있다#

퍼블릭 클라우드의 목표는 개발자가 셀프서비스로 쓰는 쉬운 인프라다. 그런데 클라우드 API 는 너무 자주 IT 부서가 기대하는 것(가상 머신)을 비추고, 개발자가 원하는 것(애플리케이션)은 비추지 않는다. 거기에 클라우드마다 고유한 서비스가 붙어 있어, 그 API 를 직접 쓰면 다른 환경으로 옮기기 어렵다.

AWS 에 서비스를 올린다고 하자. 쿠버네티스 없이 하면 서버는 EC2, 트래픽 분배는 ELB, 디스크는 EBS 로 — 전부 AWS 말로 적는다. 1년 뒤 GCP 로 옮기자고 하면 Compute Engine, Cloud Load Balancing, Persistent Disk 로 이름도 명령도 다르니 처음부터 다시 적어야 한다.

콘센트 규격만 맞추면 발전소가 어디든 상관없다. 단, 그 집에만 있는 특수 설비는 못 쓴다

쿠버네티스를 중간에 끼우면 서버는 Deployment, 트래픽 분배는 Service, 디스크는 PersistentVolumeClaim 으로 — 쿠버네티스 말로만 적는다. 그 YAML 을 EKS 에 넣으면 쿠버네티스 플러그인이 알아서 ELB 를 만들고, 같은 YAML 을 GKE 에 넣으면 구글 로드밸런서를 만든다. 내 YAML 은 한 글자도 안 바뀐다. 한국 가전이 220V 규격만 맞추면 어느 집에서든 꽂히고 발전소가 화력인지 원자력인지 알 필요가 없는 것과 같다. 쿠버네티스 API 가 그 콘센트 규격이다.

단서가 중요하다. 규격을 지키려면 그 집에만 있는 특수 설비는 못 쓴다. DynamoDB 는 AWS 에만 있으니 그것을 쓰는 순간 GCP 로 못 간다. 대신 MySQL 을 쿠버네티스 안에 직접 띄우면 어디서든 돌지만, 백업과 장애 대응을 내가 해야 한다. 책도 “강제된다(forced)” 는 표현으로 이것이 부담임을 인정한다. 실무에서는 상태 없는 앱은 쿠버네티스로 이식성을 챙기고 DB 는 그 클라우드의 관리형을 쓰는 절충이 흔하다.

용어 둘만 미리 잡아 두면 된다. PersistentVolume(PV)은 클러스터가 가진 저장 공간 한 덩어리, PersistentVolumeClaim(PVC)은 앱이 “10GB 필요하다” 고 내는 요청서다. 앱은 PVC 만 쓰고, 그것이 EBS 인지 GCP 디스크인지 NFS 인지는 클러스터가 정한다. 책 12장에서 나온다.

5.2 Efficiency — 빈자리를 채운다#

앞 절들이 개발자와 IT 관리 쪽 이점이었다면 이 절은 돈이다. 서버는 택시 미터기다. 켜 두면 손님이 있든 없든 요금이 올라간다. 전력, 냉각, 데이터센터 공간, 컴퓨팅 자체 — 서버 CPU 가 10% 만 돌고 있으면 90% 는 버리는 돈이다.

예전에 비효율적이었던 이유는 “결제 서버”, “주문 서버” 처럼 앱 하나에 서버 하나를 줬기 때문이다. 결제 서버가 새벽에 놀아도 주문 서버가 그 자리를 못 쓴다.

앱과 서버를 떼어 놨기 때문에 섞어 올릴 수 있다. 4장의 분리가 여기서 돈이 된다

개발자가 더 이상 머신 단위로 생각하지 않으니, 결제, 주문, 알림, 검색을 한 서버에 섞어 올려도 서로 영향이 없다. 한 앱이 놀 때 다른 앱이 그 자리를 쓰니 서버가 꽉 차고, 서버 수가 준다. 택시 한 대에 합승을 시키는 것이다. 쿠버네티스는 앱을 머신들에 자동으로 분배해서 기존 도구보다 높은 사용률을 만든다.

테스트 환경 이야기가 실무에서는 더 체감된다. 개발자 열 명이 각자 테스트 서버 셋씩 쓰면 서른 대이고 대부분 시간은 놀고 있다. 쿠버네티스에서는 클러스터 하나에 네임스페이스 열 개를 만들어 한 명당 하나씩 주면 된다. 서로 안 보이고 안 부딪히는데 실제 머신은 서너 대로 끝난다.

그리고 테스트가 싸지면 행동이 바뀐다. “테스트 환경 띄우는 데 30분 걸리니 커밋 모아서 하루 한 번 올려 보자” 가 “컨테이너 몇 개 띄우는 데 1분이니 커밋마다 올려 보자” 가 된다. 뭔가 깨졌을 때 “오늘 커밋 50개 중 어디지” 가 아니라 “방금 그 커밋이네” 가 된다. 효율은 돈 절약으로 끝나지 않고, 절약된 돈이 더 잦은 테스트로, 더 잦은 테스트가 더 빠른 개발로 이어진다. 책이 “결국 속도로 돌아간다” 고 하는 이유다.

5.3 Ecosystem — 고르는 게 일이다#

쿠버네티스를 쓰는 이유가 쿠버네티스 자체가 아니라 그 위에 쌓인 것들이라는 것이 마지막 이점이다. 아이폰을 사는 이유가 전화 기능이 아니라 앱스토어인 것과 같다. 쿠버네티스가 OS 라면 모니터링은 Prometheus, 패키지 설치는 Helm, 배포 자동화는 ArgoCD, 서비스 간 통신 제어는 Istio 처럼 이미 만들어진 앱이 있다. 3.4 의 오퍼레이터들도 전부 이 생태계 산물이다. 직접 짤 필요가 없고, 회사는 자기만의 핵심 로직에 집중한다.

문제는 앱스토어가 너무 커서 같은 일을 하는 앱이 열 개라는 것이다. 책의 표현으로는 해법을 찾는 게 어려운 게 아니라 많은 해법 중 뭘 고를지가 어렵다. 길잡이는 둘이다.

쿠버네티스를 쓰는 이유는 쿠버네티스가 아니라 그 위에 쌓인 것들이다. 고르는 게 일이다

첫째, CNCF 의 성숙도 등급이다. CNCF 는 클라우드 네이티브 프로젝트의 코드와 지적재산을 맡는 중립 기관이고, 프로젝트를 Sandbox, Incubating, Graduated 세 단계로 나눈다. Sandbox 는 초기 개발 중이라 얼리어답터나 기여자가 아니면 도입을 권하지 않는다. Incubating 은 실제 운영에서 유용성과 안정성을 입증했지만 커뮤니티는 아직 성장 중이다. Graduated 는 성숙하고 널리 채택된 것으로, 쿠버네티스 자신이 여기 있다. 처음 도구를 고를 때 CNCF landscape 에서 등급을 확인하는 습관을 들이면 시간 낭비가 준다.

둘째, 관리형 쿠버네티스에 통합된 것을 고르는 것이다. EKS 나 GKE 가 부가 기능으로 끼워 주는 것은 클라우드 제품에 들어갔다는 것 자체가 검증이다. 고민하기 싫으면 그것을 쓴다.

6. Discussion#

6.1 도커 컴포즈면 안 되나 — 한 대까지는 된다#

5.2 를 읽다 보면 이런 질문이 생긴다. 컨테이너 단위로 앱을 섞어 올리는 것은 도커 컴포즈도 되지 않나. 반은 맞다. 서버 한 대 안에서의 효율은 컴포즈도 똑같이 얻는다. 결제, 주문, 알림 컨테이너를 한 서버에 올리면 CPU 를 나눠 쓰니 합승 효과는 그대로 나고, 개발자 개인 테스트 환경을 가볍게 띄우는 것도 컴포즈로 충분하다. 효율 이야기의 절반은 컨테이너 자체의 이점이다.

차이는 서버가 두 대 이상이 되는 순간 생긴다.

도커 컴포즈 — 한 대
docker compose up 은 명령을 친 그 머신에 띄운다.
서버가 다섯이면 어느 컨테이너를 어디에 올릴지 내가 정하고 각 서버에서 따로 친다.
서버 1 은 빽빽하고 서버 3 은 노는데, 눈으로 보고 손으로 옮긴다.
서버 2 가 죽으면 거기 있던 컨테이너는 그냥 사라진다.
쿠버네티스 — 그 이상
서버 다섯을 하나의 큰 컴퓨터처럼 보여 준다.
"이 컨테이너 띄워라" 만 하면 자리 남은 서버를 스케줄러가 고른다.
빈 서버를 채우는 것도, 죽은 서버의 컨테이너를 다른 서버로 옮기는 것도 자동이다.
3.3 의 조정 루프가 머신 여러 대에 걸쳐 돈다.

5.2 에서 “앱을 머신들에 자동으로 분배한다” 고 한 문장이 정확히 이 차이다. 컴포즈에는 그 분배가 없다. 그래서 개인 프로젝트나 로컬 개발은 컴포즈가 더 간단하고 맞다. 쿠버네티스가 빛나는 것은 서버가 늘어나서 “어디에 뭘 띄울지” 가 사람이 감당 못 할 문제가 될 때다. 책이 1장 처음부터 분산 시스템을 강조한 이유가 여기 있다.

핵심 메시지#

속도
불변 이미지 + 선언 + 자가 치유 = 롤백이 공짜. 배포가 두렵지 않다
확장
서버도 팀도 쪼개서 늘린다. 띄우는 방식은 하나로
추상화
쿠버네티스 말로 적으면 클라우드를 갈아탄다. 전용 서비스는 규격 밖
효율
여러 서버를 하나처럼. 빈자리를 자동으로 채운다
생태계
필요한 도구는 이미 있다. 등급을 보고 고른다

다섯 이점은 결국 하나다. 운영에 쓰던 사람 시간을 개발로 돌린다. 그래서 쿠버네티스를 쓰는 동안 운영 중인 컨테이너에 들어가 뭔가 고치고 싶은 충동이 들면, 그것이 바로 이 장이 하지 말라는 일이다. 고치지 말고 새로 찍고, 명령하지 말고 선언하고, 사람이 깨지 말고 루프가 돌게 한다. 다음 편은 2장 — 그 불변 이미지를 실제로 만들고 띄운다.
