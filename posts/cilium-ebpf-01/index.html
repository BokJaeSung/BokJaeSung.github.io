1. Overview#

번호는 해당 절로 이동 · 초록 eBPF 프로그램과 도구 · 주황 검증 · 보라 공유 데이터 · 파랑 워크로드

실행 중인 커널에 내가 쓴 코드를 올려도 괜찮을까요? 커널이 멈추면 머신 전체가 멈추므로, 보통은 커널 코드를 함부로 바꾸지 않습니다.

eBPF는 바로 이 일을 안전하게 하는 기술입니다. 개발자가 쓴 코드를 실행 중인 커널에 올려 커널의 동작을 바꾸며, 커널을 다시 빌드하거나 머신을 재부팅하지 않습니다. 주로 다음 세 가지 용도로 쓰입니다.

  • 성능 추적 — 시스템 거의 모든 부분의 동작을 관찰합니다.
  • 네트워킹 — 관측 기능이 들어 있는 고성능 네트워크를 만듭니다.
  • 보안 — 악성 행위를 탐지하고 차단합니다.

이번 글에서는 두 가지 질문을 따라가 보겠습니다. eBPF는 어디서 왔을까요? 그리고 커널을 고치는 다른 방법 대신 왜 eBPF를 쓸까요?

최근에 달라진 내용(커널 코드 규모, RHEL 버전, 사이드카 없는 서비스 메시, 새 용도)은 해당 문장 옆에 빨간 글씨로 적었습니다. 2026년 11월에 공식 문서로 확인한 내용입니다.

2. History — 패킷 필터에서 커널 플랫폼으로#

2.1 BSD Packet Filter#

필터 작성자가 직접 만든 프로그램이 커널 안에서 패킷마다 실행되는 구조 · eBPF 의 출발점

BPF는 1993년 로런스 버클리 국립연구소의 Steven McCanne과 Van Jacobson이 논문으로 발표했습니다. 패킷을 받을지 버릴지 정하는 필터 프로그램을 실행하는 가상 머신입니다.

  • 명령어 — 필터는 어셈블리와 닮은 범용 32비트 명령어 집합으로 작성합니다.
  • 사용자가 쓴 필터 — 핵심은 필터를 사용자가 직접 쓴다는 점입니다. 사용자가 쓴 프로그램이 커널 안에서 실행된다는 점에 eBPF의 뿌리가 있습니다.
  • 리눅스 도입 — 1997년 커널 2.1.75에 들어왔고, tcpdump가 캡처할 패킷을 고르는 데 사용했습니다. 이때부터 BPF는 Berkeley Packet Filter의 약자로 읽힙니다.

2.2 seccomp-bpf#

2012년 커널 3.5에는 seccomp-bpf가 들어왔습니다. 이번에는 BPF 프로그램이 패킷이 아니라 시스템 콜을 보고, 유저 공간 애플리케이션의 시스템 콜을 허용할지 거부할지 정합니다.

BPF가 패킷 필터링이라는 좁은 범위를 벗어난 첫 사례입니다.

2.3 eBPF의 구성 요소#

2014년 커널 3.18부터 BPF는 extended BPF, 줄여서 eBPF가 되었습니다. 이때 다섯 가지가 함께 바뀌었습니다.

유저 공간과 커널의 접점은 bpf() 하나 · 데이터는 맵을 통해 왕래
  • 명령어 집합 — 64비트 머신에 맞게 다시 설계했고, 인터프리터도 새로 작성했습니다.
  • 맵 — eBPF 프로그램과 유저 공간이 정보를 주고받는 통로입니다. 프로그램은 이벤트마다 맵에 기록하고, 도구는 맵을 읽어 결과를 보여 줍니다.
  • 검증기 — 이 구조의 전제입니다. 커널 안에서 사용자의 코드를 실행하려면 그 코드가 커널을 망가뜨리지 않는다는 보장이 먼저 있어야 합니다(4.3).

2.4 운영 환경까지의 연표#

패킷 필터에서 시작해 추적, 보안, 스케줄링까지 커널의 여러 지점으로 확장

eBPF가 운영 환경에 자리 잡기까지의 주요 사건은 다음과 같습니다.

  • 2005년, kprobes — 커널 코드 거의 어디에나 트랩을 걸 수 있었지만, 거기에 붙일 함수는 커널 모듈로 작성해야 했습니다.
  • 2015년, kprobe + eBPF — eBPF 프로그램을 kprobe에 붙일 수 있게 되면서 리눅스의 추적 방식이 바뀌었습니다. 같은 시기 네트워크 스택에도 훅이 추가되어 eBPF가 맡는 네트워크 기능이 늘었습니다.
  • 2016년, 운영 도입 — Netflix에서 Brendan Gregg가 한 추적 작업이 널리 알려졌고, 같은 해 Cilium이 컨테이너 환경의 데이터패스 전체를 eBPF로 대체하는 첫 네트워킹 프로젝트로 발표되었습니다.
  • 2017년, Katran — Facebook(현 Meta)이 L4 로드 밸런서 Katran을 공개했습니다. 이후 facebook.com으로 가는 모든 패킷이 eBPF/XDP를 지납니다.
  • 2018년, 독립 서브시스템 — eBPF가 커널의 독립 서브시스템이 되었습니다. 같은 해 들어온 BTF(BPF Type Format)는 프로그램을 다른 커널 버전으로 옮겨 쓰기 쉽게 만들었습니다.
  • 2020년, LSM BPF — eBPF 프로그램을 리눅스 보안 모듈(LSM) 인터페이스에 붙일 수 있게 되면서, 네트워킹과 관측에 이어 보안이 세 번째 용도가 되었습니다.

프로그램 길이 제한은 처음에 명령어 4,096개였습니다. 지금은 검증기가 처리하는 명령어 100만 개까지 허용하고, 꼬리 호출과 함수 호출로 프로그램을 나눌 수도 있어서 이 제한에 걸리는 일은 드뭅니다.

  • 2026년 기준 — 2024년 10월 BPF 명령어 집합이 IETF 표준(RFC 9669)이 되었습니다. 리눅스 밖의 구현(Windows용 eBPF 등)도 같은 명세를 기준으로 삼습니다.
  • 2026년 기준 — 2024년 커널 6.12에 sched_ext가 들어와 CPU 스케줄링 정책을 eBPF 프로그램으로 작성할 수 있게 되었습니다. 네트워킹, 관측, 보안에 이은 네 번째 용도입니다.

2.5 eBPF와 BPF라는 이름#

지금의 eBPF는 패킷 필터링과 거리가 멀어서 약자를 풀어 읽는 의미가 없습니다. 하나의 고유한 이름으로 씁니다. 또 널리 쓰이는 커널은 모두 확장 기능을 지원하므로 eBPF와 BPF는 사실상 같은 말입니다.

  • 커널 안 — 커널 소스와 eBPF 프로그래밍에서는 BPF라고 씁니다. 시스템 콜은 bpf(), 헬퍼 함수는 bpf_로 시작하고, 프로그램 유형은 BPF_PROG_TYPE으로 시작합니다.
  • 커널 밖 — eBPF라는 이름이 자리 잡았습니다. 커뮤니티 사이트 ebpf.io와 eBPF Foundation이 그 예입니다.

3. Linux Kernel — 유저 공간과 시스템 콜#

3.1 시스템 콜 인터페이스#

커널은 애플리케이션과 하드웨어 사이의 소프트웨어 층입니다. 애플리케이션은 권한이 없는 유저 공간에서 실행되고, 하드웨어에 접근해야 할 때 ‘시스템 콜’로 커널에 요청합니다.

  • 파일 읽기와 쓰기, 네트워크 송수신, 메모리 사용이 모두 이 경로를 지납니다.
  • 여러 프로세스가 동시에 실행되도록 조정하는 것도 커널의 일입니다.
  • 개발자는 보통 시스템 콜을 직접 호출하지 않습니다. 언어와 표준 라이브러리가 감싸 주기 때문에 커널이 얼마나 많은 일을 하는지 의식하지 못합니다.

strace는 애플리케이션이 호출하는 시스템 콜을 모두 보여 줍니다. 화면에 hello를 찍는 명령 하나를 실행하면 결과는 다음과 같습니다.

hello 한 줄 출력 전, 프로그램 실행과 라이브러리 적재를 위한 호출 백 번 이상

3.2 관찰 지점으로서의 커널#

애플리케이션은 커널에 크게 의존하므로, 커널과 주고받는 내용을 보면 애플리케이션의 동작을 많이 알 수 있습니다. 예를 들어 파일을 여는 시스템 콜을 가로채면 어느 애플리케이션이 어떤 파일을 여는지 모두 보입니다.

다만 가로채려면 커널에 코드를 넣어야 합니다. 그 방법들은 4절에서 비교합니다.

4. Kernel Extension — 커널에 기능을 넣는 방법#

4.1 업스트림 패치#

가장 정석적인 방법은 리눅스 커널 자체에 코드를 넣는 것입니다. 하지만 이 길은 생각보다 멉니다.

  • 코드 규모 — 커널 코드는 2021년에 약 3천만 줄이었습니다. 기존 코드를 모르는 사람이 고치기는 어렵습니다. 2026년 기준 — 2026년에는 4천만 줄을 넘었습니다.
  • 수락 — 기술보다 큰 장벽입니다. 리눅스는 범용 운영체제라서, 동작하는 코드라도 모든 사용자에게 이롭다고 커뮤니티와 리누스 토발즈가 판단해야 들어갑니다. 2013년 연구에서 제출된 패치의 약 33%만 수락되었고, 대부분 3~6개월이 걸렸습니다.
  • 배포 — 수락된 뒤에도 운영 환경에 닿기까지 시간이 더 듭니다.
업스트림 경로의 시간 대부분은 코드 작성 이후, 배포판이 새 커널을 받아들이기까지

커널은 2~3개월마다 새로 나오지만, 대부분은 커널을 직접 쓰지 않고 Debian, Red Hat, Alpine, Ubuntu 같은 배포판을 씁니다. 배포판은 몇 년 된 커널을 싣는 경우가 많습니다.

예를 들어 RHEL 8.5(2021년 11월)는 2018년 8월에 나온 커널 4.18을 씁니다. 2026년 기준 — 지금의 RHEL 10도 같은 방식으로 커널 6.12 계열에 고정되어 있습니다.

4.2 커널 모듈#

‘커널 모듈’은 필요할 때 올리고 내리는 커널 코드입니다. 공식 커널과 별개로 배포할 수 있어서 업스트림 수락을 기다리지 않아도 됩니다. 대신 대가가 있습니다.

  • 안정성 — 여전히 커널 프로그래밍입니다. 커널 코드가 충돌하면 머신과 그 위의 모든 것이 함께 멈춥니다.
  • 보안 — 커널은 머신의 모든 데이터에 접근하므로, 모듈에 취약점이 있거나 작성자가 악성 코드를 넣으면 피해 범위가 머신 전체입니다.

배포판이 새 커널을 늦게 받아들이는 이유도 여기에 있습니다. 여러 환경에서 몇 달, 몇 년 돌려 본 커널이어야 문제가 드러나 있다고 볼 수 있기 때문입니다.

4.3 eBPF 검증기#

초록 유리 · 주황 조건부 · 빨강 불리. 커널 모듈의 빠름과 업스트림의 안전을 검증기 하나로 함께 확보

eBPF는 안전을 다른 방식으로 확보합니다. ‘검증기’가 프로그램을 로드하기 전에 검사하고, 안전하다고 확인된 프로그램만 올립니다. 검증기가 확인하는 것은 세 가지입니다.

  • 머신을 충돌시키지 않는가
  • 끝나지 않는 루프에 갇히지 않는가
  • 허용되지 않은 데이터에 접근하지 않는가

4.4 동적 로딩#

이벤트에 붙는 eBPF 프로그램 · 그 이벤트를 일으킨 프로세스의 시작 시점과 무관하게 실행

eBPF 프로그램은 이벤트에 붙습니다. 파일을 여는 시스템 콜에 붙인 프로그램은 어떤 프로세스가 파일을 열어도 실행됩니다.

  • 즉시 전체 관찰 — eBPF 기반 관측·보안 도구는 올리는 즉시 머신 전체를 봅니다. 컨테이너 환경에서는 호스트의 프로세스와 모든 컨테이너 안의 프로세스가 대상입니다.
  • 필요한 곳에만 — 새 커널 기능을 만들어도 다른 리눅스 사용자가 같은 변경을 받아들일 필요가 없습니다. 필요한 곳에서만 올려 쓰면 됩니다.

4.5 성능#

거르는 위치가 커널로 내려가면 유저 공간 전환 횟수 감소 · 처음 BPF 의 목적도 필요한 패킷만 골라 올리기

로드된 프로그램은 JIT 컴파일을 거쳐 CPU의 기계어로 실행됩니다.

커널과 유저 공간 사이의 전환은 비싼 작업입니다. 커널에서 미리 거르면 이 비용을 이벤트마다 내지 않아도 됩니다. 그래서 관측과 보안 도구는 복잡한 조건으로 걸러 필요한 일부만 유저 공간으로 보냅니다.

5. Cloud Native — 노드와 커널#

5.1 노드 하나에 커널 하나#

컨테이너, Kubernetes나 ECS 같은 오케스트레이터, Lambda나 Fargate 같은 서버리스는 워크로드가 어느 서버에서 실행될지 자동으로 정합니다. 서버리스에서는 사용자가 서버를 알지도 못합니다.

그래도 서버는 있고, 가상 머신이든 베어메탈이든 서버마다 커널이 하나 있습니다. 같은 머신의 컨테이너는 이 커널을 함께 씁니다.

커널을 나눠 쓰지 않는 컨테이너 · 노드 하나에 eBPF 프로그램을 한 번 올리면 그 노드의 모든 워크로드가 관찰 대상

그래서 노드의 커널에 eBPF 프로그램을 올리면 두 가지가 따라옵니다.

  • 애플리케이션을 고치지 않고, 설정도 바꾸지 않습니다.
  • 프로그램이 커널에 올라가 이벤트에 붙는 순간부터, 이미 실행 중이던 프로세스도 관찰합니다.

5.2 사이드카 모델의 한계#

‘사이드카’는 로깅, 추적, 보안, 서비스 메시 기능을 Pod마다 컨테이너로 끼워 넣는 방식입니다. 애플리케이션 소스에 라이브러리를 넣던 이전 방식보다는 편하지만, 구조에서 오는 단점이 있습니다.

  • 재시작 — 사이드카를 추가하려면 애플리케이션 Pod를 다시 시작해야 합니다.
  • YAML 수정 — 무언가가 애플리케이션 YAML을 고쳐야 합니다. 보통 어드미션 컨트롤러가 자동으로 하지만, Deployment에 레이블이 빠지는 식으로 한 번 어긋나면 사이드카가 붙지 않고 그 Pod는 관찰 대상에서 빠집니다.
  • 시작 순서 — Pod 안 컨테이너들이 준비되는 순서를 예측할 수 없어서 시작이 느려지거나 경쟁 상태가 생깁니다. Open Service Mesh 문서에는 Envoy 프록시가 준비될 때까지 앱 컨테이너가 모든 트래픽이 버려지는 상황을 견뎌야 한다고 적혀 있었습니다. 2026년 기준 — Open Service Mesh는 그 뒤 CNCF에서 보관(archived) 처리되었습니다.
  • 네트워크 경로 — 네트워크 기능을 사이드카로 구현하면 트래픽이 프록시를 거치느라 커널 네트워크 스택을 한 번 더 지납니다.
파랑은 앱이 보낸 트래픽, 주황은 프록시를 거쳐 나가는 트래픽. 앞의 두 방식의 차이는 프록시 위치 (Pod 또는 노드)

2026년 기준 — Istio는 2024년 11월 1.24에서 사이드카 없는 ambient 모드를 GA로 발표했습니다. 다만 사이드카가 없어도 프록시는 남습니다. ambient 모드는 노드마다 L4 프록시(ztunnel)를 두고, L7 기능이 필요하면 waypoint 프록시를 따로 둡니다. 그림의 가운데 칸이 이 구성입니다.

5.3 사이드카 없이 보이는 워크로드#

eBPF 기반 도구는 머신에서 일어나는 모든 일을 보므로 공격자가 피해 가기 어렵습니다.

예를 들어 공격자가 호스트에 암호화폐 채굴 앱을 띄웠다면, 그 앱에는 사이드카가 없습니다. 사이드카 기반 보안 도구는 이 앱이 채굴 풀에 연결하는 것을 보지 못합니다. 반면 eBPF로 구현한 네트워크 보안은 호스트의 모든 트래픽을 다루므로 이 연결을 막을 수 있습니다. 5.1의 그림의 오른쪽 칸이 이 경우입니다.

6. Discussion#

이번 글에서는 1993년의 패킷 필터에서 출발해 eBPF가 커널의 여러 지점으로 넓어진 과정을 살펴보고, 업스트림 패치·커널 모듈과 비교해 eBPF가 무엇을 다르게 하는지 정리했습니다.

검증기 덕분에 커널 모듈처럼 바로 올리면서도 커널을 멈추지 않고, 노드 하나에 커널 하나라는 구조 덕분에 사이드카 없이도 모든 워크로드를 볼 수 있습니다.

핵심 메시지#

사용자의 코드가 커널에서 돈다
1993년 패킷 필터부터 지금까지 바뀌지 않은 구조입니다. 바뀐 것은 붙일 수 있는 지점의 수입니다.
검증기가 전제다
커널 모듈처럼 바로 올리면서도 커널을 멈추지 않는 것은 로드 전에 검사하기 때문입니다.
올리는 순간 전부 보인다
이벤트에 붙으므로 이미 떠 있던 프로세스도, 다시 시작하지 않은 Pod도 대상이 됩니다.
커널에서 거른다
JIT 기계어로 실행되고, 필요한 이벤트만 유저 공간으로 보냅니다. 전환 비용을 이벤트마다 내지 않습니다.
노드 하나에 커널 하나
컨테이너는 커널을 함께 쓰므로 노드 단위 도구 하나가 Pod마다 붙는 사이드카를 대신합니다.
업스트림은 몇 년이 걸린다
패치 수락, 커널 릴리스, 배포판 반영을 차례로 지나야 운영 환경에 닿습니다.
